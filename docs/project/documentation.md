# 项目文档措辞与维护规范

## 适用范围与参考来源

本规范用于指导项目维护文档（包括 `docs/`、`README.md`、运维与部署说明等）的编写、修订与审阅。

本规范参考以下写作与审阅方法：

1. **[Vercel eve technical-writing skill](https://github.com/vercel/eve/blob/main/.agents/skills/technical-writing/SKILL.md)**：借用以读者任务为中心的组织方式，按文体区分完成条件，分步核实技术准确性与任务可用性，删去空泛套话与无依据推论。
2. **[Cloudflare eli5 skill](https://github.com/cloudflare/cloudflare-docs/blob/production/.agents/skills/eli5/SKILL.md)**：保留准确清楚的文字，逐项核实新增解释，专业术语在相同语境下保持定义一致。
3. **[Cloudflare How-to 指南](https://developers.cloudflare.com/style-guide/documentation-content-strategy/content-types/how-to/)**：参考操作指南的结构，说明前提、步骤和结果；本项目另要求核实操作步骤与失败后的处理办法。

---

## 一、文体类型与完成条件

每篇文档围绕一个主要任务或问题展开。适用版本、环境、权限或发布范围影响读者判断时，必须写明。根据读者目标选择文体并满足对应的完成条件：

| 文档类型 | 目标读者 | 主要内容 | 完成条件 |
| --- | --- | --- | --- |
| **业务功能说明** | 不阅读代码的项目负责人 | 关键触发条件、系统表现与业务约束 | 完整说明做决策所需的条件与对外表现，不出现内部代码名与编号 |
| **架构与概念介绍** | 需要理解全局的技术与业务人员 | 模块分工、协作边界与设计权衡 | 解释系统各部分职责与配合方式，不流水账罗列代码细节 |
| **操作指南** | 需要完成某项操作的读者 | 针对单一操作目标的执行步骤 | 包含明确前提、已验证步骤、可观察结果与失败后的下一步；未确认处理办法时报告缺口 |
| **技术参考** | 需要精准查阅参数的开发与运维 | 命令行、配置参数、数据字段、状态码与排错列表 | 内容与所述版本的实现一致，提供准确类型与取值约束 |
| **教程** | 需要完整实践的初学者 | 端到端构建引导 | 在声明前提下引导读者完成目标，给出对应的验证方式与已知限制 |

单篇文档按需组织必要内容，不强制每篇生搬硬套全部栏目；概念与参考文档不强求操作步骤。

## 二、简洁正式的表达规则

1. **按读者要做的判断组织句子**

   正文交代清楚在什么条件下、由谁或系统执行什么动作、呈现什么结果。会改变读者判断的条件必须写进正文，不改变判断的细节放技术参考。不写只有动作、没有主语的备忘式短语；原因只在读者不读会产生误解时补充说明。

2. **使用界面上的名称，不出现代码名与内部编号**

   面向非代码读者的业务正文中，直接使用界面按钮、状态或提示的实际文案（如点「回应」、显示为「已处理」）。不出现底层函数名、内部事件编号或任务名。

3. **保留准确现状，新增解释逐项核对依据**

   已有准确清晰的文字予以保留，不作主观重写。陈述系统当前表现时以已核实的行为为准，不把动作引申为未验证的结果。对新增的机制解释、因果推导与说明，必须逐项核对代码实现或规范依据。完成的正文说明中不得留存未核实标记；未获确证的关键事实记入审阅记录并说明缺何依据，严禁臆测因果。

4. **准确限定环境、权限、受众与期限**

   涉及环境差异、权限角色、通知范围、数量与期限时保持准确（例如只能选 1 天或 3 天，不要写成 1 至 3 天）。同一行为在不同环境或权限下表现不同时逐项写明；操作失败时，说明读者关心的结果（例如表单草稿是否保留）。

5. **陈述必要原因，删去空泛套话**

   因果关系直接说清，无需回避“因为”或“所以”；但要删除“需要注意的是”、“这意味着”、“请务必知悉”等空泛的提示套话，直接陈述事实本身。

6. **按需保留并解释术语**

   不自造生僻术语，不堆砌代码级表达；技术参考与操作指南中的命令、配置字段和安全限制原样保留；业务正文中确有必要的术语先用日常语言解释，并在同语境下保持定义一致。

## 三、当前说明、需求与技术参考的区分

1. **当前系统说明**

   只描述系统当前已经实现的真实行为与对外表现。功能或界面更新时，直接替换原有说明，不在正文保留“之前是”、“改为”等修改痕迹；改动过程与历史背景另存。有效的设计理由可以保留。

2. **需求与设计文档**

   记录已经批准但尚未实现的功能与规则，并明确标记为待实现状态。已批准需求说明“预期”，代码、发布配置与必要运行说明“实际”，二者不能互相覆盖。设计文档中标记为“已实现”不能单独证明已实现或已上线，必须与源码、发布配置或运行证据核对。

3. **技术参考的分层放置**

   业务正文聚焦于行为与可见结果。源码字段名、判定步骤、账号过滤规则与关联源码等实现细节，放在正文之后作为「技术参考」，并使用真实的相对链接，不带易失效的行号。

## 四、典型业务场景表达示例

以下示例说明单条业务规则，不是完整操作指南。

### 示例 A：链接维护回应

- **正文**：发布者在链接维护页面回应时需填写说明。提交后，这条维护记录显示为「已处理」，参与这项维护的反馈者会收到含这段说明的通知。网站显示的链接可用状态保持不变。
- **技术参考**：通知发给该次维护登记的参与者，去重并排除操作者本人及已注销账号；提交回应不改变网站显示的链接可用状态。链接：[`service.ts`](../../app/api/patch/resource/maintenance/service.ts)、[`WorkspaceMaintenance.tsx`](../../components/dashboard/workspace/WorkspaceMaintenance.tsx)。

### 示例 B：资源保存冲突

- **正文**：保存资源链接发生冲突时，系统拒绝这次保存。界面提示修改冲突，并保留尚未保存的内容。
- **技术参考**：保存时若打开编辑时的原链接集合或地址版本与服务器当前记录不符，即为冲突；冲突时保留尚未保存的内容与打开编辑时的对照记录。保存成功后才以新内容作为下次编辑的对照基准。链接：[`update.ts`](../../app/api/patch/resource/update.ts)、[`workspace.md`](../modules/workspace.md)。
- *说明*：若用于操作指南，须核实并补充安全的恢复方法；尚未确认的恢复路径作为缺口报告，不编造操作步骤。

### 示例 C：维护暂缓到期

- **正文**：发布者可以暂缓 1 天或 3 天。期限内，系统不接收该链接的失效反馈。到期后原记录回到待处理，不另建记录，也不再提醒发布者。暂缓到期不会重新检测链接。
- **技术参考**：暂缓期内只限制该链接的失效反馈；到期沿用原维护记录。链接：[`policy.ts`](../../app/api/patch/resource/maintenance/policy.ts)、[`workspace.md`](../modules/workspace.md)。

### 示例 D：保存后续检测异常

- **正文**：资源保存成功后，链接检测失败不会撤销已保存的修改。
- **技术参考**：保存与检测是两个步骤，检测失败不改变已保存的结果。链接：[`workspace.md`](../modules/workspace.md)、[`data-cache-upload.md`](../modules/data-cache-upload.md)。

## 五、事实核验与证据留存

根据所述行为的特点及出错后果，选择核查方式：

1. **分级验证方式**
   - **静态逻辑与稳定默认值**：包括路由分发、权限逻辑拦截、数据库事务、代码内静态文案与默认参数。以查验源码及对应测试为准，记录关键文件与函数。
   - **依赖运行环境与动态交互的事实**：包括界面实际显示、不同环境下的行为、通知投递、并发冲突与客户端反馈。按风险补充运行或界面观察证据。
   - **引用与追溯**：引用必须有真实根据且能定位。文档与测试相互引用、测试只核对文档原句，都不能证明系统具备所述行为。

2. **保留简要审阅依据**
   - 在交付说明、任务报告或评审记录中，附带简要核验说明：`变动事实 → 来源或验证方式 → 结论`。
   - 审阅依据留存在过程记录中，严禁将文档正文改写为测试日志或排错流水账。

## 六、同步维护与检查命令

系统行为、权限、命令、依赖版本或页面路径变化时，复核受影响的文档及引用。新增维护文档须从索引、模块概览或其他维护文档链接进入，不能只有文档自身的链接。

`pnpm docs:check` 默认检查相对 `HEAD` 改动的维护文档，包括已暂存、未暂存和未跟踪文件。范围为根目录的 `README.md`、`AGENTS.md`，以及 `docs/project/`、`docs/modules/`、`skills/`、`deployment/` 下的 Markdown 文件和 `docs/theme-color-system.md`。历史计划与讨论记录不在默认范围内。

检查内容：

- 修改文档中的本地相对链接目标与明确未填写的占位。
- 新增文档是否有一级标题；新增 `docs/project/`、`docs/modules/` 页面是否有来自其他维护文档的链接。
- 文件删除或改名后，其他维护文档是否仍引用旧路径。未改动文档里与本次删除无关的旧断链不阻断本次检查。

在仓库根目录运行：

```bash
# 写作过程中检查当前改动
pnpm docs:check

# 检查指定文档
pnpm docs:check docs/project/documentation.md

# 选择最近一次提交改动的文档，检查其当前工作树内容
pnpm docs:check --base HEAD~1

# 交付前运行文档检查、契约测试与检查器测试
pnpm test:docs-contracts
```

这些命令在显式调用时执行。检查不访问远程页面，也不验证站内路由、锚点或 HTML 链接。**命令通过不能证明内容准确或操作可用**，内容仍须按下一节审阅。

## 七、审阅流程与停止条件

文档修订与交付通过技术事实与可用性审核：

1. **技术事实与可用性检查**
   - 作者对照源码、测试或运行记录核验技术陈述与步骤。
   - 新增文档、实质性重写或涉及关键高风险操作（如数据迁移、回滚、生产部署）的说明，由未参与写作的独立审阅者进行事实与操作可用性检查；微小文字修正可按比例自查。
   - 核心事实无依据、给出的命令无法执行、或按指南操作无法完成任务的，判定为未通过。
   - 操作指南示例须明确区分可直接运行的完整命令与仅供说明的代码片段。
   - 改写完成后，再逐项核对新增的解释、操作与失败处理。审阅中发现缺少依据的步骤，不得出现在声称可直接交付的改写稿中；局部代码未出现某种行为，也不能据此断言整个系统都不会发生该行为。

2. **读者可用性复述**
   - 必要时由未参与起草的读者（或不熟悉代码的业务负责人）通读正文并复述关键流程。
   - 复述仅用于排查文字歧义、遗漏条件与多余期待，不作为系统实际行为的事实证据。

**停止条件**：

满足以下全部条件时本轮修改停止：

1. 离线机械检查通过；
2. 技术事实有可靠依据，操作指南能支持完成任务并确认结果；
3. 主代理裁决后无未解决的事实或可用性分歧。

达到条件即停止，不因个人文风偏好陷入无限轮次。发现文档与实际行为或需求冲突时，区分四种情况处理：文档过期、实现偏差、测试错误、已授权变更。已有授权直接执行，只有缺少依据且存在实际业务取舍时才向用户确认，不擅自修改需求或推翻已有规则。

# 维护文档标准

维护文档要让不阅读代码的项目负责人理解条件、责任、结果和限制，也让操作人员能够安全完成具体任务。新增解释必须核对依据，不能用更通顺的推测替代真实行为。

## 按读者任务组织

项目首页只做简短介绍、功能、归属和阅读入口。维护文档按读者目的分三个目录：`docs/concepts` 放原理说明，`docs/reference` 放业务规则与参考，`docs/guides` 放操作指南；新页面按文体放入对应目录，并加入[总导航](../README.md)。总导航给出分类和新开发者阅读路线，参考索引解释规则页之间的衔接，不重复整张导航。每页承担一个主要任务，同一事实由一个主要文档维护，其他页面只给必要摘要和链接。

| 文体 | 完成条件 |
| --- | --- |
| 业务说明 | 说明谁在什么条件下可以做什么，结果、权限、可见范围、金额、期限与冲突如何处理。 |
| 架构与概念 | 解释各部分职责、依赖和边界，帮助读者判断问题属于哪里。 |
| 操作指南 | 有明确前提、必要步骤、可观察结果、核实过的失败处理和恢复条件。 |
| 源码参考 | 使用中文说明的精确源码链接，帮助开发者继续追溯。 |

只有操作指南保留完成任务必需的命令与配置项。其余正文使用自然语言；所有文体都不粘贴程序实现、SQL 正文、CSS 或界面代码样例，也不整段罗列函数、变量、内部字段和状态码清单；追溯或排查需要时，可以点名关键的函数、配置项或文件。

## 简洁正式地说明结果

使用具体的人、动作和结果。读者不应先理解内部术语，才能知道自己能做什么。准确清楚的原句可以保留，不为了换一种说法而改写。下面只示范单条规则的表达，完整条件由对应的规则页维护。

| 场景 | 表述示例 |
| --- | --- |
| 保存冲突 | 保存资源链接发生冲突时，系统会提示冲突，并保留尚未保存的内容。 |
| 维护回应 | 发布者提交说明后，维护记录显示为「已处理」。网站显示的链接可用状态保持不变。 |
| 暂缓维护 | 发布者可以暂缓 1 天或 3 天。到期后，这条维护记录回到待处理，系统不会重新检测链接。 |

示例的完整规则见[用户工作台与链接维护](../reference/workspace.md)。审阅时，读者应能仅凭正文说清谁可以操作、需要什么条件，以及成功或失败后的结果。复述需要自行补充条件时，应回查依据并补齐正文。复述用于发现歧义，不能替代事实核验。

## 写清当前行为和预期

当前用户要求、有效决策与契约确定系统应当怎样工作；代码、测试和必要的运行验证用于核实实际行为。已批准但尚未实现的预期应明确作为要求；移动端、键盘、对比度等设计要求不能写成全站已经验收通过。源码存在不证明生产已经迁移或启用，历史构建、测试和压测不能替代当前版本证据。

新要求取代旧规定时，直接替换旧条款，并同步相关文档和技能。不能保留两条互相矛盾的规定，让后来者自行猜测哪条生效。

保留权限、隐私、额度、金额、时限、并发与备份恢复条件。术语首次出现时用简短日常语言解释，后文保持一致。使用界面名称，避免临时编号、阶段、作者修改历史、抽象口号和无依据的绝对保证。仍有效的上线先后顺序应改写为实际依赖条件。

## 核对事实与操作

静态规则以当前源码和有意义的测试为依据。动态显示、真实并发、通知投递、平台配置和生产运行需要相应环境证据。文档彼此引用、测试只寻找某段原文、接口存在或某次命令通过，都不能独立证明业务正确。

先核实再写；新增因果、失败处理、自动重试和补偿都需要真实依据。没有核实的步骤从完成稿中移除，在交付报告说明缺少什么证据，不给读者留下待核实标记。遇到冲突先区分文档过期、实现偏差、测试问题和已授权变更，不擅自用当前实现改掉业务要求。

新增、合并或迁移页面时，更新所有入口和引用，确保可从总导航抵达。重要重写和生产操作说明建议另行复核事实与任务可用性，是否执行由站长决定；小文字修正采用相称的自查。

## 检查与交付

文档修改后按[测试指南](testing.md)的文档检查步骤验证相对链接、标题、占位与引用。机械检查不验证自然语言、业务事实、远程页面或真实操作。旧契约若只绑定过期措辞，应保留安全含义并由负责者更新断言，不能为检查通过恢复错误表达。

交付报告记录事实与来源、迁移去向、实际检查、未验证事项和真正缺口；过程记录不进入维护正文。实质问题解决、相关检查完成后停止，不为个人文风反复扩写。

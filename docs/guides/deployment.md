# 应用部署与恢复操作指南

本指南用于把经过验证的应用版本发布到服务器，并在版本启动失败后由操作者明确选择版本恢复。数据库迁移、备份和数据维护集中在[运维指南](operations.md)，不能把应用回滚当作数据库恢复。当前仓库配置不证明目标站点已经采用同样的部署方式。

## 发布前准备

服务器需要按根目录 [.nvmrc](../../.nvmrc) 使用 Node.js 24.22.1，并安装 pnpm、Git、PostgreSQL、Redis 和 PM2。核对 PM2 应用进程实际使用同一 Node.js 版本。应用监听 3000 端口，监听地址由运行配置中的 `HOSTNAME` 决定，应填本机回环并由反向代理提供 HTTPS。准备经过审核的源码版本、与之匹配的依赖及发布产物，确认目标数据库和外部服务身份；私有配置只由操作者在受控环境管理。

发布前应已有有效的类型检查与测试结果；构建、打包或运行资产变化时还需要相应构建验证。命令见[测试指南](testing.md)。发布流水线只构建产物，不执行测试或独立类型检查，构建跳过检查的开关不能代替它们。

运行时需具备公开资源、静态文件、服务器页面产物、构建标识、验证码图片、线上文章、重定向配置以及目标架构的数据库客户端和图片处理工具。[构建后复制](../../scripts/postbuild.ts)与[发布打包](../../.github/workflows/release.yml)必须一起维护；开发环境能运行不代表发布包包含这些文件。

## 账号偏好发布依赖

账号偏好发布前，在一次性数据库完成本批迁移与真实保存验收。生产按[账号偏好结构迁移](operations.md#账号偏好结构)准备环境、预检、停写、确认备份、同步和复检，再通过现行发布入口启动本批版本。迁移保留已有标签和邮件选择。

账号偏好写入后，恢复版本须理解账号级显示设置、设置项版本及编辑会话检查。发布失败按现行流程停止失败候选并保留记录，由操作者核对兼容性后显式选版。缺少兼容恢复目标时保持必要停写并前向修复。

## 运行配置

以[示例配置](../../.env.example)和[格式校验](../../validations/dotenv-check.ts)为依据，由操作者填写项目根目录配置。以下是操作需要的项目配置名称，不复制真实值。必需格式通过不等于服务已连通；选用可选能力时还需填写其使用点要求的配置。

| 配置 | 填写与核对 |
| --- | --- |
| `KUN_DATABASE_URL` | 对应本次目标 PostgreSQL，已有数据的库先走迁移和备份。 |
| `KUN_DATABASE_POOL_MAX` | 可选每进程连接池上限，允许 1 至 1000 的整数，默认 30；受管 worktree 使用 5。总连接需求随进程数增加。 |
| `REDIS_HOST`、`REDIS_PORT`、`REDIS_PASSWORD` | 目标 Redis 连接，隔离测试不能沿用真实服务。 |
| `KUN_VISUAL_NOVEL_SITE_URL` | 必须是合法地址，但当前不被读取。规范站点地址、站点地图与搜索通知使用[站点配置](../../config/moyu-moe.ts)中的固定域名，域名变化需修改该文件。 |
| `NEXT_PUBLIC_KUN_PATCH_ADDRESS_DEV`、`NEXT_PUBLIC_KUN_PATCH_ADDRESS_PROD` | 本地和生产访问地址，请求来源保护依赖它们；域名变化时同步。 |
| `JWT_ISS`、`JWT_AUD`、`JWT_SECRET` | 登录会话设置与秘密，不能复制示例秘密用于实际站点。 |
| `NODE_ENV` | 生产为 `production`，开发按开发指南填写。 |
| `HOSTNAME`、`PORT` | 应用监听地址与端口。生产填 `HOSTNAME=127.0.0.1`；缺省时监听所有网卡的 3000 端口。部署工具启动进程时传入的监听参数不生效，以本项为准；登录环境已导出同名变量时，配置文件中的值不会覆盖它。 |
| `KUN_VISUAL_NOVEL_EMAIL_*` | 发信人、服务器、端口、账号和密码，注册验证码与邮件功能需要实际服务。 |
| `KUN_VISUAL_NOVEL_S3_STORAGE_*` | 存储凭据、桶、服务端点和区域。 |
| `KUN_VISUAL_NOVEL_S3_STORAGE_PREFIX` | 可选桶内路径前缀；未设置或留空保持现有对象路径。应用自动将该前缀加入两个公开根地址，见下节。 |
| `NEXT_PUBLIC_KUN_VISUAL_NOVEL_S3_STORAGE_URL`、`KUN_VISUAL_NOVEL_IMAGE_BED_HOST`、`KUN_VISUAL_NOVEL_IMAGE_BED_URL` | 资源与图床的公开根地址，以及图片许可主机；两个根地址不含环境前缀，主机只填域名。 |
| `KUN_CF_CACHE_ZONE_ID`、`KUN_CF_CACHE_PURGE_API_TOKEN` | 默认和图床缓存清理权限，网站未指定独立区域时也使用。 |
| `KUN_CF_CACHE_SITE_ZONE_ID`、`KUN_CF_CACHE_SITE_PURGE_API_TOKEN` | 可选网站独立区域；令牌为空时复用已获该区域清理权限的默认令牌。配置步骤见运维指南。 |
| `KUN_VISUAL_NOVEL_INDEX_NOW_KEY` | 搜索通知所需密钥，公开目录中需有对应名称与内容的验证文件。 |
| `KUN_VISUAL_NOVEL_TEST_SITE_LABEL` | 测试站禁止索引标记，正式站点删除或注释。 |
| `BANGUMI_ACCESS_TOKEN` | 外部标签和会社读取需要的访问凭据，不配置时相关调用可能失败。 |
| `KUN_NEXTMOE_API_KEY` | 可选服务端凭据，会社规划的跨来源证据使用，不进入公开构建配置。 |
| `GITHUB_REPO`、`GITHUB_TOKEN` | 发布仓库及私有发布所需令牌，仅服务器下载使用。 |
| `KUN_DEPLOY_SMOKE_URL` | 可选就绪探针，默认 `http://127.0.0.1:3000/`，必须为本机 HTTP 回环地址。 |
| `KUN_DEPLOY_READINESS_TIMEOUT_MS` | 可选就绪等待，默认 120000 毫秒，允许 5000–120000 毫秒。 |
| `KUN_GALLERY_FFMPEG_PATH` | 可选目标机 FFmpeg 绝对路径，运行用户需有执行权限，优先于内置候选。 |
| `KUN_COMPANY_IDENTITY_RESOLVER_ENABLED` | 仅服务端运行时开关；只有完成结构、回填、清理、约束与验收后才可启用，见运维指南。 |
| `KUN_ENABLE_CRON` | 可选，设为 `false` 时本进程不注册后台定时任务；其他值或不填时注册。 |

带公开前缀的变量会进入浏览器构建，不能放秘密。发布工作流使用的三个公开地址秘密配置与图床根地址配置都要匹配目标站点，私有秘密只在服务端保留。图床主机在构建时写入图片许可范围，运行时修改不生效；下载发布前按[图床构建配置](#使用-github-发布产物)核对输入，需要更换许可主机时重新构建产物。修改运行时配置后重新读取进程配置，不只依赖旧进程环境。

### S3 路径前缀

多个独立开发环境可以共用开发桶，并为各环境分配固定的路径前缀。上传、读取、删除、素材清理扫描和截图缩略图回填都会使用该前缀；业务记录和清理待办中的对象键仍保存不含环境前缀的相对路径，公开地址字段和历史缓存清理目标则保存完整 URL。扫描结果会去除环境前缀后再与数据库引用比较。

例如，为一个 worktree 配置以下值，业务路径 `patch/123/banner/banner.avif` 会对应桶内的 `worktrees/wt-a/patch/123/banner/banner.avif`：

```dotenv
KUN_VISUAL_NOVEL_S3_STORAGE_PREFIX="worktrees/wt-a"
NEXT_PUBLIC_KUN_VISUAL_NOVEL_S3_STORAGE_URL="https://img-dev.example.com"
KUN_VISUAL_NOVEL_IMAGE_BED_URL="https://img-dev.example.com"
KUN_VISUAL_NOVEL_IMAGE_BED_HOST="img-dev.example.com"
```

前缀使用 `/` 分隔的英文字母、数字、点、下划线或连字符，不能包含单独的 `.`、`..` 段或空路径段。首尾空白和首尾斜线会被移除；非空配置仅含斜线时拒绝运行。两个公开根地址可以包含存储服务自身的固定路径，应用在其后自动追加环境前缀，再追加业务路径。例如上述封面的公开地址为 `https://img-dev.example.com/worktrees/wt-a/patch/123/banner/banner.avif`。配置中始终填写不含环境前缀的根地址；若已手动加上环境前缀，先将根地址中的这部分去掉，保留独立的前缀配置，已有文件和最终公开地址无需改变。

上传结果、投稿预览和发布、头像、截图、消息图片及资源下载都由服务器组合公开地址。投稿封面组件直接使用上传接口返回的完整地址，浏览器无需读取环境前缀。URL 反向解析、文件引用检查和边缘缓存清理使用同一环境地址范围，嵌套公开根地址优先匹配更长的地址。资源文件上传会在占用上传登记和写入存储前检查公开根地址是否缺失或为空白。图片许可主机只填写域名，配置应在构建和启动前确定。

生产环境可省略前缀或留空，原对象路径和公开地址保持不变。前缀与该环境的数据库一起保留；改变前缀不会搬迁已有对象，也不会改写数据库中的完整地址。路径分组不限制凭据权限，需要防止跨环境访问时，由存储提供商将凭据权限限制到各自前缀。

已有数据的环境首次启用或改变前缀，不能仅修改配置：旧的完整 URL 可能仍能显示，但新的 URL 解析、删除和扫描范围不再覆盖旧位置，可能留下无法清理的对象或使依赖地址识别的操作失败；投稿、贴纸等从相对键生成的地址会直接指向新前缀，未搬迁的文件可能无法显示。前述「已有文件和最终公开地址无需改变」仅适用于从根地址中拆出同一个实际前缀。切换已有数据的存储位置需要另行处理对象及其引用的迁移，本功能不提供自动迁移。

## 首次空库安装

仅适用于已核对为全新的空库，且已取得与目标版本一致的代码。已有持久库不能执行本节初始化。

1. 安装并填写上述配置，确认 PostgreSQL、Redis 与反向代理准备就绪。
2. 执行初始化：

   ```bash
   pnpm deploy:install
   ```

   它安装依赖、同步开发初始化结构并建立临时上传目录，不启动应用。依赖安装不锁定版本文件，锁文件被改写后，后续部署的干净工作区检查会失败，需先核对并还原；现有脚本会给上传目录宽泛写权限，应由服务器文件访问边界保护该目录。
3. 按[运维指南](operations.md)核对依赖的数据库约束、触发器和迁移检查。直接同步数据模型不会安装所有手写约束，初始化命令成功不能代替生产结构校验。
4. 在项目目录构建并启动：

   ```bash
   pnpm typecheck
   pnpm build
   pnpm start
   ```

5. 反代到 `http://127.0.0.1:3000`，保留访问主机、原地址和协议的代理信息，配置真实 DNS 与 HTTPS。按运行检查验证。首次站点安装需要超级管理员时，确认已获该账号初始化授权，注册受控首个账号，在目标项目运行 `pnpm prisma studio`，核对账号后把用户的 `role` 设为 `4` 并刷新登录。该步骤只适用于已核对的首次空站初始化，不用于修改已有站点的任意账号。

若结构检查、构建或启动失败，先停止后续步骤，保留输出并核对本节前提，不对已有库重置。需要变更反代配置时由服务器运维使用实际平台设置，不复制一段与目标未知的配置。

## 发布已经审核的版本

### 使用 GitHub 发布产物

工作流监听主分支与手动触发，使用一次性数据库和 Redis 构建，生成带版本标签与精确提交标识的清单。它不替代发布前测试。服务器工作区必须干净，依赖已安装，数据库迁移已按[运维指南](operations.md)完成；下载后会在目标机器生成并注入匹配架构的数据库客户端与 FFmpeg。

推送发布版本或手动触发前，发布操作者须在 GitHub 仓库的 **Settings → Environments → buildPublicEnv → Environment secrets** 中配置并核对 `KUN_VISUAL_NOVEL_IMAGE_BED_URL`。图床根地址属于公开构建配置，存为 Secret 是为了与项目现有工作流配置保持一致，图床域名仍会进入前端产物。工作流直接读取此 Secret，经步骤的环境变量传给[构建配置准备器](../../scripts/prepareReleaseImageBed.ts)，生成图床 URL 与图片许可主机，不从 S3 公开地址推断图床位置。已有三个公开地址秘密配置保留各自用途。

输入须为 HTTPS 根 URL，主机使用精确域名，端口省略或使用默认 443。允许存储服务自身的固定路径；路径保留在生成的 URL 中，末尾斜线移除，环境前缀仍按 [S3 路径前缀](#s3-路径前缀)单独填写。缺失或空白、占位域名 `example.com`、`example.net`、`example.org` 及其子域、通配符或 IP 主机、非默认端口、凭据、查询、片段、空白、控制字符、编码控制字符及反斜线都会被拒绝。查询和片段即使为空也不能携带。

工作流通过环境变量把输入传给准备器，在创建构建配置、初始化临时数据库及构建之前校验。校验失败时只报告配置名和错误类别，停止后续构建与打包，不生成正式发布产物。发布操作者仍须核对远端 Secret 的实际图床根地址与目标站点是否一致，作为推送发布的前置条件。服务器启动配置仍须与构建输入对应，运行时填写正确主机不能修复已有产物中的图片许可。

维护窗口内，在同一 shell 加载操作者现有的受控运维环境脚本，关闭命令追踪；公开示例中的路径须替换为目标服务器实际路径：

```bash
set +x
source '<受控运维环境脚本的绝对路径>'
```

停止全部应用实例并确认停止，完成并确认备份，再按[运维指南](operations.md)逐条执行本次需要的审核 SQL 与复检。无需 SQL 的更新省略迁移步骤。备份和数据库恢复由操作者负责，部署工具不替代这些动作。

```bash
pm2 stop kun-touchgal-next
pm2 status
```

完成准备后，常规更新最新发布：

```bash
pnpm deploy:pull
```

命令在部署互斥锁内先要求源码可快进更新，再选择最新产物。不能快进、工作区有修改或产物不匹配时终止，不覆盖本地修改。

维护窗口应固定已审核版本。先让服务器源码以正常快进方式到达该标签的精确提交，再执行下列命令，尖括号替换为真实审核标签：

```bash
KUN_DEPLOY_RELEASE_TAG='<已审核发布标签>' pnpm deploy:pull:pinned
```

固定模式只获取标签，不拉取分支、不合并或切换源码；当前源码、实际标签和产物清单必须指向同一提交。变量只对本次命令生效，不写入长期配置。缺清单的历史产物不能交给现有部署工具，只能依据已审核的人工快照恢复方案处理。

候选依次执行资源链接兼容迁移与生产结构检查、生成并注入数据库客户端、生成站点地图，最后检查运行资源，通过后才开始候选启动。兼容迁移会修改数据库，候选在后续步骤失败时数据库可能已经变化，详见[运维指南](operations.md#生产结构检查)。已验证版本保存于独立发布目录，只有候选通过就绪检查才提交当前与上一版的原子链接；构建目录中的兼容链接不承担备份职责。历史目录通过[发布清理命令](#清理服务器历史发布)管理。

### 在服务器构建

服务器有足够构建资源且不依赖发布下载时使用：

```bash
pnpm deploy:build
```

它在同一互斥锁内快进源码、安装锁定依赖、执行会先运行资源链接兼容迁移的生产结构检查、构建候选并通过同样的激活流程。准备条件和结构迁移要求与下载发布相同。资源不足时保留原版本目录并排查服务器容量，可选择已审核发布产物，不能随意减少实例数规避现有就绪契约。

### 确认切换成功

激活会记录切换日志，重启后要求恰好三个应用实例在线且指向候选目录，再由本机 HTTP 探针确认成功响应或跳转。候选开始启动后发生启动或就绪失败，工具只停止属于该候选的应用实例，并再次核对进程已停止，非零退出。停止无法确认时明确报告「未能确认停止」，同时保留启动与停机错误；操作者须检查实际进程状态。工具不会自动启动其他版本或恢复数据库，失败后按[人工选版恢复](#离线回退应用)处理。

就绪等待从 PM2 启动命令成功返回后开始计时，默认预算为 120 秒。单次 HTTP 探针最多等待 5 秒，并受剩余预算约束；预算耗尽后不再发起探针，超时错误会显示本次配置的等待毫秒数。

```bash
pm2 status
pm2 logs kun-touchgal-next --lines 200 --nostream
```

同时从目标站点检查首页、登录、游戏详情、资源、图片、本人工作台和受权后台，查看站点地图与相关缓存错误。上传链路只在本次授权覆盖真实写入时验证；没有授权或环境证据时如实记录未验证。

## 清理服务器历史发布

下载发布和服务器构建都把完整运行版本保存在 `.deploy/releases`。每次候选通过三个 PM2 实例及本机 HTTP 就绪检查、完成切换后，工具在同一部署锁内清理未被引用的受管版本目录。保留目录以 `.deploy/current` 和 `.deploy/previous` 的实际指向为准，不按版本名称或时间挑选；两者相同时只需保留一份。清理失败会记录告警，不回退已经验证可用的新版本，可在核对后重试。

处理服务器上已有的积压时，在该应用项目根目录先预览：

```bash
pnpm deploy:cleanup
```

命令列出保留、删除和跳过的目录，预览不删除发布文件。核对当前与上一版符合预期、PM2 进程实际运行目录与当前版本一致，并确认无需再从待删目录恢复更早版本，然后执行：

```bash
pnpm deploy:cleanup:apply
```

执行会重新读取版本指针并持有部署互斥锁，不能与部署或回退并行；只删除发布根目录中符合部署命名规则且未被引用的真实目录，首次收编的 `legacy-initial` 也遵循同样规则。陌生名称、普通文件和符号链接会跳过，发布目录外的兼容备份不在范围内。命令不重启应用，也不连接数据库或 GitHub。

存在中断或失败激活记录时，清理会停止，先按[人工选版流程](#离线回退应用)恢复并确认运行状态。版本指针缺失或越界、发布根目录为符号链接时也会停止，应先核对并修复部署布局，再重新预览；不要为强行通过清理检查删除恢复记录或篡改版本链接。删除失败时，已成功删除的历史目录不会恢复，重跑预览核对剩余目录。超过当前与上一版的历史恢复能力依赖另行保留的审核产物，不能依赖已经清理的服务器目录。

## 离线回退应用

恢复目标由操作者核实与当前数据库、业务数据和运行配置兼容；版本较旧或目录存在都不能证明兼容。账务、维护冻结和会社约束等变更可能需要持续停写，先按[数据库恢复边界](operations.md#失败与数据库恢复)判断。没有兼容目标时保持停机并前向修复。

失败会保留候选、原版本、激活记录与错误事实，停止发布清理。新激活在就绪成功后才提交版本指针；失败时的 `current` 通常仍表示最后成功版本，但其进程已停止，指针不能证明在线。带有未决记录的既有布局也可能已经把 `current` 指向未通过检查的候选，必须结合工具输出与实际 PM2 状态核对。

存在未决记录时，普通下载、固定下载、服务器构建和 `pnpm start` 都拒绝自动启动，部署入口在更新源码、下载和迁移前停止。不要删除记录或手动改链接绕过检查，也不要用直接重启 PM2 的方式跳过选版。记录损坏、版本目录缺失或布局不可信时，保留资料并人工检查；工具不会自行清除记录或猜测目标。

先只读列举受管版本，再用列表编号或已知的完整受管发布 ID 预览一个具体版本。不能填写目录、`current` 或 `previous`：

```bash
pnpm deploy:rollback --list
pnpm deploy:rollback --preview '<列表编号或受管发布 ID>'
```

列表使用无需颜色的中文编号菜单，显示真实发布标签、短提交号，并标注本次失败或未决候选、最近成功版本、更早版本及其他保留版本。最近成功版本取自未决记录的原版本，或没有未决记录时的当前指针；这些标注都不证明进程在线，也不判断数据库兼容性。完整发布 ID 与路径放在预览及选中摘要中；列表变化后编号也可能变化，应以本次显示为准。

版本须通过现有路径、运行资源与清单检查才能启动；`legacy-initial` 的来源标为未知，由操作者额外核对。列举和预览只持有本次临时操作锁，不加载运行配置、不收编目录、不切换指针、不启停进程，也不访问数据库或发布平台。状态摘要显示候选停机是否已确认，失败详情保留在激活记录中，执行失败时保留原始错误诊断。

交互式恢复使用原入口：

```bash
pnpm deploy:rollback
```

在 TTY 中先输入列表编号，核对选中摘要的标签、短提交号和状态后，输入 `y` 才切换和启动；完整发布 ID 由程序绑定，无需重复输入。默认取消；空输入、Ctrl-C、EOF、无效编号或无效确认不启动，也不归档或改变持久部署状态。等待输入期间始终持有部署互斥锁，确认后重新检查所选目录、运行资源、清单和部署状态；发生变化则拒绝执行并释放自身锁。非 TTY 无参数调用会停止，受控自动执行必须绑定具体的完整发布 ID 与相同确认值，不能用列表编号或通用确认开关代替：

```bash
pnpm deploy:rollback --release '<受管发布 ID>' --confirm '<同一受管发布 ID>'
```

明确执行时先保留原未决记录的历史，再建立本次恢复记录；历史无法保存则不启动。可以明确选择旧版，也可以选择失败候选重试。所选版本仍须通过三个实例和本机 HTTP 就绪检查，失败只停止本次所选实例并保留新旧记录，不自动尝试另一个版本；停止无法确认时同时报告原始原因和停机失败。成功后提交当前与上一版指针并结清未决记录，人工恢复本身不清理版本目录；后续正常发布或显式清理仍按当前与上一版的保留规则执行，清理前核对其他恢复需要。

恢复命令不改 Git、不访问发布平台、不执行数据库结构检查或恢复，也不修改数据库。需要恢复结构或数据时，保持相关写入停止，使用经审核的专用恢复方案。

## 启用链接检测

前提是[链接健康与维护依赖迁移](operations.md#链接健康与维护结构)已完成，且网站与独立检测服务版本经过核对。网站适配五家网盘，不代表本仓库附带的固定补丁服务已启用同样范围；固定服务的构建、许可证与限制见[检测服务指南](../../deployment/link-checker/README.md)。

在网站服务器填写以下运行时配置：

| 配置 | 要求 |
| --- | --- |
| `KUN_LINK_CHECKER_ENDPOINT` | 可信服务根地址；同机可用 `http://127.0.0.1:6734`，跨机用受限 HTTPS，不能带用户信息、查询或片段。网站固定请求 `/v1/check`。 |
| `KUN_LINK_CHECKER_API_KEY` | 独立服务为本站分配的原始密钥，不加认证前缀，不用网站登录凭据、用户 cookie 或提取码。 |
| `KUN_LINK_HEALTH_TRACKING_STARTED_AT` | 可选真实追踪启用时间，使用含时区的标准时间；不知道时留空，不填写构建时间冒充。 |

跨机代理只向网站后端开放检测入口，保留认证，关闭缓存、不跳转，不记录请求体、分享地址、认证或 cookie。核对提供者确实已启用，保持分享详情验证，并同步两台机器时钟。仅当实际远端版本支持相应语义时，配置 `LLC_QUARK_VERIFY_DETAIL=true` 与 `LLC_QUARK_BLOCKED_AS_DEAD=true`；本仓库固定补丁对屏蔽仍返回无法判断，不能用该开关改变它的策略。

重新读取网站运行配置：

```bash
pm2 restart ecosystem.config.cjs --only kun-touchgal-next --update-env
```

无需为这些运行时变量单独构建。在受权样本上，用登录账号打开可见且受支持的资源，点击检测，观察本次安全结论和时间；无需下载或具备发布者权限。空配置或失败只返回无法判断。失败时检查服务连通、认证、代理、提供者与时钟，不以真实分享进行未经授权的整站扫描。

## 检查动态截图缩略图

目标机需要真实可用的视频处理工具。默认优先使用自备绝对路径，其次发布目录内和项目本地的可选工具，再使用依赖携带工具与系统工具。依赖的安装脚本需被允许执行，下载发布会注入目标机器架构的工具，不能只搬构建机器的二进制。

有明确需求的 Linux x64 或 arm64 服务器可以安装可选增强工具：

```bash
pnpm gallery:ffmpeg:install
```

随后通过本地样本验证，下面命令只读写本地文件，不接触数据库或对象存储：

```bash
pnpm exec esno scripts/verifyGalleryAnimatedAvifThumbnail.ts ./public/images/animated-sample.avif ./public/images/tmp/animated-sample-thumb.avif
```

确认输出真实多帧缩略图及帧数，不能把首帧静图当作动画。需要重新打包工具时走正常发布，配置改变则重读进程环境。失败排查权限、安装脚本、架构和编码支持；原图仍可保留，缩略图可退为首帧或缺省，不承诺每次都生成动画。

## 常见发布故障

| 现象 | 下一步 |
| --- | --- |
| 源码、标签或清单不一致 | 停止切换，核对同一版本，不能混用一个版本迁移和另一个版本产物。 |
| 结构差异阻断 | 按运维指南补齐审核迁移，不扩大检查例外或执行工具建议的假差异重建。 |
| 找不到运行目录或入口 | 检查当前链接和发布目录完整性，不手工删除旧版；兼容入口支持两种既有服务器文件。 |
| 发布目录链接越界 | 当前收编流程会修复早期绝对链接；保留旧目录并核对工具输出，不手工删掉恢复来源。 |
| 数据库客户端无法加载 | 核对目标机生成及候选注入是否完成，不手工复制一个缺依赖的客户端包。 |
| 部署锁或中断记录残留 | 核对持锁进程，不删除正在使用的锁；未决记录按人工选版流程明确处理，后续部署不会自动恢复。 |
| 网站被禁止索引 | 核对测试站标记，修改后按正常配置重读流程处理。 |
| 图片或站点地图缺失 | 核对图床、构建时的图片许可主机与运行资产复制。下载发布会在服务器重新生成站点地图，生成失败只记录日志、不阻断部署，先查部署日志；必要时运行 `pnpm build:sitemap` 后按发布流程纳入产物。 |
| 启动后 CPU 满载，定时告警重复同一时刻 | 按[定时任务故障处理](operations.md#定时告警刷屏与-cpu-满载)临时停用后台任务并核对运行产物中的调度依赖。`Ready` 不代表事件循环持续可用，不能反复原样重启或只更新源码目录依赖。 |

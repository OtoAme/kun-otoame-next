## 0. 术语表

| 术语 | 定义 |
|---|---|
| 站长 | 运营本站的那个人。 |
| 站方 | 以管理员角色（`role >= 3`）执行动作的一方。当前只有站长一人具备该角色，文中「站方」指角色，「站长」指人。涉及 OtoAme 资源盘的操作（添加官方链接、存量合并、重新镜像）在权限上对管理员开放，能否实际执行取决于该管理员是否持有资源盘账号；目前只有站长持有，将来可能给受信任的管理员另开账号。 |
| 发布者 | 一条资源的 `user_id` 所指的用户。发布者只对自己发布的资源负责，不对他人内容做任何裁决。 |
| 提问者 | 发布一条求助的用户。求助锚定到某条资源时，「发布者」仍指该资源的发布者，两者是不同的人，除非资源发布者自己发求助。 |
| 回答者 | 在求助下发布回答的用户。 |
| 归属方 | 一件事务的责任人，只有两种取值：发布者、站方。归属方在事务创建时由规则确定，不靠人分派。 |
| 工单 | 一条「请归属方改变站内数据」的请求，例如修链接、换文件、移动资源、删除内容。有归属方、有状态机、有超时。用户界面上不出现「工单」这个词，用户看到的是「举报」「遇到问题」「反馈」等入口。 |
| 求助 | 一条「请教社区」的提问，提问者需要的是信息，站内数据不会改变。没有归属方、没有超时升级，只有回答与采纳。 |
| 失效报告 | 用户对某条链接点「报告失效」的一次投票，附一个原因标签，不写文字。它不是工单；报告累积到阈值后由系统开工单。 |
| 揭示 | 用户或访客点「获取下载链接」使链接地址可见的动作。每次揭示写入一条 `patch_resource_access` 记录，该表没有清理逻辑，记录永久保留。访客也可以揭示（受配额限制）。 |
| 链接版本 | 每条链接的整数版本号。地址（`content`）每变更一次加一。揭示记录与失效报告都写入当时的版本号。 |
| 强证据 / 弱证据 | 失效报告的两个等级。强证据指网盘页面明确显示文件已删除、已过期、违规，或链接要求付费。弱证据指打不开、超时，这类现象多数是国内网络环境所致。 |
| 健康 | 一条链接当前能否使用的事实，取值 `ok`、`suspect`、`disputed`、`broken`，可逆。它不是资源的 `status`，两者互不影响。 |
| 官方链接 | 资源下 `official = true` 的链接，存储类型为 OtoAme 资源盘（`storage = touchgal`），由站方添加，归属方是站方。 |
| 镜像 | 站方把发布者的文件复制到资源盘并在同一条资源下添加一条官方链接的动作。镜像不是另一条资源。 |
| 补链 | 发布者更换某条链接的地址。地址变更即补链，不区分用户是用编辑表单还是「补链」按钮。 |
| 镜像版本确认 | 系统或站方向发布者发出的一个二选一问题：你当前链接指向的文件与官方链接保存的文件是否为同一内容。用于判断是否需要重新镜像。 |
| 版本疑点 | 存量合并时无法确定用户链接与官方链接是否为同一文件。由于存量数据没有可用信号，所有存量候选对都视为有版本疑点，合并前一律询问发布者，见 5.7。 |
| 存量 / 存量合并 | 存量指历史上站长搬运后另建的、与用户资源内容相同但互不关联的重复资源。存量合并指用工具把这些重复资源改造成「用户资源下的官方链接」。 |
| 可用 | 一条资源至少有一条链接的健康不是 `broken`。可用性由链接推导，不存字段。 |
| 我也遇到了 | 求助帖上的一个按钮，表示另一名用户遇到同样的问题。它累积到阈值时触发系统开工单。 |
| 提出相同问题（同问） | 求助帖上的另一个按钮，为点击者新建一条锚定相同对象、引用原帖的求助。与「我也遇到了」的区别见 8.4。 |
| 求物 | 求助的一种意图：请求某样东西。分两类：「条目资源」指某游戏的本体、补丁、资料集等应当出现在条目资源列表里的东西；「站外事物」指第三方软件、网站、工具等。只有条目资源类的求物才有资源回答，见 8.4。 |
| 未落地的求物 | 条目资源类求物中，锚定对象是游戏名称而不是条目的那些，因为该游戏在站内尚无条目。条目出现并关联后即「落地」。见 8.4。 |
| 资源回答 | 只对已落地的条目资源类求物可用的一种回答形式：回答者主动选择填写资源表单，系统同时做两件事：在求助帖中立即发布一条含链接的普通回答，不经审核；按现有流程创建一条待审核的资源，审核通过后出现在条目的资源列表。普通文字回答里的链接不会进入任何审核队列。见 8.4。 |
| 悬赏 | 提问者在发布求助时额外指定的一笔点数，发布时暂扣，采纳时结算：大部分付给被采纳的回答者，一小部分由系统烧毁。见 8.4。 |
| 小喇叭 | 首页的用户短消息流，发布需付萌萌点，不可回复。 |
| 官方置顶 | 站方发布的小喇叭在生效期内占据小喇叭第一页的第一行。它占用一个普通名额，不额外增加行数。 |
| 横幅 | 站方发布「重要」级小喇叭时，在全站每个页面顶部渲染的一条可关闭通知。 |
| 分页范围 | 小喇叭页最多显示的页数乘以每页条数。在范围内的小喇叭始终公开显示，不看年龄。 |
| 首页聚合 | 首页的「最新求助」「最新评论」栏目把站内各处的内容汇总展示。 |
| 注册时长门槛 | 账号自注册起经过的天数需达到某个值才能触发某项效果。本文只在首页聚合中使用它，不用于限制发布。 |
| 统一收件箱 | 后台的单一待办列表，所有需要站方处理的事项按等待时长与优先级排在一起。 |
| 待合并队列 | 后台列出存量合并候选对的列表，每一对是同一条目下一条用户资源与一条站长资源。 |
| 资源管理菜单 | 资源卡片上仅管理员可见的下拉菜单，集中站方对该资源的操作：编辑、删除、添加官方链接、手动发起镜像版本确认、标记已测试等。当前卡片上的编辑与删除按钮是它的前身。 |
| 「有效」标记 | 登录用户对一条求助回答点「对我有效」的动作。累积到阈值时该回答被系统标记为「社区验证有效」。 |
| 链接检测 | 由服务器访问链接地址并判断其是否仍可用的功能，只在用户报告失效、归属方或站方手动点检测、发布者补链时运行，不定时扫描。检测结果作为失效报告之外的另一种证据来源。属于后期功能，见 4.9。 |

## 1. 背景：产品与运营工具链的错位

OtoAme 由 touchgal 分叉而来。touchgal 是站长中心化的资源站。OtoAme 在六个月内加入了用户投稿条目、用户发布资源、创作者、萌萌点经济、私聊、评分评论，实际上已经是社区化的内容站。但运营工具链仍是资源站形态：反馈是一条消息，审核是一个布尔位，公告是构建期读取的 MDX，没有按资源的责任归属，没有负载指标。

| 内容类型 | 谁在生产 | 谁应当负责 | 现在谁收到投诉 |
|---|---|---|---|
| 游戏条目 | 站长 + 用户投稿 | 投稿人、审核者 | 站长 |
| 官方资源 | 站长 | 站长 | 站长 |
| 搬运资源 | 用户发布，站长镜像 | 质量归原发布者，可用性归站长 | 站长承担全部 |
| 用户网盘资源 | 用户 | 用户 | 站长 |
| 下载、解压、运行 | 无人 | 用户自己与社区 | 站长 |

三个后果：所有例外汇入同一个收件箱，每条都要站长亲自分类；用户无法自助也无法互助，发布者明明可查却收不到通知；站长没有正当拒绝的机制，每次拒绝都是个人行为。

站长角色需要重新定义：从内容生产者变为平台运营者，工具让社区承担常规事务，站长只保留规则制定与例外处理。

## 2. 治理原则

### 2.1 三层模型

| 层 | 处理什么 | 依据 | 例子 |
|---|---|---|---|
| 机制层 | 有客观答案的事务 | 阈值、外部权威数据、自动状态 | 链接是否失效由揭示过链接的登录用户投票判定；条目信息以 VNDB、Bangumi、Steam、DLsite 为准 |
| 责任层 | 关于某一内容的事务 | 谁发布的，谁负责 | 资源工单送给发布者；投稿被要求修改时由投稿人自己改 |
| 裁决层 | 只剩规则与例外 | 站长一人 | 是否属于收录范围、是否违规、极少数事实争议 |

每一层的目标是让下一层收到的事务更少。品味类判断（哪个标签更贴切、某条评价是否公允）有意放给点赞数、举报数和外部同步，不进任何人的队列。

### 2.2 三条硬约束

1. 不设版主、不招志愿者。站长不是该类游戏的玩家、与用户交流少、无法评估用户判断力，因此不把裁量权分给他人。责任层不要求信任任何人的判断力，因为发布者只对自己的资源负责。
2. 不给创作者「镜像到 OtoAme 资源盘」权限。资源盘后端是 S3，成本与脆弱性不允许分散写入。镜像只由站方执行。
3. 私聊保持纯社交用途。用户与发布者之间的问询全部走工单与求助，不做私聊例外。

角色模型保持现有四级（用户 1、创作者 2、管理员 3、超级管理员 4）。后台各队列门槛统一到管理员级；破坏性操作（封禁、删条目、站点设置、群发邮件）保留超级管理员。涉及 OtoAme 资源盘的操作在权限上对管理员开放，与现有代码一致（`app/api/patch/resource/route.ts` 中资源盘存储类型要求 `role >= 3`）；能否实际执行取决于是否持有资源盘账号，目前只有站长持有。

### 2.3 站方在新模型中出现的位置

需要动作的：

- 官方链接作为归属方的核实、确认、补链。
- 镜像队列、重新镜像队列、存量合并的逐条确认。
- 违规举报、资源发错条目、发布者申请下架、链接争议的裁决。
- 纠错投稿与新条目投稿的审核。
- 发布者归属的工单超时后升级到站方的两个按钮。
- 镜像版本确认在发布者未回应时的兜底判断。

只看不做的：

- 已失效链接视图（第 4.8 节）。
- 运营指标（第 10 节）。

除此之外的事务不应到达站方。

## 3. 模块 A：工单系统

### 3.1 现状与目标

现有反馈是 `user_message` 的一行（`app/api/patch/feedback/service.ts`），无目标对象、无类型、无处理人，处理即 `status` 置 1，回复内容靠字符串反解（`app/api/admin/feedback/service.ts`）。现有举报表 `patch_report`（`prisma/schema/patch-report.prisma`）有目标类型、三级外键、处理人与回复。工单系统把反馈提升到举报的建模水位，两者合并为一张表。

### 3.2 实体

| 实体 | 字段 | 说明 |
|---|---|---|
| `case` | `kind` | 类型，见 3.3 |
| | `target_type`、`target_id` | 目标对象：链接、资源、条目、评论、评价、用户、小喇叭、求助 |
| | `patch_id` | 所属条目，用于聚合展示 |
| | `link_version` | 链接类工单所针对的链接版本 |
| | `reporter_id` | 开启者。系统开启时为空 |
| | `owner_type`、`owner_id` | 归属方类型（`publisher` 或 `staff`）与具体用户。创建时由类型与目标确定 |
| | `status`、`resolution` | 状态与结案结论，见 3.4 |
| | `public` | 是否在资源卡片显示徽标 |
| | `source` | 开启来源：用户、系统、发布者转换、求助升级 |
| `case_message` | `case_id`、`author_id`、`body` | 多轮对话 |
| `case_subscriber` | `case_id`、`user_id` | 重复报告合并为订阅，结案时统一通知。只有登录用户 |

### 3.3 类型、归属与开启方式

| 类型 | 目标 | 归属方 | 开启方式 |
|---|---|---|---|
| 链接疑似失效 | 链接 | 链接归属方（官方链接为站方，其余为发布者） | 系统，失效报告加权和达阈值（4.3） |
| 链接争议 | 链接 | 站方 | 系统，核实可用后 30 天内再次达阈值（4.4） |
| 资源与描述不符 | 资源 | 发布者（官方资源为站方） | 用户在「遇到问题」中选择相应现象；或系统由求助帖「我也遇到了」达阈值开启；或发布者把求助转为工单 |
| 资源发错条目 | 资源 | 站方 | 用户 |
| 发布者申请下架 | 资源 | 站方 | 发布者（5.4） |
| 镜像版本确认 | 资源 | 发布者 | 系统在存量合并发现版本疑点时开启；或管理员在资源管理菜单中手动发起（5.6） |
| 条目信息错误 | 条目 | 不进队列，界面直接引导转为纠错投稿（第 6 节） | 用户 |
| 违规举报 | 评论、评价、用户、小喇叭、求助 | 站方 | 用户点「举报」 |
| 其他 | 条目 | 站方 | 用户，入口放在所有类型之后 |

违规举报是唯一必然落到站方手上的类型，因为它是规则问题；去重与阈值自动隐藏只负责压低数量。

用户开启的、归属方为发布者的工单，同一用户对同一资源每天最多一条。系统开启的工单不受此限制。

### 3.4 状态、超时与结案结论

状态：`open`（已开启，等待归属方首次处理）、`waiting_reporter`（归属方已回复，等待开启者补充）、`waiting_owner`（开启者已补充，等待归属方）、`resolved`（已结案）、`rejected`（不受理）、`merged`（合并入另一条工单）。

| 规则 | 内容 |
|---|---|
| 等待开启者超时 | `waiting_reporter` 持续 14 天无回应，自动 `resolved`，结论「开启者未回应」 |
| 等待发布者超时 | 归属方为发布者的工单在 `open` 或 `waiting_owner` 持续 7 天无操作：链接疑似失效类，链接转 `broken`，结论「超时失效」；资源与描述不符类，升级到站方，站方只有「隐藏资源」与「忽略」两个按钮 |
| 站方归属的工单 | 没有超时，由统一收件箱排序与第 10 节指标约束 |
| 重开 | 开启者对结案不满意，结案后 7 天内可重开一次，状态回到 `open` |
| 「隐藏资源」的效果 | 资源 `status` 置 1（现有取值，含义为封禁或下架），写入后台日志与原因，通知发布者；发布者修正后站方一键恢复为 0。这是站方裁决，不是链接健康，与「健康不进 `status`」不矛盾 |

结案结论按类型枚举：

| 类型 | 可能的结论 |
|---|---|
| 链接疑似失效 | 核实可用、确认失效、超时失效、已补链 |
| 链接争议 | 站方判可用、站方判失效、自动收敛可用、自动判失效、已补链 |
| 资源与描述不符 | 已修正、无法复现、不在受理范围、升级后隐藏、升级后忽略、开启者未回应 |
| 资源发错条目 | 已移动、不成立 |
| 发布者申请下架 | 同意下架、拒绝下架 |
| 镜像版本确认 | 内容相同、内容有变化、发布者未回应 |
| 违规举报 | 已处理、不成立 |
| 其他 | 已处理、不在受理范围 |

### 3.5 去重、订阅、公开徽标

同一目标、同一类型、未结案的工单只允许一条；后来者不新建工单，而是成为订阅者。公开工单在资源卡片显示「已有 N 人报告，发布者处理中」，N 为订阅者数。结案通知发给开启者与全部订阅者。

### 3.6 入口

一个表单，多个入口。入口决定预填的目标对象与可见的类型集合。

| 入口 | 位置 | 预填 | 可见类型 |
|---|---|---|---|
| 报告失效 | 每条链接旁 | 链接、链接版本 | 只有失效报告的原因标签，不是工单表单 |
| 遇到问题 | 资源卡片底部 | 资源 | 按现象分流（8.2），可能导向失效报告、工单或求助 |
| 举报 | 评论、评价、用户、小喇叭、求助旁 | 对应对象 | 只有违规举报 |
| 反馈 | 条目页 | 条目 | 条目信息错误（引导转纠错投稿）、资源发错条目、其他 |

失效报告与工单是两种不同的东西：前者是投票，后者是请求；「遇到问题」里选择「打不开」等现象时会被导向前者。

### 3.7 界面

- 发布者：个人页「我的资源 · 待处理」面板，列出自己资源上的工单、疑似失效与争议中的链接、镜像版本确认。发布者不进管理后台。
- 站方：统一收件箱（第 7 节）。
- 用户：「我的工单」页面。通知链接指向工单本身。现状是处理结果作为系统消息发出且链接指向首页。
- 处理方有快捷回复模板：已修复、需要截图、请参考指南、不在受理范围。

## 4. 模块 B：链接健康、失效报告与补链

### 4.1 原则

上一版设计把三件事塞进一个状态字段：链接现在能不能打开、这条链接是否被另一条取代、站方有没有备份。拆开后：

- 健康是一条链接可逆的事实，用 `health` 字段表达。
- 补链是历史，进侧表；链接行本身是一个槽位，地址可换、槽位不变，因此不存在「已替代」这种状态。
- 镜像不是状态，是资源下的另一条链接（第 5 节）。

本文推翻 `decision-making/6.resource-link-model.md` 第 3 条「链接不需要状态」。当时的目标是控制改动范围，现在的目标是让「某条链接挂了」在数据上可表达。

### 4.2 健康四态

| 健康 | 含义 | 前台展示 | 计入可用 |
|---|---|---|---|
| `ok` | 没有有效的失效报告 | 正常 | 是 |
| `suspect` | 失效报告达阈值，等待归属方处理 | 链接旁显示「多名用户报告可能失效」，仍可揭示 | 是 |
| `disputed` | 归属方核实可用后 30 天内再次达阈值 | 链接旁显示「发布者称可用，多名用户称失效」，仍可揭示 | 是 |
| `broken` | 归属方确认失效，或等待超时，或争议判定失效 | 从卡片折叠隐藏，计入「N 条链接已失效」 | 否 |

### 4.3 失效报告

**动作。** 登录用户在链接旁点「报告失效」，选一个原因标签，不写文字。访客看到按钮但点击后提示登录；访客不能报告。原因是报告必须可归因到账号，访客标识可以清除后重来。

**资格。** 报告者必须满足两个条件：一，对该链接有 30 天内的揭示记录（`patch_resource_access`）；二，报告请求携带的链接版本等于当前版本。版本不匹配时返回「该链接已更新，请刷新后重试」。这同时拦住两种情况：发布者已补链而报告者页面未刷新；报告者揭示的是旧地址。同一用户对同一链接版本只能有一条有效报告。

**证据强弱与权重。** 站长的经验是绝大多数「打不开」来自国内网络环境而不是链接失效，因此报告分强弱：

| 原因标签 | 强弱 | 权重 | 备注 |
|---|---|---|---|
| 网盘页面显示文件已删除、已过期、违规 | 强 | 1.0 | 一名用户一条报告计 1.0 |
| 链接要求付费，或与发布说明不符 | 强 | 1.0 | |
| 打不开、超时 | 弱 | 0.5 | 先显示网络提示，用户点「已尝试更换网络或加速器」后才写入 |
| 下载慢 | 不计 | 0 | 引导至下载指南，不写入报告 |

窗口内加权和达到阈值（3.0，72 小时）触发 `suspect`。例如三条强证据，或六条弱证据，或一强四弱。报告绑定链接版本，地址变更后旧版本的报告不再计数。

### 4.4 流转规则

| 从 | 到 | 触发者 | 条件与结果 |
|---|---|---|---|
| `ok` | `suspect` | 系统 | 窗口内加权报告和达阈值。系统开一条「链接疑似失效」工单给归属方，报告者成为订阅者 |
| `suspect` | `ok` | 归属方 | 点「我已核实可用」，记录 `verified_at`。工单结论「核实可用」。本轮报告者对该链接版本的后续报告在冷却期内照常记录但权重为 0；新报告者不受影响 |
| `suspect` | `broken` | 归属方 | 点「确认失效」。工单结论「确认失效」 |
| `suspect` | `broken` | 系统 | 超时无归属方操作。工单结论「超时失效」 |
| `ok` | `disputed` | 系统 | 核实可用后 30 天内再次达阈值。系统开一条「链接争议」工单给站方，两个按钮：可用、失效 |
| `disputed` | `ok` | 站方或系统 | 站方点「可用」，结论「站方判可用」；或 30 天内没有来自新报告者的强证据加权和再次达阈值，自动清除，结论「自动收敛可用」 |
| `disputed` | `broken` | 站方或系统 | 站方点「失效」，结论「站方判失效」；或来自新报告者的强证据加权和再次达阈值，结论「自动判失效」。弱证据在争议态不计 |
| `broken` | `ok` | 归属方 | 点「我已核实可用」，受核实频率限制。适用于确认失效与超时失效两种来源 |
| 任意 | `ok` | 地址变更 | 补链（4.5）。健康重置，版本加一。未结案的疑似失效或争议工单结论「已补链」 |

**核实频率限制。** 同一链接版本每 30 天最多核实一次。

**冷却期的含义。** 冷却不是惩罚报告者，而是防止同一批人单独决定结果：核实之后要再次触发，必须有新的报告者。如果链接确实失效，新的下载者很快就会补上证据；如果归属方误判，代价只是几次失败的下载，随后由新证据纠正。

**信任方向。** 第一轮信任归属方的证词；第二轮由强证据决定，弱证据不能推翻证词；僵局交给站方做一次「打开试试」，这是链接健康上站方唯一的裁决，且可以不做，系统在 30 天后自行收敛。

### 4.5 补链

编辑保存时检测到地址变更即按补链处理，不区分用户用的是编辑表单还是「补链」按钮；按钮只是把表单定位到地址栏并展开下面的单选。补链效果：

1. 健康重置为 `ok`，版本加一，`verified_at` 清空。
2. 旧地址、旧存储类型、旧大小、变更原因、操作者写入链接历史表。
3. 相关未结案工单以「已补链」结案并通知开启者与订阅者。
4. 表单要求发布者回答镜像版本确认的二选一：「内容相同」（同一文件换网盘，或重新打包但内容不变）或「内容有变化」（新版本、修复文件等）。资源没有官方链接时该问题不出现。回答「内容有变化」时资源进入重新镜像队列（5.6）。

### 4.6 资源可用性

一条资源只要有一条链接的健康不是 `broken` 就可用。全部链接 `broken` 的资源从默认列表折叠到底部「已失效资源」区，不删除、不下架，署名与历史保留，同时出现在发布者个人页待修复列表。`patch_resource.status` 维持现有三个值，不掺入健康语义。资源列表现由 `app/api/patch/resource/get.ts` 按 `status: 0` 过滤、链接按 `sort_order` 排序，这两处都需要读取健康。

### 4.7 数据变更

| 对象 | 变更 |
|---|---|
| `patch_resource_link` | 新增 `health`、`health_changed_at`、`verified_at`、`version`、`official`、`content_changed_at`。最后一个只在地址变更时写入，存量为空。`updated` 因下载计数而失真（5.7），不作为任何业务判断依据 |
| `patch_resource_access` | 新增 `link_version` |
| 新表：链接失效报告 | 链接 ID、链接版本、报告者用户 ID、原因标签、权重、时间。阈值、冷却、争议都从这张表算 |
| 新表：链接历史 | 链接 ID、旧地址、旧存储、旧大小、变更原因（补链、编辑、合并）、镜像版本确认的回答、操作者、时间 |

### 4.8 已失效链接视图

后台提供一个只看不做的视图，列出所有 `broken` 链接，可按归属方类型、所属资源是否有官方链接、网盘主机、失效时长筛选。用途：

- 官方链接的 `broken` 同时进入统一收件箱作为待办（补链或移除），因为站方是归属方。
- 无官方链接且全部链接失效的资源是「已丢失」记录，说明镜像晚了一步；这个数字是全量镜像政策的直接考核指标。
- 按网盘主机汇总的失效比例构成「网盘历史存活率」，用于镜像队列的层内排序（5.5）。

### 4.9 链接检测（后期功能）

由服务器访问链接地址并判断其是否仍可用。多数网盘的失效页面有固定特征（「文件不存在」「分享已取消」等文案），可以程序识别；部分网盘有反爬或需要登录，检测结果不可靠。因此检测不独立改变健康，也不在后台定时扫描，只在有人动手时运行，结果作为证据并入 4.3 的加权。

不做定时扫描的理由：扫描结果如果不显示，等于白做；如果显示「已失效」，用户看到就不会再点击和报告，机制失去用户证据；而且大范围扫描容易触发网盘的反爬封禁。

| 触发 | 检测结果 | 处理 |
|---|---|---|
| 用户点「报告失效」 | 判定失效 | 用户的这条报告自动标为强证据（1.0），并附加一条权重 2.0 的「系统检测」证据；两者合计 3.0，达到阈值，链接立即转 `suspect`。也就是说检测与用户报告同时成立时，一名用户就足够 |
| 用户点「报告失效」 | 判定可用 | 用户仍可选原因标签提交，但弱证据旁显示「系统检测该链接可访问，请确认网络环境」；权重按 4.3 原规则 |
| 用户点「报告失效」 | 无法判断 | 按用户选择的原因标签正常写入 |
| 归属方或站方点「检测」 | 任意 | 只把结果显示给点击者，不写入证据。归属方看到失效后可以直接确认失效或补链 |
| 发布者补链保存 | 任意 | 立即检测一次，把结果显示给发布者，不写入证据 |

「系统检测」证据只在用户报告时产生，因此不会出现「系统认为失效但没有任何用户报告」的状态，用户看到的链接在达到阈值前始终是正常样式。

站长将提供同行站点的失效检测实现作为参考，设计细节等参考到手后再展开。本节在参考到手前不实施。

## 5. 模块 C：官方镜像作为原资源下的链接

### 5.1 模型

现状：站长把用户资源搬运到资源盘后另建一条资源（`creator.mdx` 对用户的承诺是「搬运到资源盘并重新发布」），两张卡片内容重复，署名归站长，两张卡片的反馈都落到站长。新模型：官方镜像是原资源下的一条 `official` 链接，存储类型 `touchgal`。这正是决策六「一个资源下可能存在多个镜像」所指的能力。

| 维度 | 镜像作为独立资源（现状） | 镜像作为原资源下的官方链接 |
|---|---|---|
| 卡片数量 | 两张 | 一张 |
| 署名 | 站长 | 原发布者 |
| 责任路由 | 两张都指向站长 | 官方链接归站方，用户链接归发布者，文件内容问题归发布者 |
| 原链接失效后 | 原卡片消失，镜像卡片与之无关 | 同一卡片内折叠失效链接，官方链接继续可用 |
| 访客配额 | 按链接存储类型计，不变 | 不变 |
| 存量数据 | 无关联 | 需要合并工具（5.7） |

「站方已备份」由是否存在官方链接推导，不单独存字段。「站方已测试」是资源级字段 `official_verified_at`，只有站方真正运行过才写入；发布者自称测试过不算站方担保。

### 5.2 卡片结构

```
资源卡片
  标题 · 类型 / 语言 / 平台
  发布者头像与名字 · [站方已备份] · [站方已测试]
  备注
  链接列表：官方链接置顶，其余按发布者的 sort_order，broken 者折叠
    ├ [OtoAme 资源盘] 1.2 GB · 站方镜像 · 获取下载链接
    ├ [自定义链接] 1.2 GB · 发布者 · 获取下载链接 · 报告失效
    └ 已折叠：1 条链接已失效 · 最近补链 3 天前
  底部：点赞 · 获取次数 · 遇到问题
```

### 5.3 归属与权限

- 官方链接的归属方是站方，其余链接的归属方是资源发布者。
- 添加官方链接在权限上对管理员开放，与现有资源盘存储类型的门槛一致（`app/api/patch/resource/route.ts`）。能否实际执行取决于是否持有资源盘账号，目前只有站长持有，将来可能给受信任的管理员另开账号。
- 发布者的编辑表单里官方链接只读；服务端拒绝非管理员对官方链接行的任何改动或删除。现有更新逻辑（`app/api/patch/resource/update.ts`）按链接 ID 做差量，只需加这一层保护。
- 发布者仍可编辑名称、备注、类型、语言、平台，官方链接不受影响。
- `components/patch/resource/resourcePermissions.ts` 的「资源归属者或管理员可管理」需要细化到链接级。

### 5.4 发布者对含官方链接资源的三种动作

原则：发布者永远可以立即让自己的贡献从公开视图消失或脱离自己的名字；只有物理删除站方文件需要站方。

| 动作 | 即时效果 | 需要站方 | 适用场景 |
|---|---|---|---|
| 删除我的链接 | 发布者自己的链接删除，资源与署名保留，官方链接照常 | 否 | 不想再维护网盘 |
| 移交给站方 | 资源 `user_id` 改为执行移交时的站方账号；原发布者记入 `origin_user_id`；署名按发布者选择保留（显示原发布者名字）或匿名（显示「用户投稿」），由 `credit_visible` 控制；发布者的链接删除；已发放的发布奖励不收回，因为贡献仍然存在 | 否 | 离站、隐私、不想再与该资源关联 |
| 申请下架 | 发布者自己的链接删除；资源写入 `takedown_requested_at`，期间所有链接不可揭示，卡片显示「发布者已申请下架，等待站方处理」；生成「发布者申请下架」工单，理由必填 | 是。站方一键「同意下架」（删除资源盘文件、删除资源）或「拒绝下架」（清空 `takedown_requested_at`，恢复揭示，附理由；发布者可重新添加自己的链接） | 文件本身有问题：版本错误、含有害内容、发错游戏 |

站方未处理时，警示与暂停状态持续，不自动删除。资源盘文件是站方资产，全量兜底政策以此为前提；发布者一时冲动的下架不会摧毁存档，而有害文件在站方处理前已对用户不可获取。

无官方链接的资源：发布者删除行为与现状一致，含发布奖励的收回。

### 5.5 镜像队列与优先级

全量镜像是政策，队列的作用是不遗漏、按序、每条省时间。

**队列定义。** 满足以下全部条件的资源进入队列：存在存储类型为外部网盘（`storage = user`）的链接；不存在官方链接；不在存量合并候选对中（5.7）。另加重新镜像项（5.6）。队列本身就是完整性检查，后台首页显示「未镜像 / 总数」。对象存储（`storage = s3`）上的文件已在站方存储，不需要镜像。

**排序。**

| 层级 | 范围 | 层内排序 |
|---|---|---|
| 一 | 游戏资源区（`section = galgame`） | 获取次数、是否为该条目唯一可用资源、网盘历史存活率（4.8）、体积 |
| 二 | 类型为「资料集」的资源 | 同上 |
| 三 | 补丁区中不在对象存储上的文件 | 同上 |

**省时间的三个杠杆。** 「添加官方链接」一键动作，在原资源上新增 `official` 链接并预填大小；研究资源盘的离线下载能力，对允许直链抓取的托管站让服务器直接拉取，站长只处理需要客户端登录的国内网盘；手工部分做成可批量的状态流：待下载、已下载待上传、已上传待建链接、完成。

审核通过与镜像解耦：先通过公开，镜像按优先级慢慢来。社区资源的前台文案是「站方备份排队中」，不是「未保存副本」。

存储成本随投稿线性增长。对象存储链接已有哈希字段，同一文件被多条资源引用时可按哈希去重；长期零获取的镜像可考虑转低频访问存储级别，需先确认资源盘对该级别的读取兼容。

### 5.6 镜像版本确认与重新镜像

问题：官方链接保存的是镜像当时的文件；发布者之后补链，系统无法知道新地址指向的文件与官方链接是否为同一内容。重新压缩一次、换一个网盘都会改变大小与哈希，但内容不变，不需要重新镜像；换成新版本则需要。这个判断只有发布者知道，所以要问发布者，而不是猜。

**触发。**

| 场景 | 处理 |
|---|---|
| 发布者补链 | 补链表单内直接回答（4.5 第 4 条），不另开工单 |
| 存量合并，每一对候选都需要（原因见 5.7） | 管理员在待合并队列中对一对或一页候选对点「询问发布者」，该候选对进入「待发布者确认」状态；系统开一条「镜像版本确认」工单给发布者，正文写明官方备份的创建时间与两条链接的地址。合并在得到回答或管理员决定之前不执行 |
| 管理员手动发起 | 在资源管理菜单中点「询问镜像版本」，开同样的工单。用途是自动触发覆盖不到的情况，例如用户在求助或工单中说官方链接是旧版本，或站长注意到资源描述改成了新版本号 |

**回答与后果。**

| 回答 | 资源标记 `mirror_check` | 已有官方链接的资源 | 待合并的候选对 |
|---|---|---|---|
| 内容相同 | `fresh` | 不进重新镜像队列 | 恢复为可合并，管理员一键合并 |
| 内容有变化 | `stale` | 进入重新镜像队列，按所属层级排序；官方链接旁显示「官方备份为旧版本」直到重新镜像完成 | 恢复为可合并，合并后同左 |
| 7 天未回应 | `unconfirmed` | 进入重新镜像队列所属层级的末尾，标注「发布者未确认」，管理员决定是否重做 | 保持暂停，队列标注「发布者未确认」，管理员决定按 `unconfirmed` 合并或继续等待 |

重新镜像完成后 `mirror_check` 回到 `fresh`，「官方备份为旧版本」提示消失。

### 5.7 存量合并工具

存量指历史上站长搬运后另建的重复资源：同一条目下，一条用户资源与一条站长资源内容相同、互不关联。如果不合并：镜像队列会把这些用户资源当作无官方链接列出，导致重复镜像；两张卡片分摊点赞与获取次数；用户网盘失效时用户卡片落入「已失效」区而站长卡片与之无关。因此存量必须处理。新模型不依赖存量合并完成，有候选对的用户资源在合并前不进镜像队列。

**工具形态。** 只做在后台。

- 待合并队列：系统按同条目、同分区、名称相似给出候选对，列出两条资源的名称、发布者、创建时间、链接列表，并附「待合并」总数。管理员可以手动把系统没配对的两条资源加为一对，也可以把误配的一对标记为「不是同一资源」。每一对有五种状态：未询问、待发布者确认、内容相同可合并、内容有变化可合并（合并后官方链接标为旧版本并进重新镜像队列）、未回应（管理员决定）。队列提供「询问发布者」与「批量询问本页」两个按钮，让发布者的回答先于管理员的处理到达。
- 合并弹窗：在队列中选中一对后打开。弹窗执行：把站长资源的资源盘链接移入用户资源并标 `official`；合并获取次数与点赞；删除站长资源那张卡片；写入链接历史（变更原因「合并」）。
- 前台条目页的资源管理菜单可以放一个「去后台合并」的快捷入口，只是跳转，不在前台重复实现。

**节奏。** 由管理员逐条手动执行，不设截止日期，队列驱动。每合并一对，镜像队列的「未镜像」数就少一条虚假项。

**版本判断。** 存量数据里没有能区分「同一文件」与「新版本」的信号，逐项说明：一，链接历史表不存在于存量。二，资源与链接的 `updated` 都不可用：现有下载计数每次点击都会更新 `patch_resource` 与 `patch_resource_link` 两张表的 `download` 字段（`app/api/patch/resource/download/service.ts`），Prisma 的 `@updatedAt` 随之刷新两张表的 `updated`，所以几乎每条被下载过的资源与链接的更新时间都晚于镜像创建时间。三，文件大小不可用：`size` 是用户手填的字符串，准确性无法保证，而且站方重新压缩时会加约 10% 的恢复记录，官方文件天然比原文件大，同一内容也会显示为大小不同。因此存量合并不做自动判断，每一对候选都先询问发布者（5.6），得到「内容相同」或「内容有变化」后再合并；7 天未回应的由管理员决定按未确认合并或继续等待。这符合「不合并未经确认的版本」的原则，代价只是时间，而合并本来就是队列驱动、不设截止的。

面向未来的数据：链接新增 `content_changed_at`，只在地址变更时写入（4.7）；补链表单当场收集发布者的回答（4.5）。新模型上线后不再需要事后推断版本。

### 5.8 获取计数

以揭示为准，不以点击为准。揭示时用户已经付出配额或点数，是明确的下载意图；同一访问者对同一链接 24 小时内只计一次（与现有访问授权语义一致）；资源级计数按访问者去重，同一人揭示同一资源的多条链接只计一次（与配额规则一致）。用户复制地址绕过跳转的问题因此不存在，因为揭示已经计数。

计数包含访客的揭示（按访客标识去重）；这与失效报告要求登录是两件事，计数是统计，报告是证据。

前台文案从「下载次数」改为「获取次数」。跳转点击仍然记录，仅作为发布者与管理员可见的辅助统计。官方链接的揭示计入资源总数，署名归发布者；分链接计数显示各自份额。

**历史数据处理。** 现有 `download` 字段保留，现有数值原样保留作为初始值，不重算；切换之后只按揭示规则累加。旧数值按点击计，新增量按揭示计，两者定义不同但都是「有多少人想下载」的近似，混在一起不会造成用户可见的下降，只可能让增长速度看起来变快，因为揭示通常多于点击。不重算的理由：重算只能覆盖揭示记录系统上线之后的时期，对更早的资源没有数据，反而会造成数字下降。

用户能投稿新条目（`patch_submission`，完整状态机与押金），却不能修正已有条目，只能发反馈让站长手改（`app/api/edit/route.ts` 要求管理员）。在投稿表上增加类型字段区分新建与修正。

| 规则 | 内容 |
|---|---|
| 提交资格 | 登录用户，含普通用户 |
| 押金 | 零 |
| 审核 | 全部审核，无先生效后审 |
| 载荷 | 目标条目 ID 与变更过的字段 |

## 7. 模块 E：管理后台

### 7.1 统一收件箱

现有后台按模块分页（反馈、举报、待审资源、投稿各一页），无优先级，处理一轮要切换五六个页面。不设版主之后，后台效率是唯一剩下的负载杠杆。

- 一个队列：待审条目、待审资源、升级到站方的工单、举报、待镜像、待合并、官方链接的健康事项，全部进同一列表，按等待时长与优先级排序。
- 左列表右详情：右侧展示处理所需的全部上下文，包括这项为什么到了站方、归属方是谁、系统已经做了什么。
- 一键动作与模板：通过、拒绝、模板回复、标失效、移动到正确条目，每个动作一个键，不弹二次确认，改为可撤销。
- 键盘导航与批量操作。
- 今日已处理计数，让站长能设预算。

### 7.2 技术栈决策

后台用 shadcn，独立根布局与独立样式入口隔离；前台保持 HeroUI v2，将来若升级走 v2 到 v3 的官方渐进迁移路径，不为统一而重写前台。

依据：项目是 Tailwind v4 CSS 优先配置（`styles/tailwind.css` 通过 `@plugin './hero.ts'` 加载 HeroUI，`@custom-variant dark`），HeroUI 把 `background`、`foreground`、`primary`、`secondary`、`default`、`content1` 至 `content4` 注册为 Tailwind 工具类；shadcn 在 `@theme inline` 里注册 `background`、`foreground`、`primary`、`secondary`、`muted`、`accent`、`card` 等。前四个家族重名，放进同一样式入口时工具类只能有一个定义，后声明者覆盖先声明者。HeroUI v3 的主题变量同样无前缀，与 shadcn 同样撞名。

隔离方案：用路由组拆成前台与后台两个根布局（现状只有一个根布局 `app/layout.tsx`，导入 `styles/index.css`，后台布局 `app/admin/layout.tsx` 嵌套其下），后台样式入口只含 Tailwind 与 shadcn 令牌，不加载 HeroUI 插件。后台样式与脚本完全不进前台包，深浅色都用 `.dark` 类。前后台切换是整页加载。

### 7.3 迁移清单与前台预览问题

后台共 66 个组件文件，43 个直接引用 HeroUI，等于整套后台 UI 重写。后台复用的公共组件：通用件四个（错误页、浮动卡片、分页、加载态），替换成本极低；领域件五个（投稿预览、资源卡片、贴纸缩略图、点数账本、条目属性），需要后台版本或抽成不依赖 UI 库的展示逻辑。实现时在前端技能文件里加一条「后台路由组只用 shadcn」。

前台预览问题：后台审核投稿时需要看到「这条投稿发布后在前台长什么样」，现状是后台直接引用前台组件 `components/submission/PatchSubmissionPreviewView.tsx`。隔离后后台不能再渲染 HeroUI 组件，而 `app/submission/[id]/page.tsx` 是作者的编辑器，不是预览页。方案方向：在前台根布局下新增一个仅管理员可访问的预览路由，渲染前台真实样式；后台详情面板用 iframe 嵌入该路由，或提供「在新标签打开预览」。同理适用于资源卡片预览。站长已确认这就是所指的问题，具体方案（路由形态、权限校验、iframe 与新标签的取舍、投稿数据如何传给前台预览）待详细讨论。

## 8. 模块 F：入口分流、求助区与受理范围

### 8.1 定位

工单是「请你改」：需要某个归属方改变站内数据，所以有归属方、有状态机、有超时。求助是「教教我」：提问者需要信息，站内数据不变，所以没有归属方、没有超时升级，只有回答与采纳。工单永远不能被公众认领，求助永远不会被分派。运行、下载、解压类问题从来不是工单。

### 8.2 现象分流

资源卡片底部只有一个「遇到问题」按钮。第一步选哪条链接或整条资源，第二步选现象。分流原则：凡是可能由用户侧造成的现象一律先求助；只有站内数据本身可判定的现象才直接进工单。

| 现象 | 去向 | 归属 |
|---|---|---|
| 网盘显示已删除、已过期；链接要求付费 | 失效报告，强证据 | 系统，达阈值后归属方 |
| 打不开、超时 | 先显示网络提示；确认已尝试更换网络后写入失效报告，弱证据 | 同上 |
| 下载慢 | 下载指南 | 无 |
| 版本与描述不符、缺少描述中声明的文件、内容与条目不符 | 工单：资源与描述不符 | 发布者 |
| 压缩包损坏、解压失败、无法启动、乱码、存档问题 | 求助，锚定到该资源，附检查清单（核对文件大小与校验码、重新下载） | 社区回答，发布者收到通知 |
| 发在了错误的条目下 | 工单：资源发错条目 | 站方 |
| 疑似违规或有害内容 | 举报 | 站方 |

压缩包损坏多数是下载不完整，因此归入求助而非工单，由 8.3 的桥接规则在必要时升级。链接旁的「报告失效」按钮是前两行的快捷入口，与经「遇到问题」到达的是同一投票。

### 8.3 桥接规则

1. 锚定到资源的求助里，发布者可点「这是资源问题，转为工单」，生成一条「资源与描述不符」工单归自己，求助帖保留并链接到工单。
2. 求助帖上「我也遇到了」达阈值，系统自动开一条「资源与描述不符」工单给发布者并链接到求助帖；工单结案时在求助帖贴一条系统回复。
3. 用户把环境问题发成工单时，发布者可一键「转为求助」，工单以「不在受理范围」结案，内容复制为一条锚定到该资源的求助，提问者为原开启者。
4. 三条规则都不经过站方。

### 8.4 求助区

独立实体，但每条求助必须锚定到一个对象：一个游戏、一条资源，或一个固定话题类别。不存在无对象的自由发言。

**固定话题类别（2026-09-05 站长已确认）。** 用于不属于任何具体游戏或资源的求助。

| 类别 | 收什么 | 不收什么 |
|---|---|---|
| 运行环境 | 系统区域与语言设置、运行库、兼容性、显示与字体、通用的启动问题 | 某个具体游戏的启动问题，应锚定到该游戏 |
| 下载与解压 | 网盘客户端、加速与网络、分卷与校验、解压软件与密码格式 | 某条链接打不开，应走报告失效 |
| 账号与站务 | 登录、邮箱验证、萌萌点规则、投稿与创作者申请的流程性疑问 | 需要站方改数据的请求（例如改名、恢复内容），应走工单「其他」 |
| 作品推荐 | 求推荐某类作品、找一部忘了名字的作品 | 无 |
| 其他 | 上述都不适用的求助 | 无 |

「作品推荐」与小喇叭的「求推荐」用途有重叠：求助有回答与采纳机制、费用低；小喇叭无回答、费用高但曝光在首页。两者并存时用户会按需要选择。站长已决定保留该类别。

**状态。**

| 状态 | 含义 | 进入条件 |
|---|---|---|
| 未解决 | 等待回答 | 发布时 |
| 已解决 | 提问者采纳了一条回答 | 提问者操作 |
| 已关闭 | 长期无活动 | 无新回答、无「我也遇到了」持续 14 天 |

**规则。**

| 规则 | 内容 |
|---|---|
| 回答 | 平铺，不嵌套。已解决与已关闭的求助仍接受新回答（后来者可能有更好的解法）。已关闭的求助收到新回答时仍通知提问者（发求助的人），但不再通知所锚定资源的发布者，也不出现在「待回答」列表 |
| 采纳 | 提问者在任何状态下都可以采纳一条回答，包括已关闭之后，不需要先重开，没有时间限制。采纳使求助变为已解决，被采纳的回答者按下方「费用与奖励」段获得奖励 |
| 「有效」标记与社区验证 | 任何登录用户可对一条回答点「对我有效」，每人每条回答一次。未被采纳的回答累计达到阈值（3 人）时，系统标记为「社区验证有效」，回答者按「费用与奖励」段获得奖励。投票人的门槛与生效的等待期见「费用与奖励」段。这解决提问者已离开、无人采纳但解法确实有效的情况。「社区验证有效」的回答在「相似求助」中优先展示 |
| 重开 | 只有提问者可以重开自己的求助，每次关闭后最多重开一次，没有时间限制。重开的含义是「我的问题还没解决，请再看看」：求助回到未解决，重新进入「待回答」列表，并再通知一次所锚定资源的发布者。重开与采纳无关：关闭很久之后出现了好回答，提问者直接采纳即可，不必重开。其他用户不能重开他人的求助 |
| 我也遇到了 | 任何登录用户在任何状态的求助上可点一次。效果：计数加一；点击者订阅该求助，出现被采纳或社区验证有效的回答时收到通知；锚定到资源时计入 8.3 的桥接阈值。不新建求助，不付费 |
| 提出相同问题（同问） | 见下方「同问」段 |
| 隐藏 | 举报达阈值自动隐藏 |
| 提问前 | 展示相似求助，社区验证有效的回答优先 |
| 费用与奖励 | 见下方「费用与奖励」段 |
| 通知 | 锚定到资源时通知该资源的发布者 |

**费用与奖励。** 目标是三条：回答者有动力；任何合谋都不能从系统净赚点数；用户之间的点数转移只有悬赏一条通道，且每次转移都有损耗。

| 规则 | 内容 |
|---|---|
| 发布费 | 提问者发布求助时扣 5 点，不退，包括被采纳之后。这是提问的价格，不是押金 |
| 奖励 | 每条求助最多奖励一条回答：先发生的那个事件（提问者采纳，或社区验证有效）决定被奖励的回答。奖励 3 点，由系统发放。同一条求助不会奖励第二条回答；之后再被社区验证有效的回答只获得标记，不获得点数 |
| 悬赏 | 可选，提问者发布时指定，范围 10 到 50 点。发布时从提问者可用余额中暂扣，复用现有的萌萌点预留机制（`user_moemoepoint_reservation`，与投稿押金相同：暂扣期间不可用但仍计入总额，结算与释放走同一套幂等原语）。悬赏金额公开显示在求助列表与帖顶。只有提问者采纳时结算：暂扣额从提问者账上扣除，被采纳的回答者收到悬赏的 90%（向下取整，且至少比悬赏少 1 点），其余由系统烧毁。悬赏付给被采纳的回答，与哪条回答拿到了 3 点系统奖励无关 |
| 悬赏不可撤回 | 发布后悬赏只能提高，不能降低或撤回；唯一例外是求助尚无任何回答时，提问者可以撤回悬赏（暂扣释放，发布费不退）。提问者不能在已有回答的情况下不采纳而手动关闭求助，只能等自动关闭。这两条防止用悬赏引来回答之后再收回 |
| 社区验证与悬赏 | 社区验证有效不触发悬赏结算，只发 3 点系统奖励；否则三个账号合谋点「有效」就能拿走陌生提问者的悬赏 |
| 悬赏的释放与迟到采纳 | 求助自动关闭，或因举报达阈值被隐藏时，暂扣释放，点数回到提问者可用余额。之后提问者仍可采纳：采纳时若可用余额不低于悬赏额，按原规则结算；不足则只发系统奖励，界面在采纳前告知，帖中标注「悬赏未结算」 |
| 采纳不可更改 | 每条求助只能采纳一次，采纳后不能更换或取消。被采纳与被社区验证有效的回答对作者变为只读，不能编辑或删除，防止先被采纳再把内容换成广告或恶意链接 |
| 「有效」投票的门槛 | 投票人注册满 7 天；每人每条回答一次；每人每天最多投 10 次。社区验证只在求助发布满 7 天且提问者尚未采纳时才生效，给提问者的采纳留出优先权 |
| 净效果 | 系统对每条求助至少净回收 2 点（发布费 5 减奖励 3），有悬赏时再回收悬赏的 10%。自问自答的循环每轮至少亏 2 点，有悬赏时再亏悬赏的 10% |
| 转移风险 | 悬赏是全站唯一的用户间点数转移通道。同一个人用多个账号把签到攒的点数集中到主账号仍然可能：以 50 点悬赏计，小号付出 5 点发布费加 50 点悬赏，主号收到 45 点悬赏加 3 点系统奖励，每轮损失约 13%。加上下面的限额与注册时长要求，以及每个账号都要邮箱验证并每天手动签到的人力成本，这条路收益很低。此为已知的剩余风险，不再额外设防 |
| 「有效」合谋风险 | 三个满 7 天的小号给主号的回答点「有效」，可以在任何人的求助上为主号赚取 3 点系统奖励，每天最多 3 次。系统不因此净发点数，因为每条求助的奖励仍不超过发布费；受害的是本应得到奖励的真实回答者。缓解：7 天等待期让提问者先采纳；每日投票与奖励上限；后台指标可以看到「总是同一批人投同一个回答者」的模式。此为已知的剩余风险 |
| 防刷限额 | 每人每天最多发布 3 条求助；每人每天最多获得 3 次系统奖励（悬赏结算不计入此上限）；每人每天悬赏总额上限 50 点；提问者与回答者都必须注册满 7 天才产生点数奖励与悬赏结算，否则只有采纳标记；回答者不能是提问者本人 |
| 界面文案 | 发布时显示「发布费 5 点，其中 3 点将奖励被采纳或被社区验证有效的回答」；设置悬赏时显示「悬赏 N 点已暂扣，采纳时回答者将获得 M 点」。技术上发布费在发布时扣、系统奖励在采纳时发、悬赏走预留与结算，三者独立记账。新增的费用与奖励必须同步 `constants/moemoepoint.ts` 里的规则展示数据，该文件的注释要求展示金额与实现一致 |

关于「等 14 天被关闭后再回复」这类操纵：关闭后的采纳与关闭前的采纳规则完全相同，系统奖励同样是 3 点、同样每条求助只发一次，悬赏同样只在采纳时结算且付出永远少于暂扣，关闭前后没有可利用的差别。

**同问。** 「提出相同问题」在任何状态的求助上可用。流程：点击后打开新建求助表单，锚定对象与原帖相同且不可改，标题预填原帖标题，正文要求点击者写自己的情况（环境、已尝试的办法），发布费照收。新求助顶部显示「同问自：原帖标题」并链接原帖，原帖的回答以只读摘要形式显示在新求助的回答区上方，避免重复回答。原帖显示「N 条同问」及链接。同问只有一层：对一条同问再点「提出相同问题」，新求助链接到最初的原帖而不是这条同问。原帖出现被采纳或社区验证有效的回答时，所有同问的提问者收到通知。

| 动作 | 新建求助 | 付费 | 得到自己的回答 | 收到通知的条件 |
|---|---|---|---|---|
| 我也遇到了 | 否 | 否 | 否，只能看原帖的回答 | 原帖出现被采纳或验证有效的回答 |
| 提出相同问题 | 是 | 是 | 是 | 原帖与自己的求助任一出现上述回答 |

**求物与资源回答。** 求物是求助的一种意图，指请求某样东西。发布时先选类别：

| 类别 | 指什么 | 锚定对象 | 回答形式 |
|---|---|---|---|
| 条目资源 | 某游戏的本体、补丁、资料集等应当出现在条目资源列表里的东西 | 已有条目时锚定到条目；没有条目时以游戏名称锚定，称为「未落地的求物」 | 文字回答；已落地时另有「资源回答」 |
| 站外事物 | 第三方软件、网站、工具、字体、模拟器、购买渠道等不属于条目资源的东西 | 话题类别；与某游戏相关时也可锚定到该游戏 | 只有文字回答 |

规则：

- 所有文字回答（含链接）都与普通求助的回答相同，不经审核即可见，也不进入任何审核队列。审核队列只与下面的资源回答有关。
- 未落地的求物在帖子顶部显示「此游戏尚无条目」与一个投稿入口，游戏名称预填。所有未落地的求物同时出现在条目投稿页的「大家在求的游戏」列表里，作为对全体用户的任务提示；投稿并通过后按现有规则获得发布条目奖励，不另设奖励。管理员也可以直接新建条目。条目发布后，投稿人、提问者或管理员任一方点「关联到条目」，求物落地。
- 求物遵守与小喇叭相同的「无回应义务」声明：发布界面提示「求物不构成对站方或任何发布者的请求」。
- 资源回答只在已落地的条目资源类求物上出现，是回答者主动选择的一种回答形式：点「发布资源来回答」，填写现有的资源表单（链接、大小、类型、语言、平台、备注）。提交后系统同时做两件事。一，在求助帖中立即发布一条普通回答，正文是表单内容的文字版，含链接，不经审核即可见，提问者可以立刻采纳。二，按现有流程创建一条挂在该条目下的资源：创作者与管理员的直接公开，普通用户的进入现有审核队列（`status = 2`），审核通过后出现在条目的资源列表，帖中的回答加上「已收录到条目资源列表」标记。求助帖的可用性不依赖审核，审核人员不在线只影响资源何时进入条目列表。
- 资源回答的审核拒绝分两种：「不收录」时帖中回答原样保留；「违规」时帖中回答一并隐藏。
- 未落地的求物落地之后，回答者可对自己的文字回答点「转为条目资源」，用回答内容预填资源表单重新提交，进入资源回答的流程。这一步同样是回答者自愿的。
- 已知的取舍：求助帖里的链接是普通文字，不经过揭示与配额机制，这与评论区里的链接一致。发布者仍有动力走正规资源发布，因为只有资源卡片才有发布奖励、署名、获取计数和站方镜像兜底。
- 资源回答的回答者同时获得现有的发布资源奖励（3 点，资源审核通过时）与本节的求助奖励（3 点，被采纳或社区验证时），两者独立。
- 首页「最新求助」可按意图与类别筛选，求物默认包含。

站长唯一要守住的纪律是不做默认回答者。首页「最新求助」默认把未解决且无回答的排在前面。这是所有模块里方差最大的一个，盯住「无人回答率」。

### 8.5 首页聚合的可见性

首页新增「最新求助」与「最新评论」。两条规则：所属条目为 NSFW 时，对未开启 NSFW 的访客隐藏；被自动隐藏的内容，以及作者注册时长门槛未满（3 天）的内容，不进入首页聚合。门槛只影响是否上首页，不影响发布本身；把它设得短是因为当前用户少，新用户的内容应尽快被看见。

## 9. 模块 G：沟通

### 9.1 小喇叭

首页用户短消息流，发布需付萌萌点，尚未实现。设计原则：价格固定，曝光时长随量浮动；量少时曝光长、价值高，量多时自然缩短；被刷下首页就重发，是对萌萌点消费的刺激。价格本身就是发布门槛，不另设注册时长门槛：普通用户仅靠签到攒够售价需要约十天，积极贡献者更快，这已经隐含了筛选。

| 规格 | 内容 |
|---|---|
| 价格 | 50 点。要求可用余额不低于售价，不允许负数；官方发布免费 |
| 首页组件 | 只显示第一页，固定条数（6 条），最新在前 |
| 小喇叭页 | 同样页宽分页，最多显示 10 页。分页范围内的小喇叭始终公开显示，不看年龄：一条发布 40 天但仍在范围内的小喇叭照常显示 |
| 分页范围外 | 不再出现在小喇叭页；关联了游戏的，在该游戏页的条目里继续显示，直到发布满 3 个月；作者个人页永久可见 |
| 关联游戏 | 可选。用途包括为某个游戏应援、推荐、征集同好。关联后在该游戏页的关联小喇叭条目里显示（9.2）。关联的对象只能是游戏，不能是资源 |
| 单向广播 | 小喇叭不可回复，因此它上面的任何需求（求资源、求补丁、求攻略等）不构成对站方或发布者的请求，没有人有回应义务。发布界面固定显示一行提示：「小喇叭不可回复；需要他人回应的内容请使用求助区或投稿」。规则页写明同一条。不禁止用户发需求，也不对内容做用途审查，因为审查需要人判断，而价格已经限制了数量 |
| 编辑 | 发布后 5 分钟内可编辑一次 |
| 重发 | 允许，不做同文本去重，价格本身就是防刷 |
| 退款 | 自删不退；因违规被删不退；误判恢复则退 |
| 管理 | 不允许回复；举报达阈值自动隐藏；关键词过滤兜底；每条带举报入口 |
| 价格调整 | 运行一个月观察日均条数：低于每天一条说明贵了，高于二十条说明便宜了。不做动态定价 |

**关联游戏的理由（2026-09-05 站长已确认保留）。** 一，被刷下首页之后，关联了游戏的小喇叭在该游戏页继续显示到发布满 3 个月，这是购买者付出高价后仍然持有的剩余价值，没有它，量大时小喇叭只剩几小时的首页曝光。二，应援、推荐、征集同好这些用途天然指向某一部作品，关联让内容落到有兴趣的人面前。三，关联把话题拉回作品本身，减少无对象的闲聊。

### 9.2 游戏页条目、官方置顶与横幅

**游戏页的关联小喇叭条目。** 条目页顶部区域或桌面端侧栏的一个紧凑条，显示最新 3 条关联该游戏的小喇叭与「更多」链接。不放进评论区，因为评论是讨论、小喇叭是单句且不可回复。条目名称待定，「大家在说」只是占位；命名需要体现「这些是关于这部作品的小喇叭」，并与「小喇叭」这个品牌词一致，候选见第 13 节。

**官方置顶。** 小喇叭表加 `official` 与 `level` 两个字段，`level` 取值「普通」「重要」，只对官方小喇叭有意义。

| 级别 | 效果 |
|---|---|
| 普通 | 生效期内占据小喇叭第一页的第一行（首页组件与小喇叭页都是如此），样式与用户消息区分 |
| 重要 | 在普通效果之外，全站每个页面渲染一条可关闭的顶部横幅 |

官方置顶占用第一页的一个普通名额，不增加行数，也不预留空间：有生效中的官方小喇叭时第一行是它，其余名额按时间排普通小喇叭；没有时第一行就是最新的普通小喇叭。同一时间只置顶一条，取最新的生效中官方小喇叭；更早的官方小喇叭按时间进入普通列表并带官方标记。官方小喇叭有生效起止时间（默认 72 小时），过期后不再置顶。

**横幅。** 同一时间全站只显示一条，取最新的生效中「重要」级官方小喇叭；发布新的重要小喇叭即取代旧的，旧的保留小喇叭行但不再渲染横幅。横幅在首页也显示，位于页面最顶部；同一条重要小喇叭此时同时出现在横幅和小喇叭第一行，这是有意的重复。关闭状态按小喇叭 ID 存于浏览器本地，新的重要小喇叭会再次显示。不做站内通知群发：全表写入浪费资源，且消耗红点信誉。

### 9.3 MDX 分工

MDX 保留，用于指南、规则、受理范围这类长文档。问题只是把它用在了时效性通知上，分工明确后不需要改造 MDX。官方小喇叭需要细节时链接到一篇 MDX。内容目录加载器（`lib/mdx/getPosts.ts`）没有草稿过滤，目录下所有文件都会发布，草稿不要放进去。

### 9.4 维护流程

状态页用 1Panel 的站点停用页自定义：当前状态一句话、预计恢复时间、Telegram 链接、联系邮箱、一句「资源与账号数据不会丢失」。它只在站点被停用且面板正常时显示，服务器整体宕机时不显示，对计划维护够用。不另建应用内维护模式。

维护清单：维护前先发重要级官方小喇叭（横幅生效）再停用站点；维护后恢复站点再更新小喇叭。上次事故的教训是缺这张清单，不是缺工具。

### 9.5 群发邮件

保留不动，标注为不常规使用。它在单个请求里同步并发发送（`app/api/admin/mail/service.ts`），无队列无重试，只在真正严重的公告时使用。

## 10. 模块 H：运营指标

后台首页现在只有新增用户、条目、资源、评论（`app/api/admin/stats/service.ts`）。改为负载指标：

- 每个队列：积压数量、最老一项的等待时长、近 30 天中位处理时长。
- 每周新增工单按类型的趋势，指出下一个该用设计消灭的问题类别。
- 未结案失效工单最多的发布者排名。
- 未镜像 / 总数，待合并数，`mirror_check` 为 `stale` 与 `unconfirmed` 的数量。
- 官方链接的 `suspect`、`disputed`、`broken` 数。
- 无官方链接且全部链接失效的资源数（已丢失）。
- 求助区无人回答率。
- 自动处理占比：机制层与责任层消化了多少事务而没有到站方手里。这个比例上升是重构成功的定义。

## 12. 非目标与已排除方案

- 不设版主、志愿者或能力授权体系。
- 不给创作者镜像权限。
- 不做私聊的运营用途例外。
- 不做站内通知群发。
- 不做应用内维护模式。
- 不接受访客的失效报告。
- 不做资源级担保等级枚举；用「是否存在官方链接」与 `official_verified_at` 两个事实代替。
- 链接不设生命周期状态（如「已替代」）；补链只改地址、记历史。
- 不允许他人重开别人的求助；用「提出相同问题」关联。
- 小喇叭不设注册时长门槛；价格即门槛。
- 小喇叭只关联游戏，不关联资源。
- 小喇叭不做内容用途审查；需求类内容不禁止，只声明无回应义务。
- 存量合并工具只做在后台，前台至多放跳转入口。
- 不重做评论、评价、私聊；不换框架；不改萌萌点经济的既有规则，只新增小喇叭与求助区两项消费。
- 不为统一 UI 而重写前台。
- 站方不裁决链接健康，唯一例外是争议态的可选「打开试试」。
- 悬赏是全站唯一的用户间点数转移通道，且每次结算都烧毁一部分；不新增其他转移通道。
- 链接检测不做定时扫描，只随手动动作触发。
- 求物不单设区域，是求助的一种意图；文字回答里的链接不进入任何审核队列；只有回答者主动选择的资源回答才创建待审核资源，进入条目资源列表才走现有审核。
- 存量合并不做自动版本判断，每一对都先询问发布者。

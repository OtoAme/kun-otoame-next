# 模块 07（PM 版）：求助区与费用奖励

状态：设计草稿，待站长审阅。上游：[总计划](./00-master-plan.md)第 4.8 节、[设计基线](../7.operations-layer-redesign.md)第 8.3 至 8.5 节。技术细节见配对的[实施计划](./07-help-zone.md)。基线「费用与奖励」整段属未审定事项 D8，本文不把它当作已批准。

## 目标与责任人

让运行、下载、解压这类站方无法在用户机器上解决的问题由社区消化，并把「求资源」从催更变成可回答、可采纳、可落地为条目资源的事。业务与运营责任人是站长，负责规则定稿与上线验收；交付责任在实施方。站长在求助区不做默认回答者，站方侧只保留隐藏与恢复、关联条目、处理举报三类动作；回答、采纳、桥接全部由用户与资源发布者完成。

## 功能介绍与使用流程

### 1. 求助的对象与类型

求助区是一个公开的社区问答区，用来消化运行、下载、解压、找东西这类站方无法代替用户操作的问题。每条求助必须挂在一个对象上，没有无对象的自由发言。可挂的对象有三类：一个游戏条目、一条具体资源，或五个固定话题之一。

| 固定话题   | 收什么                                                   | 不收什么                               |
| ---------- | -------------------------------------------------------- | -------------------------------------- |
| 运行环境   | 系统区域与语言、运行库、兼容性、显示与字体、通用启动问题 | 某个具体游戏的启动问题，应挂到该游戏   |
| 下载与解压 | 网盘客户端、加速与网络、分卷与校验、解压软件与密码格式   | 某条链接打不开，应走「报告失效」       |
| 账号与站务 | 登录、邮箱验证、萌萌点规则、投稿与创作者申请的流程疑问   | 需要站方改数据的请求，应走工单「其他」 |
| 作品推荐   | 求推荐某类作品、找一部忘了名字的作品                     | 无                                     |
| 其他       | 上述都不适用                                             | 无                                     |

发帖时还要选意图：**提问**（我需要信息）或**求物**（我请求某样东西）。求物再分「条目资源」与「站外事物」，可挂的对象不同：

| 意图            | 可挂对象                                                                   |
| --------------- | -------------------------------------------------------------------------- |
| 提问            | 游戏、资源、话题                                                           |
| 求物 · 条目资源 | 已有条目时挂该条目；站内还没有这个条目时按游戏名称发，称为「未落地的求物」 |
| 求物 · 站外事物 | 话题；与某个游戏相关时也可以挂该游戏                                       |

求物不挂到单条资源上——求一样东西的对象是作品或话题，不是别人已经发布的那一条资源。

「作品推荐」与小喇叭的「求推荐」用途重叠，站长已决定两者并存：求助有回答与采纳、费用低；小喇叭没有回答、费用高但曝光在首页，用户按需要选。

### 2. 发一条求助

发布前，界面按所选对象与标题列出相似求助，其中被社区验证有效的回答排在前面，让提问者先看有没有现成答案。发布界面同时说清三件事：这条求助由社区回答，不是向站方或某个发布者下单（求物尤其明示「不构成对站方或任何发布者的请求」）；本次的费用与奖励；一句话的受理范围提示，内容只对应当时已经上线的能力，完整规则正文随将来的站点文档统一编写。

提交后扣发布费（金额与悬赏见第 7 小节），求助进入「未解决」，并出现在求助区的「待回答」列表里等人来答。挂到某条资源的求助会通知该资源的发布者。

提问者不能删除自己的求助，也不能在已经有回答的情况下手动关掉它。这两条防止用悬赏引来回答之后再把钱抽走。

### 3. 回答、「对我有效」与采纳

任何登录用户都可以回答，回答平铺显示，不做楼中楼。已解决和已关闭的求助仍然接受新回答，因为后来者可能有更好的解法。有新回答时提问者会收到通知；挂在资源上的求助在关闭之前，新回答还会再提醒一次该资源的发布者，关闭之后就不再打扰他。

回答作者在自己的回答被采纳、拿到该求助的系统奖励或被社区验证之前可以编辑或删除它，之后转为只读，防止先被采纳再把内容换成广告或恶意链接。提问者也可以在自己帖子里补充说明，但自答不能被采纳、不算「有人回答了」，也不产生奖励。

**采纳。** 只有提问者能采纳，任何状态下都可以，包括帖子已经关闭很久之后，不需要先重开，也没有时间限制。采纳让求助变成「已解决」。每条求助只能采纳一次，采纳后不能更换或取消。帖子被隐藏期间提问者仍能采纳当时没有被隐藏的回答；隐藏与恢复的完整效果见第 8 小节。

**「对我有效」与社区验证。** 任何登录用户可以对一条回答点「对我有效」，每人每条回答一次，重复点击不生效也不消耗当天额度。未被采纳的回答累计到阈值人数时，系统给它打上「社区验证有效」标记。这一步专为「提问者已经离开、没人采纳但解法确实有效」准备，因此有两道限制：投票人要注册满一定时长；社区验证只在求助发布满等待期、且提问者仍未采纳时才生效，把优先权留给提问者。被标记为社区验证有效的回答，在别人看「相似求助」时优先展示。相关阈值、等待期与每日投票额度见第 7 小节，随 D8 审定。

### 4. 关闭、重开，以及两种「我也有这个问题」

一条**未解决**的求助连续 14 天既没有新回答也没有人点「我也遇到了」，系统把它转成「已关闭」，它从待回答列表消失。已解决的求助不会再被自动关闭。关闭之后收到新回答仍然通知提问者，但不再打扰所挂资源的发布者。

只有提问者能重开自己的求助，别人不能重开他人的帖子。每经历一次关闭，提问者有一次重开机会：重开的含义是「我的问题还没解决，请再看看」，帖子回到未解决、重新进入待回答列表，并再通知一次所挂资源的发布者；如果之后又静置满 14 天被关闭，还可以再重开一次。重开与采纳无关——关闭很久后出现了好回答，直接采纳即可，不必先重开。

同一个问题的两种表达方式效果完全不同：

| 动作                 | 新建求助 | 付费 | 会得到属于自己的回答 | 什么时候收到通知                   |
| -------------------- | -------- | ---- | -------------------- | ---------------------------------- |
| 我也遇到了           | 否       | 否   | 否，只能看原帖的回答 | 原帖出现被采纳或社区验证有效的回答 |
| 提出相同问题（同问） | 是       | 是   | 是                   | 原帖或自己的帖任一出现上述回答     |

「我也遇到了」在未解决、已解决、已关闭三种状态下都能点，每人一次：计数加一，点击者就此订阅该帖；挂在资源上的求助还会把它计入第 6 小节的桥接阈值。帖子被隐藏期间不能点。

「提出相同问题」会打开新建求助表单：对象与原帖相同且不能改，标题预填原帖标题，正文要求点击者写自己的情况（环境、已经试过的办法），发布费照收。新帖顶部显示「同问自：原帖标题」并链接回原帖，原帖的回答以只读摘要显示在新帖回答区上方，避免重复回答；原帖那边显示「N 条同问」及链接。同问只有一层：对一条同问再点「提出相同问题」，新帖仍然链接到最初的原帖。原帖出现被采纳或社区验证有效的回答时，所有同问的提问者都会收到通知。

### 5. 求物、落地与资源回答

**未落地的求物。** 站内还没有这个游戏的条目时，帖顶显示「此游戏尚无条目」和一个投稿入口，跳过去时游戏名已经预填，投稿人可以再改。所有未落地的求物同时出现在「发布条目」页的「大家在求的游戏」列表里，作为对全体用户的任务提示；投稿并通过后按现有规则拿发布条目奖励，不另设奖励。管理员也可以直接新建条目。条目存在之后，该条目的投稿人、提问者或管理员任一方点「关联到条目」，这条求物就算落地，只会成功一次。

**文字回答一律不经审核。** 求物的所有文字回答（包括其中的链接）与普通求助的回答完全一样：立即可见，不进任何审核队列。求助帖里的链接是普通文字，不走获取链接的揭示与配额那一套，这与评论区里的链接一致；发布者仍有动力走正规资源发布，因为只有资源卡片才有发布奖励、署名、获取计数和站方镜像兜底。

**资源回答。** 只有已经落地的「条目资源」类求物才有这一形式，而且完全由回答者自愿选择：点「发布资源来回答」，填现有的资源表单（链接、大小、类型、语言、平台、备注），提交后系统同时做两件事。一，在帖子里立即发布一条普通回答，正文是表单内容的文字版并含链接，不经审核，提问者可以马上采纳。二，按现有流程在该条目下创建一条资源，是否需要审核沿用站内现行的资源发布规则（这一点与基线表述有差异，见「风险与未决」）；通过后资源进入条目的资源列表，帖子里那条回答加上「已收录到条目资源列表」标记。求助帖能不能用不依赖审核，审核人不在线只影响资源什么时候进条目列表。

资源侧的既有门槛一律照旧：可用萌萌点要求、同时只能有一条待审资源、按角色限制的存储类型。门槛不满足时整次提交失败并说明原因，不会悄悄只留下一条文字回答；用户可以改发普通回答，那是另一次明确操作。

审核拒绝分两种：判「不收录」时帖子里的回答原样保留；判「违规」时帖子里的回答一并隐藏。

未落地的求物落地之后，回答者还可以对自己已经发过的文字回答点「转为条目资源」，用回答内容预填资源表单重新提交，走同一条资源回答流程。同一条回答只能转换一次，帖子里保留最后一次的审核结论。

资源回答的两份奖励各按各自的规则结算：资源侧沿用现有的资源发布奖励；求助侧的系统奖励仍受「每条求助只有一个名额」与第 7 小节的资格限制，并不是每个用资源回答的人都能拿到。两本账相加后的净额与基线的说法有差异，见「风险与未决」。

### 6. 与工单的三条桥接

求助区与工单（用户界面上是「遇到问题」「举报」这类入口）之间有三条通道，三条都不经过站方：

1. **求助转工单。** 挂在某条资源上的求助，该资源的发布者可以点「这是资源问题，转为工单」，生成一条归自己处理的「资源与描述不符」工单，求助帖保留并链接到工单。
2. **「我也遇到了」达阈值自动开单。** 挂在资源上的求助累计到 3 人点「我也遇到了」，系统自动给该资源的发布者开一条「资源与描述不符」工单并链接求助帖。
3. **工单转求助。** 用户把环境问题发成了工单时，发布者可以一键「转为求助」：工单以「不在受理范围」结案，内容复制成一条挂到该资源的求助，提问者仍是原来开工单的那个人。只复制原开启者本人写的初始描述与对象信息，工单里后续的对话和站方备注不会带过去；找不到可归属的开启者时不提供这个入口。

第 1、2 条产生的工单按「资源 + 类型」去重：同一条资源的多条求助可能被归到同一条工单上，但每条求助只关联一次。

工单每次结束（解决、隐藏、移动都算）都会在每条关联的求助帖里贴一条系统回复说明结果，工单重开后再结束会再贴一条。系统回复不能被投票、不能被采纳、不算有人回答。

工单转过来的求助怎么收费、是否占用当天的发布名额、能不能拿系统奖励，属于待站长审定的 D8。本模块按一个候选实现：不收费、不占名额、因此也不发系统奖励，只保留采纳标记。这只是候选，不是已批准的规则。

### 7. 费用、奖励与悬赏（整段待站长审定）

这一段整体属于 D8，尚未批准。下面按三类收支分列候选规则与候选数值：发布费（提问时付给系统）、系统奖励（系统发给一条回答）、悬赏（提问者付给被采纳的回答者）。三者各自独立记账。定稿前这些数值不写进对外的规则说明页，也不作为承诺。

| 项目               | 候选规则                                                                                                                                                                                                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 发布费             | 每条求助 5 点，不退，被采纳之后也不退。它是提问的价格，不是押金                                                                                                                                                                                                  |
| 系统奖励           | 每条求助最多奖励一条回答，3 点由系统发放。采纳与社区验证之中先发生、且当时符合资格的那一个事件决定奖给谁（资格见「防刷限额」行）；此后再被社区验证有效的回答只得标记，不再得点数                                                                                 |
| 悬赏               | 可选，发布时指定 10 到 50 点，从可用余额暂扣（暂扣期间不可用，但仍计入总额），金额公开显示在列表与帖顶                                                                                                                                                           |
| 悬赏结算           | 只在提问者采纳时结算：暂扣从提问者账上扣除，被采纳的回答者拿到九成（向下取整，且至少比悬赏少 1 点），其余由系统烧毁。悬赏付给被采纳的回答，与谁拿到系统奖励无关                                                                                                  |
| 社区验证与悬赏     | 社区验证有效只发系统奖励，不触发悬赏结算，否则几个账号互点「有效」就能拿走陌生提问者的悬赏                                                                                                                                                                       |
| 悬赏只能加不能减   | 发布后只能提高，不能降低或撤回；唯一例外是帖子还没有任何用户回答（系统回复不算）时可以撤回，暂扣退回可用余额，发布费不退。追加只在求助仍未解决、未采纳、未隐藏时可用，已解决的帖子不能再追加                                                                     |
| 悬赏释放与迟到采纳 | 求助自动关闭或整帖被举报隐藏时，暂扣释放回可用余额。之后提问者仍可采纳：可用余额够悬赏额就按原规则结算；不够则不结算悬赏，界面在采纳前告知，帖中标「悬赏未结算」，这次采纳还能不能带来系统奖励仍按名额与资格判断。已经撤回过的悬赏不会因为后来的关闭或隐藏而复活 |
| 「对我有效」的门槛 | 投票人注册满 7 天，每人每条回答一次，每人每天最多 10 次；社区验证阈值 3 人，且只在求助发布满 7 天、提问者尚未采纳时生效                                                                                                                                          |
| 防刷限额           | 每人每天最多发 3 条求助；每人每天最多拿 3 次系统奖励（悬赏结算不计入这个上限）；每人每天悬赏总额上限 50 点；提问者与回答者都要注册满 7 天才产生点数奖励与悬赏结算，否则只有采纳标记；自答不产生奖励                                                              |

还有三处细节需要站长一起定，本模块各按一个候选实现。一，资格不够或当天奖励次数已用完时，那唯一的奖励名额不被消耗，只给回答留下标记，之后再出现的合格事件仍可以取走它一次；但这不等于保证补发——例如第一个事件是一次不合格的采纳，而社区验证只在提问者尚未采纳时才生效，这个名额此后就没有事件能取走了。二，追加悬赏按哪一天、按什么金额计入每日额度（候选是按发生当日的毛额，释放或撤回不返还额度）。三，悬赏释放或撤回之后能不能重新暂扣（候选是不开放）。此外，注册时长不够导致悬赏不结算时，暂扣的点数会当场退回可用余额，不会因为帖子已解决就冻在那里。

### 8. 首页曝光、可见性与站方治理

首页新增「最新求助」与「最新评论」两栏。最新求助默认把「未解决且还没有人回答」的排在前面；可按意图与类别筛选，求物默认包含在内。

可见性规则一致适用于求助列表、详情、首页、相似求助与同问摘要：所挂条目属于 NSFW 时，对没有开启 NSFW 的访客隐藏；挂在资源上的求助随该资源当前所属条目的分级与屏蔽设置判断；所挂的条目或资源被删除后，这条求助不再公开显示（挂话题的求助不受影响）；被隐藏的内容不公开。另有一条只作用于首页的门槛：作者注册不满 3 天的内容暂不进首页聚合，但不影响发布，也不影响作者本人和其他人在求助列表与详情里正常看到它——新用户付了发布费就应该立刻看到自己的帖子。门槛设得这么短，是因为当前用户少，新用户的内容应该尽快被看见。「最新评论」用同一套规则：所属条目为 NSFW 时对未开启的访客隐藏，作者注册不满 3 天的评论也暂不进首页。

站方在求助区的角色被刻意压到最小：站长不做默认回答者，回答、采纳、桥接全部由用户与资源发布者完成。站方侧只有三类动作——把违规的求助或回答隐藏、把误判的恢复、把未落地的求物关联到条目。登录用户可以举报求助或回答，提交后由站方在工单模块的队列里处理；求助不进统一收件箱，因为站方不是这里的责任人。求助或回答被举报达阈值时自动隐藏，阈值尚未定（见「风险与未决」）。

隐藏是可以恢复的临时状态，分两种，效果不同：

- **整帖被隐藏。** 公众看不到这条求助，任何人不能再回答或互动，暂扣的悬赏释放回提问者的可用余额；提问者仍保留一个只有自己能看的视图，可以在里面采纳当时没有被隐藏的回答。恢复之后帖子照常可读、可回答，只是已经释放的悬赏不会重新暂扣。
- **单条回答被隐藏。** 只有那条回答从帖子里消失，求助本身照常可读、可回答；隐藏期间它不能被投「对我有效」，也不能被采纳，恢复后按正常条件重新可用。

「无人回答率」作为一个数字加在既有的后台概览里，站长用它盯住这个模块最大的风险：没人回答时，压力会重新落回站长身上。本模块不另做看板或图表。

## 范围

包含：求助与回答实体、三态与互动、同问、求物与资源回答、三条桥接、发布费 / 系统奖励 / 悬赏三类账务、首页最新求助与最新评论、发布界面的费用与无回应义务提示、入口内的一句话受理范围提示、后台可见的无人回答率数字。

不包含：完整运营指标看板、版主体系、嵌套回答、求助帖内链接的揭示与配额、既有资源发布奖励与资源审核语义的改动、会社相关字段。举报的提交与处理沿用工单模块的站方队列，本模块只提供目标解析与隐藏、恢复。

## 依赖与上线批次

业务前置是 03（工单状态契约与结案回调）与 05（入口分流）。按分批上线约定作为「07 求助区」一个批次整体发布：发布、回答、采纳、桥接、求物、资源回答与审定后的扣费、奖励、悬赏释放与结算必须同批可用，不提前开放没有完整处理能力的入口。求助入口上线时替换 05 的临时去向，并在入口内提供与当时真实能力一致的一句话受理范围提示。完整规则正文随将来的站点文档统一编写，不新增页面。

## 任务与里程碑

沿用总计划编号，不改动：M07-1 实体与阅读；M07-2 状态与互动；M07-3 工单桥接；M07-4 求物与资源回答；M07-5 账务；M07-6 首页与入口。M07-1 至 M07-4 的非账务部分可在 D8 未定时完成；M07-5 全部，以及 M07-3 中「工单转求助」的收费与发布资格分支，在 D8 定稿前不实现，也不把候选数值写进规则展示页。

## 验收

1. 锚定对象（含尚无条目的求物）与可见性在服务端判定，锚定资源的求助继承其所属条目的分级与屏蔽规则；回答平铺；已关闭的求助仍可回答与采纳；每个关闭周期提问者可重开一次。
2. 每条求助只能采纳一次且不可更换或取消；被采纳或被社区验证的回答，作者不能改正文、不能删除。
3. 同问只连最初原帖一层；关闭前后的通知接收人规则正确，已关闭的求助不再通知锚定资源的发布者，也不出现在待回答列表。
4. 三条桥接的重试不产生重复：同一资源的多条求助可以共享一条工单，但每条求助只关联一次；工单每次有效结案给每条关联求助恰好一条系统回复；原开启者与锚定对象保留。
5. 文字回答立即可见且不进入任何审核队列；资源回答按站内现行角色规则决定是否待审；审核判「不收录」时帖中回答原样保留，判「违规」时联动隐藏。
6. 状态变更与收支在同一事务内完成；发布与追加悬赏的网络重放不会二次扣费；关闭、采纳、社区验证并发发生时不重复发放奖励或重复结算悬赏；余额不足按审定规则展示。
7. 隐藏与分级过滤在所有读取面一致生效；作者注册满 3 天只是上首页的门槛，不影响新用户在普通列表与详情看到自己刚付费发布的求助；页面与接口都不泄露被过滤内容。
8. 发布界面明示求助由社区回答、求物不构成对站方或任何发布者的请求；入口提示与真实处理流程一致；站长能在后台看到无人回答率，这是阶段 4 已批准的验收项。

## 风险与未决

- D8 未定：费用奖励整体与全部新增参数、桥接转求助的收费与发布资格、奖励资格不足或已达每日奖励上限时唯一名额如何处理、追加悬赏如何计入每日悬赏额度。它阻塞 M07-5 与 M07-3 的一个分支，不阻塞其余任务。
- 已核实两处与基线不符：现有资源发布奖励在资源创建时即发放（含待审状态），审核拒绝时不回收；创作者的第一条资源仍需审核。因此一条收到 N 条资源回答的求物，求助账净回收一份，资源贡献账另发出 N 份，合并后不是基线所说的净回收。这已是源码事实，站长只需决定接受这一增量还是调整求助侧的奖励额；调整资源奖励发放时点或增加拒绝回收属于全站改账，本模块不提出。
- 举报达阈值自动隐藏是基线要求的能力，但阈值尚无依据，也不能沿用小喇叭的候选值。该值未定即阻塞本批的上线定稿，人工隐藏只是临时手段。
- 方差最大的指标是无人回答率。上线后要看它是否让站长被迫成为默认回答者；本模块在后台给出一个可复算的数字，精确口径与完整指标页由指标模块定稿。

## 实验要证明什么

以下实验全部尚未执行，只列业务判据；步骤见实施计划。

- **E07-01 锚定、同问、关闭、重开与采纳**：四类锚定与意图的合法组合按基线收窄（求物不锚定资源），锚定资源的求助继承所属条目的分级；被锚定的资源被删、求物落地后条目又被删，两种情况都不再公开，也不会被误当成从未落地的求物；满 14 天无活动才关闭，刚收到回答的求助不会被同一轮任务关掉；每个关闭周期可重开一次；迟到采纳与关闭前采纳结果一致；同问只连原帖一层且原帖回答只读展示。
- **E07-02 发布费、奖励、悬赏及并发账务守恒**：三类账务事件独立记账；发布与追加悬赏的重放不二次扣费；并发（采纳 / 自动关闭 / 社区验证同时发生）不重复发放或重复结算；先由社区验证获奖的回答之后被另一条采纳时只支付悬赏；悬赏撤回、释放、迟到采纳与余额不足各有唯一结果，撤回后即使帖被关闭或隐藏，之后采纳也不再扣一分悬赏；已解决的求助不能再追加悬赏，避免点数被永久预留；注册时长不足导致悬赏不结算时，暂扣的点数当场释放，不会冻结在已解决的帖上；纯求助账与既有资源贡献账分列，N 条资源回答对应 N 份既有发布奖励。
- **E07-03 有效投票、我也遇到了、工单桥接和通知**：投票与「我也遇到了」的重复点击不额外消耗每日额度；同一资源的多条求助共享一条工单而每条只关联一次；工单每次结束（解决、隐藏、移动都算）都给每条关联求助恰好一条系统回复，重开后再结束会再回一次；采纳或社区验证时的通知接收人（提问者、我也遇到了的人、各同问提问者、锚定资源发布者）正确且不重复；工单转求助只带过来原开启者本人写的初始问题，不泄露工单内的后续对话与站方备注；求助与工单两侧同时操作不会互相卡死；被隐藏的求助公众不可见、不能再回答，但提问者仍能采纳既有回答；举报能在工单模块的站方队列里被真正处理。
- **E07-04 求物落地、资源回答与审核联动**：只有经核实的投稿人、提问者或站方能把求物关联到条目，且只成功一次；资源回答的回答与资源要么一起成立、要么都不成立，中断重试不会多出一条资源与一份发布奖励，同一条文字回答被并发点两次「转为条目资源」也只产生一条资源；文字部分立即可见且提问者可立刻采纳；审核通过后帖中出现收录标记；「不收录」保留回答、「违规」联动隐藏。
- **E07-05 可见性、相似求助、限额与无回应义务**：隐藏与分级过滤在列表、详情、首页、接口、相似求助与同问摘要一致生效，锚定资源的求助不会绕过分级设置泄漏；注册未满 3 天的作者能在普通列表与详情看到自己的求助，只是不上首页；相似求助优先展示社区验证有效的回答；四项日限额在并发与重复点击下都不被突破；后台显示的无人回答率能按口径复算，提问者自答、系统回复与被隐藏的回答都不算已回答；分流入口的真实切换点被替换，发布界面的无回应义务与受理范围提示与当时能力一致。

# 模块 04：链接健康、失效报告与补链（PM 版）

草稿待审，未实施。技术细节见[实施计划](./04-link-health.md)；批次与任务编号见[总计划](./00-master-plan.md)第 4.5 节；规则依据[基线](../7.operations-layer-redesign.md)第 4.1 至 4.8 节。

## 1 目标

- 链接失效由机制处理：获取过该链接的登录用户投票，达阈值自动通知归属方；发布者归属的链接在 7 天无动作后自动折叠，资源盘链接不套用该超时（D5 候选），只留站方待办。
- 补链是一次普通编辑：换地址即恢复正常、旧证据作废、相关事项自动结案并留痕。
- 链接是稳定槽位：改名称、备注、排序不重建链接，不丢用户已获取记录，也不抹掉访客已消耗的获取配额。

口径：链接类事务由机制与发布者消化的比例；站方队列只剩官方链接与争议裁决。

## 2 责任人

| 角色   | 负责                                           | 不负责                    |
| ------ | ---------------------------------------------- | ------------------------- |
| 报告者 | 选一个现象标签投票，不写文字                   | 不做判定，看不到他人证据  |
| 发布者 | 自己资源的链接：核实、确认失效、补链           | 不裁决他人内容，不进后台  |
| 站方   | 资源盘链接的同类动作；争议做一次「打开试试」   | 不修他人网盘，不逐条巡检  |
| 系统   | 阈值判定、开事项、超时折叠、争议收敛、补链结案 | 不主动检测链接（模块 10） |

站长只需定稿未决事项；争议裁决可以不做，30 天后系统自行收敛。模块 06 前，资源盘链接的故障一律归站方，不送发布者。

## 3 功能介绍与使用流程

本模块让「某条下载链接还能不能用」成为站内可表达、可自动流转的事实：获取过该链接的登录用户可以投票报告失效，累计到阈值时系统自动开一条事项通知归属方；归属方核实、确认失效或直接补链；发布者归属的链接若一直没人处理，到期由系统自动折叠。失效报告是一次投票而不是一条请求，只有累计到阈值才变成需要人处理的事项。站方不逐条巡检链接，系统也不会主动访问链接判断可用性，那属模块 10。

| 功能                | 谁能用                       | 主要结果                                                               |
| ------------------- | ---------------------------- | ---------------------------------------------------------------------- |
| 报告失效            | 登录且近期获取过该链接的用户 | 达阈值即标为「疑似失效」并通知归属方                                   |
| 核实可用 / 确认失效 | 该链接的归属方               | 链接回到正常或标为已失效，对应事项同时结案                             |
| 补链                | 该链接的归属方               | 链接恢复正常、旧证据作废、未结案事项以「已补链」结案并留下变更记录     |
| 失效折叠与待修复    | 全站可见；发布者本人         | 已失效链接从卡片折叠；全部失效的资源沉到「已失效资源」并进入待修复清单 |
| 已失效链接清单      | 站方                         | 只看不做，用于处理资源盘链接、观察各网盘当前失效比例                   |

### 3.1 四种健康状态与前台显示

| 状态     | 含义                                             | 前台显示                                                                               | 仍可获取             |
| -------- | ------------------------------------------------ | -------------------------------------------------------------------------------------- | -------------------- |
| 正常     | 有效报告尚未累计到阈值                           | 与现在一致                                                                             | 是                   |
| 疑似失效 | 报告累计到阈值，等归属方处理                     | 链接旁提示「多名用户报告可能失效」                                                     | 是                   |
| 有争议   | 核实可用后又被新的报告者推到阈值                 | 提示「发布者称可用，多名用户称失效」；归属方是站方时改为「站方称可用，多名用户称失效」 | 是                   |
| 已失效   | 归属方确认失效、等待发布者处理超时，或争议判失效 | 从链接列表折叠，卡片显示「N 条链接已失效 · 最近补链 X 天前」                           | 卡片不再提供获取入口 |

四种状态都可逆，也都不改变资源本身的公开状态。被折叠的链接仍可在「遇到问题」里被选中作为反馈对象，该入口由模块 05 交付。

### 3.2 报告失效：谁能报、报什么、怎么计入

三条资格同时满足：已登录；30 天内有过这条链接的获取记录，且那次获取拿到的就是当前地址（记录与当前链接版本一致）；提交时链接版本仍未变化。访客看得到按钮，点击后提示登录，报告必须能归到一个账号上。链接刚被补链时，旧页面提交会收到「该链接已更新，请刷新后重试」；仅刷新页面不产生资格，需要按新地址再获取一次（在原有 24 小时授权未到期时再获取一次不消耗新的获取配额，见 3.5）。本模块上线之前的获取记录一律算「版本未知」，不作为资格（见第 5 节），因此上线初期符合资格的人会随新的获取逐步增多。

报告只选一个现象标签，不写文字，报告者也看不到别人报了什么。

| 现象                                   | 处理                                                   | 计入权重 |
| -------------------------------------- | ------------------------------------------------------ | -------- |
| 网盘页面显示文件已删除、已过期、违规   | 强证据                                                 | 1.0      |
| 链接要求付费，或取得方式与发布说明矛盾 | 强证据                                                 | 1.0      |
| 打不开、超时                           | 先显示网络提示，用户确认已尝试更换网络或加速器后才提交 | 0.5      |
| 下载慢                                 | 不写入报告，直接导向下载指南                           | 不计     |

72 小时内加权累计达到 3.0 转为「疑似失效」，例如三条强证据、六条弱证据，或一强四弱。同一个人在同一轮证据里只算一条；唯一性按链接版本算还是按证据轮次算，属 D6 待定。勾选「已尝试更换网络」只是提交前的确认，不代表站方核实过提交者的网络环境。网盘本身要求登录属于正常取得方式，不算证据；文件内容、版本或缺件与描述不符走资源问题事项，不走报告。核实之后冷却期内老报告者再报是留痕不计权还是直接拒绝，同属 D6 待定；两种做法都不改变「核实后的 7 天冷却期内必须有新的报告者才能再次触发」这条规则，而链接一旦进入争议就始终只认新报告者的强证据（见 3.4）。

### 3.3 归属方处理：核实、确认失效、补链与超时

每条链接各自有归属方：普通链接归该资源的发布者，资源盘链接归站方，模块 06 之前资源盘链接的故障一律由站方处理，不会送给普通发布者。疑似失效由系统开一条事项交给归属方并通知，报告者成为该事项的订阅者，结案时一并收到结果。发布者在自己的个人页处理，不进管理后台。

- **我已核实可用**：链接回到正常，结论「核实可用」。同一个链接版本 30 天内最多核实一次，防止反复宣称可用。已失效的链接也能用这个动作恢复。
- **确认失效**：链接标为已失效并从卡片折叠，结论「确认失效」。
- **直接补链**：见 3.5，补链本身就是最终解决。

发布者归属的事项连续等待发布者处理满 7 天没有动作（中途回复过就从新一轮等待重新计时，不跨轮次累计），系统把链接标为已失效并以「超时失效」结案，用户看到的效果就是该链接折叠、资源仍在。资源盘链接不套用这条超时（基线里站方归属的事项不设超时），只留在站方待办中等站方处理；这条边界的最终确认属 D5 待定。

### 3.4 争议与自动收敛

核实可用之后 30 天内，若有新的报告者再次把加权累计推到阈值，链接转为「有争议」并把事项交给站方，站方只有「可用」「失效」两个按钮，实际动作通常就是自己打开试一次。这是链接健康上站方唯一的裁决动作，而且可以不做。

- 争议只认新报告者的强证据，弱证据在争议中不计。
- 冷却 7 天针对的是核实之后的普通情形：核实后 7 天内，原先那批报告者再报不推动结果，7 天之后才重新计权。一旦链接已经进入争议，原批报告者的强证据在整个争议期间都不推动结果，不会因为满了 7 天而翻转。
- 争议期间新报告者的强证据累计到 3.0，系统当即判为已失效，结论「自动判失效」。
- 自进入争议起 30 天内没有再次达到阈值，系统自动把链接恢复为正常，结论「自动收敛可用」，因此站方不处理也不会卡住。

信任方向是：第一轮信任发布者的证词，第二轮由强证据决定，僵局交给站方一次判断或交给时间收敛。误判的代价只是几次失败的下载，随后由新的证据纠正，本模块不对报告者或发布者附加惩罚。

### 3.5 补链、变更记录与自动结案

保存编辑时只要地址变了就按补链处理，不区分用的是编辑表单还是「补链」按钮，后者只是把表单定位到地址栏。补链的效果：链接回到正常、这条链接上此前的报告全部作废、未结案的疑似失效或争议事项以「已补链」结案并通知开启者与订阅者。旧地址、旧存储类型、旧大小、变更原因和操作者进入链接变更记录，只在站方视图和将来的合并工具里可见，不出现在任何公开页面。对用户而言：已经获取过旧地址的人，只要原来那 24 小时授权还没到期，就可以直接再获取一次拿到新地址，不消耗新的获取配额，之后也就重新具备了报告资格。

只改名称、备注、排序、类型这类信息不算补链：链接身份不变，任何人已经获取过的记录与访客已经用掉的获取配额都不受影响，用户不需要重新获取。发布者删掉自己某条链接时，这条链接上未结案的事项一并结案（结论用什么措辞属 04-a 待定），变更记录仍然保留。资源里已经有官方链接时，补链还要回答「内容相同 / 内容有变化」的二选一，这个问题随模块 06 交付。

### 3.6 资源可用性、失效折叠与发布者待修复

一条资源只要还有一条链接不是已失效就算可用。全部链接都失效的资源不删除、不下架，署名与历史保留，只是在条目页从默认列表沉到底部的「已失效资源」区，同时出现在发布者个人页的「链接待修复」清单里，让发布者一眼看到该修哪些。

### 3.7 站方的只读视图与资源盘链接待办

后台增加一个只看不做的「已失效链接」清单，可按归属方、所属资源是否已有资源盘链接、网盘主机、失效时长筛选。用途有三个：找出需要站方补链或移除的资源盘链接；把「没有资源盘链接」与「该资源的链接已经全部失效」两个条件合起来看，识别基线所说备份晚了一步的「已丢失」记录，完整的已丢失资源统计由模块 09 交付；看各网盘当前的失效比例，供模块 06 的镜像排队参考。该比例是当前在库链接的一份健康快照，起算于本模块上线，不是历史存活曲线。

资源盘链接被标为已失效时进入站方统一待办，可做的事就是补链或移除。疑似失效与争议本身已经是事项，会照常出现在收件箱，本模块不再为它们重复列一条待办。这份清单与待办都不显示链接地址、提取码和解压码；站方需要看地址时仍走资源详情的既有权限。

## 4 范围

在内：稳定槽位、链接版本、获取记录的版本、报告与阈值、四态流转、核实频率与冷却、争议与收敛、补链与链接历史、失效折叠、卡片报告入口与警示、发布者待修复、后台失效链接视图、资源盘链接失效进站方待办。

不在内：官方标记、镜像与存量合并、移交与下架、获取计数口径（模块 06）；完整现象分流表单与受理范围正文（模块 05）；服务器主动检测（模块 10）；事项表与通知载体（模块 03）。

## 5 依赖与上线批次

前置为模块 03、01。04 与 05 同批发布，入口不得早于处理能力。顺序固定：按现有维护窗口停写并排空在途请求 → 加字段 → 全部实例切到含 04 与 05 的同一构建 → 冒烟校验 → 恢复站点写入并启用定时任务；入口随该构建生效，不做双写，也不新增运行时开关。迁移前的获取记录一律「版本未知」，不作为报告资格，不虚构历史；切换后仍在 24 小时授权内的用户需再点一次「获取下载链接」才补上当前版本记录，不额外消耗配额，这是已知的一次性成本。

## 7 验收

1. 隔离环境复现两条链路：报告 → 疑似失效 → 超时 → 折叠；补链 → 新版本恢复 → 旧事项结案。
2. 所有仍在使用的编辑入口都走稳定槽位，没有重建链接的遗留写入端。
3. 资源公开状态不因健康改变，可用性完全由链接推导。
4. 资源盘链接的故障只出现在站方队列，且不产生重复待办。
5. 同一链接的并发报告只开一条事项、只发一次通知，且不会两边都不触发。
6. 站长实际跑一轮：一条链接走到折叠、一条走到补链恢复，全程不手工改数据。

## 8 风险与未决

| 项   | 内容                                                                                                           | 阻塞位置                            |
| ---- | -------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| D5   | 事项重开窗口与「已换版本」的关系；站方归属不超时与链接 7 天超时的边界                                          | M04-4，需与模块 03 状态契约同时定   |
| D6   | 报告唯一性按版本还是按证据轮次；冷却期报告是记零权重（冷却期满后由同一条记录重算）还是直接拒绝；旧获取记录资格 | M04-2、M04-3，定稿前不写迁移脚本    |
| 04-a | 移除链接与删除资源时未结案事项的结论命名                                                                       | M04-1，需模块 03 同意新增一个结论值 |

风险一：少数人误判。第一轮信任发布者、第二轮要求新报告者、僵局由站方或 30 天收敛兜底，代价是几次失败下载，本文不加惩罚机制。风险二：切换后一段时间几乎无人满足报告资格，机制看起来不动，属预期行为，按新产生的获取记录验收。

## 9 实验要证明什么

四个实验编号固定，全部「未执行」，只在隔离环境进行。

**E04-01** 稳定槽位与迁移不损坏既有事实：改元数据不动链接身份与获取记录；基点完整时删除一条链接必须成功，而基于旧基点、漏掉他人新增链接的保存必须被拒；同一条链接换版本后，用户在原授权内再次获取能记录新版本、拿到的地址与所记版本同源、不延长授权、不多耗配额；刷新恢复只读，不返回过期版本、不制造证据；移除链接后访客已消耗的配额不凭空减少、历史仍可区分；四条删除入口都不留下悬空的链接事项；在已有报告与补链之后重跑迁移，真实状态完全保留。

**E04-02** 资格与计权只在服务端成立：访客、无获取、旧版本、版本未知、超 30 天一律拒绝；强弱证据分别计 1.0 与 0.5，下载慢与缺少网络确认的弱证据都不写入，网盘要求登录不算强证据；重复提交不新增记录；72 小时窗口与「从核实时刻起算的 7 天冷却」边界固定，冷却与争议中的老报告者留痕但不推动结果。

**E04-03** 流转在并发下唯一且不漏：三种阈值组合都当场触发一次；先后到达的两笔报告不会都不触发（用持锁、等待、放行控制次序）；核实、冷却不因进入争议而延长、争议内强证据即时判失效、未达阈值 30 天收敛、发布者 7 天超时、站方归属不自动失效、补链后旧任务与旧证据全部无效、换版本后不可重开。

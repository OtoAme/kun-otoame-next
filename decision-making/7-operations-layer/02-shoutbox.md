## 2 偏离与理由

| 偏离                                           | 基线            | 做法与理由                                                                                                                                                                                            |
| ---------------------------------------------- | --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 官方消息不受 5 分钟编辑限制                    | 9.1             | 用户消息严格一次；官方可随时改正文、级别、区间、链接。9.4 要求维护后更新公告，窗口远超 5 分钟，且编辑窗口是对付费内容的防滥用规则                                                                     |
| 首页与游戏页的小喇叭由客户端组件取数           | 未规定          | 首页 `force-static`、条目页 ISR，静态载荷会把生效与过期边界冻住，并迫使每次发布清理页面缓存                                                                                                           |
| 范围外不物理删除任何行                         | 9.1             | 可见性只由查询范围决定，代码里不存在删除路径，这是「作者永久可见不被清理」最强的实现形式                                                                                                              |
| 「三个月」按上海时区自然月逐条到期             | 9.1             | 到期时刻 = 发布时刻加 3 个自然月（目标月不足则截到该月末）。不用固定 90 天，也不用「now 减 3 个月」——两者不互逆，例如 2 月 28 日发布的消息在 5 月 30 日应已到期，倒减法会算成仍在期内。月末样本进单测 |
| 举报接入现有 `patch_report`，`patch_id` 改可空 | 3.2             | 总计划 M02-4 要求阶段 2 前接旧举报补目标类型；新建表会在模块 03 合并时多一次迁移                                                                                                                      |
| 不新增周期任务                                 | 总计划 4.3、5.3 | 生效与过期由查询时刻判定、缓存寿命夹到下一个时间边界，没有需要 cron 承担的正确性工作，也没有要清理的数据；见第 7 节                                                                                   |

## 3 术语

| 术语                | 定义                                                                                                                                                                                                                             |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 可见基础条件        | `status = 0 AND (official = false OR effective_from <= now)`，首页、小喇叭页、游戏页关联条与他人视角的作者页一律套用；未生效官方行只在控制台列表可见；过期官方行进入时间线并带官方标记                                           |
| 展示槽位 / 分页范围 | 首页与小喇叭页共用一条虚拟列表；分页范围是槽位 0 到 59，即 10 页 × 6 条，范围内与年龄无关。置顶占掉槽位 0 时普通消息只剩 59 个名额，范围边界必须按同一条时间线取第 `59 - 置顶条数` 条，不能另算一个「第 60 条」                  |
| 置顶 / 横幅         | 置顶取最新 `official AND status = 0 AND effective_from <= now < effective_to`（任意级别）；横幅取其中最新的 `level = 'important'`，同样显式要求 `status = 0`，撤回的官方消息两处都不出现。两者可能不是同一条，过期时点也可能不同 |
| 时间线查询          | 按 `created desc, id desc` 且排除当前置顶那条的公开查询，避免同页重复                                                                                                                                                            |
| 时间边界            | 置顶与横幅的 `effective_to`、下一条待生效官方的 `effective_from` 中最早者                                                                                                                                                        |
| 误判恢复            | 站方把隐藏或删除的消息改回公开，首次恢复触发唯一一次退款                                                                                                                                                                         |
| 显示掩码            | 保留消息、只清空其关联游戏名称与链接，用于对仅限全龄的请求隐藏 NSFW 条目信息                                                                                                                                                     |
| 状态 0/1/2/3        | 公开 / 作者自删 / 隐藏待复核 / 站方终止。状态 3 在用户消息上是「违规删除」，在官方消息上是「已撤回」，界面与通知按 `official` 取文案，不给官方消息挂违规标签                                                                     |

## 4 数据模型

### 4.1 `prisma/schema/shoutbox.prisma`（拟新增）

模型 `shoutbox`，命名沿用既有 schema 风格。

| 列                                | 类型                                                                    | 说明                                                                         |
| --------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `id`                              | `Int @id @default(autoincrement())`                                     | 主键，横幅关闭状态与举报都按它引用                                           |
| `user_id`                         | `Int` + 关系 `onDelete: Cascade`                                        | 作者；官方消息是执行发布的站方账号                                           |
| `request_id`                      | `String @db.VarChar(64)`，`@@unique([user_id, request_id])`             | 客户端 UUID，按用户维度唯一。不设全局唯一，避免用他人 UUID 读到他人内容      |
| `content`                         | `String @db.VarChar(500)`                                               | 校验层限 200 字，列宽留余量                                                  |
| `link`                            | `String @default("") @db.VarChar(1000)`                                 | 官方详情链接（9.3 的长文），非官方必须为空串                                 |
| `official` / `level`              | `Boolean @default(false)` / `String @default("normal") @db.VarChar(16)` | `normal` / `important`，仅对官方有意义                                       |
| `status`                          | `Int @default(0)`                                                       | 见术语表                                                                     |
| `cost`                            | `Int @default(0)`                                                       | 本次实际扣费；退款按它，调价不影响历史                                       |
| `patch_id`                        | `Int?` + 关系 `onDelete: SetNull`                                       | 只能是条目；条目删除时消息保留、关联清空                                     |
| `effective_from` / `effective_to` | `DateTime?`                                                             | 官方生效区间，非官方必须为空                                                 |
| `edited_at`                       | `DateTime?`                                                             | 非空即用掉唯一一次编辑机会                                                   |
| `hidden_at`                       | `DateTime?`                                                             | 进入 status 2 时写入，恢复时清空；用于「隐藏中」筛选与展示，不依赖 `updated` |
| `refunded_at`                     | `DateTime?`                                                             | 非空即误判退款已发生                                                         |
| `created` / `updated`             | `DateTime`                                                              | 常规时间列                                                                   |

索引（按查询需要）：`[status, created desc, id desc]` 时间线与计数；`[patch_id, status, created desc]` 游戏页；`[user_id, created desc, id desc]` 作者页；`[official, status, effective_to]` 置顶与横幅。

约束（写在生产 sync SQL，Prisma 无法表达；本地 `prisma db push` 不会创建，因此约束类断言必须在由 sync SQL 建库的隔离库上跑）：`status IN (0,1,2,3)`；`level IN ('normal','important')`；`cost >= 0`；形态约束——官方行两个时间非空且 `effective_to > effective_from`，非官方行 `level = 'normal'`、两个时间为空、`link = ''`。最后一条是安全不变量：任何路径都不能让用户消息变成全站横幅。

## 5 接口、校验、权限、幂等

沿用仓库约定：route 解析与鉴权、service 归属与事务，解析用 `kunParse*`，失败以 HTTP 200 返回中文字符串，写请求经既有 CSRF 与来源校验。新增校验在 `validations/shoutbox.ts`、常量与文案在 `constants/shoutbox.ts`、类型在 `types/api/shoutbox.ts`、自然月函数在 `utils/shoutboxTime.ts`（均拟新增）。不改 `middleware.ts`，不为本模块加鉴权排除项。

### 5.1 公开读接口（拟新增 `app/api/shoutbox/route.ts`、`service.ts`）

`GET /api/shoutbox`：`page` 1–10，`limit` 只接受缺省或 6，`patch` 可选且须匹配八位 `unique_id`；上面的 `page` 上限只针对无 `patch` 的总流，带 `patch` 时只校验正整数、不设额外上限——任何固定上限都会变成基线没有要求的产品限制。返回 `{ pinned, shoutboxes, page, totalPages, validUntil }`，`pinned` 只在 `page = 1` 且无 `patch` 时可能非空。

- 总流分页（无 `patch`）：有置顶时第 1 页取时间线 `skip 0 take 5` 并把置顶置于最前，第 N(>1) 页 `skip (N-1)*6-1 take 6`；无置顶时 `skip (N-1)*6 take 6`。`totalPages = min(10, ceil(min(公开条数, 60)/6))`，第 10 页正好落在槽位 59。
- 游戏页可见集合：`可见基础条件 AND patch_id = X AND (是当前置顶那条 OR 在分页范围内 OR 未到期)`。「在分页范围内」用渲染总流的同一条时间线（已排除置顶那条）取范围边界行：`ORDER BY created desc, id desc OFFSET (59 - 置顶条数) LIMIT 1`——这是零基 `OFFSET`，有置顶时落在第 59 条、无置顶时落在第 60 条；条数不足该 `OFFSET` 时没有边界行，此时判定为「当前全部公开消息都在范围内」，不能让 `(created, id) >= NULL` 把旧消息误判成范围外。「未到期」按逐条到期判定：`((created AT TIME ZONE 'UTC' AT TIME ZONE 'Asia/Shanghai') + INTERVAL '3 months') AT TIME ZONE 'Asia/Shanghai' > $now`，`$now` 是与本次请求其它时间判断共用的注入参数，不用 `now()`，实验才能注入时钟；月末由 Postgres 的月加法自动截断。这里假设 `created` 是 Prisma `DateTime` 默认映射的 `timestamp(3)`（无时区、存 UTC），迁移评审时按新 schema 生成的实际列类型复核一次，若为 `timestamptz` 则去掉第一次 `AT TIME ZONE 'UTC'`。Prisma 查询构造器写不出这个表达式，这一条查询走 `Prisma.sql`，`utils/shoutboxTime.ts` 只用于界面提示与单测对照。仍在分页范围内的关联消息不因年龄被截走。
- 游戏页「更多」的分页：按上面这个并集独立分页、每页 6 条，不套总流的 10 页与 60 条封顶。基线只限制小喇叭页最多 10 页，同一游戏近三个月的关联消息应当都能翻到；关联条固定取该集合最新 3 条。`totalPages = ceil(可见集合条数 / 6)`，条数与当页数据在同一条 `Prisma.sql` 里算；同一查询先得出总数；`page > totalPages` 时跳过该页消息行读取，返回空列表与真实 `totalPages`，无需另建分页机制。
- 掩码：载荷带条目分级，序列化时按请求偏好清空 NSFW 条目的关联信息，消息本身保留。掩码在缓存之后、响应之前执行，Redis 只存一份全集载荷。

`GET /api/shoutbox/banner`（拟新增，只导出 GET）：无参数，返回最新生效重要级官方消息与 `validUntil`，没有则 `null`。

作者个人页数据走服务端读取、不进 Redis、响应 `private, no-store`；本人与站方看全部状态并显示状态标签，其他访问者按可见基础条件过滤——不只是 `status = 0`，站方账号名下未生效的官方行同样不可见。

### 5.2 用户写接口

| 方法     | 校验与权限                                                                                           | 事务与幂等                                                                                                                                                                                                                                                                                                                                                                                                                             |
| -------- | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST`   | 登录；`requestId` 为 UUID；正文去空白后 1–200 字；`patchId` 可选且须存在；关键词命中在进入事务前拒绝 | 单事务内先 `INSERT` 再 `spendMoemoepoint(50, requiredAvailable 50, idempotencyKey = shoutbox:publish:{userId}:{requestId})`。唯一冲突（P2002/23505）时整笔回滚，然后在事务外按 `(user_id, request_id)` 重读：只有确实读到本人这条记录、且它的 `official` 与本次请求类型一致时才作为幂等成功返回，读不到就按真实错误上报，不用「任何唯一冲突都算重放」掩盖别的约束冲突；不能在已中止的事务里继续查询；`40001`/P2034 做最多 2 次有限重试 |
| `PUT`    | 登录；本人；正文长度与关键词校验与 `POST` 共用同一 schema 和拒绝分支                                 | 条件更新 `id AND user_id AND official = false AND status = 0 AND edited_at IS NULL AND created > now - 5 分钟`；命中 0 行再读一次给出具体原因                                                                                                                                                                                                                                                                                          |
| `DELETE` | 登录；本人                                                                                           | 条件更新 `id AND user_id AND official = false AND status IN (0,2) → 1`。允许自删已被自动隐藏的消息，不静默禁止；自删不退款、不改举报状态，站方对它只能用 `resolve` 结案，不恢复也不退款                                                                                                                                                                                                                                                |

`cost` 与 `official` 只由服务端常量决定，不接受客户端传值。同一用户复用已用过的 `requestId` 但正文不同时以首次写入为准：返回既有行，不更新正文、不二次扣费，也不做载荷指纹比对；若既有行的 `official` 与本次请求类型不符，返回冲突提示且不改行，避免一次付费请求被当成官方发布。不做注册时长门槛、频率限制与同文去重。

### 5.3 举报（拟新增 `app/api/shoutbox/report/route.ts`）

登录；不能举报自己的消息；官方消息按待定口径保留举报入口，正常落库进复核队列。事务顺序：`SELECT ... FOR UPDATE` 取目标行 → 查同一举报人是否已有该目标的待处理举报 → 插入举报行（`target_type = 'shoutbox'`、`shoutbox_id`、`patch_id` 取消息关联或 `NULL`、`reported_user_id` 取作者）→ 统计该消息待处理举报的不同举报人数 → 达阈值且 `official = false` 时条件更新 `status = 0 → 2` 并写 `hidden_at`，只有这次更新命中 1 行才给作者发一条通知。行级锁让先查后插的重复检查与阈值计数都具备并发正确性，事务极短，不用 Serializable 加重试。取到目标行后先核对可举报资格：只有 `status = 0` 的消息接受新举报；未生效的官方消息（`official AND effective_from > now`）、已撤回或已删除（`status = 3`）、作者已自删（`status = 1`）的消息一律拒绝，避免靠猜 ID 给不可见内容制造举报；已进入隐藏待复核（`status = 2`）的消息允许继续接收在途举报，它们作为同一待办的补充证据，不再触发第二次隐藏。目标在举报之后才被自删的，旧举报仍可用 `resolve` 结案。通知用 `createMessage`，不用先读后写的 `createDedupMessage`。

| `GET /api/admin/shoutbox`           | `role >= 3` | 列表与筛选 `tab = pending_review \| public \| removed \| official`；`pending_review` 覆盖两类并集：存在待处理举报的消息（含官方与作者已自删的）与所有 `status = 2` 的消息（含站方主动隐藏、举报已结案的），按「最早一条待处理举报的时间，没有待处理举报时按 `hidden_at`」正序，保证最老待办可达且隐藏中的消息不会无处可查；其余按 `created desc`；响应 `private, no-store`                                                                                                                                                                                                |
| `POST /api/admin/shoutbox`          | `role >= 3` | 发布官方消息：正文、级别、`effectiveFrom`（默认当前）、`effectiveTo`（默认 +72 小时）、可选链接、`requestId`；`official = true`、`cost = 0`，不写账务                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `PUT /api/admin/shoutbox`           | `role >= 3` | 改官方正文、级别、区间、链接；`action = end` 把 `effective_to` 提前到当前，条件是 `official = true AND status = 0 AND effective_from < now AND effective_to > now`（严格小于：`effective_from = now` 会写出 `effective_to = effective_from` 而违反约束），对未生效、恰好开始与已过期的消息不执行并返回提示，重复 `end` 命中 0 行、无副作用，也不会把已过期的区间延长回当前；`action = cancel` 是软撤回，条件更新 `official = true AND status = 0 → 3`，未生效（含恰好开始）与生效中的官方消息都用它，撤回后不进任何列表也不会到点生效。条件更新一律要求 `official = true` |
| `POST /api/admin/shoutbox/moderate` | `role >= 3` | `hide`：`0 → 2` 并写 `hidden_at`；`remove`：`IN (0,2) → 3`；`restore`：`IN (2,3) → 0` 并清 `hidden_at`；这三个动作带 `official = false` 守卫。`resolve`：带结论（受理或驳回）与回复文案，只给该消息的待处理举报下结论并通知，不改消息状态，守卫 `status <> 2`（隐藏中的消息只能 `remove` 或 `restore`）——它是官方消息与作者已自删（`status = 1`）消息的举报的唯一闭环；官方内容本身的处置走 `PUT` 的 `end` 或 `cancel`                                                                                                                                                    |

退款与状态恢复分开：`restore` 的 CAS 不含 `refunded_at` 条件，第二次误判也能恢复可见；退款只在同事务内满足 `cost > 0 AND refunded_at IS NULL` 时执行一次（账务幂等键 `shoutbox:{id}:restore-refund`），因此累计退款不超过实付——这是账务硬约束，不列入待定项。动作与举报的关系按下表，`hide` 只隐藏、不结案，否则隐藏待复核的消息会从待办队列里消失：

| 动作      | 消息状态                 | 该消息的待处理举报           | 通知                                   | 账务           |
| --------- | ------------------------ | ---------------------------- | -------------------------------------- | -------------- |
| `hide`    | `0 → 2`                  | 保持待处理                   | 只通知作者                             | 无             |
| `remove`  | `IN (0,2) → 3`           | 全部置为已处理               | 作者与每个举报人                       | 无             |
| `restore` | `IN (2,3) → 0`           | 全部置为已驳回               | 作者与每个举报人                       | 首次恢复退一次 |
| `resolve` | 不变，守卫 `status <> 2` | 全部按结论置为已处理或已驳回 | 每个举报人，结论涉及作者时一并通知作者 | 无             |

`resolve` 用于不需要改消息状态的结论：官方消息、作者已自删的消息、票数不足未触发隐藏的普通举报；它不能对 `status = 2` 使用，隐藏中的消息只能 `remove` 或 `restore`，否则会留下一条隐藏却没有待办的消息。没有待处理举报时 `resolve` 是幂等空操作：不发通知、不写审计。官方 `PUT` 的重复请求靠条件更新命中 0 行来保证无副作用，不额外声称它由状态机保证幂等。作者已自删的消息只能 `resolve`，结案并通知，不恢复、不退款（基线「自删不退」）。

处置与结案在同事务内先对目标行 `FOR UPDATE`，再按 `shoutbox_id` 选取并更新当时的待处理举报、发上表要求的通知、写一条 `admin_log`（`shoutbox_official_publish` / `shoutbox_official_update` / `shoutbox_moderate`，后者覆盖 `hide`、`remove`、`restore`、`resolve`）；处置期间并发提交的新举报要么被这次结论覆盖，要么留在待处理里等下一次，不会漏通知也不会重复通知。

给模块 03 的接线合同只有一条：消息状态转换与退款这两个领域操作接受调用方传入的事务句柄（与账务原语同一形态），03 接手后在自己的工单事务里按结论调用它们并自行发通知，不需要回头调用按 `reportId` 入参的旧处理器。本期不预造无人调用的适配函数，切换时再最小抽出。门槛依据基线 2.2：后台队列统一管理员级，本模块不物理删除数据，不属破坏性清单。

旧举报侧只做最小改动：`adminReportTargetTypeSchema` 增加 `'shoutbox'`；`serializeReport` 的 `targetType` 与 `patch` 改为可空安全并补 `shoutbox` 子对象；`buildReportNotice` 的类型标签与通知链接在 `patch` 为空时改用小喇叭链接；`handleReport` 对 `target_type = 'shoutbox'` 直接返回「请在控制台小喇叭复核页处理」，不在旧路径重复实现处置，也不动旧路由 `role >= 4` 的门槛；`recomputePatchRatingStat` 与条目缓存失效只在 `patch` 非空且目标为评论/评价时调用。可空适配要覆盖全部引用点，已确认的有 [components/admin/report/ReportCard.tsx](../../components/admin/report/ReportCard.tsx)（第 157 行用 `report.patch.name`）与 [components/admin/report/ReportHandler.tsx](../../components/admin/report/ReportHandler.tsx)（第 19 行用 `report.patch.uniqueId`），实现时按 `report.patch` 与 `AdminReport['patch']` 的引用清单逐处过一遍，不只改类型。模块 01 的统一收件箱把举报作为四来源之一、在同一次查询里覆盖多种目标类型，本模块只在它的谓词与详情映射里增加 `shoutbox`，不新增第五个来源，也不改 01 已定的门槛；旧 `getReport` 仍按单一 `targetType` 取数，除可空适配外不动。评论与评价的举报创建端不变。

### 5.5 缓存、响应头与失效

新增 `app/api/shoutbox/cache.ts`（拟新增），键 `shoutbox:list:v1:p{page}`、`shoutbox:banner:v1`、`shoutbox:patch:v1:{patchId}:p{page}`，基础时长写进 [config/cache.ts](../../config/cache.ts)（列表与横幅 60 秒、游戏页关联条 300 秒）。三步缺一不可：

1. 载荷自带 `validUntil`，它是一个时刻而不是时长：在「严格晚于当前、且到点会改变本页可见集合」的边界里取最早者，再与 `now + 基础时长` 取小。参与的边界有三类：当前置顶或横幅的 `effective_to`、下一条待生效官方消息的 `effective_from`、本页中「只靠未到期这一支才可见」的行（既不在分页范围内、也不是置顶）的三个月到期时刻。先过滤再取最小值：仍在分页范围内的旧消息合法可见，它的到期时刻可能早已过去，把它算进来会让 `validUntil` 钉在过去，该页永远无法缓存并陷入立即重取。待生效边界由一次极小查询取得，到期边界对本页已过滤的数据取最小值。
2. Redis 寿命 `ttl = floor((validUntil - now) / 1000)` 秒（`validUntil` 的定义已把它夹在基础时长之内），小于等于 0 就不写缓存；`isCachedValueValid` 每次用调用时刻的当前时间与载荷的 `validUntil` 比较，判定过期时 `getOrSet` 会把缓存当未命中并重新取数（[lib/redis.ts](../../lib/redis.ts) 第 423 至 425 行），不会把过期载荷返回；若重新取数也失败，接口返回不含置顶与横幅的安全空结果（横幅接口返回 `null`），而不是旧值。
3. 响应头逐请求算：带登录或分级/屏蔽偏好 cookie 的请求（判定复用 `isPersonalizedApiRequest`）返回 `private, no-store`；匿名请求返回 `public, s-maxage=floor(min(30, (validUntil - now) / 1000))`，单位秒、向下取整、没有下限，且不带 `stale-while-revalidate`，算得 0 秒时返回 `no-store`。这就是不复用共享匿名缓存层的原因：那层固定含 5 分钟陈旧供给，会跨过生效边界。

写入后失效：用户发布/编辑/自删、站方处置、官方发布/编辑/提前结束，都在事务提交后执行 `delKvPattern('shoutbox:*')` 与 `purgePublicApiCache(['/api/shoutbox', '/api/shoutbox/banner'])`；不调用 `invalidateAnonymousApiResponseCaches()`，不改 [app/api/patch/cache.ts](../../app/api/patch/cache.ts)。清理可能返回失败或超时，失败只记日志、不回滚业务，也不让客户端以为发布失败；这正是维护清单要求人工到前台确认横幅的原因。

### 5.6 幂等与并发一览

| 业务        | 数据库层保证                                                              | 重试或并发后的效果                                                                               |
| ----------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 发布与扣费  | `(user_id, request_id)` 唯一 + 账本幂等键 + 可用余额条件更新              | 一次发布一行一账；余额刚好 50 的并发只成功一次；不可能为负；他人重用同一 UUID 各自成功且互不可见 |
| 编辑 / 自删 | 条件更新含状态、`edited_at`、时间窗与 `official = false`                  | 第二次命中 0 行，内容不变，无账务                                                                |
| 自动隐藏    | 目标行 `FOR UPDATE` + `status = 0 AND official = false → 2`               | 并发举报只有一次转换成功，作者只收到一条通知                                                     |
| 站方处置    | 条件更新限定原状态集合 + `official = false`                               | 双请求只有一个生效，`admin_log` 与通知只记胜出的一次                                             |
| 误判退款    | 恢复 CAS 与 `cost > 0 AND refunded_at IS NULL` 的退款分支同事务但条件分开 | 状态可多次恢复，退款只一次，累计不超过实付；官方消息 `cost = 0` 不产生账务                       |
| 重复举报    | 行锁内的待处理举报检查                                                    | 第二次返回已举报文案，不插入新行                                                                 |

事务内不做网络副作用；缓存与边缘清理在提交后执行。

## 7 定时任务

本模块不新增周期任务，也不改既有四个任务（[server/cron.ts](../../server/cron.ts)）。理由：生效与过期由查询时刻判定，Redis 寿命与 `s-maxage` 都向下取整夹到下一个时间边界，边缘不会跨界供旧值，因此没有需要 cron 承担的正确性工作，也没有需要清理的数据（本模块无删除路径）。加一个只做缓存失效的任务是空壳：`*/5` 的调度漏跑一轮就是 10 分钟空档，任何固定回看窗口都补不齐，而它本来也不承担正确性。

已打开的页面到 `validUntil` 时先按当前时刻丢弃已经不该显示的内容，再去重取，顺序不能颠倒：横幅与置顶按生效区间丢弃，游戏页的关联条与「更多」按同一可见谓词移除已到期的范围外行。重取失败或拿到空结果时按基础缓存时长退避再试，期间保持「不显示」，不继续挂着旧横幅或过期的关联行。页面从后台恢复可见（`visibilitychange`）时同样先用当前时刻校验手上的载荷，过期就先移除再重取。不引入推送通道，也不新增可调参数。

总计划第 4.3 节 M02-5 的「周期任务沿用 `server/tasks/`」与第 5.3 节「官方消息生效/过期、可见范围维护」的任务责任行，按本节口径同步为「由查询时刻判定加缓存寿命夹取保证，本模块不交付周期任务」。

## 8 迁移与回填

三段式生产 SQL（拟新增，日期按定稿日）：

1. `production-shoutbox-preflight-<日期>.sql`：`BEGIN TRANSACTION READ ONLY`。清点 `patch_report` 行数、`patch_id` 空值数（首次应为 0）、`target_type` 取值分布、是否已存在 `shoutbox` 表与同名约束、`patch_report` 现有索引与外键。只读无 DDL。
2. `production-shoutbox-sync-<日期>.sql`：`CREATE TABLE IF NOT EXISTS public.shoutbox`（含四类 CHECK、四条索引、作者 `ON DELETE CASCADE`、条目 `ON DELETE SET NULL`）；`ALTER TABLE public.patch_report ADD COLUMN IF NOT EXISTS shoutbox_id INTEGER` 并补外键与索引；`ALTER TABLE public.patch_report ALTER COLUMN patch_id DROP NOT NULL`。全部可重复执行，无数据回填——小喇叭是新能力，没有存量。
3. `production-shoutbox-postflight-<日期>.sql`：只读结构校验（列可空性、四类 CHECK、索引、外键存在）。行数与 preflight 快照的比对只在首次部署做；脚本重跑时不断言 `shoutbox` 为空表或举报行数不变，避免把结构校验和一次性基线混为一谈。

顺序与边界：备份 → preflight → 在审定窗口执行 sync → postflight → `pnpm prisma:deploy-safe`（前面含可写兼容迁移，不是纯只读检查）→ 构建部署 → 冒烟 → 最后开放用户发布与官方发布入口。生产不用 `prisma db push`，不放宽 schema 守卫。`DROP NOT NULL` 是目录级变更、锁时间极短，仍安排在窗口内执行。文档阶段不执行以上任何命令。

回退：一旦有真实付费消息写入，不能盲目退到不认识 `shoutbox` 的旧代码（用户已扣的点会失去对应内容），预案是先关发布与官方发布入口（前台隐藏加接口返回停用文案），保留读取、处置与退款能力，再定位问题前滚。`patch_id` 恢复 NOT NULL 的前提是不存在空值行，已有小喇叭举报后必须先处理这些行，回退脚本先查后改，不预置反向 DDL。已发生的扣费与退款以账本为准，不做应用层反向补偿。

### E02-01 消费、编辑、删除与误判退款

- 目的：证明 50 点消费与三种退款边界在真实事务下守恒，重试与并发都不产生第二笔账，恢复能力不被退款资格阻断。
- 前提：三个账号余额 50 / 49 / 500，两个仅用于测试的关键词。
- 步骤：①余额 50 的账号用同一 `requestId` 并发发两次，再用新 `requestId` 发第二条；②对一次成功发布重放三次相同请求，再用同一 `requestId` 提交一次不同正文；③另一账号复用他人已用过的 `requestId` 发布；④余额 49 发布一次、命中关键词发布一次、把一条已发布消息编辑成命中关键词的正文一次；⑤编辑在第 4 分 59 秒与第 5 分 01 秒各一次，成功后再编辑一次；⑥删除路径：自删、从隐藏态自删、站方 `remove`、`hide` 后 `restore`、再 `hide` 再 `restore`；⑦对官方消息提交 `hide` / `remove` / `restore`；⑧作者编辑与站方 `hide` 并发提交；⑨作者自删一条已被举报的消息后，站方对它执行 `resolve`。
- 通过：并发只成功一条且余额 50→0；重放后一行一账、余额不变；同一 `requestId` 的不同正文不更新原行也不二次扣费；他人复用同一 UUID 各自成功且读不到对方内容；余额 49 与关键词命中都不产生消息行与账目，编辑命中关键词被拒且正文不变；只有第 4 分 59 秒那次编辑成功；自删与 `remove` 余额不变；首次 `restore` 余额 +50 且 `refunded_at` 落库，第二次 `restore` 恢复为公开但余额不变，累计退款等于 `cost`；官方消息的 `hide`/`remove`/`restore` 都被拒绝（结束官方消息只能用 `end` 或 `cancel`）；并发编辑与隐藏的结果等价于某个合法串行顺序——编辑先提交则两者都成功且最终为隐藏，隐藏先提交则编辑被拒且正文不变，不出现更新丢失或状态自相矛盾；已自删消息执行 `resolve` 后余额不变、不产生任何账目；全程 `moemoepoint - moemoepoint_reserved` 不为负。
- 失败：任一次重复扣费、重复退款、负余额、关键词命中仍扣费、退款金额与 `cost` 不一致，或第二次恢复无法把消息改回公开。
- 时间点：M02-1 与 M02-4 退款分支编码完成、sync SQL 定稿后，本批上线前。
- 证据与清理：账本导出（用户、方向、金额、原因码、幂等键、时间）、消息行状态快照、并发脚本与输出、失败断言记录。结束后 drop 隔离库、清该实例 Redis 前缀键，不向生产写入任何行。

### E02-02 分页保留、关联游戏、官方置顶与横幅过期

- 目的：证明分页范围、三条保留规则、置顶与横幅的生效过期都由查询时刻决定，不依赖任何定时清理；同时跑通一次维护清单。
- 前提：每个时间场景用独立夹具与新注入时钟，不在同一份数据上来回推进（推进过的时钟不能再用来断言「尚未生效」）。基础夹具造 70 条公开用户消息，`created` 覆盖今天、40 天前、100 天前；其中 20 条关联条目 A（含 5 条 100 天前且仍在分页范围内、5 条 100 天前且已掉出范围）、5 条关联 NSFW 条目 B；条目 C 关联 70 条近期消息，用于验证「更多」能翻过 10 页；官方消息六条：生效中普通级（较晚过期）、生效中重要级（较早过期）、已过期重要级、10 分钟后生效的重要级、`effective_from` 恰好等于注入时刻的一条，以及一条发布时间排在最新 60 条之外、但生效区间在当前的旧官方消息。第二份夹具只放 20 条公开消息（含旧的关联消息），用于「不足该 `OFFSET` 时没有边界行」。月末到期样本（3 月 31 日与 11 月 30 日发布的关联消息各一条）必须放在已掉出总流范围的位置，否则到期后仍可见本身就是正确结果，断不出到期逻辑。
- 步骤：①在有置顶与无置顶两种状态下取第 1、2、10、11 页与首页模块；②断言 40 天前但在 60 槽内的消息可见，第 61 条起不在小喇叭页；③取条目 A 的关联条与 `?patch=A`，断言仍在 60 槽内的 100 天前关联消息可见、已掉出 60 槽且超三个月的不可见、作者个人页两者都可见；④仅限全龄与开启 NSFW 两种请求各取一次，断言条目 B 的掩码差异且消息本身都在，同一 Redis 载荷不串味；⑤把注入时钟推到重要级 `effective_to` 前后各 1 秒，取横幅与第 1 页，断言横幅消失而普通级仍占置顶；再推到普通级过期后与 10 分钟后那条生效后各取一次；⑥在未推进时钟的场景里断言未生效官方消息在任何列表都不出现、过期官方消息进入时间线并带官方标记；对未生效的那条执行 `cancel`，断言它不再出现、也不会到点生效，并核对状态 3 在官方消息上显示为「已撤回」；对生效中的那条执行 `end` 并重复执行一次，再分别对「`effective_from` 恰好等于当前」与「已过期」的官方消息执行 `end`；⑦缓存边界：先在边界之前取一次、把载荷写进 Redis，再推进时钟越过边界重取，断言拿到的不是热缓存里的旧置顶或旧横幅；对条目 A 的游戏页做一次同样的热缓存后推进，边界取该页范围外关联行里最早的那个将来到期时刻，并同时断言页内仍在范围内的 100 天前消息没有把 `validUntil` 钉到过去——该页仍可缓存、`s-maxage` 大于 0；剩余寿命小于 1 秒时取一次，断言 `s-maxage` 为 0 或 `no-store`；⑧关闭横幅后重载三次，再发一条新的重要级消息重载；⑨已打开的页面停留跨过 `effective_to`，断言其按 `validUntil` 自行更新；再把页面切到后台、跨过下一个边界后恢复可见，断言它按当前时刻复查并更新；再把重取接口置为失败，断言页面先丢掉已过期的横幅与置顶再退避重试，不把旧横幅继续挂着；⑩到期断言：对 3 月 31 日与 11 月 30 日发布的两条关联消息，在各自到期时刻之前、恰好等于、之后三个采样点各取一次游戏页与「更多」；⑪让那条排在最新 60 条之外的旧官方消息成为置顶，重取第 1 页、第 10 页、条目 A 的关联条与「更多」；⑫取条目 C 的「更多」第 11、12 页，断言总流封顶不影响单游戏分页；再各取一次非正整数 `page` 与远超 `totalPages` 的 `page`，断言前者被校验拒绝、后者返回空列表与真实 `totalPages` 且未读取越界页消息行；⑬在只有 20 条公开消息的夹具上取总流与旧关联消息的游戏页，断言没有边界行时全部判为范围内；⑭维护演练：发官方重要消息 → 在前台两个页面与控制台确认横幅 → 停用本地实例 → 恢复 → 更新同一条消息并确认前台文案变化。
- 通过：有置顶时第 1 页仍 6 行且第一行为官方，第 2 页起无重复无跳条，总流 `totalPages` 不超过 10 而带 `patch` 的「更多」不受此封顶影响，超出 `totalPages` 的页返回空列表与真实页数、非正整数 `page` 被校验拒绝；置顶来自时间线之外时普通名额只有 59，小喇叭页因此掉出范围的那条与游戏页并集用的是同一条边界并同时退出；公开消息不足该 `OFFSET` 时没有边界行、全部判为范围内；置顶与横幅按各自条件独立取值与独立过期；`end` 只对 `from < now < to` 生效，对恰好开始、未生效与已过期都不执行且不改数据，重复 `end` 无副作用，`cancel` 覆盖未生效（含恰好开始）与生效中，撤回后状态 3 在官方消息上显示「已撤回」；未生效不出现、过期进时间线；游戏页可见集合符合三项并集，到期时刻之前可见、等于与之后不可见，月末按截到月末处理；掩码只影响关联信息；关闭状态按消息生效；热缓存后越过边界不会返回旧置顶、旧横幅或已到期的范围外关联行，而仍在范围内的旧消息不会把 `validUntil` 钉到过去；页面恢复可见后按当前时刻复查，重取失败时不再展示过期横幅；演练每步都有可核对的前台观察。
- 失败：任一页重复或漏条、置顶把行数变成 7 行、过期仍置顶或仍出横幅、未生效消息提前出现或撤回后仍到点生效、`end` 写出违反区间约束的数据或把已过期区间延长回当前、分页范围内的关联消息被年龄截走、公开消息不足 60 条时旧关联消息被判成范围外、同一游戏近三个月的消息因总流封顶翻不到、两处算出的范围边界不一致、热缓存在边界之后仍被返回、`validUntil` 被已经过去的到期时刻钉住而使该页无法缓存或反复重取、`s-maxage` 跨过边界、掩码吞掉整条消息，或清单某步无法执行。
- 时间点：M02-2 与 M02-3 完成后，本批上线前。生产维护演练另按运维方式单独记录，不并入本实验结论。
- 证据与清理：各页载荷与页面截图、注入时钟标注、`validUntil` 与响应头记录、演练时间线。结束后 drop 隔离库、清 Redis。

### E02-03 举报过渡、恢复、权限与缓存

- 目的：证明小喇叭举报能进现有举报载体并被真实处理与恢复，权限一处不漏，空 `patch` 不破坏旧读取面，处置后各读取面按声明时间更新。
- 前提：隔离库执行完整 sync（含 `patch_id DROP NOT NULL`）；预造若干存量评论举报与评价举报行；账号覆盖 `role` 1、2、3 与未登录会话；多进程运行以复现部署形态。
- 步骤：①举报一条未关联游戏与一条关联游戏的消息，断言举报行 `patch_id` 分别为空与有值；②同一举报人重复举报；不同举报人依次达阈值；两人并发提交临界的第三与第四条；③按 D3 候选口径举报官方消息并凑够阈值人数，再用 `resolve` 结案；另对一条作者已自删的被举报消息执行 `resolve`；再按 ID 直接举报一条未生效的官方消息、一条已撤回的官方消息、一条作者已自删的消息与一条已删除的消息各一次，并对一条隐藏中的消息追加一条在途举报；④权限矩阵：未登录与 `role` 1、2 访问站方列表、官方发布、处置接口，`role 3` 访问同一组接口，另确认旧举报只读路由仍要求 `role >= 4`、旧处理路径对小喇叭返回引导而不误处理；⑤站方对同一目标并发两次 `remove`；对另一目标先 `hide` 再驳回举报；⑥处置后依次请求首页模块、小喇叭页、关联条、横幅、作者个人页、控制台列表，记录首次反映变化的时刻与响应头；⑦回归：处理一条存量评论举报与一条评价举报，断言状态、通知、评价统计重算与条目缓存失效与改动前一致；⑧断言小喇叭举报出现在 01 的收件箱来源里，且控制台待复核队列按最早待处理举报时间正序可达，最老的待办不会被挤掉；⑨断言空 `patch` 的举报在旧列表、详情组件（`ReportCard`、`ReportHandler`）、通知链接三处都不报错、链接指向小喇叭；⑩在站方处置事务执行期间并发提交一条新举报，断言它要么被本次结论覆盖并通知、要么保持待处理留给下一次；⑪用 `role 4` 账号打开旧举报只读路由做正例、`role 3` 做反例；⑫对一条消息先 `hide`，断言它仍在待复核队列、只有作者收到通知，再对它提交 `resolve`（应被拒），最后用 `restore` 或 `remove` 结案。
- 通过：未关联游戏的举报正常落库；重复举报被拒；阈值达成只隐藏一次、作者只收一条通知；官方消息被举报后进队列但不自动隐藏，官方与已自删消息的举报都能用 `resolve` 结案并通知举报人、不产生恢复与退款，处置期间并发提交的新举报既不漏通知也不重复通知；`hide` 之后举报仍是待办、只有作者收到通知，对 `status = 2` 的 `resolve` 被拒；未生效、已撤回、已自删与已删除的目标都拒绝新举报，隐藏中的目标接受在途举报且不触发第二次隐藏；旧举报只读路由对 `role 3` 拒绝、对 `role 4` 放行；`role` 1、2 与未登录对站方接口全部被拒、`role 3` 全部可用、旧路由门槛不变；并发 `remove` 只生效一次且 `admin_log` 只一条；驳回后消息恢复、作者与举报人各收到对应通知、余额 +50 且只一次；六个读取面在响应头声明的时间内反映变化；存量举报回归无差异；空 `patch` 全链路无异常。
- 失败：任一低权限账号成功执行站方动作、官方消息被自动隐藏、并发处置产生两次通知或两次退款、旧举报流程因 `patch_id` 可空而报错或丢链接、某读取面在声明时间之后仍是旧值。
- 时间点：M02-4 完成、迁移在隔离库演练之后，本批上线前。
- 证据与清理：举报行与消息行快照、通知列表、`admin_log` 导出、权限矩阵逐格结果、各读取面时间戳与响应头、存量举报回归对照。结束后 drop 隔离库、清 Redis、移除测试通知。

三个实验按主覆盖归属分工：账务主覆盖在 E02-01，时间与可见性在 E02-02，权限与举报闭环在 E02-03；E02-03 里出现的退款只是驳回举报流程的连带断言，不重复 E02-01 的账务边界。不新增测试平台、不搭压测框架、不为每个按钮建实验。

## 3. 术语

| 术语        | 定义                                                                                                                                                                                             |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| verdict     | 一次检测的结论：`broken`（判定失效）、`available`（判定可用）、`unknown`（无法判断）；内部原因 `unsupported`（主机不在 D10 决定的支持清单内）、`blocked`（请求边界拒绝）对外一律表现为 `unknown` |
| reason code | 结论的机器可读原因，如 `pattern_deleted`、`login_required`、`rate_limited`、`timeout`、`host_unsupported`、`address_blocked`；用于日志、界面文案与样本比对，不携带页面正文                       |
| 系统证据    | 报告表中 `source = system_check` 的一行，权重 2.0，绑定链接与链接版本，无报告者                                                                                                                  |
| 支持清单    | 主机（含子域规则）到判定信号与「无法判断」条件的映射表，内容由 D10 决定，清单外主机恒为 `unsupported`                                                                                            |
| 检测预算    | 单次检测允许的连接、首字节、总耗时与响应体上限；超出即 `unknown`                                                                                                                                 |

## 4. 数据模型

- **无新表、无新链接字段。** 系统证据写入模块 04 的链接失效报告表（下称报告表）。本模块对该表的契约是三条：一，有区分来源的列（`source`，取值 `user` / `system_check`，默认 `user`）；二，报告者列对系统行可空；三，数据库层保证「同一链接、同一版本、同一证据轮次至多一条系统证据」。
- **唯一性方案（选定）。** 模块 04 计划明确的拟建报告表为 `patch_resource_link_report`，唯一键 `(link_id, link_version, evidence_round, user_id)`、`user_id` 非空。本模块采用最小兼容扩展：保留该用户唯一键不变；`user_id` 改为可空；新增 `source`（`user` / `system_check`，默认 `user`）与可空 `system_key`（系统行写 `l{link_id}:v{link_version}:r{evidence_round}`，用户行为 `NULL`），对 `system_key` 加普通唯一约束。Postgres 把 `NULL` 视为互不相同，用户行不受该约束影响，系统行则每链接、每版本、每轮至多一条。不重建用户唯一键、不使用部分唯一索引，生产 schema 检查需识别两个新列、一个新唯一约束以及 `user_id` 的 `DROP NOT NULL`。这三项由本模块交付，不要求模块 04 预留。
- **每轮至多一条且不刷新。** 重复检测既不新增系统行，也不刷新既有行的 `created` 与 `weight`；核实可用或进入争议后由 04 开新的 `evidence_round`，同一 `link_version` 的旧检测结果不得落入新轮。
- **不存检测历史。** 不新增「最后检测时间」「最后检测结果」字段；手动检测与补链检测的结论只在响应中返回。短期结果缓存放 Redis（键含链接 ID、链接版本、证据轮次与地址哈希，TTL 分钟级），用于抑制重复出站请求与反爬风险。缓存命中允许写证据：若本轮尚无系统证据（例如缓存来自此前的只读手动检测），首次用户报告仍写一条；已有系统证据则不再写、不刷新时间。系统行的证据发生时间取检测时的 `checkedAt`（写入 `created` 或等效时间列），报告请求重放不重置 72 小时窗口起点。缓存结果早于当前 72 小时窗口起点或早于本轮开始时只作展示，不转为证据，也不为用户弱标签升权。
- **用户语义查询的共享投影。** `user_id` 可空后，所有「报告者」语义的读取都必须加 `source = 'user' AND user_id IS NOT NULL`：订阅者与通知名单、本轮报告者集合、冷却判定、争议态只认用户强证据、对外展示的报告人数。该条件落在模块 04 报告 / 健康 helper 的一处共享投影里，本模块不新建统计口径。系统证据只进入允许计入的加权求和，不算人数、不进订阅名单，也不会产生 `user_id` 为空的订阅记录。
- **常量。** `constants/linkCheck.ts`（拟新增）：系统证据权重 2.0、检测预算、缓存 TTL、限流阈值、reason code 与前台文案键、支持清单占位（D10 前为空表）。权重与 04 的 1.0 / 0.5 保持同一口径来源。

## 5. 接口、校验、权限、幂等

| 触发                  | 落点                                                                                         | 权限                                                                                                  | 数据库写入                                                                                                                                                                                                      |
| --------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 用户报告失效          | 04 的报告服务在事务前调用本模块 `resolveLinkCheckVerdict`                                    | 沿用 04 资格校验：登录、目标可见、30 天内有该链接揭示记录、请求版本等于当前版本                       | 事务内每链接、每版本、每证据轮次至多一条系统证据（仅 `broken`）；用户行先按 04 的当前资格与轮次判定是否可计权，只有可计权的行在 `broken` 时把弱标签升为强证据 1.0，`available` / `unknown` 完全保持 04 的原权重 |
| 归属方 / 站方手动检测 | `POST /api/patch/resource/link-check`（拟新增 `app/api/patch/resource/link-check/route.ts`） | 普通链接：资源 `user_id` 本人（沿用 04 的编辑权限）或 `role >= 3`；官方链接：按模块 06 的官方链接门槛 | 无                                                                                                                                                                                                              |
| 发布者补链保存        | 04 的资源更新链路在事务提交后调用                                                            | 沿用 04 的编辑权限                                                                                    | 无                                                                                                                                                                                                              |

- **校验。** `validations/linkCheck.ts`（拟新增）：`patchId`、`resourceId`、`linkId` 正整数，`linkVersion` 非负整数。服务端二次核对链接属于该资源、资源属于该条目，再取 `content` 与 `storage`；不接受客户端传入地址，也不接受客户端提交的 verdict——结论只能由服务端本次请求产生或来自服务端缓存。
- **权限与隐私。** 响应只含 `verdict`、`reasonCode`、`checkedAt`、`linkVersion`、证据轮次与用于展示的主机名，不回传页面正文、响应头、最终跳转地址、提取码与解压码；响应头 `private, no-store`；日志沿用现有结果日志风格，只记主机、verdict、reason、耗时，分享地址的 query 不入日志。已申请下架、隐藏或已删除的目标：手动检测只对被授权的管理者可用，公开报告路径在目标不可见时按 04 直接拒绝，两条路径都不返回地址。状态写入沿用中间件既有 CSRF 与 origin 校验，不新增排除项。失败沿用「返回中文字符串」的既有契约；429 与 `Retry-After` 只出现在手动检测接口，报告与补链路径遇限流时只把结论降级为 `unknown`，报告与保存照常完成。
- **限流与降级。** 复用现有 Redis 限流脚本形态，独立键前缀 `link-check:rate-limit:v1:`，按操作者与按主机各一层。Redis 不可用时手动检测与报告路径都不发出站请求，直接返回 `unknown`（对出站取失败关闭，避免绕过限频撞上反爬）。
- **幂等与顺序。** 顺序固定为：资格、目标可见性与版本预检（只读）→ 网络调用（事务外，有预算）→ 报告事务。任一预检不通过都不发出站请求，避免把不合格的报告当成出站代理。verdict 作为入参进入 04 的报告事务，在 03 / 04 共用的链接锁内先复核「链接当前版本 = 检测时版本」且「当前 `evidence_round` = 检测时轮次」：不成立则 verdict 整体按 `unknown` 对待——不写系统证据，也不把用户弱标签升为 1.0，用户权重按 04 的当前轮与当前资格重新计算；版本不符时报告本身按 04 规则返回「该链接已更新，请刷新后重试」，仅轮次变化时报告照常写入当前轮并可在界面标「结果已过时」。迟到结果一律不推动健康。系统证据用 `createMany({ skipDuplicates: true })` 或 `INSERT ... ON CONFLICT DO NOTHING` 插入；不得在事务内 `catch` `P2002` 后继续查询或聚合，Postgres 该事务已中止。若实现上只能用普通 `create`，则按 [授权服务](../../app/api/patch/resource/download/access/grant.ts) 的方式对整个外层事务做有界重试。阈值计算、健康流转、建单与系统通知仍由 04 在同一事务内一次完成，本模块不产生第二次通知。
- **预算与过时标记。** 单链接检测总预算为秒级上限（解析、连接、首字节、读取分档），报告接口因检测增加的延迟有固定上界，超预算即 `unknown` 并继续写报告。补链保存在事务提交后检测本次地址发生变更的链接，按总预算封顶，未检测到的条目在响应里明确标 `unknown`；检测异常、超时或被限流都不改变保存已成功的结果。三种触发的响应都带链接版本与证据轮次，与当前值不一致时标记「结果已过时」而不是当作当前结论——版本与轮次守卫不只用于用户报告路径。

## 6. 前后台界面及文件

拟新增：`app/api/patch/resource/link-check/route.ts`（手动检测）、`service.ts`（verdict 编排、版本与轮次守卫、限流与缓存）、`request.ts`（受限出站请求）、`rules.ts`（支持清单与判定信号，内容待 D10）、`types.ts`；`validations/linkCheck.ts`；`constants/linkCheck.ts`。

`request.ts` 的实施落点（只服务本模块，不做全站抓取层）：用 Node 内置 `https.request` / `http.request` 并传自定义 `lookup`，把审核通过的那个 IP 交给连接层，同时保留原主机名用于 `Host` 头与 TLS `servername`，并保留默认的证书链与主机名校验（不关闭 `rejectUnauthorized`，`servername` 与关闭校验是两回事）；重定向自行逐跳实现，每跳重做主机与地址审核，不用「先 lookup 再普通 fetch」的二次解析方式，那样会留下重绑定缺口。Node 的 `timeout` 只触发事件、不会自动中断请求（[Node 官方 http 文档](https://nodejs.org/docs/latest-v24.x/api/http.html)；该链接只说明 API 能力，本仓库精确 Node 版本下的装配仍需实施期实测），因此用显式定时器加 `req.destroy()` / `res.destroy()` 覆盖连接、首字节与读取。DNS 阶段还没有 `req` 可销毁：总预算到期时先结束本次检测并判 `unknown`，迟到返回的解析回调禁止再建立连接。请求头固定 `accept-encoding: identity`，但对端不保证遵守——响应 `Content-Encoding` 非 `identity` 时直接判 `unknown` 并停止读取，不解码、不引入解压依赖；按已读字节数硬截断，不把 `Content-Length` 当唯一限制；不带 cookie、授权头、提取码或任何附加字段，不执行页面脚本；分享地址原有 query 只用于本次请求。

## 8. 迁移与回填

- **迁移边界。** 模块 04 不预留系统证据相关列，这次兼容迁移是本模块的实际交付：新增 `source`（默认值 `user`，既有行取默认值即可，不做无条件 `UPDATE` 回填）与可空 `system_key`；对 `user_id` 执行 `DROP NOT NULL`，并同步 Prisma 模型、类型与所有读取该列的查询（用户语义查询按第 4 节改为 `source = 'user' AND user_id IS NOT NULL`）；再建 `system_key` 唯一约束；用户唯一键 `(link_id, link_version, evidence_round, user_id)` 不动。顺序是在维护窗口内一次做完兼容 DDL（两列、`user_id` 放宽非空、`system_key` 唯一约束），全部就绪后再部署已带共享投影的应用并同时启用系统证据写入；不加运行时开关，也不搭多阶段发布框架。不批量检测历史链接、不回填任何 verdict、不新增「为了以后」的字段。
- **演练与发布。** 在隔离库演练迁移与回滚，生产按 [部署说明](../../docs/project/deployment.md) 先只读 preflight（列、约束、重复行计数）→ 已审 sync 与回填 → postflight → schema 检查与部署安全检查 → 冒烟 → 开启入口。文档阶段不运行上述命令。
- **回退。** 已写入的系统证据行保留，仍被 04 的聚合读取；停用本模块的方式是把支持清单置空（全部返回 `unknown`）并下线手动检测入口，不删历史证据行。已有数据写入后不回退到不认识 `source` 列、或缺少第 4 节共享投影的旧版本——那种版本会把系统行当成报告者算进人数、订阅名单与争议判定。

### E10-01 三种触发、三态结果、证据版本与去重（未执行）

- **目的。** 证明三种触发 × 三种结果的写入范围正确：只有「用户报告 + `broken`」在本轮写入一条系统证据；除基线 4.9 允许的「可计权报告 + `broken` 升为强证据」外，检测不改动用户报告的权重；手动与补链检测不写证据、不改变健康；版本或轮次变化后的迟到结果被丢弃。
- **前提与隔离环境。** 隔离测试数据库（04 迁移已应用）；verdict 由注入的桩提供，不发出真实请求；`now` 注入；Redis 使用测试键前缀。
- **关键步骤与数据组合。** 每组先写明初始健康、既有在窗证据与报告者身份，再断言差量。
  1. 三种触发 × `broken` / `available` / `unknown`，初始为「`ok`、无在窗证据、报告者不受冷却」共九组：断言只有「用户报告 + `broken`」新增一条 `source = system_check` 行，且其 `link_version` 与 `evidence_round` 等于检测时值，该组加权和 3.0 达阈值转 `suspect` 并只建一条工单；「用户报告 + `available` / `unknown`」两组按 04 权重正常写用户行（强标签 1.0、弱标签 0.5），健康由 04 规则决定，不因检测结论增减；手动与补链检测六组证据行数为 0、健康不变、结果只回操作者。
  2. 阈值边缘与升权正例：既有在窗证据 2.5 时，用户报告 + `unknown`（弱标签 0.5）→ 达 3.0 正常转 `suspect`；既有 2.5 时，用户报告 + `available`（强标签 1.0）→ 同样正常转 `suspect`，证明检测不阻断用户证据本身；初始无在窗证据、报告本轮可计权时，弱标签（打不开 / 超时）+ `broken` → 用户行升为 1.0、系统行 2.0，合计 3.0 转 `suspect`，证明升权只在可计权且判定失效时发生。
  3. 版本与轮次竞态：屏障在 verdict 返回后、报告事务提交前，另一会话提交一次补链（版本加一）或完成一次核实（开新轮）；断言 verdict 被丢弃、系统行不存在；补链场景报告返回「该链接已更新，请刷新后重试」，核实开新轮场景用户行按 04 新轮规则写入而系统证据不落新轮。两种场景都断言迟到 verdict 不把弱标签升为 1.0，用户权重按当前轮与当前资格计算。
  4. 去重与缓存：同一用户重复提交、两名用户并发提交（同为 `broken`）→ 本轮系统行恒为 1，`created` 与 `weight` 不被刷新；缓存来自此前只读手动检测时，首次用户报告仍写一条系统行，且该行证据时间等于检测时的 `checkedAt`，不因报告请求重放而把 72 小时窗口起点前移；缓存早于窗口起点或早于本轮开始时只展示、不写证据，也不为用户弱标签升权。
  5. 保守规则（第 2 节）：冷却期内报告者 + `broken` → 用户行权重 0、系统行 1 条、加权和不达阈值、健康不变；`disputed` 态下旧报告者 + `broken` → 不因系统证据判失效；`disputed` 态下新报告者的强证据自身达阈值 → 按 04 规则判 `broken`，与有无系统证据无关。
  6. 副作用：三种触发都不新增 `patch_resource_access` / `_grant` 行、不改 `download`；手动与补链检测不写链接行。用户报告触发 04 合法更新健康时，链接行 `updated` 会随 `@updatedAt` 变化，属正常结果，只断言本模块自身不额外写链接行。通知按同一次实际健康转移由 04 统一发一次，不因系统证据多发（不与「尚未达阈值的报告」作对比）；系统证据不进订阅者与通知名单、不计入对外报告人数，也不产生 `user_id` 为空的订阅记录。
- **通过判据。** 上述断言全部成立；`available` 与 `unknown` 从不写系统证据，也从不改变用户这条报告本身的权重与是否成立。**失败判据。** 同一轮系统证据多于一条或时间被刷新；版本或轮次已变仍写入系统证据或仍把弱标签升权；规则外改动用户权重（不可计权的报告被升权，或 `available` / `unknown` 改了权重）；系统证据被算作报告人数、订阅者或通知对象；检测失败或超时导致报告接口 5xx 或报告丢失；手动或补链检测改变了健康。
- **验证时间点。** M10-2 实现完成后、上线前；04 报告服务改动同批回归。
- **证据与清理。** `tests/unit/api/link-check-service.test.ts`、`tests/unit/api/link-check-report-evidence.test.ts`（均拟新增）用例与隔离库前后行快照，并扩展 [现有资源更新测试](../../tests/unit/api/patch-resource-update.test.ts) 覆盖补链保存后的调用；清理测试库本次数据与测试键前缀。

### E10-02 出站请求协议、地址、重定向、超时边界（未执行）

- **目的。** 证明受限请求 helper 不会越界访问，且所有拒绝与异常路径降级为 `unknown`，不产生失效判定。
- **前提与隔离环境。** 不访问真实网盘，也不访问任何公网服务。分两层：地址策略单测直接对策略函数取值，生产策略始终拒绝私网，不提供 `allowLocal` 之类的生产开关；真实传输测试只经测试注入的连接器或注入的 `lookup`（把某个「已允许」的样例地址定向到本机 socket），与生产装配路径互斥。支持清单与 `now` 同样由参数注入。
- **关键组合。** 协议 `ftp:` / `file:` / `data:` / `javascript:` 与缺协议 → 拒绝且无出站；主机规范化正例：大小写混写、末尾点、IDN / punycode 写法在规范化后等于清单内主机 → 正常进入地址校验并按规则判定，不因写法被拒；主机边界拒绝项：越界子域、URL 内含 userinfo、非默认端口、用十进制或十六进制 IPv4 写法绕过主机清单 → 拒绝；解析到 `127.0.0.0/8`、`10/8`、`172.16/12`、`192.168/16`、`169.254/16`、`0.0.0.0`、`::`、`::1`、`fe80::/10`、`fc00::/7`、IPv4 映射地址 → 拒绝；一次解析返回多个地址且其中含私网 → 整体拒绝；实际连接必须使用已审核的那个地址（注入连接器记录目标 IP），审核地址与连接地址不一致即为失败项；重定向链超上限、跨主机到清单外主机、重定向到私网、循环 → 拒绝且不跟随下一跳，每跳重做主机与地址审核；连接、首字节、读取与总预算超时 → `unknown` 且断言 socket 已销毁，DNS 阶段超时 → `unknown` 且断言零连接、迟到的解析回调不再建立连接；报告接口总延迟在上界内；响应体按已读字节硬截断，覆盖「声明 `Content-Length` 偏小但实际更大」与未声明长度的分块响应；对端忽略 `accept-encoding: identity` 而返回 `Content-Encoding: gzip` 等 → 直接 `unknown` 并停止读取，不解码；未知状态码、403、429 与超时一律 `unknown`，404 只在托管站规则明确时才判 `broken`，不把任意 404 泛化为失效；断言日志与响应不含完整地址、query、提取码、页面正文，且请求未带 cookie 与授权头。
- **通过判据。** 全部组合无越界连接，无 `broken` 来自被拒绝路径，均在预算内返回。**失败判据。** 出现对私网或清单外主机的实际连接；任一拒绝或超时路径被判为 `broken`；日志泄露地址或凭据。
- **验证时间点。** M10-2 实现期间持续运行，上线前完整跑一次。
- **证据与清理。** `tests/unit/api/link-check-request.test.ts`（拟新增）用例、注入层记录的连接列表与耗时断言；关闭本地测试服务器，不保留抓取内容。

### E10-03 参考实现适配与「无法判断」的验收样本（未执行）

- **目的。** 以参考实现为依据确认支持清单、判定信号与「无法判断」边界并给出规模结论（M10-1）；实现完成后再核对本实现在同批样本上的分类与误判。参考实现是依据，不是绝对真理。
- **前提与隔离环境。** D10 已交付参考实现与支持范围；样本以脱敏响应片段保存到 `tests/fixtures/link-check/`（拟新增），移除真实分享地址、提取码与 cookie；在隔离环境执行，不在生产站点跑批量。
- **关键步骤与数据组合。**
  1. 阶段 A（M10-1，不依赖本模块代码）：每个候选托管站收集至少四类样本——正常分享页、已删除 / 已取消 / 已过期页、需登录或验证码页、限流或反爬响应；任一类缺失则该站不进支持清单，恒为 `unsupported`。逐站记录参考实现使用的判定信号及其覆盖不到的情形，产出支持清单与规模估算。
  2. 阶段 B（M10-2 完成后）：用同批样本跑本实现，逐条与参考实现的分类对照，记录差异与依据。
  3. 阶段 B 收尾：站长授权下做一次受控真链抽查，仅走手动检测入口，限定条数与间隔，逐条人工核对。
- **通过判据。** 正常分享页样本被判 `broken` 的数量为 0（硬判据）；需登录、验证码、限流与未知状态一律 `unknown`（硬判据）；清单外主机恒 `unknown`；与参考实现的差异只允许朝更保守方向（参考判失效而本实现判 `unknown`），且每条差异都有样本或托管站页面行为作依据并记录在案。**失败判据。** 任一正常页或需登录页被判 `broken`；判定依赖参考实现中不存在、也无样本支撑的自造特征；样本类别不全却把该站写入清单；把阶段 B 的对照提前到实现存在之前充当结论。
- **验证时间点。** 阶段 A 在 D10 到手后、M10-2 开工前；阶段 B 在 M10-2 完成后、上线前。
- **证据与清理。** 样本清单与分类对照表、差异说明、抽查记录；删除含真实地址的原始抓取，fixtures 只留脱敏片段。

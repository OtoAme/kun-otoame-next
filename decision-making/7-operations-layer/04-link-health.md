## 3 术语

| 术语           | 定义                                                                                                                                                                                                                               |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 链接槽位       | `patch_resource_link` 的一行；地址可换、行不换，故无「已替代」态                                                                                                                                                                   |
| 链接版本       | 槽位整数版本，地址每变更一次加一；获取记录与报告都写入当时版本                                                                                                                                                                     |
| 证据轮次       | 同一版本内的证据分段。核实可用、确认失效、进入争议、争议结论各加一；版本变更归零。争议收敛以 `health_changed_at` 为基准；冷却只以 `verified_at` 为基准，不能用 `health_changed_at`，否则进入争议会重设它并变相延长原批报告者的冷却 |
| 老报告者       | 在该链接当前版本、更早轮次里有过权重大于 0 的报告行的用户；「新报告者」即不在此集合内。只留下零权重记录的用户仍算新报告者，一次被判零权重的提交不等于有效证据                                                                      |
| 有效报告       | 权重大于 0，且属当前版本、当前轮次、72 小时窗口内的报告行                                                                                                                                                                          |
| 归属方（过渡） | `storage = 'touchgal'` 归站方，其余归资源 `user_id`                                                                                                                                                                                |

## 4 数据模型

### 4.1 既有表

`patch_resource_link` 新增两类列（与第 8 节口径一致）：`health VarChar(20) NOT NULL DEFAULT 'ok'`（生产加 CHECK，开发库 `db push` 无 CHECK，读取处必须有兜底分支）、`version Int NOT NULL DEFAULT 1`、`evidence_round Int NOT NULL DEFAULT 0`，由 DDL 一次填充既有行；`health_changed_at`、`verified_at`、`content_changed_at` 可空且无默认，存量保持空。因此 sync 不含数据 UPDATE。新增 `@@index([health, health_changed_at])`。

`patch_resource_access`：新增 `link_version Int?`，空值表示迁移前的获取，永不构成资格；`link_id` 由必填改可空、外键动作改 `SetNull`。受影响读取点：`grant.ts` 的配额 `count` 不涉及 `link_id`，行为不变；`restore/service.ts` 与 [get.ts](../../app/api/patch/resource/get.ts) 的查询本就按 `link_id in (...)` 过滤，只需补空值类型防护。

不新增：资源级健康字段、`status` 新取值、`official`。

### 4.2 新表（拟新增 `prisma/schema/patch-resource-link-health.prisma`）

`patch_resource_link_report`：`link_id`（外键 Cascade）、`link_version`、`evidence_round`、`user_id`（外键 Cascade，仅登录用户）、`reason VarChar(32)`、`weight Decimal(3,1)`（实际计入权重，可为 0.0）、`created`。约束 `@@unique([link_id, link_version, evidence_round, user_id])`，索引 `@@index([link_id, link_version, evidence_round, created])`。阈值、冷却、争议全部从这张表算；链接被移除时报告随之删除，因此不需要槽位快照。

`patch_resource_link_history`：`resource_id`（外键 Cascade，非空）、`link_id Int`（原槽位 ID 的快照，不建外键，链接删除后仍能区分多条被删链接）、`from_version`、`old_content`、`old_storage`、`old_size`、`reason`（`relink` / `edit` / `remove` / `merge`）、`operator_user_id`（外键 SetNull）、`created`。索引按 `resource_id, created desc` 与 `link_id, created desc`。历史行含真实旧地址，仅站方视图与模块 06 读取，不进任何公开响应，审计沿用 [\_helper.ts](../../app/api/patch/resource/_helper.ts) 的脱敏 helper。

FOR UPDATE`，再重读并锁定其资源与链接。这样并发插入的新资源只有两种合法结局：在父行锁生效前提交，从而被这次重读捕获；或在插入时因外键检查需要父行上的共享锁而等待，待删除提交后因父行已不存在而失败。单条资源的三条删除链路没有这个间隙问题，目标资源行本身会被删除锁住，新增链接的外键检查同样要等它。与既有编辑或计数触发器相互等待时，按数据库回滚加现有的有界重试或可重试错误处理，本文不承诺全仓库无死锁，也不为此做全仓库锁改造 |

证据权重（唯一来源建议放 `constants/linkHealth.ts`，拟新增）：`deleted`（网盘显示已删除/过期/违规）强 1.0；`access_condition`（要求付费，或取得方式与发布说明矛盾；网盘本身要求登录不算）强 1.0；`unreachable`（打不开、超时，须携带 `networkAcknowledged`）弱 0.5；`slow` 服务端拒绝写入并返回下载指南提示。

权重降为 0.0 的三种情形：核实后的冷却期内由老报告者提交（`now - verified_at < 7 天`）；争议轮内的弱证据；争议轮内的老报告者强证据（无时间豁免，由 30 天收敛结束）。同轮重复提交不新增行，只有两种结果：若已有零权重行且本次按上表算出正权重，则更新该行的 `weight` 与 `created` 并继续走 5.2 的聚合与流转（代价是不保留该用户的首次提交时间，本模块接受这一取舍，不为此加列）；若重算仍为 0.0 或与现值没有有效变化，则只返回「您已报告过该链接」，不更新 `created`、不进入聚合，避免用一条永不计权的记录把有效窗口往后挪。唯一键形状与本条同属 D6。

时间边界（实现建议，统一由服务端注入的 `now` 求值，不改系统或数据库时钟）：资格 `created >= now - 30 天`；窗口 `created >= now - 72 小时`；核实间隔为 `verified_at` 为空或 `now - verified_at >= 30 天`；争议窗口 `now - verified_at < 30 天`（恰好 30 天不再算争议，按普通疑似失效处理）；冷却 `now - verified_at < 7 天`；发布者超时 `now - 状态进入时间 >= 7 天`；争议收敛 `now - health_changed_at >= 30 天`。

### 5.2 报告与流转的原子性

报告在一个事务内按序完成：① 以 `tx.$queryRaw` 对目标链接行取 `SELECT ... FOR UPDATE`（仓库已有原生 SQL 用法）；② 用锁内读到的 `version`、`evidence_round`、`health`、`verified_at`、`health_changed_at` 复核版本与资格；③ 按锁内读到的既有行分支：没有既有行则插入，有零权重既有行且本次算出正权重则原地更新为正权重（0 转正），其余情况只回提示并结束；④ 插入与 0 转正都继续聚合当前版本当前轮次 72 小时内的 `SUM(weight)`；⑤ 达阈值则做状态转换并调用模块 03 开事项或结案；⑥ 只有胜出的那次转换发送一条系统通知。资格读取、锁内复核、聚合与流转是同一条分支，任何会改变加权和的写入都必须走完它，不允许在前面用唯一冲突提前返回而让合法的 0 转正永不计权。行锁使插入与聚合对同一链接串行：第二笔在取锁处等待，放行后必然看到前一笔，因此既不会重复触发也不会漏触发，不设任何 cron 阈值兜底。取锁约定统一为「条目行（仅条目删除需要，见 4.3）→ 资源行 → 链接行（ID 升序）→ 事项行（ID 升序）」：归属方动作与站方裁决先取链接行锁再取事项锁；编辑、补链与删除按 5.3 先取资源行锁；报告只取链接行锁再取事项锁，且在持有链接或事项锁期间不反向申请资源写锁。这是本模块内的约定，跨模块的完整无环性要在 03 与 04 的实现期按全部调用链复核，本文不作绝对保证。所有时间比较按 5.1 的边界表。真正的唯一约束冲突（`P2002`，即同一用户两笔并发首报）在事务外捕获并返回提示，不在已中止的事务里继续查询。命中 `P2034`，或 Prisma 7 pg adapter 暴露的 `DriverAdapterError` / `TransactionWriteConflict` / SQLSTATE `40001` 时，按 `grant.ts` 现有形态做有上限的事务外退避；业务校验失败不重试。

| 转换                | 条件（条件更新均含 `id`、`version`、`evidence_round`、原状态）                       | 附带写入                                                                          |
| ------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| `ok → suspect`      | 当前轮次 72 小时内加权和 ≥ 3.0，且 `verified_at` 为空或 `now - verified_at >= 30 天` | 开「链接疑似失效」给归属方，报告者转订阅者                                        |
| `ok → disputed`     | 同上但 `now - verified_at < 30 天`                                                   | `evidence_round + 1`（争议轮从空开始）、开「链接争议」给站方                      |
| `suspect → ok`      | 归属方核实，`verified_at` 为空或距今 ≥ 30 天                                         | `verified_at = now`、轮次 +1、结论「核实可用」                                    |
| `suspect → broken`  | 归属方确认，或任务判定 7 天超时                                                      | 轮次 +1、结论「确认失效」或「超时失效」                                           |
| `disputed → broken` | 争议轮内强证据加权和 ≥ 3.0，在该报告事务内立即执行；或站方点「失效」                 | 轮次 +1、结论「自动判失效」或「站方判失效」                                       |
| `disputed → ok`     | 站方点「可用」；或未达阈值且 `health_changed_at` 早于 30 天（任务）                  | 轮次 +1、结论「站方判可用」或「自动收敛可用」                                     |
| `broken → ok`       | 归属方核实，同一 30 天频率限制                                                       | 同「核实可用」                                                                    |
| 任意 `→ ok`         | 地址变更                                                                             | 版本 +1、轮次归零、`verified_at` 清空、`content_changed_at = now`、结论「已补链」 |

### 5.3 编辑写入（M04-1）

[update.ts](../../app/api/patch/resource/update.ts) 改为按 ID 差量：事务内先对资源行取 `SELECT ... FOR UPDATE`（这是唯一能挡住并发新增槽位、也能覆盖空集合的边界），再按 ID 升序锁定既有链接行；随后把 `baseLinks` 与库内实际集合逐条比对，ID 集合与每条版本都必须一致，不一致整笔拒绝并提示刷新，从而挡住基于旧基点、漏掉他人新增链接的保存。增改删由 `links` 相对 `baseLinks` 计算，因此删除库内确实存在且基点里有的链接是合法操作，必须成功。重复 ID、不属于该资源的 ID、以及 `links` 里出现基点之外的既有 ID 一律拒绝。既有链接以基点里的版本做条件更新，影响 0 行返回「该资源已被他人修改，请刷新后重试」；纯元数据字段（名称、备注、类型、语言、平台、排序）仍是最后写入生效，不做字段级合并。地址变化按 5.2 末行处理并写历史行。S3 删除、上传 finalize、缓存失效仍在事务外，沿用现有补偿顺序。`validations/patch.ts` 增加 `baseLinks`（ID 与版本对，允许为空数组，`version` 必须为正整数）与 ID 唯一性校验：`links` 里的新槽位不得携带任何既有 ID，携带 ID 的条目必须出现在基点里。是否允许把链接删到零仍由现有资源校验（至少一条链接）与模块 06 的三种发布者动作决定，04 不放宽整资源规则。编辑弹窗经 `accessResourceLinksForEdit` 水合时一并带回基点；管理侧读取 DTO 可返回完整基点元数据，公开读取仍不下发地址与两种码。前台普通编辑、后台整表单、以及只添加或只删除链接的保存共用这一条写入边界，不另建通用版本系统。[admin/resource/update.ts](../../app/api/admin/resource/update.ts) 不改调用方式，ID 稳定后其摘要的 ID 配对分支才真正命中。

### 5.4 获取、恢复与版本（核心修复）

- `grant.ts`：在同一事务内读取链接的 `version` 与响应所需字段（`storage`、`size`、`content`、`code`、`password`、`hash`），并把这份快照连同实际写入的 `link_version` 一起返回；`reused` 判定增加 `link_version = 当前版本`，空值不算命中。用户在有效授权内再次获取同一链接的新版本时写一条 `link_reveal`、沿用原 `expires`、不新增 `resource_grant`、不消耗配额。
- `access/service.ts`：保留事务前那次查询用于 404 与可见性判定，但响应体改用 grant 返回的同事务快照，不再序列化事务外读到的 `target`。Serializable 并不保证与任意 READ COMMITTED 写入都冲突，因此允许一次一致的旧快照完成（用户拿到旧地址、记录的也是旧版本），但绝不允许给旧地址标注新版本；模块 03、04 的资格一律按实际记录的版本判定。
- `restore/service.ts`：仅返回 `link_version` 等于当前版本的行；旧版本与空值不返回、不新增任何行，保持只读。
- `get.ts`：`revealed` 改为同口径（版本匹配才算已获取），并在 `links.select` 增加 `health`、`version`；界面因此回落为「获取下载链接」，用户在同一授权内点一次即补上当前版本记录，不消耗配额。切换后仍在授权内的老用户会多点一次，属预期的一次性成本。
- 隐私：未授权响应不含 `content`、`code`、`password`；已授权的获取结果与管理员资源详情按现状返回必要字段；后台失效视图只给主机名与失效时长；新增接口一律 `private, no-store`，状态写入沿用现有 CSRF 与 origin/referer 校验。

## 8 迁移与回填

三份 SQL（拟新增，沿用 `migration/production-*` 的 preflight / sync / postflight 三段式）。preflight 只读：清点链接、资源、access 行数、`storage` 分布、单用户单链接最大记录数、是否已存在同名列或表。sync 只做结构变更，加列按字段分两类：`health`、`version`、`evidence_round` 为 `NOT NULL DEFAULT`，由 DDL 一次填充既有行；`health_changed_at`、`verified_at`、`content_changed_at` 与 `patch_resource_access.link_version` 为可空且无默认，既有行保持空。因此 sync 不含任何无条件数据 UPDATE。另外 `patch_resource_access.link_id` 执行 `DROP NOT NULL` 并把外键改为 `ON DELETE SET NULL`；外键重建可拆成 `NOT VALID` 与 `VALIDATE` 两步，但这不构成「无长锁」的承诺，实际锁时长与是否需要进一步拆分 DDL 由演练结果决定，按现有维护窗口流程执行，不预先搭迁移框架。建两张新表与索引、加 `health` 的 CHECK；全部语句幂等，重跑只补缺失结构，不改已有数据。postflight 分两套断言：首次部署后的数据基线断言（新表为空、`link_version` 全为空）与常规重跑的结构断言（列、表、索引、约束与外键动作存在），重跑不得要求新表为空或版本列全空。schema 与 SQL 必须一致，否则 [生产 schema guard](../../scripts/checkPrismaProductionSchema.ts) 会以漂移终止部署。

切换点由数据表达：`link_version IS NULL` 即迁移前的获取，永不构成资格，不新增配置项。旧版本写入端与新列不兼容（它会重建链接并按旧形状写 access），所以不能让新旧写入端并存：按现有维护窗口流程执行备份 → preflight → 停写并排空在途请求 → 审核后执行 sync → postflight → `pnpm prisma:deploy-safe`（注意它会先跑可能写入的 `migration:resource-links`，不是纯只读，见 [开发指南](../../docs/project/development.md)）→ 全部实例切到含模块 04 与 05 的同一构建 → 冒烟校验 → 恢复站点写入并启用定时任务。入口随该构建一同生效，本批既不需要也不引入运行时开关、双写或迁移框架。回退边界：新列上线后禁止回退到重建链接的旧版本，否则会连带删除获取记录与配额事件；需要停用时先关入口与任务、保留数据，已写入的报告、历史与已变更的健康不做盲目回滚。文档阶段不执行上述任何命令与 SQL。

## 9 实验方案

共同前提：使用项目现用 PostgreSQL 版本的 disposable `_e2e` 库、独立 Redis 实例或注入式 mock（不改动正在使用的服务）、独立 3100 dev server；样本自建，不接触生产库，不读取任何 `.env` 变体；证据脱敏，不记录地址、提取码、解压码、visitor token、IP 或其哈希；演练后 reset 该库并删除 dump。并发一律按「T1 持锁 → T2 在取锁处等待 → 放行 T1 → 观察 T2」的次序控制，不以「同时发请求」宣称竞态，也不设计行锁下不可能成立的交错；时间一律由注入的 `now` 控制，不改系统或数据库时钟。执行状态：四个实验全部未执行。

### E04-01　稳定槽位、迁移、同 ID 换版本与恢复

目的：证明 M04-1、M04-2 不损坏既有链接身份、获取记录、配额事实，且换版本后的获取能被正确记录、迁移可重跑。

单测层：扩展 [patch-resource-update.test.ts](../../tests/unit/api/patch-resource-update.test.ts) 覆盖元数据编辑零链接写、基点缺失或版本不匹配、基点与库内集合不一致、重复 ID、他资源 ID 五种拒绝，并加一条正向用例：基点完整时删除一条链接必须成功；新增迁移静态契约测试（参照 `resource-access-bootstrap-migration.test.ts`）锁定加列按字段分类、sync 无无条件 UPDATE、DDL 幂等、postflight 两套断言分离。

库内步骤：① 按第 8 节演练一次：停写并确认在途请求排空 → preflight → sync → postflight（首次基线）→ 切新版本 → 恢复写入；② 造一条含 `user`、`s3`、`touchgal` 三链接的资源，预置「授权有效且已获取」「授权过期」「从未获取」三种记录，并造一个访客已消耗日配额的 `resource_grant`；③ 前台与后台各整表单保存一次，只改名称、备注、排序；④ 同一槽位两笔补链按持锁、等待、放行的次序提交；⑤ 逐一提交基点版本过期、缺基点、基点漏掉他人新增槽位、重复 ID、他资源 ID 五种请求；⑥ 授权内获取 v1 → 补链到 v2 → 同一链接再次获取；⑦ 对 v1 记录与空版本记录发起 restore；⑧ 在基点完整的前提下移除一条链接；⑨ 在已存在报告、补链、历史之后重跑 sync 与 postflight；⑩ 对四条删除调用链各执行一次（资源删除、后台资源删除、条目删除、审核拒绝），并对条目删除做两个并发样例，分别对应两种合法顺序：样例甲在删除事务取到 `patch` 父行锁之前提交一条新资源及其未结案链接事项；样例乙在父行锁已生效之后才发起插入，让它停在外键检查处等待。不构造「父行锁生效期间插入成功」的第三种情形，那在 PostgreSQL 下不成立。

通过判据：③ 未改动槽位的 ID、`version`、`evidence_round` 与其全部 access 行不变（`updated` 变化不作为任何判断依据）；④ 只有一笔成功，另一笔返回冲突且不产生第二条历史、版本只加一次；⑤ 五种请求全部被拒且零写入；⑥ 新增一条 `link_reveal` 且 `link_version = 2`，响应体返回的地址与该条记录的版本同源（用补链前后不同的地址串区分），`expires` 不变，无新 `resource_grant`，访客日/周配额计数不变；⑦ 两类记录都不返回、不新增任何行；⑧ 删除本身成功，该链接的报告被级联删除，历史行保留且能按快照 ID 区分，其 access 行仍在、`link_id` 为空、访客配额计数不变，未结案链接事项结案一次；⑨ 重跑不报错，版本、健康、历史、报告与 `link_version` 分布完全保留，postflight 的结构断言通过且不要求新表为空；⑩ 四条链路都在同一删除事务内、以锁内重读的真正将删集合为准关闭未结案的链接类事项，关闭发生在删除链接之前，每条结案只发一条通知；样例甲的新资源被这次重读捕获并一并关闭，样例乙的插入在删除提交后因父行不存在而失败、不留下任何事项，两种顺序都没有悬空事项。

失败判据：未改动槽位的 ID 或其获取记录发生变化；基点完整的合法删除被拒；配额计数因删除单条链接而减少；响应地址与所记版本不同源；restore 返回旧版本或新增行；换版本后的获取没有记录或延长了授权；任一删除链路留下悬空链接事项；重跑覆盖已有数据。验证时间点：本地完成后、04 与 05 合批发布前；生产按第 8 节顺序执行同一组 preflight / postflight。证据：preflight 与 postflight 输出、编辑前后槽位对照表、配额计数对照、脱敏样本行。

### E04-02　资格、证据权重与窗口

目的：证明资格与计权只在服务端成立，窗口与冷却边界一致。单测层：权重表与三条零权重规则的纯函数、窗口与 30 天边界、schema 校验。

具名组合（不做机械穷举）：1 访客提交；2 登录但无获取记录；3 只有空版本记录；4 只有旧版本记录；5 当前版本但获取在 30 天以外；6 恰好 30 天边界（按 5.1 边界表含恰好 30 天）；7 强证据、弱证据、`slow` 各一次，另加缺少与显式 `false` 的 `networkAcknowledged` 弱证据各一次，以及一次「网盘要求登录」情形；8 同一用户同轮重复提交，分两种：无有效变化的重复，以及零权重行在冷却期满后按强证据重提（0 转正）；9 窗口边界：恰好 72 小时计入、72 小时加一秒不计入；10 在核实后保持 `ok` 的普通样例上，以 `verified_at` 为起点，由同一名老报告者在第 6 天与第 8 天各提交一次；11 争议轮内弱证据、争议轮内老报告者强证据，以及只留过零权重记录的用户在争议轮内的强证据。

通过判据：1 至 5 全部拒绝且零写入，4 返回刷新提示；7 强 1.0、弱 0.5，`slow` 不写入，`networkAcknowledged` 缺失与显式 `false` 的弱证据都被拒绝，「网盘要求登录」不被当作强证据；8 两种重复都不新增行：无有效变化的只回提示、不动 `created`、不进入聚合；0 转正的更新同一行并走完聚合与流转分支；真正并发首报的唯一冲突提示在事务外返回；9 窗口内外与聚合结果一致；10 第 6 天记权重 0.0 且不刷新 `created`，第 8 天同一行转为正权重、更新 `created` 并参与聚合（按 D6 主建议；若站长改选每版本唯一，第 8 天应被直接拒绝，本条判据随之取反）；11 前两种写行但权重 0.0，只留过零权重记录的用户仍按新报告者计权。失败判据：任何凭空版本、旧版本或访客身份写入的有效报告；冷却起点被 `health_changed_at` 的后续变化改写；`Decimal` 聚合与阈值判定不一致。验证时间点：单测随 M04-3；边界与唯一约束在隔离库、发布前。证据：报告行（`reason`、`weight`、`link_version`、`evidence_round`）与 `SUM` 输出。

### E04-03　流转、冷却争议、补链与旧版本竞态

目的：证明流转在并发下唯一且不漏触发，争议规则与超时策略成立。单测层：八种转换的条件与结论、核实频率、任务候选查询与幂等、`tests/unit/cron-registration.test.ts` 增加新任务注册断言。

库内步骤：① 三种阈值组合各一次：3 强、6 弱、1 强 4 弱；② 两笔报告按 T1 持链接行锁、T2 在取锁处等待、放行 T1 后再放行 T2 的次序执行；③ 归属方核实可用，随后 30 天内再次核实；④ 用两个互相独立的夹具做冷却，起点都是 `verified_at`，只用可达操作、不直接改状态：夹具一在核实后保持 `ok`，第 6 天与第 8 天各由同一名老报告者提交一次；夹具二走「核实 → 新报告者触发争议 → 站方判可用（该动作不写 `verified_at`）」，随后在距核实第 8 天由老报告者提交；⑤ 新报告者在核实后 30 天内达阈值，另做恰好 30 天与 30 天加一秒两点；⑥ 争议轮内新报告者补足 3.0 强证据；⑦ 争议轮未达阈值并把注入的 `now` 推进到 30 天后运行任务；⑧ 发布者归属 `suspect` 满 7 天运行任务，`touchgal` 归属同条件运行任务；⑨ 任务已选中旧版本记录并在取锁处等待时先提交补链，再放行任务，随后用旧版本重试报告与重开；⑩ `broken → ok` 核实。

通过判据：① 三种组合都在写入该条报告的同一事务内转 `suspect`，只一条事项、一次通知；② 后到的一笔在放行后必然看到前一笔，最终恰好触发一次，既不重复也不漏；③ 记录 `verified_at`、轮次 +1、结论「核实可用」，30 天内第二次核实被拒；④ 夹具一第 6 天不改变状态、第 8 天可再次推动；夹具二在仍处争议轮时，老报告者即使已过 7 天仍记 0.0，而争议经站方判可用结束后，同一人在距核实第 8 天按 `verified_at` 起点正常计权，证明冷却没有被 `health_changed_at` 的重设延长；⑤ 转 `disputed` 且轮次 +1，触发争议的那批证据不参与争议判定，两个时间点按 5.1 边界表分界（恰好 30 天不再算争议）；⑥ 在该报告事务内即时转 `broken`、结论「自动判失效」；⑦ 任务收敛为 `ok`、结论「自动收敛可用」；⑧ 发布者归属转 `broken`、结论「超时失效」，`touchgal` 归属不自动转、只保留站方待办，模块 03 的通用超时任务未重复处理；⑨ 补链后 `version + 1`、`health = 'ok'`、历史写入、旧事项结论「已补链」，任务的条件更新影响 0 行，旧版本报告被拒，换版本后的事项不可重开；⑩ 允许。

失败判据：重复触发或漏触发、重复通知、任务把补链后的链接改为 `broken`、冷却期报告推动状态、冷却因进入争议而延长、争议进入即被判失效、结论与实际流转不符。验证时间点：M04-4 完成后、发布前；并发部分必须在真实 PostgreSQL 上做。证据：健康时间线（`health`、`health_changed_at`、`version`、`evidence_round`）、事项状态与结论、通知条数、任务日志与锁记录、屏障交错时序。

### E04-04　可用性、隐私、缓存与官方过渡归属

目的：证明可用性由链接推导、未授权响应不外泄凭据、缓存与故障降级不改变业务结果、资源盘链接归属正确且不重复待办。单测层：`get.ts` 的分组与 `revealed` 口径、后台视图字段白名单、缓存失效调用、`resource-permissions.test.ts` 的链接级归属。

步骤：① 把一条资源全部链接置为 `broken`；② 抓取公开资源列表、报告成功与失败响应、发布者待修复、后台失效视图、审计记录，并另抓一次已授权的获取结果与管理员资源详情作对照，同时对一条 `broken` 链接直接调用获取接口；③ 对 `touchgal` 链接依次触发 `suspect`、`disputed`、`broken`，检查收件箱与发布者面板；④ 达阈值、核实、补链提交后立即读取条目页与公开列表；⑤ 用独立 Redis 实例或注入式 mock 制造中断，提交报告并运行任务，再恢复。

通过判据：① 资源 `status` 仍为 0，仅折叠到「已失效资源」，署名与历史保留，出现在发布者待修复；② 未授权响应与后台视图、审计记录都不含 `content`、`code`、`password`，后台视图只有主机名与失效时长且失效比例按 6 节的分母口径标注起算时间，而已授权的获取结果与管理员详情仍按现状返回必要字段（不计为泄露）；折叠后的公开列表仍下发该链接的脱敏标识（`id`、`storage`、`size`、`health`、`version`），使模块 05 能选中它作为反馈目标；对 `broken` 链接的直接获取维持既定语义，不新增拒绝，授权与配额规则不变；③ `suspect` 与 `disputed` 只通过模块 03 的事项项出现在收件箱，`broken` 作为 04 的新来源出现且动作为补链或移除，同一链接不出现两条待办，全程不进任何发布者面板；④ 缓存失效被调用，重新读取不再返回旧健康；⑤ Redis 中断期间报告与流转仍落库、缓存失败只记日志、任务取不到锁则跳过；读取面只承诺按既有失效调用或缓存 TTL 最终刷新，不要求中断期间立即读到新值；恢复后任务按到期记录补跑且不重复通知。

失败判据：未授权响应泄露凭据；健康语义写入资源公开状态；资源盘故障进入发布者队列或产生重复待办；缓存失败导致「响应成功而数据未落库」或反之。验证时间点：M04-5 完成后、合批发布前。证据：脱敏响应快照、收件箱项清单、缓存失效调用记录、Redis 中断与补跑日志。

## 11 非目标

不做服务器主动检测与其证据存储（模块 10）：本模块不预加证据来源或「系统」标记字段；模块 10 接入时沿用本文的报告资格约束，必须校验当前 `version` 与 `evidence_round`、不跨轮累计旧检测结果，归属方手动检测与补链检测只显示给操作者、不改变健康。不做 `official` 标记、镜像与存量合并、移交与下架、获取计数口径切换（模块 06）；不做完整现象分流表单与受理范围正文（模块 05、站点文档）；不新建消息总线、通用队列、工作流平台、规则后台、角色层级或全站配额平台；不新增限频基础设施；不为健康新增资源级字段，也不把健康写进 `status`；不回填历史获取记录的版本，不推断存量文件版本；不拒绝对 `broken` 链接的直接获取请求（前台不再提供入口，服务端语义与配额规则不变）；不改动点击计数与 `updated` 行为；不修复整条资源删除时配额事实随之消失的既有行为。

## 2. 偏离与理由

| 偏离                     | 基线/计划原文                             | 本文做法                                      | 理由                                                                                                                   |
| ------------------------ | ----------------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 载荷额外携带每字段基点值 | 「目标条目 ID 与变更过的字段」            | 提交时由服务端写入 `base`（各字段当时的现值） | `patch.updated` 覆盖不到别名与标签关系的变更，单一时间戳无法判定过期；字段级基点是判断「只更新提议字段」的最小充分事实 |
| 审阅界面不含会社列       | 基线 6 的三列表把会社列为按外部数据裁决项 | 会社从校验层、服务层、DTO 与界面全部排除      | 与实施编排第 8 节的会社隔离约定冲突，按已确认约定执行并在此显式记录，不悄悄改产品；会社仍归独立线                      |

其余属实现细节而非产品偏离：纠错不复用 `publishSubmissionCore`（该函数必然新建条目、写会社、发奖励），基点过期时整体拒绝并要求审核者刷新后显式勾选覆盖（部分应用会让「批准了什么」无法复述）。

## 3. 术语

| 术语       | 定义                                                                                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------- |
| 纠错提案   | `patch_submission` 中 `kind = correction` 的行，指向一个已存在条目                                            |
| 目标条目   | 提案要修改的 `patch` 行                                                                                       |
| 白名单字段 | 名称、别名、发售日、标签、介绍、封面这六项，其他键一律拒绝                                                    |
| 基点值     | 提交时刻目标条目各白名单字段的规范化现值，冻结在载荷的 `base` 中                                              |
| 现值指纹   | 服务端对目标条目白名单现值的规范化摘要，用于提交与审核两处的乐观校验                                          |
| 过期提案   | 现值与基点不符的提案，界面标「已变化」                                                                        |
| 未结提案   | 状态属于 `draft`、`pending`、`changes_requested` 的纠错行；上限一律按作者本人计算，不是全站每条目一条         |
| 无效拒绝   | `review_reason_code = invalid` 的驳回，是唯一计入冷却的处理；判违规按既有规则处理，不额外扩大本模块的冷却处罚 |
| 双审       | 两个审核请求同时到达同一提案的竞态，不是双人会签制度                                                          |

## 4. 数据模型

只扩展[现有 schema 文件](../../prisma/schema/patch-submission.prisma)，不新建表。

| 变更                                                                         | 约束与默认值                                           | 说明                                                                                                                                                                                                                                               |
| ---------------------------------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `kind String @default("new") @db.VarChar(16)`                                | 取值 `new` / `correction`                              | 默认值使既有行与新建路径完全不变                                                                                                                                                                                                                   |
| `target_patch_id Int?` + 关系 `patch_submission_target`，`onDelete: SetNull` | 索引见下                                               | 条目被删除时置空、保留提案供驳回；`name` 列复用为提交时的目标条目名，队列检索沿用既有 `@@index([name])`                                                                                                                                            |
| `request_key String? @db.VarChar(107)`                                       | `@@unique([user_id, request_key])`                     | 零押金没有 reservation 可挂幂等键，改用用户范围请求键；既有行为 NULL，Postgres 允许多个 NULL 并存，不制造 0 点预留                                                                                                                                 |
| `review_reason_code String? @db.VarChar(32)`                                 | 取值 `invalid`/`duplicate`/`superseded`/`out_of_scope` | 纠错驳回必填，只有 `invalid` 计入冷却；新建投稿保持 NULL，不重写既有处罚逻辑，也不靠中文关键词猜次数                                                                                                                                               |
| `cooldown_until DateTime?`                                                   | 只写在触发冷却的那条无效驳回上                         | 冷却必须从 30 天窗口内第三次无效驳回起算满 30 天；仅按「最近 30 天内 ≥3 次」实时计数会在最早一次滑出窗口后提前解禁。落一个到期时刻即可，不建处罚记录表、不加定时任务；查询按既有 `[user_id, status, created(sort: Desc)]` 索引过滤，不为它再加索引 |
| `@@index([kind, status, submitted_at])`                                      | —                                                      | 纠错队列与混合队列的最老优先取数                                                                                                                                                                                                                   |
| `@@index([target_patch_id, status])`                                         | —                                                      | 目标条目删除时 `SetNull` 的反向查找、后台按条目查看相关提案，以及作者本人在该条目的未结检查；条目页只提示作者自己的提案，不开放他人提案的公开查询                                                                                                  |

不新增：奖励/悬赏字段、提案历史版本表、字段级审计表、任何「以后可能用」的列。`patch_id`（新建投稿产出的条目，`@unique`）对纠错行永远为 NULL，避免与该条目自身的新建投稿行冲突。

纠错载荷（`payload`，`kind = correction` 时 `payload_version = 1`）：

| 键              | 类型与规则                                                                                         |
| --------------- | -------------------------------------------------------------------------------------------------- |
| `targetPatchId` | 整数，必须与 `target_patch_id` 一致                                                                |
| `changes`       | 仅允许 `name`、`alias`、`tag`、`released`、`introduction`、`banner` 六键；至少一键；未知键直接判错 |
| `base`          | 与 `changes` 同键，值为提交时刻的规范化现值，由服务端写入，客户端不可提供                          |
| `reason`        | 提交者说明，≤1007 字符                                                                             |

`changes.banner` 只是布尔标记，真正的图片沿用既有 `banner_key` / `banner_thumbnail_key` / `banner_original_key` 列与既有封面上传路径。规范化规则：字符串 trim；`alias`、`tag` 去重 trim 后按码位排序；`banner` 用 `patch.banner` 原字符串。现值指纹为规范化结果的摘要。

配额语义：`countActiveSubmissions` 增加 kind 参数，新建走 `kind = new` 与既有 `PATCH_SUBMISSION_DEPOSIT.maxActive`，纠错走 `kind = correction`，两条上限都以作者为范围——同一作者对同一目标条目最多 1 条未结、该作者合计最多 3 条未结（基线第 6 节原文）。不同作者可对同一条目各有一条未结，草稿只占作者自己的名额，因此不设全站目标唯一约束；素材字节配额 `sumActiveSubmissionBytes` 保持不分类型，共用同一 200 MB 上限，不因拆 kind 翻倍。

幂等与并发约定：创建靠用户行锁 + `(user_id, request_key)` 唯一索引；提交靠「源状态 `draft` 或 `changes_requested` 且 `revision` 未变」的条件更新；审核靠「源状态 `pending` 且 `revision` 等于请求携带的 `expectedRevision`」的条件更新，胜出者才写通知。`expectedRevision` 必须来自管理员当时看到的详情 DTO，不能在服务里重读当前 `revision` 再和自己比对——那样管理员看到 R3、作者撤回改成 R6 之后，旧界面上的批准仍会通过一份没人看过的载荷。加锁顺序固定为「需要用户锁时先用户行 → 需要目标时先目标条目行 → 最后提案行」；加锁前的只读预查仅用于定位加锁对象，不作权威，取锁后必须重读校验，纯读不加锁。本文不宣称全调用链绝不死锁，锁冲突与已识别的可重试事务冲突沿用现有有界重试。通知一律用事务内 `createMessage`，不用 [`createDedupMessage`](../../app/api/utils/message.ts)（先读后写，无数据库并发保证）。纠错的四个审核动作各写一行专用 `correction_review` 类型的 `admin_log`，与新建投稿的 `submission_review` 及会社诊断日志分开，好让模块 09 按来源拆分处理时长；本模块同时把该类型纳入模块 01 的「今日已处理」计数白名单，并在 `constants/admin.ts` 补中文标签；不加 kind 列、不建事件表。

必须补的 kind 分流（都在现有文件内改，属正确性修复）：[`review.ts`](../../app/api/patch-submission/review.ts) 的 `approvePatchSubmission` 拒绝 `kind != new`（否则旧发布路径会把纠错载荷当新条目建 patch）；[`service.ts`](../../app/api/patch-submission/service.ts) 的 `getPatchSubmission`、`updatePatchSubmissionDraft` 拒绝纠错行落入新建编辑器，`listOwnPatchSubmissions` 按 kind 输出摘要与链接（纠错指向 `/correction/{id}` 并带目标条目 `unique_id`）；`submitPatchSubmission` 与撤回按 kind 分支，纠错的撤回、`changes_requested` 后补充重提交、终态隐藏沿用现有状态机与 `hidePatchSubmission`；`rejectPatchSubmission` / `violatePatchSubmission` 按 kind 切换文案（纠错无押金，不能说「押金已返还」），其中 reject 对纠错必填 `reasonCode`，violate 不写 `reasonCode`、不计入冷却，沿用既有违规处理；[`admin service.ts`](../../app/api/admin/patch-submission/service.ts) 的列表返回 `kind` 与目标条目回链，`AdminPatchSubmissionDetail` 补上现在缺的 `revision`（现只有 `payloadVersion`）并同步模块 01 复用的映射，详情对纠错行不再构建新建预览（`buildPatchSubmissionPublishPreview` 只适用于新建载荷），改由纠错详情接口承担；删除草稿沿用现有实现（`reservation_id` 为空时本就跳过账务）。

冷却口径（基线：30 天内 3 次无效 → 冷却 30 天）：纠错的无效驳回在同一事务内先锁作者用户行，统计该作者最近 30 天内（含本次）`review_reason_code = invalid` 的纠错终态数，达到 3 次时把本次 `reviewed_at + 30 天` 写入本行 `cooldown_until`。创建与提交取该作者所有未过期 `cooldown_until` 的最大值，大于当前时间即拒绝并展示解除时刻。这样窗口内第三次驳回之后即使更早的记录滑出窗口也不会提前解禁，且不需要定时任务或处罚记录表。冷却只作用于其后的创建与提交：在第三次驳回落库之前已经建好的草稿是合法的，它会在下一次提交时被拦下，不追溯删除。

apply 事务（`apply.ts`，隔离级别 ReadCommitted，全部在一个事务内）：

1. 先做一次不加锁的预读，取提案的 `target_patch_id` 与作者，仅用于定位加锁对象；再按固定顺序取锁：先 `SELECT id FROM patch WHERE id = $1 FOR UPDATE` 锁目标条目行，后 `SELECT ... FOR UPDATE` 锁提案行。取锁后重读提案并校验 `kind = correction`、`status = pending`、`target_patch_id` 与预读一致、`revision` 等于请求携带的 `expectedRevision`，任一不符即中止（预读结果不作权威）。沿用现有自审规则。
2. 在已持目标行锁的前提下读当前值：`patch` 行、`patch_alias`、`patch_tag_relation → patch_tag.name`。行锁必须在读现值之前取得，否则 ReadCommitted 下另一份提案或站方编辑可以在「读现值」与「写回」之间提交，指纹校验形同虚设。目标为空（已删除，`target_patch_id` 被 `SetNull`）时抛出可读错误，提案保持 `pending` 供驳回。
3. 重算现值指纹：与审核者提交的 `fingerprint` 不符则要求刷新；与 `base` 不符的字段列为过期，缺少 `overrideStale` 时拒绝。
4. 只写提议字段：`patch.update` 处理 `name`、`introduction`、`released`、`banner`；`patch_alias` 全量重建（该表无被引用的下游记录，与资源链接的情形不同）；标签按差量写 `patch_tag_relation`（`deleteMany` 不再需要的 + `createMany({ skipDuplicates })`），缺失标签沿用 [`tagEnsureHelper`](../../app/api/edit/tagEnsureHelper.ts) 的别名解析创建；`patch_tag.count` 由既有语句级触发器维护（`migration/production-tag-company-count-sync-2026-08-30.sql` 第 168 至 187 行安装在 `patch_tag_relation` 上，按语句增减计数），服务不手工累加。
5. 换封面时先确认本提案确有上传完成的封面素材，再把 `patch.banner` 指向它（沿用 `buildPatchSubmissionPublishedAssetUrl`）；旧封面若是 `patch-submission/` 前缀的键，把主图与其 `banner-mini`、`banner-full` 三个尺寸一并 `enqueueSubmissionOrphanCleanupJobs(tx, keys, 'banner_replace')`（[orphanCleanup.ts](../../app/api/patch-submission/orphanCleanup.ts)），旧的 canonical 素材不删除。提案上传过封面但最终没有采用时，这些素材在同一事务内一并入队回收，不永久滞留。清理执行前 `loadServingSubmissionAssetKeys` 会按线上 `patch.banner`（含三尺寸推导）复核，仍在服务的对象被取消，不会误删。
6. 条件更新提案为终态：`where` 同时要求 `status = pending` 与请求携带的 `expectedRevision`，写 `published`、`reviewed_by_id`、`reviewed_at`、`settled_at`；失败即说明已被撤回、被改动或被他人处理。
7. 同事务写一条作者系统通知（链接 `/correction/{id}`）与一条 `correction_review` 类型的 `admin_log`。全程不调用任何萌萌点原语。

提交后（事务外，失败只记录不回滚）：`invalidatePatchContentCache(uniqueId)`、`invalidatePatchListCaches()`，标签有变化时 `invalidateTagCaches()`（[cache.ts](../../app/api/patch/cache.ts)）；有素材入队时 `processSubmissionOrphanCleanupJobsBestEffort`。外部通知沿用既有条目改写路径的既定做法，不额外接 IndexNow。

写入与读取面对照：条目详情、条目列表与首页、标签页与标签列表、作者的提案列表与通知未读、后台队列计数。

## 7. 定时任务

无新增定时任务。冷却在无效驳回时落一个到期时刻、在创建与提交时读取，未结上限按请求时计数，都不需要扫描；提案没有超时自动结案规则（基线未定义）；素材清理沿用既有 orphan cleanup 机制与命令。因此不涉及 `withTaskLock` 无续租带来的重复执行问题。已知取舍：被遗弃的纠错草稿会一直占用该作者在该条目的名额，作者可自行删除，与既有草稿不自动过期的行为一致。

## 8. 迁移与回填

1. 迁移内容：新增 `kind`（带默认值）、`target_patch_id`、`request_key`、`review_reason_code`、`cooldown_until` 五列，新增两个索引与一个唯一索引。既有行由默认值覆盖，无需数据回填。
2. preflight（只读）：统计 `patch_submission` 行数与各状态分布；确认没有既有列名冲突；确认唯一索引 `(user_id, request_key)` 在全 NULL 数据上可建。
3. 顺序：先执行迁移让新列与索引可用，再部署会查询 `kind` 的新 Client 与应用（应用不得在列存在之前查询 `kind`），确认旧发布路径已拒绝纠错行，最后开放前台入口；需要时用既有维护窗口保证切换期间没有旧写入端。入口开放前数据库里不会存在纠错行。
4. postflight：抽查默认值生效、索引存在、既有新建投稿的创建/提交/审核路径未受影响。
5. 回退边界：一旦存在纠错行，只能回退到仍带 kind 守卫的兼容版本，或停用纠错的读写与审核路径而保留守卫。不能退回不认识 `kind` 的版本，也不能靠把未结提案改成 `changes_requested` 来规避——作者仍可再提交，旧审核路径仍会建出重复条目。数据库列与已产生的行不回删；已写入条目的修正不做数据回滚。
6. 全流程在隔离库演练；生产按既有 preflight/sync/postflight 与部署安全检查执行，本文阶段不运行这些命令。

## 9. 测试与实验方案（全部未执行）

共用前提：隔离测试数据库（真实 Postgres，覆盖触发器与唯一约束）、Vitest、注入式 `now` 假时钟，不修改机器时间；并发用测试层屏障或受控事务交错实现，不在生产代码里加延迟开关；外部数据源与 S3/CDN 用 mock。相关单测归入对应实验编号。

### E08-01 零押金、资格、未结限额与冷却

- 目的：证明纠错不触碰账务、不占用新建名额，按作者范围的未结上限与无效冷却在并发与日期边界下成立。
- 样本与步骤：(a) 同一用户对同一条目连续创建两条 → 第二条被拒；(a2) 两个不同用户各对同一条目创建一条 → 都成立，草稿只占作者自己的名额；(b) 同一用户的两个创建请求在锁用户行处交错 → 只成立一条；(c) 已有 3 条分属不同条目的未结 → 第 4 条被拒；(d) 同 `requestId` 重试 → 返回同一行；同 `requestId` 换一个 `targetPatchId` → 报错而不是返回原来那条；(e) 新建投稿回归：role 1 用户 5 条草稿上限与 10 点押金不受纠错行影响，纠错不计入新建 `maxActive`；(f) 素材字节：纠错草稿封面计入同一 200 MB 总额，不因拆 kind 翻倍；(g) 冷却触发：注入 25/20/5 天前的三次 `invalid` 驳回，第三次落库 `cooldown_until` → 创建被拒并提示解除时刻；(g2) 时钟推到第一次已超出 30 天窗口、但距第三次不足 30 天 → 仍在冷却；(g3) 时钟等于 `cooldown_until` → 放行，早一秒 → 仍拒绝；(g4) 无效驳回事务与创建事务并发（一个持用户行锁）→ 两种合法先后顺序都成立：创建先提交时草稿合法存在并在下一次提交时被冷却拦下，驳回先提交时创建直接被拒；判据是不出现「冷却已生效仍放行新的创建或提交」，而不是按事后累计次数追认已建草稿违法；(h) 两次 `invalid` + 一次 `duplicate` → 不冷却；(i) 判违规不写 `invalid`，不改变冷却计数。
- 通过判据：以上断言全部成立；`user_moemoepoint_ledger` 与 `user_moemoepoint_reservation` 在纠错路径零新增行。
- 失败判据：同一作者在同一目标下出现第二条未结、一个用户的草稿挡住另一个用户、余额或预留发生变化、纠错挤占新建名额、冷却提前解除或依赖中文关键词匹配。
- 时间点：M08-2 完成、开放前台入口之前。
- 证据：Vitest 输出；隔离库按 kind/status 的计数快照与账务表 diff。
- 清理：测试库 truncate 相关表，不触碰生产。

### E08-02 修正白名单、双审与并发条目更新

- 目的：证明只有白名单字段被写入，会社与外部 ID 永不被纠错改写，同提案双审、同条目多提案、站方编辑与作者改动这四类竞态都不会破坏条目。
- 样本与步骤：(a) 载荷带 `vndbDevelopers`、`dlsiteCircleName`、`vndbId`、`officialUrl`、截图等 → 校验层拒绝；(b) 闭环：介绍、标签、封面各一次通过，断言 `patch` 行、`patch_alias`、`patch_tag_relation` 差量与 `patch.banner`，并断言 `patch_tag.count` 由 `migration/production-tag-company-count-sync-2026-08-30.sql` 安装的语句级触发器变化、服务未写过 count；(c) 双审：两个 approve 在条件更新前交错 → 一成功一失败，条目只更新一次、系统通知 1 条、`admin_log` 1 条；(c2) 同一条目上两位作者的提案同时通过 → 后一份要么因目标行锁串行后指纹不符被拒、要么按新现值合法写入，任何一份的字段都不会被旧值盖回；(c3) 审核与既有后台编辑（`updateGalgame` 的六字段写入，含 `handleBatchPatchTags` 的差量写与 `ensureAliases` 的补写）受控交错 → 合法串行下后提交者按其既定语义生效，先读旧现值的纠错审核被拦下，别名与标签关系不会退回旧集合；(c4) 管理员先 GET 详情拿到 `expectedRevision`，作者随后撤回、改动并重新提交使 `revision` 前进，旧界面上的审核请求才到达 → 四个审核动作都因 `expectedRevision` 不符被拒，管理员不会批准自己没看过的载荷；不采用「在审核已持提案锁之后插入作者修改」这种会被阻塞、无法复现的写法；(d) 过期：审核前用另一事务改介绍 → 指纹不符被拒且条目未变；刷新后带 `overrideStale` 再审 → 成功并写入新值，日志记录覆盖事实；(e) 目标条目删除 → 报「目标条目已删除」，提案保持 `pending` 且可驳回；(f) 旧路径保护：把纠错行传入 `approvePatchSubmission` → 拒绝，不产生新 `patch`；(g) 驳回记录 `reasonCode`、无账务变动，未被采用的素材被清理；通过后仍被线上条目引用的素材不被清理。
- 通过判据：全部断言成立，且任一失败路径都不留下半写条目。
- 失败判据：非白名单字段落库、基于过期基点的纠错审核把旧值写回条目、`revision` 变化后仍发布旧内容、重复通知、仍在服务的素材被清理。
- 时间点：M08-4 完成后、上线前。
- 证据：条目及关系表的前后行快照、通知与日志计数、受控交错记录下来的实际取锁顺序、Vitest 输出。
- 清理：同上。

### E08-03 外部对照、预览、素材与缓存通知回归

- 目的：证明三列审阅的外部数据可辨认且可降级、不污染会社快照，素材、缓存与作者读回路径在通过后正确，既有新条目投稿与后台队列未回归失败。
- 样本与步骤：(a) 外部源 mock 分别返回成功、超时、404 → 三种呈现均可继续审核，成功与失败都带来源与取数时间；断言 `company_candidates` 未被写、审阅 DTO 不含任何会社键、外部值不会自动写进条目；(a2) 作者侧：目标不存在、或按其既有可见规则不可见时请求创建或提交 → 拒绝，不因客户端知道 ID 而放行；管理员侧：外部抓取按管理上下文执行，条目存在即可，不因管理员自己的前台 NSFW 偏好被误拒，条目不存在才拒绝；(a3) 非作者请求 `/correction/{id}` → 拒绝，作者本人 → 正常返回；目标随后被删除时作者仍能读到提案与基点快照，读不到目标的受限内容；(b) 断言抓取发生在事务外：apply 事务执行期间外部请求计数为 0；(c) 封面：通过后 `patch.banner` 指向提案素材，旧的 `patch-submission/` 封面三个尺寸一并入队，仍被引用时被 cancel，旧 canonical 素材未被删除；(c2) 提案上传封面后又取消该项变更并通过 → 未采用的素材入队回收，线上封面不变；(d) 缓存：通过后内容、列表、（标签变化时）标签失效函数各调用一次，失效失败只记录且不回滚已提交的修正；(e) 作者路径：`/correction/{id}` 能读到本人草稿、待审与终态，「我的投稿」列表按 kind 给出正确链接与目标条目，作者收到 1 条可回到提案的系统通知，管理员侧提交通知文案区分纠错；(f) 回归：既有 `tests/unit/patch-submission-*` 全绿，并在隔离库跑一次真实新建投稿闭环（押金、发布、奖励）；(g) 队列与审计：混合 kind 的待审队列仍按模块 01 的 `COALESCE(submitted_at, created), id` 最老优先，纠错以 `kind` 与目标条目回链接入现有投稿来源、不新增来源，最老一条在过滤前后都可达；纠错的每个审核动作只写一行 `correction_review`，与 `submission_review` 可区分，并被模块 01 的「今日已处理」白名单正确统计一次。
- 通过判据：以上全部成立；无任何生产环境调用。
- 失败判据：事务内出现网络调用、会社快照被写、仍在服务的素材被误删、未采用的素材永久滞留、作者读不到自己的提案、最老待办被新类型挤出队列。
- 时间点：M08-5 完成后、上线批次验收前。
- 证据：mock 调用记录、S3/CDN mock 的删除与 purge 列表、缓存函数调用计数、Vitest 输出。
- 清理：清空测试库与 mock 状态。

# 模块 05：入口分流（项目管理版）

状态：设计待审，未实施。配对实施计划（技术细节以它为准）：[05-issue-entry.md](./05-issue-entry.md)。总计划：[00-master-plan.md](./00-master-plan.md)（本模块任务编号 M05-1 至 M05-5）。产品依据：[运营层设计基线](../7.operations-layer-redesign.md) 第 3.6、8.1 至 8.3、8.6 节。

## 1 目标与责任人

目标：让用户在提交之前就把「资源出问题了」拆成四条去向——机制（失效报告投票）、责任（发布者的资源事务）、社区（下载与运行环境类求助）、站方（规则、放错条目、官方资源与官方链接、合法升级），站方不再逐条做人工分类与转达。判断标准是现象表每一分支都有唯一去向，且到达站方的只有工单与链接健康两模块定义为需站方处理的事项。

责任人：站长负责业务规则与上线后的运营验收；设计、实现与验证由实施方完成。本模块不新增角色、权限层级或协作方。

## 2 功能介绍与使用流程

本模块做的是「提交之前的分流」：把资源相关的入口收成一个，把用户能看到的现象翻译成唯一去向，让投票、发布者事务、社区求助、站方裁决各走各的路。它自身不处理任何事项——真正的处理分别由链接健康、工单、求助区、纠错投稿四个模块承担。

### 2.1 三个入口，各自能做什么

| 入口     | 位置                                       | 谁能用                                                         | 能做什么                                                                       |
| -------- | ------------------------------------------ | -------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 遇到问题 | 每张资源卡片底部（排在点赞、展开链接之后） | 未登录可见说明，提交需登录                                     | 两步选择：先选目标（卡片里的某条链接，或整条资源），再选现象，界面给出唯一去向 |
| 报告失效 | 每条链接旁（由链接健康模块提供）           | 未登录可见说明；提交需登录，且 30 天内获取过这条链接的当前版本 | 链接失效类现象（强证据与弱证据）的快捷方式，与「遇到问题」写的是同一份投票     |
| 反馈     | 条目页动作区                               | 未登录可见说明，提交需登录                                     | 只剩三项：条目信息错误、资源发错条目、其他                                     |

评论、评价等内容的举报入口仍在各自内容旁边，本模块不改动它们。

### 2.2 两步选择怎么走

1. 第一步选目标：列出这张卡片里的全部链接（包含已被折叠的失效链接，标注「已失效」）以及「整条资源」。单链接的资源默认选中那条链接，界面始终显示当前选中的目标。
2. 第二步选现象：按目标类型给出现象清单，每个现象下方写明谁来处理、预计首次响应多久，以及提交后会发生什么。可以退回第一步换目标，关闭对话框不保存草稿。
3. 提交后界面明确告诉你结果落在哪里：记录了一次报告、已交给归属方、已交给站方，还是只是打开一篇指南。

| 现象                                                 | 目标               | 谁处理                                                                    | 用户看到的结果                                                                                 |
| ---------------------------------------------------- | ------------------ | ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |

| 链接要求付费，或取得方式与发布说明不符               | 某条链接           | 同上                                                                      | 记一次强证据报告                                                                               |

### 2.4 链接失效报告的规则（用户视角）

- 报告是投票，不是请求。证据未达阈值时不会产生任何处理待办，链接也不会因此下架；当你这一条使证据达到阈值时，系统才把事项交给这条链接的归属方。
- 强证据：网盘页面明确显示已删除、已过期、违规，或链接要求付费、取得方式与发布说明不符。网盘本身正常的登录要求不算失效；文件内容与描述不符属于资源问题，走 2.5 第一条。
- 弱证据：打不开、超时。界面先给网络提示，只有你确认「已尝试更换网络或加速器」之后这条报告才算数，不确认就不会提交。「下载慢」不写入报告，只带你去下载指南。
- 达阈值之后：发布者归属的链接在疑似失效状态满 7 天无人处理，由系统自动判为失效并从卡片折叠；站内资源盘（官方）链接归站方，按当前规则没有自动超时，会留在站方待办里（官方链接的超时边界随工单与链接健康两个模块定稿，届时提示同步）。具体归属由系统给出，界面不自行判断。
- 如果这条链接在你打开页面之后已经换过地址，界面会请你刷新再报告，避免为旧地址投票。

### 2.5 内容问题、环境问题与违规的区分

- **资源与描述不符**是内容问题：版本与描述不符、缺少描述中声明的文件、内容与条目不符都走这一条，由该资源的实际归属方受理——普通资源归发布者，官方资源归站方；普通发布者的资源即使已经有了站方镜像，内容问题仍归原发布者。
- **压缩包损坏、解压失败、无法启动、乱码、存档问题**先按环境问题排查，这一分支不直接开出任何事项。求助区上线前给出检查清单（核对文件大小与校验码、重新下载；校验码只有站内对象存储链接才提供，其余链接只能核对大小并重新下载）与现有的网站说明、下载相关问题解答、压缩包修复教程，并说明求助区上线后可以直接在这里提问；上线后同一位置换成锚定该资源的求助入口，由社区回答，发布者会收到通知，站方与发布者都没有回应义务。如果后来确认问题出在资源本身，由求助区的转换规则接手，不在本入口直接开事务。求助区的费用与奖励规则仍在审定中，本模块在它上线之前不出现任何点数、悬赏或收费说明。
- **疑似违规或有害内容**按违规举报受理，站方处理，预计 3 天内首次响应。它和条目页的「其他」不是一回事：「其他」是兜底渠道，同样由站方处理，但不承诺时限。两者在界面上分列，不合并、不互相替代。

### 2.6 条目页「反馈」的三项

- **条目信息错误**：纠错投稿上线之前只显示说明——条目资料以外部数据源为准，自助修正入口会随纠错投稿一起开放；这一分支不提交任何事项，也不建立由站方替用户改字段的队列。上线后同一位置换成「提交修正」，填正确内容、审核通过即生效。
- **资源发错条目**：提示到对应的资源卡片提交，并提供跳转，避免只说「资源有问题」却看不出是哪一条。
- **其他**：保留原来的自由文本，交站方处理，不承诺时限。

### 2.7 登录、资格与提示口径

- 未登录也能看到全部入口、现象清单与说明，提交时引导登录。
- 报告失效还要求 30 天内获取过这条链接的当前版本。是否满足由系统判定；界面不会因为「此刻没有可见的已获取链接」就拦下仍然有资格的人，只给一句中性提示。
- 目标必须真实且可见：跨条目、已删除、已隐藏的目标一律被拒绝，不会产生任何事务或报告。
- 所有时间都写「预计首次响应」，不是处理完成时限，界面不出现「保证几天处理完」这类说法。
- 入口内只放一句话的受理范围提示，并说明求资源、催更这类请求不通过本入口受理，指向内容贡献指南；完整的受理范围正文随站点文档统一发布。尚未上线的分支写明当前能做什么，不承诺未上线的能力。

## 3 本模块做与不做

| 做                                             | 不做                                         |
| ---------------------------------------------- | -------------------------------------------- |
| 选目标、选现象、唯一去向、分支提示与临时去向   | 失效报告、工单、求助、纠错投稿本身的处理能力 |
| 复用链接健康模块的报告提交与工单模块的事务提交 | 新增队列、后台视图、定时任务或新依赖         |
| 入口内一句话受理范围与预计首次响应             | 完整受理范围页正文（随站点文档统一编写）     |
| 与新入口冲突的两篇现有指南的最小文案修订       | 重写站内指南体系                             |

## 4 依赖与上线批次

- 硬前置：工单模块须先登记资源目标的违规举报类型，并完成旧反馈、旧举报写入的切换；链接健康模块须把链接版本下发到前台，并拒绝没有网络确认（或确认为否）的弱报告。任一前置未达成，这一批就不满足上线条件，不能靠砍掉必需分支来通过验收。这两处的服务端校验是唯一权威。
- 与链接健康模块同一批次发布（总计划第 3.3 节）。入口不得早于处理能力开放。
- 官方镜像上线之前，资源盘链接的归属方是站方，因此链接类提示统一写「该链接的归属方」，具体归属由系统返回，界面不自行推断，并按两种归属提示对应后果。
- 求助区上线时替换环境类临时去向，纠错投稿上线时替换条目信息错误分支；两处替换分别记在 M07-6、M08-5。

## 6 验收

1. 用完整现象表逐项走通：条目、资源、链接与链接版本这些目标不丢失。
2. 指南路径存在：网站说明、下载相关问题解答、压缩包修复教程、内容贡献指南四篇均可打开，检查清单与用户实际能看到的信息一致。
3. 提示中的处理方与预计首次响应对应当时已上线的能力，尚未上线的分支写明当前去向。
4. 本模块引用到的流程里没有把资源处理引向私聊、评论区或邮箱的句子，被修订的两篇指南复查通过；站点既有的联系方式与版权说明保持不动。
5. 与链接健康模块同批完成本地与隔离环境验证后再发布，上线后记录一轮真实使用结果。

## 7 风险与未决事项

- 费用与奖励整段仍待审定（D8）。本模块在求助区上线前不出现任何点数、悬赏或收费文案；桥接转求助的收费与资格、奖励资格不足的名额处理仍按 D8 定稿，本文不视为已批准。
- 资源级「疑似违规」不在基线违规举报的目标清单内，属基线内部遗漏。处理方式是让工单模块补登这一类型（站方处理、预计 3 天内首次响应），不把它降级成不承诺时限的「其他」。
- 弱证据的「已尝试更换网络」无法由服务端证明用户真的换过网络，但这次确认仍必须随请求提交，缺失即被拒绝。
- 基线受理范围页里「发布者超时未响应即转给站方」的概括与工单、链接健康两节不一致：单条报告只是投票，达到阈值后才进入归属方处理；此后发布者归属的链接满 7 天无处理自动判失效，站方归属的官方链接没有自动超时、只留在站方待办，只有资源与描述不符类才升级站方。分支提示按这两种归属分别写，并说明这是预计首次响应而不是处理完成时限。
- 现有下载指南与压缩包修复教程把资源问题引向评论区、Telegram 与邮件，与新入口冲突。本模块随入口修订这两处，完整规则正文仍随站点文档。
- 纠错投稿上线前，条目信息错误只给说明、不进任何队列；这一点已由本模块任务定下，不再另设例外。

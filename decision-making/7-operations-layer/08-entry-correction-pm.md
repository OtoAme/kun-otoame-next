# 模块 08：条目纠错投稿（PM 视图）

状态：设计草稿，未实施。技术细节见配对的[实施计划](./08-entry-correction.md)；任务编号、上线批次与依赖见[总计划](./00-master-plan.md)第 3.3、4.9 节；产品规则见[基线](../7.operations-layer-redesign.md)第 6 节。

## 1. 目标与责任人

用户发现条目信息有错时，现在只能提交反馈、等站长手工改。本模块让登录用户直接提交「修正提案」，站方在一个页面对照条目当前值、用户提议值与外部数据源的值，确认后一键写回条目。目标是把条目纠错从「人工代改」变成「提案—审核—自动写入」，让站方只做判断、不做录入。

责任：站长审核全部提案；实施方交付提交、审阅、写入、通知与入口切换。费用与奖励不在本模块：纠错零押金、零奖励，按基线原文执行，不另开审批项。会社、开发商、社团数据仍归会社独立线，本模块不碰。

## 2. 功能介绍与使用流程

条目信息写错时，用户不再只能写反馈等站长代改，而是自己提交一条「修正提案」，站方对照后一键采纳。纠错复用现有的投稿与审核体系：用户在「我的投稿」里看到自己的提案，站方在同一个待审队列里处理它。

### 2.1 谁能做什么

| 角色                   | 能做什么                                                                   | 门槛                       |
| ---------------------- | -------------------------------------------------------------------------- | -------------------------- |
| 登录用户（含普通用户） | 对自己当前能看到的已收录条目提交修正提案；管理、撤回、补充、隐藏自己的提案 | 登录即可，不需要创作者身份 |
| 站方管理员             | 在后台待审队列里逐条审阅纠错，三列对照后通过、要求修改、驳回或判违规       | 后台管理员级               |

纠错全程不动萌萌点：不收押金，也不发奖励。审核者不能审自己提交的提案，自审限制与超级管理员的例外沿用既有投稿规则。

### 2.2 用户可以修正的六项内容

| 可修正项 | 用户提交的形式                                                           | 审核主要依据     |
| -------- | ------------------------------------------------------------------------ | ---------------- |
| 名称     | 一个新的条目名                                                           | 以外部数据源为准 |
| 别名     | 一整组别名（采纳后整组替换）                                             | 以外部数据源为准 |
| 发售日   | 一个新的发售日                                                           | 以外部数据源为准 |
| 标签     | 一整组标签（采纳后只增删有差异的部分；站内还没有的标签在采纳时一并建立） | 以外部数据源为准 |
| 介绍     | 新的介绍正文                                                             | 站方判断         |
| 封面     | 上传一张新封面                                                           | 站方判断         |

纠错不接受其他修改：会社、开发商、社团（由会社独立线负责，遇到这类错误沿用现有引导）；VNDB / Bangumi / Steam / DLsite 等外部 ID；官网；内容分级；截图；以及资源与下载链接本身。这些内容在填写和提交时就被拒绝，不会被顺带改掉。

### 2.3 提交一条纠错：免费，但有资格与限额

用户从条目页的「反馈 → 条目信息错误」进入纠错页，只填要改的那几项，可以附一句说明。可以先存草稿慢慢改、先把新封面上传好，草稿只有自己可见。

提交时系统会记下「提交那一刻条目长什么样」，作为后续判断提案是否过期的基点。两种情况提交不会成功：填写期间条目已经被改动过（提示刷新后重新确认要改什么），以及提议内容与当前条目完全一致（没有实际改动的空提案）。

资格与限额，全部按提交者本人计算（下面的「未处理」指草稿、待审核、需要修改这三种状态）：

- 同一个条目上，每人最多 1 条未处理的提案；全部条目合计，每人最多 3 条未处理的提案。草稿也占自己的名额，自己删掉即释放。
- 名额不跨用户：别人在同一条目上有提案，不会挡住你提交。
- 30 天内被以「内容无效」驳回 3 次，从第三次驳回起冷却 30 天。冷却期间不能新建也不能提交，界面显示解除时刻，到期自动恢复；已存在的草稿保留，不会被追溯删除。
- 目标条目必须是提交时自己能看到的条目，看不到或已删除的条目不能拿来提案。
- 纠错的未处理名额与新建条目投稿的名额分开计算、互不占用；但上传的封面等素材与投稿共用同一容量上限，不会因为多了纠错而翻倍。

### 2.4 我的提案：状态与可做的操作

提案有六种状态：草稿、待审核、需要修改、已采纳、未采纳、违规关闭。对应能做的操作：

- 草稿：继续编辑、提交、直接删除。
- 待审核：可以撤回，回到草稿继续改（撤回不扣任何东西）。
- 需要修改：站方退回并写了原因，按原因补充后重新提交。
- 已采纳 / 未采纳 / 违规关闭：不可再改，可以从自己的列表里隐藏，站方记录不受影响。

提案与新建投稿并列出现在「我的投稿」里，标明这是一条纠错并链到被修正的条目；系统通知可以点回提案本身。条目页还会提示「你在这个条目上已有一条未处理的提案」，只提示自己的，不公开别人的提案。

### 2.5 站方审阅：三列对照与四种结果

提案提交后站方会收到待审通知。纠错进入现有的待审投稿队列，带类型标记和目标条目回链，仍是最老的先处理，不新建第二个队列。

详情页只列用户真正改过的字段，每个字段三列并排：条目当前值、用户提议值、外部数据源的值。名称、别名、发售日、标签按外部数据裁决，介绍与封面是仅有的两道判断题。外部数据是按条目已有的外部 ID 现场取的，标明来源和取数时间；取不到就标注「无法获取」，审核照样能继续。外部数据只作参照，既不会自动写进条目，也不返回会社信息。

四种处理结果：

| 结果     | 含义                                                                                 | 用户看到什么                                               |
| -------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| 通过     | 采纳提议                                                                             | 条目更新，收到一条通知，可回看提案与条目                   |
| 要求修改 | 方向对但需补充                                                                       | 提案回到「需要修改」，附站方原因，可改后再提交             |
| 驳回     | 不采纳，必须选一类理由：内容无效、重复提案、已被他人修正或目标已变、不属于可修正范围 | 提案标为未采纳并显示原因；其中只有「内容无效」计入冷却次数 |
| 判违规   | 恶意或违规内容，沿用既有违规处理                                                     | 与现有投稿违规一致，不额外计入纠错冷却                     |

通过之后只有用户提议的那几项被改写，条目其余内容一律不动；条目内容即时更新，前台展示随之刷新，作者收到一条可以回到提案的通知。

两条保护：

- **旧内容不会盖掉新内容。** 审核时如果条目已被别人改过，界面会把变化的字段标出来，站方必须刷新后显式确认才能覆盖，不确认就不能通过；在旧界面上批准一份作者已经改动过的提案同样会被拒绝并要求刷新。目标条目在审核期间被删除时，提案不会被强行写入，站方按「目标已变」驳回，作者仍能回看自己提交过的内容。
- **同一轮审核只生效一次。** 同一份提案被多名管理员同时处理时只生效一次、只发一条通知；同一条目上另有提案、或站方刚做过编辑时，基于旧内容的那一次审核会被要求刷新后重新确认。站方在后台的正常编辑不受纠错影响。

### 2.6 封面替换如何落地

换封面的提案里，作者上传的新图在提案页就能预览，旁边是条目现在的封面，一眼看出换成什么样；上传与预览沿用既有投稿的方式，不另建一套素材流程。通过后新封面归线上条目，被替换下来的旧图按既有清理流程回收；提案被驳回、判违规，或作者最终取消了换封面这一项，已上传但没被采用的图片同样会被回收，不会长期占空间。仍在被条目使用的图片不会被清理掉。

### 2.7 入口衔接与不受理的问题

- 条目页反馈里的「条目信息错误」改为提交修正提案；工单里的同名类型也不进人工队列，界面直接引导转为纠错（基线原文）。
- 运行、下载、解压、链接失效、发错条目等问题都不走纠错，仍按各自入口（工单、失效报告、求助区）处理；纠错页只处理条目信息本身。
- 会社、开发商、社团的错误由会社独立线处理，纠错不接这类提案，相关引导与文案保持现状。
- 后台审阅页最终放在控制台哪个位置随模块 01 定稿（未决事项 D2），功能与规则不受影响。

## 4. 依赖与上线批次

设计上依赖两处：模块 01 提供后台审核界面载体与统一队列，模块 05 提供条目页的问题分流入口，08 只把其中的「条目信息错误」换成真实提案入口，沿用 05 定下的分流常量与对话框，不新建入口。排期上按总计划第 3.1 节仍排在模块 07 之后，作为独立一批发布，最小范围是提交、差异审核、冲突检查、写入条目和通知全部可用。纠错并入现有「待审投稿」这一来源，只多一个类型标记与目标条目回链，不新增第五个来源、不另建主队列；会社字段继续由独立线处理，不阻塞本批。

## 6. 风险

- **覆盖他人编辑**：提案在审核期间条目被改动。已用基点比对与显式确认拦住，风险是站方图快忽略提示；界面把「已变化」做成必须勾选才能通过。
- **入口被滥用**：零押金意味着灌水成本低。靠未结上限与无效冷却控制，不引入押金。
- **封面素材归属**：通过后素材归线上条目，驳回后素材才清理。沿用既有清理机制，不新建资产系统。
- **与模块 05 的交接**：入口切换点以 05 交付的分流常量与对话框为准，08 只替换其中的条目信息错误分支；这是排期依赖，不是设计分歧。

| 编号   | 要证明的业务结论                                                                                                                                                                                                                                                                                                                                                                           |

| E08-01 | 提交纠错不动任何萌萌点、不占用新建投稿的名额；同一用户在同一条目只能有一条未结、每人合计最多三条，不同用户互不挤占；30 天内第三次无效驳回起冷却满 30 天且不提前解除；重复提交不会产生两条提案，重放的请求也不会落到别的条目                                                                                                                                                                |

| E08-03 | 三列里的外部数据来源与取数时间可辨认、取不到时可正常审核；对当前用户不可见或已删除的条目不能被拿来提交提案，别人的提案也读不到；换封面后条目显示新图，仍在服务的图片不被清理，没被采用的上传图片会被回收；通过后条目页与列表正常刷新，缓存清理失败只记录并按既有过期时间恢复、不回滚已写入的修正；作者能从通知与自己的列表回到提案；既有新条目投稿流程与后台待审队列的最老优先顺序未被破坏 |

三个实验都在隔离环境执行，不改动生产数据，也不用真实时间等待日期边界。

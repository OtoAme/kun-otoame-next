# 模块 08：条目纠错投稿（PM 视图）

状态：设计草稿，未实施。技术细节见配对的[实施计划](./08-entry-correction.md)；任务编号、上线批次与依赖见[总计划](./00-master-plan.md)第 3.3、4.9 节；产品规则见[基线](../7.operations-layer-redesign.md)第 6 节。

## 1. 目标与责任人

用户发现条目信息有错时，现在只能提交反馈、等站长手工改。本模块让登录用户直接提交「修正提案」，站方在一个页面对照条目当前值、用户提议值与外部数据源的值，确认后一键写回条目。目标是把条目纠错从「人工代改」变成「提案—审核—自动写入」，让站方只做判断、不做录入。

责任：站长审核全部提案；实施方交付提交、审阅、写入、通知与入口切换。费用与奖励不在本模块：纠错零押金、零奖励，按基线原文执行，不另开审批项。会社、开发商、社团数据仍归会社独立线，本模块不碰。

## 2. 用户流程

1. 用户在条目页的「遇到问题 → 条目信息错误」进入纠错页。
2. 可修正的只有六项：名称、别名、发售日、标签、介绍、封面。其余内容不开放给用户修改。
3. 提交不收押金，全部进入人工审核。提交时系统冻结「提交那一刻条目长什么样」，作为判断提案是否过期的基点。
4. 站方在后台看三列：当前值、提议值、外部数据。名称、别名、发售日、标签按外部数据裁决；介绍与封面是仅有的判断题。
5. 通过后条目立即更新，提交者收到通知并能回看自己的提案；驳回必须选理由，用户可看到原因。
6. 若审核期间条目已被别人改动，界面明确提示「已变化」，站方要么刷新后确认覆盖，要么退回提案，不允许用旧内容盖掉新内容。

## 3. 范围

| 本次交付                                                     | 不在本次                                       |
| ------------------------------------------------------------ | ---------------------------------------------- |
| 六个字段的提案、三列审阅、写入条目、通知                     | 会社/开发商/社团、外部 ID、官网、分级、截图    |
| 零押金；同一用户对同一条目 1 条、每人合计 3 条未结；无效冷却 | 纠错奖励点数、悬赏、批量纠错、自动采纳外部数据 |
| 条目信息错误入口切换到纠错，我的提案可回看                   | 旧反馈数据的归档与迁移（模块 09）              |

## 4. 依赖与上线批次

设计上依赖两处：模块 01 提供后台审核界面载体与统一队列，模块 05 提供条目页的问题分流入口，08 只把其中的「条目信息错误」换成真实提案入口，沿用 05 定下的分流常量与对话框，不新建入口。排期上按总计划第 3.1 节仍排在模块 07 之后，作为独立一批发布，最小范围是提交、差异审核、冲突检查、写入条目和通知全部可用。纠错并入现有「待审投稿」这一来源，只多一个类型标记与目标条目回链，不新增第五个来源、不另建主队列；会社字段继续由独立线处理，不阻塞本批。

## 6. 风险

- **覆盖他人编辑**：提案在审核期间条目被改动。已用基点比对与显式确认拦住，风险是站方图快忽略提示；界面把「已变化」做成必须勾选才能通过。
- **入口被滥用**：零押金意味着灌水成本低。靠未结上限与无效冷却控制，不引入押金。
- **封面素材归属**：通过后素材归线上条目，驳回后素材才清理。沿用既有清理机制，不新建资产系统。
- **与模块 05 的交接**：入口切换点以 05 交付的分流常量与对话框为准，08 只替换其中的条目信息错误分支；这是排期依赖，不是设计分歧。

## 8. 实验要证明什么（业务判据，均未执行）

| 编号   | 要证明的业务结论                                                                                                                                                                                                                                                                                                                                                                           |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| E08-01 | 提交纠错不动任何萌萌点、不占用新建投稿的名额；同一用户在同一条目只能有一条未结、每人合计最多三条，不同用户互不挤占；30 天内第三次无效驳回起冷却满 30 天且不提前解除；重复提交不会产生两条提案，重放的请求也不会落到别的条目                                                                                                                                                                |
| E08-02 | 通过后只有用户提议的字段被改写，会社与外部 ID 永远不被纠错改动；同一份提案被两人同时处理只有一个结果生效，同一条目的两份提案或站方编辑与审核交错时，基于新现值的一次可以生效、基于旧现值的一次被拦下，过期基点的纠错审核不会把旧值写回条目（站方后续正常编辑仍按既有语义生效）；管理员在旧界面上审核已被作者改动过的提案会被拒绝，不会批准自己没看过的内容；目标被删时不误写；驳回不扣点数 |
| E08-03 | 三列里的外部数据来源与取数时间可辨认、取不到时可正常审核；对当前用户不可见或已删除的条目不能被拿来提交提案，别人的提案也读不到；换封面后条目显示新图，仍在服务的图片不被清理，没被采用的上传图片会被回收；通过后条目页与列表正常刷新，缓存清理失败只记录并按既有过期时间恢复、不回滚已写入的修正；作者能从通知与自己的列表回到提案；既有新条目投稿流程与后台待审队列的最老优先顺序未被破坏 |

三个实验都在隔离环境执行，不改动生产数据，也不用真实时间等待日期边界。

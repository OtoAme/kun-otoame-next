# 模块 03：工单系统（项目经理视角）

状态：草稿，待站长审阅。实施细节见 [03-case-system.md](./03-case-system.md)，总计划见 [00-master-plan.md](./00-master-plan.md)，依据[运营层设计基线](../7.operations-layer-redesign.md)第 3 节。写作阶段未运行命令、未连数据库、未执行实验。

## 1 目标

把「无目标、无责任人、无到期的一行反馈」改成有目标对象、有归属方、有状态、有超时的事项：资源问题直达发布者，规则问题留给站方，用户看得到进度并收到结果。成效按资源类事务由发布者消化的比例、站方队列中确需站方处理的占比、首次回应时长判断（基线 1、2 节）。本模块只记录事实——其中包括每次结案的实际执行者是系统、发布者还是站方，否则「由发布者消化的比例」这一口径无法计算——指标展示属模块 09。

## 2 责任人

站长审定第 8 节未决项，上线后是唯一站方处理人；发布者在前台处理自己资源上的事项，不进后台，7 天不处理自动升级站方；站方对升级来的资源问题只做隐藏或忽略，不代为修复（基线 8.6）；实施方按第 6 节交付，验收由站长核对实际结果。

## 3 功能介绍与使用流程

本节写清本批上线后各角色实际能做什么。命名待 D4 定稿，本文对用户侧页面暂称「问题处理」，不代表已批准；界面不出现「工单」二字。

### 3.1 本批受理的问题类型与处理方

一个表单、多个入口，入口决定预填的对象与可选类型（基线 3.3、3.6）。

| 入口位置                                           | 用户看到的选项                       | 谁处理                                                                 | 处理方可给的结果                                                                                                                                                                                                        |
| -------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 资源卡片「报告问题」                               | 资源与描述不符（预填这条资源）       | 该资源的发布者；官方资源沿用现有前台判定（作者是站方管理员账号）归站方 | 发布者可给已修正、无法复现、不在受理范围；发布者超时后升级到站方，由站方给隐藏资源或忽略；报告者久不回应由系统给「开启者未回应」。官方资源从一开始就在站方队列，由站方自己处理，没有 7 天升级，也不会自动结案（见 3.5） |
| 条目页「反馈」                                     | 条目资料有误                         | 本批只给引导文案，不生成事项（模块 08 上线后改指纠错投稿）             | 无                                                                                                                                                                                                                      |
| 条目页「反馈」                                     | 资源发错条目（需选中本条目下的资源） | 站方                                                                   | 已移动、不成立                                                                                                                                                                                                          |
| 条目页「反馈」                                     | 其他                                 | 站方                                                                   | 已处理、不在受理范围                                                                                                                                                                                                    |
| 评论、评价、小喇叭旁，以及用户资料页新增的「举报」 | 违规举报                             | 站方                                                                   | 已处理、不成立                                                                                                                                                                                                          |

每个入口内附一句话，说明这类问题由谁处理、预计多久第一次回应，沿用基线 8.6 已定稿口径，不另开规则页。选中的资源如果刚被移动到别的条目，提交会被拦下并提示刷新，避免把问题挂到错误条目上。

### 3.2 报告者：提交、合并为关注、查看进度

填写现象即可提交，不需要选择责任人：谁处理由系统按对象判定，用户改不了。

如果同一个对象上已经有一条同类型的未结事项，系统不再新建第二条，而是把这位用户登记为关注者，界面直接告知已有多少人报告、当前谁在处理。刚好碰上那条事项结案的瞬间，会提示「刚刚结案，可以重新提交」，重新提交就会新开一条，不会把人挂在已结案的事项上。

提交后可在「问题处理」页跟进，页面分三个页签：我提交的、待我处理、我关注的。收到处理方回复后可以继续补充说明（纯文字，本批不做附件上传）；结案时会收到通知，通知点开直达这条事项的详情，不再像现在那样跳回首页。

为防刷，同一用户对同一条资源、归属发布者的问题每天最多提交 1 条；违规举报不受这个上限约束，靠同对象同类型的合并压重复量。

### 3.3 多轮补充、通知与自动时限

事项在「等待处理方」和「等待报告者」之间往复，双方都能看到当前轮到谁。报告者在轮到处理方时继续追加说明，不会把处理方的时限往后推。每一轮动作都会通知下一位该处理的人，升级时发布者与报告者都会收到通知；关注者不参与中间过程，只在结案时收到一次通知。

| 情形                                                 | 时限              | 结果                                                                               |
| ---------------------------------------------------- | ----------------- | ---------------------------------------------------------------------------------- |
| 归属发布者的资源问题，发布者一直不处理               | 7 天              | 升级到站方；发布者与报告者都收到通知                                               |
| 归属发布者的资源问题，发布者已回复而报告者不再回应   | 14 天             | 自动结案，结论为「开启者未回应」                                                   |
| 站方队列里的事项，无论一开始就归站方还是升级后归站方 | 不自动结案        | 只按等待时长排队；是否给站方事项也加同样的等待上限属 D5，尚未定                    |
| 报告者对结果不满                                     | 结案后 7 天内一次 | 事项回到待处理并通知处理方；若该对象此时已有新的未结事项，会提示去那一条，不重复开 |

### 3.4 发布者：在自己的页面处理自己的资源

发布者不进后台。自己资源上的问题出现在「问题处理」页的「待我处理」里，有新问题时会收到通知；可以逐条查看现象、回复、请求补充材料，或选择结论结案。为省事提供四条快捷回复：已修复、需要截图、请参考指南、不在受理范围（基线 3.7）。

发布者只能看到和处理自己资源上的事项；能读到报告者填写的现象正文，但看不到报告者是谁。放着 7 天不处理，事项会转给站方，届时站方只能隐藏资源或忽略，不会代为修文件或改描述，因此拖延对发布者本人不利。

### 3.5 站方：统一收件箱与可用裁决

属于站方的事项进入模块 01 的统一收件箱，等待最久的排在最前，且最老一条一定看得到，不会因为分页或截断被永远挤掉。站方在详情里可以回复（同样可用上面四条快捷回复）、结案，并按类型使用对应动作：

- 升级上来的资源问题：只有隐藏资源与忽略两个动作。隐藏后该资源在前台不再出现，发布者收到通知；发布者修正后，由造成这次隐藏的那条事项恢复，且只能恢复一次；其他事项或其他原因造成的隐藏不能用它来恢复。
- 资源发错条目：站方可把资源直接移动到正确条目并以「已移动」结案，两侧条目的资源信息同步更新；资源与其链接的身份不变，用户此前拿到的下载授权不受影响。判定不成立时以「不成立」结案。
- 违规举报：以「已处理」结案必须伴随一次真实处置——删除被举报的评论或评价、小喇叭按模块 02 既有的处置方式、目标是用户时先在既有用户管理入口完成处置（门槛不变）再回事项登记结论；以「不成立」结案只需写明理由，不删除任何内容。被举报的内容在站方动手前已被删除时，事项仍可正常结案并记下「目标已不存在」，不需要多删一次。
- 其他与目标已删除的事项：详情会显示「目标已删除」而不是报错，站方仍可结案。

隐藏与忽略这对快捷裁决是给升级上来的他人资源问题用的。站方自己名下的官方资源被报「与描述不符」时，直接用现有的资源管理入口改正内容，再回事项里以已修正、无法复现或不在受理范围结案，不走升级这条路。

站方也可以不等 7 天就直接介入某条仍归发布者的事项（这类事项不占站方收件箱，只能从详情进入）。此时归属不变，系统会记下这次实际是站方处理的，供日后统计「哪些事务真的由发布者消化」。

### 3.6 谁能看到什么

事项详情一律按身份开放：报告者本人始终能看到自己那条的全部往来，当前处理方能看到现象正文与对话，管理员在后台能看到完整内容；无关的登录用户与访客一概打不开详情，也搜不到。

公开的只是资源卡片上的那一小块徽标：显示「已有 N 人报告，发布者处理中」或「站方处理中」，只给人数和当前处理方，不带现象正文、不带报告者身份、不带任何下载信息。资源类问题「公开」指的就是这个徽标，不是把内容公开。

违规举报比资源问题更严：被举报人看不到、也不会收到通知。关注者在结论出来前只看到自己已提交过，结案时收到一次通知；关注者具体能看到多少细节以站长审定的 D4 口径为准，未审定前按最保守口径执行（只发结案通知，不开放详情）。

### 3.7 旧入口过渡与暂未开放的去向

条目页反馈、评论举报、评价举报、小喇叭举报四个旧入口在本批一起切到新系统，切换后旧队列不再新增。旧的反馈与举报记录仍然可查，历史通知里的链接仍然点得开；模块 02 上线后已经产生、尚未处理的举报继续按原来的方式处理完，直到模块 09 统一归档退役，不做数据搬迁。小喇叭原有的举报达阈值自动隐藏、误判后恢复与退款规则照旧生效，只是改由事项承载：达阈值只会先把内容隐藏，事项仍留在站方队列等人处置。

以下能力本批不开放，入口内只显示当前实际可去的地方，不承诺上线时间：链接疑似失效与链接争议（模块 04）、资源卡片上的完整现象分流与资源违规举报（模块 05）、发布者申请下架与镜像版本确认（模块 06）、求助区、求助与回答的举报、工单与求助互转（模块 07）、条目资料修正（模块 08）。这些类型的处理方与归属按各模块已定的契约先冻结好，将来由对应模块直接接上，不会临时降级成「其他」而改掉归属和时限；其中仍有未决项（例如站方事项的等待上限 D5、链接类报告资格与记录方式 D6、模块 06 合并后的对象引用与统计口径 D7）由对应模块定稿，本批不代为承诺。

## 4 范围

交付：事项模型与状态规则；提交、查看、补充、重开；去重与关注；发布者面板；站方处理、升级裁决与资源隐藏/恢复；「资源发错条目」的站方移动动作；违规举报的真实处置动作；结案与升级通知直达详情；两个超时任务；资源卡片公开徽标；条目页反馈、评论举报、评价举报、小喇叭举报四个旧入口切换，并按基线补上最小的用户举报入口。官方资源沿用现有前台口径（作者角色大于 2）归站方，普通资源归发布者。小喇叭的阈值自动隐藏、误判恢复与退款沿用模块 02 的规则，只把载体换成事项。

不做：链接类事项与失效报告（04）、资源卡片完整现象分流与资源违规举报入口（05）、下架与镜像确认（06）、求助区、求助举报与互转（07）、条目资料修正（08）、旧数据归档与指标看板（09）。上述类型的归属与时限本批已冻结成契约，后续模块直接接入，不降级成「其他」。未上线能力在入口内显示当前实际去向。

## 5 依赖与上线批次

依赖模块 01 的后台收件箱与模块 02 的小喇叭举报写入端。顺序 01→02→03 不变，03 独立成批发布。上线必须成套：提交/查看/补充、发布者处理、站方处理与升级裁决、通知、两个超时任务、四个旧入口切换，且旧记录与历史通知链接仍可用。模块 04、06、07 后续通过本模块冻结的内部接入边界开启与结案，不另开写入口。

## 7 验收

1. 一条资源问题从提交、回复、补充到结案通知，全程不需站长介入。
2. 发布者放置 7 天的事项自动进入站方收件箱，站方用隐藏或忽略即可结案，发布者收到通知。
3. 多人报告同一现象只产生一条事项，卡片显示人数与当前处理方，结案时全部收到通知。
4. 站方收件箱最老一条一定可见，不因分页或截断被挤掉。
5. 关注者、被举报人、无关登录用户、访客对同一条私有事项的可见内容符合审定口径。
6. 切换后旧反馈与旧举报队列零新增，旧记录与历史链接可访问，切换前已存在的待处理举报仍按原方式处理到模块 09 归档为止；上线前完成 E03-01 至 E03-04 并留存证据，上线后站长实际处理一轮。

## 9 实验要证明什么

四项实验均在隔离环境执行，状态全部为未执行，执行与文档审阅分开记录。

- E03-01：归属与公开性只由服务端按目标推导（现有口径下的官方资源归站方，其余归资源发布者），客户端传入不生效；每种目标都校验存在与可见，页面上下文与目标当前所属条目不一致时拒收；各身份看到的内容符合审定矩阵；徽标只给数量与处理方；移动与恢复只有站方能做，移动后两侧条目数据一致且不改资源与链接身份，恢复只对本事项造成且仍有效的隐藏生效。
- E03-02：同目标同类型在并发下只有一条未结事项，后来者成为关注者且不重复；每人每资源每天一条在并发与跨日边界成立；重开只允许一次，撞上新事项时给出明确去向。
- E03-03：两个超时按状态进入时间触发，站方事项不被自动结案；用户操作与自动任务同时发生只有一个结果、一次通知；隐藏与移动整体成功或整体不生效；隐藏、忽略、移动、内容处置都走同一条结案路径并通知关注者；小喇叭阈值只触发隐藏、不触发结案。
- E03-04：四个旧入口切换后旧队列零新增、旧记录与旧处理日志仍可查；新增的用户举报入口可用；未开放类型（链接、镜像、资源违规、求助举报）无法通过接口创建也不会被降级成「其他」；未上线模块的选项显示当前去向。

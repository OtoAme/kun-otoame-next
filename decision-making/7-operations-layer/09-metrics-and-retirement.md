## 3. 术语

| 术语         | 定义                                                                               |
| ------------ | ---------------------------------------------------------------------------------- |
| 队列         | 一个需要站方或归属方处理的待办集合，有明确的「进入时间」和「处理完成时间」两个事实 |
| 积压         | 当前处于未处理状态的项数；最长等待 = 现在减去最老一项的进入时间                    |
| 处理完成时间 | 该项离开队列的时间戳，来源逐队列列在 4.1                                           |
| 点位型指标   | 只能表示「某一时刻的值」的指标（积压、最长等待、计数、比率），历史值需要快照       |
| 窗口型指标   | 由窗口内的完成事件算出的指标（中位处理时长、周趋势），可随时从源表重算             |
| 起算时间     | 某指标最早可靠记录的日期；之前一律显示为空，不显示 0                               |
| 自动处理占比 | 机制层与责任层消化的事务占全部事务的比例，分类见 4.4                               |
| 归档         | 旧反馈、旧举报保持原表原行、只读可查，不再接收新事项                               |
| 逐路由重定向 | 每条旧后台路径映射到一个具体的可用目标，而不是统一跳转                             |

### 4.2 拟新增

`prisma/schema/ops-metric.prisma`（拟新增）：

| 字段                        | 类型与约束                                                                                                                                                       |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                        | `Int @id @default(autoincrement())`                                                                                                                              |
| `metric_key`                | `String @db.VarChar(64)`，如 `backlog_count`、`oldest_wait_seconds`、`auto_handled_ratio`                                                                        |
| `scope`                     | `String @default("") @db.VarChar(64)`，队列或类型标识，全站项为空串                                                                                              |
| `stat_date`                 | `DateTime @db.Date`，由同一次采样时刻按 Asia/Shanghai 自然日推出                                                                                                 |
| `sampled_at`                | `DateTime`，本次运行的采样时刻，整批指标共用一个值。语义是「这批数字来自该时刻开始的一次运行」；各来源分次查询，不承诺数据库同一瞬间的一致快照，也不为此开长事务 |
| `numerator` / `denominator` | `Int` / `Int?`，比率存分子分母，不存浮点结果；秒类指标（最长等待）取整数秒、向下取整                                                                             |
| 约束                        | `@@unique([metric_key, scope, stat_date])`、`@@index([metric_key, stat_date])`                                                                                   |

一行一个数字而不是 JSON，理由是口径要能被 SQL 复核。只保存基线要求、且事后无法从业务事实重算的点位型指标（各队列积压与最长等待、镜像与官方健康计数、已丢失资源数、两项比率的分子分母）；窗口型指标不入表。

`admin_log.queue_entered_at DateTime?` 由 06 首次交付（可空），本模块复用同一列、不再新建，只补上审核类动作的写入值：`submission_review` 与 `correction_review` 用 `COALESCE(submitted_at, created)`，`resource_apply_approve` 与 `resource_apply_decline` 用资源行 `created`，`creator_review` 用申请消息的 `created`（5.4）。历史行保持为空、不回填，各队列中位时长的起算日期即对应写入的上线日。因此本模块对数据库的新增只有 4.2 的快照表一张。

### 4.3 明确不新增

不建通用事件表、队列注册表、指标中间层、告警表；不给 `user_message`、`patch_report` 加列；不在 `patch_resource` 上加审核时间字段（它解决不了被删除的拒绝项）；`admin_log` 复用 06 已交付的 `queue_entered_at`，本模块不加新列；不新增依赖或基础设施。

## 5. 接口、校验、权限、幂等

### 5.1 新增读接口（拟新增 `app/api/admin/metrics/`）

- `GET /api/admin/metrics`：`role >= 3`；query `window` 默认 30、范围 1–90（校验 schema 拟新增到 `validations/admin.ts`）。`window` 就是全局窗口 W：中位处理时长、周趋势与两项比率都按选定的 W 取数，4.4 表里的「近 30 天」即 W 的默认值，不存在第二套固定窗口；快照只按默认 W 每日写一次，改 W 只影响即时查询。无人回答率不另写实现：07 已在它规划的后台概览接口里给出这个数字与分子分母，09 把 W 作为该查询的窗口参数复用同一个函数（07 概览自身固定用默认 30），两处必须是同一份代码，不复制第二套 SQL，也不为该复用另建接口或存储；完整指标页与统一快照仍按本计划交付。返回各队列的积压、最长等待秒数、中位处理时长（无来源时为 `null`）、镜像与健康计数、两项比率的分子分母、每项的 `startedAt` 与 `source`；响应头 `private, no-store`。
- `GET /api/admin/metrics/history`：`role >= 3`；query `metric`（枚举）、`scope`、`from`、`to`，跨度上限 180 天；只读快照表，缺失日期返回 `null` 而不是 0。
- 复用现有 [stats](../../app/api/admin/stats/route.ts) 与 [sum](../../app/api/admin/stats/sum/route.ts) 作为内容增长小节，不重写口径；两者现状拒绝 `role < 4`，统计与日志的门槛在 01 核心交付中不动；页面早迁时由承接任务落实 5.3 的矩阵，未早迁则在本模块把这两个只读接口定为 `>= 3`，统计口径本身不改。
- 指标接口只读，不进公开缓存白名单，不写库、不发系统通知。

### 5.2 归档与旧端关闭的最小扩展

- 旧反馈：`getFeedback` 现无 `status` 过滤且按 `created desc`。新增可选参数 `status: 'all' | 'pending' | 'handled'`（默认 `all`），只加 where 分支，保持现有调用与 01 收件箱行为不变。

### 5.4 幂等与事务

- 快照：整批指标共用一个 `sampled_at`，在一个事务里按 `(metric_key, scope, stat_date)` 写入；已有行时只在新 `sampled_at` 更晚时覆盖（条件更新），晚提交的旧采样不能覆盖更新的值，也不累加。[withTaskLock](../../server/tasks/withTaskLock.ts) 无续租，正确性由唯一键与该条件更新保证，不靠锁。
- `queue_entered_at` 由各主审核服务在已有事务内随审计行一起写入（资源申请见 [resource-apply/service.ts](../../app/api/admin/resource-apply/service.ts) 的 `admin_log.create`），不新增事务、通知或缓存调用。审计行不可变，重复请求由各模块既有的状态条件拦截，不会产生第二条完成事件。
- 新条目与纠错投稿走同一条审核服务，只有 `submission_review` 一个类型时两类历史时长无法区分。08 已接 `correction_review`：新条目仍写 `submission_review`（01 的口径不变），`kind = correction` 写 `correction_review`，仍是同一条主审计行，不加 kind 列、不建事件表；01 的今日已处理白名单与 `constants/admin.ts` 的中文标签也由 08 一并扩展。09 只消费这两个类型，不保留双归属。
- 创作者申请迁移时的必要修复（现状：[creator/service.ts](../../app/api/admin/creator/service.ts) 的 `approveCreator` 与 `declineCreator` 都先读后写，事务内对 `user_message` 无条件 `update`，`createMessage` 未传事务客户端，`user.update` 把 `role` 无条件 `set: 2`，日志写通用的 `approve`、`decline`，列表也不过滤 `status`）：两个动作都在同一个既有事务内先做条件更新——按 `id`、`type = 'apply'`、`recipient_id IS NULL`、`status IN (0, 1)` 抢占该消息，并校验发件人有效、同意动作携带的 `uid` 与 `sender_id` 一致；命中 0 行即返回既有提示，不改角色、不发通知、不写完成事件。胜出方发通知（这次传事务客户端）、写原有那一条日志并改为 `creator_review`。角色只在同意动作里改，且必须条件写而不是读后判断：`updateMany` 限定 `id = uid` 且 `role` 在可提升范围（现状即 `role = 1`）才置 2，命中 0 行就不改角色、不刷新会话，因此被其他管理员并发提升过的账号不会被落后的写降级；拒绝动作不碰任何角色。封禁与角色体系的其他部分不动。`creator_review` 的中文标签补进 `constants/admin.ts` 并接入 01 的今日已处理计数；早迁先交付条件审核、通知与角色保护、专用类型及今日计数，不提前依赖 `queue_entered_at`；06 交付该字段后，由 09 按 4.2 接齐创作者写入，早期无该值的日志不回填。队列实际由谁迁移，这条 CAS 与专用类型就由谁实现；09 不重复修复，只补尚未完成的写入与指标读取。修复只落在这条队列现有的两个服务上，不新建审核框架。
- 若 D9 选择迁移旧数据，脚本以来源表主键为幂等键，目标侧需要唯一约束；该约束属 03 的表，是跨模块前置，见第 12 节。

- **preflight（只读）**：旧反馈按 `status` 的分布与最早/最晚时间；`patch_report` 按 `status`、`target_type` 分布，含目标行已被置空的条数；`user_message.link` 以 `/admin` 开头的取值与条数；`patch_resource.status=2` 数量与最老一条；`patch_submission` pending 数量。输出留作发布记录。
- **sync**：只新增快照表。`admin_log.queue_entered_at` 由 06 交付，09 只补写入值，因此本模块对既有表没有 schema 变更；上线顺序上 09 在 06 之后，若该列尚未上线，先补齐 06 的迁移再发本模块。先在隔离库演练，生产按 preflight → sync → postflight 再执行部署安全检查；`pnpm prisma:deploy-safe` 前置含可写兼容迁移，不是只读检查（见[总计划](./00-master-plan.md)第 7 节与 [checkPrismaProductionSchema.ts](../../scripts/checkPrismaProductionSchema.ts)）。文档阶段不运行这些命令。
- **回填**：不回填 `queue_entered_at`，不回填快照历史；各队列中位时长的起算日期即对应写入的上线日，首次镜像另受 06 的 `cutoverAt` 约束，创作者队列从 `creator_review` 开始同时写入 `queue_entered_at` 起算；旧反馈队列退役后停止统计。
- **发布 A（能力）**：快照表、字段、任务、指标页、剩余迁移页面、归档页；尚未退役的旧页面保持可访问，已早迁页面沿用已验证的目标。
- **发布 B（退役）**：在一个维护窗口内按顺序执行——停止待退役旧处理端写入 → 最终盘点（复跑 preflight 并与 A 时基线比对）→ 归档校验 → 关闭或删除旧处理端与页面 → 启用逐路由重定向。前置是 A 稳定使用一轮、归档可读、历史通知抽样可达，不以旧队列未处理数为 0 作为前置。
- **回退边界**：B 的回退只恢复旧页面的可达性并移除重定向，同时保留 03 对旧创建端的关闭与本模块归档的只读守卫，不得顺手重启旧的新建或处理链路；A 的回退是停任务、保留表与字段，不删除已写入的快照。生产已写入数据后不盲目退旧代码；旧表不物理删除，归档随时可查。

## 9. 测试与实验方案

三个实验状态均为**未执行**。并发与日期边界用测试层屏障与注入的 `now`/假时钟，不改机器时间，不加生产延迟开关。

### E09-01 指标定义、时间窗口、去重与历史起算

- **目的**：证明口径表每项的分子/分母、状态过滤与窗口正确；重开、合并、自动结案不重复计入；无历史项显示起算时间；快照重跑幂等。
- **前提与隔离**：隔离测试数据库（独立 schema），不连生产；03、04、06、07、08 的字段已定稿。
- **样本与步骤**：工单——同目标重开一次（重开后仍未结）、合并入另一条、系统超时结案、升级站方后结案各一条；投稿——审核时间跨 30 天边界（第 30 天整点及其前后一秒），并含一条退回后重投再通过的；资源审核——一条通过、一条拒绝（资源行已删除）；举报——`handled_at` 有与无；求助——零回答、仅提问者自答、只有系统回贴、回答被隐藏、有他人可见回答；链接——官方 `suspect`/`disputed`/`broken` 各一条，全部 `broken` 且无官方链接的资源，以及一条零链接资源；镜像——仅对象存储的资源与 user 加对象存储混合的资源各一条；快照——同日连跑两次、跨日一次、人为缺一天、一次「旧采样晚提交」与一次跨午夜启动的运行；另造一个完成事件数为偶数的队列、一个窗口内没有有效结案工单也没有新建求助的零分母窗口，以及一条含 `storage = user` 链接的资料集资源；镜像样本按三条队列各自的规则造：完成行上没有 `queue_entered_at` 的旧记录、切换时在队且切换后完成的、切换后新入队并完成的、首次队列退队后再次入队的、同一资源重做两轮各带自己那次 `capturedAt` 的、一条人工重新配对后仍保留原 `created` 的候选，以及一条 `resolved_at` 非空的候选；求助侧另造一条被隐藏的求助与一条锚定对象已不可公开的求助，并保留已有的「有他人可见回答」正例。
- **通过判据**：每项等于夹具的期望值表；重开后未结的工单不计入已结，`merged` 项不单独计数；退回重投产生两条完成事件、各按自己的进入时间算时长；拒绝项计入时长；零链接资源不计入已丢失，仅对象存储的资源不计入未镜像；系统回贴与被隐藏回答不算回答；窗口为 `[now-30d, now)`，周边界为 Asia/Shanghai 周一 0 点；空队列积压为 0，最长等待与无样本的中位数为 `null` 且带起算日期；偶数样本的中位数等于两中点均值；零分母窗口的比率为 `null` 且分子分母都返回，同一队列的积压仍是 0；含 user 链接的资料集计入首次镜像队列、仅对象存储的资源不计入，未镜像比率的分母是有 user 链接且未下架的 `status = 0` 资源、被候选暂缓的资源仍在分子里但单列；镜像时长等于完成审计行的 `created` 减同一行的 `queue_entered_at`，只有该值为空的行被排除，切换时在队的项按 `cutoverAt` 起算并带「自可观测起点」标注，再入队重设只发生在首次队列、重新配对的候选仍用原 `created`，`resolved_at` 非空的候选不在积压里；官方链接健康待办的时长取自对应工单行的 `queue_entered_at` 与 `closed_at`，不从 `health_changed_at` 反推；无人回答率与 07 后台概览在同一窗口下给出同一个数字与同一对分子分母，被隐藏的求助与锚定对象不可公开的求助都不入分母；工单等待时长用 `ops_case.queue_entered_at`、分层用结案 `actor_type`；同日两次快照只有一行、值等于较新采样，晚提交的旧采样不覆盖新值；缺失日期返回 `null`。
- **失败判据**：任何重复计数、把 `merged` 或重开算两次、无历史显示 0、空队列显示 `null` 或空样本显示 0；快照重复行、旧采样覆盖新采样、一次跨午夜运行写出两个日期、窗口边界左右漂移；用 `status_changed_at` 代替工单队列起点、用开启来源反推结案执行者、用资源 `created` 代替重做起点、把切换时在队的项整批排除或反过来当成完整历史等待、从 `health_changed_at` 反推官方健康待办的历史时长、无人回答率与 07 概览给出两个不同的数字。
- **验证时间点**：来源模块上线且聚合服务实现后、指标页发布前。
- **证据与清理**：夹具与期望值表、聚合输出、快照两次运行的行、单测报告；回收隔离 schema，复位假时钟。
- **归此编号的单测**：口径纯函数（窗口、中位数、比率分类）、快照 upsert 幂等、两个新接口的鉴权与参数校验（沿用 [admin-stickers-route.test.ts](../../tests/unit/api/admin-stickers-route.test.ts) 的 mock 方式）。

### E09-02 旧记录归档和全部后台路径迁移

- **目的**：证明旧反馈与旧举报按审定方案（D9）归档后可读、可重复执行、重复可识别，未结项与全部举报目标类型都不漏；旧写入端已关闭；18 条旧路径逐条有可用目标且筛选与详情编号不丢；各类动作的权限与审定矩阵一致。
- **前提与隔离**：隔离库导入生产结构并构造样本（已处理与未处理反馈、三种状态举报、`link` 指向 `/admin/feedback` 的历史通知）；不在生产执行迁移脚本。
- **样本与步骤**：跑 preflight 记录基线 → 执行审定方案两次 → 比对数量与幂等键 → 18 条旧路径各访问一次（含 `?page=2`、搜索参数与 `[id]` 深链），用真实 Next 路由冒烟而不是断言静态表 → 按权限类别各取一个代表动作（`>= 3` 的常规管理、`>= 4` 的删除条目、`>= 4` 的用户封禁与站点设置、若保留的旧反馈处理端），每个用不足与足够的角色各调一次 → 归档查询覆盖未结与已处理、评论与评价与 02 扩展的目标类型、目标行已被置空的行 → 创作者队列按 5.4 造四组：两名管理员在测试层屏障下同时处理同一条申请；对一条已被同意过、当事人现为管理员的旧申请再点一次同意（验证消息 CAS 命中 0 行）；一条仍是 `status IN (0, 1)` 但当事人已经是管理员的申请（验证角色条件写不降级）；先读取该申请、期间由另一动作把当事人提升，再提交同意（验证落后的写不覆盖）；另各跑一次拒绝，确认拒绝不改任何角色 → 抽样 20 条历史通知点击。
- **通过判据**：二次执行不新增行；归档页能按状态、时间、目标类型查到未结与已处理项，目标已删除的行仍显示理由、处理人与结论且正文标为不可恢复；旧创建端与处理端按 5.2 与 D9 的选择关闭或保留；每条旧路径到达可用页面或归档且参数与 ID 保留，伪造的来源或 ID 回落默认列表；权限结果与 5.3 的审定矩阵逐条一致；D9 若保留存量处理，该动作能在控制台完成且仍要求 `>= 4`，旧页面照常退役、旧接口保留，只有站长决定延期时才把那一个旧页面排除在退役之外；创作者队列的并发只产生一次状态变更、一次通知与一条完成事件，未处理但当事人已是管理员的申请被同意后角色与会话都不变，落后提交的写不降级，拒绝动作不改任何角色；历史通知全部可达。
- **失败判据**：重复迁移无法识别、旧写入端仍能新增运营事项、任何旧路径 404 或落到空收件箱、权限与审定矩阵不一致（放宽或误收紧都算失败）、归档漏掉未结项或某类举报目标、用旧内容伪造已删除的正文、创作者申请的任何路径把已有管理员降级、拒绝动作改动角色、或重复发通知。
- **验证时间点**：发布 A 之后、发布 B 之前；发布 B 后复跑路径矩阵一次。
- **证据与清理**：preflight/postflight 输出、路径矩阵表、权限矩阵表、通知抽样记录；回收隔离库，工作区不留样本数据。
- **归此编号的单测**：归档查询的状态与目标类型分支、深链参数的来源与 ID 校验、迁移页面接口的角色校验。静态重定向表不写只镜像实现的纯函数测试，由上面的路由冒烟覆盖。

### E09-03 停用页、部署验证与退役恢复

- **目的**：证明 schema 变更与两次发布按生产流程可安全执行与回退；1Panel 停用页在停用时可见、恢复后站点正常。
- **前提与隔离**：隔离环境完成含生产构建的部署演练；停用页优先在测试站点演练，在生产演练时必须放进有预告的维护窗口。1Panel 自定义停用页的配置入口按实施时的面板版本核实，本文不假定按钮位置。
- **步骤**：preflight → sync → postflight → 部署安全检查与构建 → 冒烟（指标页、归档页、迁移页面、旧路径重定向）→ 按第 8 节顺序执行退役 → 模拟回退（移除重定向、恢复旧页面可达性，确认旧创建端与旧处理端仍关闭、归档仍只读，且旧代码在新表新字段存在时正常）→ 面板演练：先发重要级官方小喇叭（02 能力）→ 到前台确认横幅可见 → 停用站点 → 访问核对五要素 → 恢复站点 → 再访问一次 → 更新或结束该条重要公告。
- **通过判据**：迁移可重复执行且 postflight 与 preflight 的差异可解释；构建与冒烟通过；回退后旧页面可达但旧新建与旧处理链路仍关闭，已写入数据不影响旧代码；停用页含状态、预计恢复、Telegram、邮箱与数据保留说明；恢复站点后横幅正常且该条重要公告已更新或结束；维护清单在 [deployment.md](../../docs/project/deployment.md) 更新。
- **失败判据**：sync 需要人工修补、回退需要删除已写入数据或重开了旧处理链路、停用页缺任一要素或恢复后仍显示、恢复后公告仍停留在维护中、重定向导致已登录用户循环跳转。
- **验证时间点**：发布 A 前完成迁移与构建演练；发布 B 前完成重定向与回退演练；停用页在最近一次计划维护中演练。
- **证据与清理**：演练输出与截图、冒烟清单、回退记录、停用页截图；销毁隔离环境，测试站点恢复启用。
- **归此编号的检查**：cron 注册测试更新；现有部署命令契约测试随 schema 变更复跑；按仓库测试约定，schema 变更跑全量测试并执行一次生产构建。

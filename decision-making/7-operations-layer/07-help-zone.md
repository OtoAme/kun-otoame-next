## 3. 用户流程、参数与账务口径

完整说明见 [PM 用户流程](./07-help-zone-pm.md#先看三个用户流程)，此处列同一候选包的实现口径。**全部新增参数待 D8 批准**，包括旧稿出现过的时长与阈值；现有资源门槛与贡献奖是源码事实，不属本次重新定价。

| 参数／分支                       | 候选整包                                                                                                               |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 发布／系统奖                     | 发布费 5 点不退；每帖一次系统奖 3 点，首个合格采纳或社区验证事件领取                                                   |
| 悬赏                             | 总额 10～50 点；支付 `min(floor(总额×90%), 总额−1)`，差额销毁；按总额取整                                              |
| 发帖、系统奖、悬赏、有效票日限额 | 上海自然日分别为每人 3 帖、3 次系统奖、新增预留毛额 50 点、10 票；重复请求不计，释放／撤回不退毛额额度                 |
| 点数资格                         | 提问者与收款回答者均注册满 7 天且账号存在；不合格或回答者注销只给采纳标记且释放 held；当日系统奖满额不妨碍合格悬赏结算 |
| 社区验证                         | 投票人满 7 天、非回答作者、每回答一次；3 票、帖满 7 天且未采纳；只标记及可能发系统奖，不解决帖子、不付悬赏             |
| 关闭／桥接                       | 未解决帖无他人新回答或首次“我也遇到了”满 14 天关闭；3 名不同他人的“我也遇到了”触发资源事项桥接                         |
| 首页                             | 作者满 3 天，仅限制首页求助／评论聚合，不限制普通列表或详情                                                            |
| 举报隐藏                         | 每目标每处置轮 3 名注册满 7 天的不同举报人，排除目标作者；提交时判资格，不后补；恢复开新轮，旧票不再触发，需主动重报   |
| 事项转求助                       | 两侧都不收发布费、不占原开启者发布额、不发求助系统奖；初始无悬赏；原提问者日后可自愿设置悬赏                           |
| 释放／撤回后                     | 不再新设或追加预留；释放后迟到采纳可确认直付，撤回后永不复活                                                           |
| 资源贡献账                       | 保持现行创建发奖与拒绝／删除行为，接受分账净发出                                                                       |

理由：5／3 让普通问答净回收 2 点；小额悬赏和毛额日限额限制转移规模；7 天点数／投票资格与 3 天首页门槛使新人仍可提问回答；14 天给低活跃社区留等待时间；3 名举报人是低流量治理候选，暂时隐藏仍需站方复核。07 的举报轮次不复用 04 链接版本／投票轮次，不引入通用投票平台。

**余额例 A：小雨提问、小岚回答。** 双方合格，均无其他预留，记作“总额／预留／可用”。

| 步骤          | 小雨        | 小岚      | 求助账                               |
| ------------- | ----------- | --------- | ------------------------------------ |
| 初始          | 100／0／100 | 20／0／20 | 0                                    |
| 发布、悬赏 20 | 95／20／75  | 20／0／20 | 扣发布费 5，预留 20                  |
| 普通回答      | 95／20／75  | 20／0／20 | 不动                                 |
| 采纳          | 75／0／75   | 41／0／41 | 扣悬赏 20，付 18，发系统奖 3，销毁 2 |
| 重放          | 75／0／75   | 41／0／41 | 不动                                 |

总额 120 → 116，净回收 `5−3+2=4`。无悬赏时最终分别为 95／0／95、23／0／23，净回收 2。由其他回答先获社区奖时，采纳小岚只支付 18，不能再给第二份 3 点。

从发布后另走关闭／隐藏分支：小雨回到 95／0／95，小岚仍 20／0／20；恢复／重开不再预留。可用余额充足并明确确认迟到采纳，最终仍为 75／0／75 与 41／0／41；若释放后另花掉 80，小雨剩 15／0／15，确认只采纳后仍剩 15，小岚得系统奖后 23，不部分扣悬赏。任一方点数资格不足时，采纳释放原有预留，小雨 95／0／95、小岚 20／0／20；只有系统奖日额已满时，悬赏照付，最终 75／0／75 与 38／0／38。撤回后即使关闭／隐藏再采纳也不扣悬赏。若小岚在采纳前注销，只留下回答，小雨确认只采纳后由 95／20／75 回到 95／0／95，悬赏转 unsettled，不向已不存在的账号发任何点数，也不占系统奖励次数；小岚注销前后的全站余额变化不混入本次求助结算例。

**余额例 B：小岚、小夏各提交一条资源回答。** 无悬赏，三人初始总额为小雨 100、小岚 20、小夏 20。发布扣费后小雨 95，两次创建贡献奖后小岚 23、小夏 23，采纳小岚后变为 26、23；总额 140 → 144，全部预留为零。

| 账本     | 收  | 发  | 系统净额 |
| -------- | --- | --- | -------- |
| 求助     | 5   | 3   | 回收 2   |
| 资源贡献 | 0   | 6   | 发出 6   |
| 合计     | 5   | 9   | 发出 4   |

单条资源回答净发出 1，N 条净发出 `3N−2`，前提是无悬赏且求助奖已发。待审创建已获贡献奖，通过不重发、拒绝不回收；普通删除另按现行规则回退。隐藏、判违规不追溯撤销已完成的求助奖励／悬赏。

**余额例 C：事项转换。** 原开启者小雨 100／0／100、当天已发 3 条，处理方转换后两项均不变；转换不受原开启者可用余额／当日发帖额度限制。采纳不发求助系统奖。小雨日后主动设置 20 点悬赏才预留成 100／20／80，合格采纳后为 80／0／80，回答者若从 20 起则得 18 后为 38／0／38；该帖仍无系统奖。

## 4. 数据模型

以下均为拟新增或拟修改，当前没有求助实体实现。新表集中于拟新增 `prisma/schema/help.prisma`，既有 [user](../../prisma/schema/user.prisma)、[patch](../../prisma/schema/patch.prisma)、[resource](../../prisma/schema/patch-resource.prisma)、[账务](../../prisma/schema/moemoepoint.prisma)补必要反向关系；不向 user 增加一组每日归零列。上海日界复用 [getShanghaiQuotaWindows](../../app/api/patch/resource/download/access/timeWindow.ts) 的 dailyStart／dailyResetAt，日键从同一窗口生成，不另写时区算法。

| 实体               | 必要字段与约束                                                                                                                                                                                                                                                                                                         |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `help_post`        | 作者、意图 `question/request`、求物种类 `entry_resource/external`、锚定类型及字段、标题正文、`open/solved/closed`、隐藏与举报处置轮、创建／更新时间、`last_activity_at`、`closed_at`、采纳回答及时间、奖励回答及原因、原帖、悬赏总额与状态、事项关联、单次桥接的来源／原提问者／操作者／锚定事实、来源事项、发布请求键 |
| `help_answer`      | 父帖、可空作者、`user/system`、正文、隐藏与举报处置轮、社区验证时间、请求键、结案事件键、可空资源引用、资源状态、创建／更新时间                                                                                                                                                                                        |
| `help_answer_vote` | 回答、用户、创建时间；回答＋用户唯一，禁止自投，资格在写入时检查                                                                                                                                                                                                                                                       |
| `help_me_too`      | 帖、用户、创建时间；帖＋用户唯一，排除提问者；兼作订阅事实                                                                                                                                                                                                                                                             |
| `help_bounty`      | 帖、顺序号、金额、客户端请求键、唯一 reservation 引用；帖＋请求键及帖＋顺序号分别唯一                                                                                                                                                                                                                                  |
| `help_daily_quota` | 用户＋上海自然日复合主键；发布次数、系统奖次数、新增预留毛额、有效票次数；在业务事务内条件累加                                                                                                                                                                                                                         |

关键约束：

- 发布按作者＋请求键唯一，回答按作者＋请求键唯一；命中还要校验父帖、动作类型与规范化输入一致，跨语义复用请求键拒绝，不能冒充成功。
- `accepted_answer_id`、`awarded_answer_id` 各为单独指针，必须属于同帖；采纳、发奖后不可改删回答，注销回答者只清作者关系而不重置已完成事实。系统回答不可进入这两个指针。
- `case_id` **不唯一**，同资源多帖可关联同一未结事项；每帖只从空写一次。`from_case_id` 唯一，一事项只转一帖。系统回贴用父帖＋03 结案消息 ID 唯一。
- `bounty_state` 为 `none/held/released/settled/withdrawn/unsettled`。`bounty_total` 保留已承诺总额，释放不清零；已撤回仍留金额作历史，但不再付款。
- 资源引用删除时置空，`resource_state` 保留 `none/pending/listed/not_listed/violation` 的最后结论；任何非 `none` 都表示已转换过，不能借资源删掉再次转换获奖。资源存在且仍公开才显示可跳转卡片。
- 求助作者删除与其求助、悬赏行及现有 reservation 的级联保持一致；不新增注销平台。实现时实测无无主 pending 预留，账务历史按现有注销规则处理。
- 桥接来源事实保存原求助 ID、原提问者 ID、执行者分类与操作者 ID（系统动作无个人操作者）、当时资源及所属条目 ID；现有作者和锚定字段继续保留。`reporter_id` 是事项读取身份，不能代替这些来源事实，也不把来源事实向公众开放；实际字段与 03 允许载荷在接线合同中登记，不新增通用事件表。
- 有效票／我也遇到了／同问数按事实关系查询，不另维护冗余计数。系统奖及采纳指针不因投票人注销而重新开放；社区标记代表当时达标事实。
- 举报复用 03 的举报事实，按目标＋处置轮＋举报人去重；所需目标子类型、轮次与读取合同先登记 03，再实施，不另建举报队列。帖子和回答分别计轮，恢复只推进该目标轮次。

锚定合法组合：

| 锚定          | 合法意图                                 | 字段与公开条件                                                                       |
| ------------- | ---------------------------------------- | ------------------------------------------------------------------------------------ |
| `patch`       | 提问、条目资源求物、与游戏相关的站外事物 | 条目存在且可见；删除置空后不公开                                                     |
| `resource`    | 仅提问                                   | 资源存在并可公开，按其**当前**所属条目的分级／屏蔽判断；缓存的 patch_id 不能代替联表 |
| `topic`       | 提问、站外事物                           | 五个固定话题之一，不带资源或条目 ID                                                  |
| `wanted_game` | 仅未落地条目资源求物                     | 非空游戏名；落地原子改成 `patch` 并填条目 ID，原名仅展示，条目后来删除也不退回此类   |

所有公开查询先过滤自身隐藏，再应用上表与回答隐藏。`topic/wanted_game` 不依赖条目存在，但仍须经过自身隐藏过滤。索引覆盖状态＋活动时间、隐藏＋状态＋创建时间＋ID、条目／资源／作者＋创建时间、原帖、事项、回答父帖＋创建时间、资源引用、社区验证时间及日配额主键。

**统一事务纪律。** 按本次路径实际涉及的对象，统一为 **resource（若有）→ case → help（多帖按主键升序）→账户（按用户 ID 升序）→日配额**；没有资源／事项的普通互动从 help 开始。在父帖保护内重验隐藏、对象、状态和权限后才落子表，不能把“先锁父帖”套到将调用资源／事项原语的路径。资源审核／删除与求助资源转换共同遵守已存在资源先于父帖的顺序；新资源行在共享守卫通过后的同一事务中创建，不能假装预锁尚不存在的资源行，也不能把新行创建后再反向访问其它既有资源。

新开事项也没有可供预锁的 case 行：先锁现存 resource，再调用 [openCaseInternal](../../app/api/case/service.ts) 按唯一去重键插入或取得已有事项；拿到实际 case 后，复用其锁定／冲突处理，再锁 help 绑定。先持 help 后才发现需要桥接时，回滚短事务，从 resource 重新开始；不能保持父帖锁反向去开事项。事项结案、资源移动等现有调用方若要写回 help，也必须遵守该顺序，不能在已锁 case 后新增资源锁。

所有账户写入及必要的日配额采用统一顺序，系统奖／悬赏／贡献奖在相同事务中完成。失败全部回滚，死锁／序列化冲突仅作有界整笔重试；不靠 Redis 短锁证明数据库门槛和唯一性。注销有既有外键级联顺序，须对账户锁与父帖／回答交错实测，不能以一次账号预查询代替并发保护。

**三条桥接。** 拟新增 `app/api/help/bridge.ts` 接受调用方事务，使用 03 的 `openCaseInternal`／`closeCaseInternal`，复用归属、去重及统一结案出口。不能调用自行开事务且写死 `source=user` 的公开 `createCase`，不能把桥接拆成跨 HTTP 的两次提交。

1. 处理方手动转资源事项：资源锚定、操作者符合当时 03 处理权限；按 resource→case→help 顺序解析或创建 `resource_mismatch`，再锁帖关联。按 `publisher_convert` 的已登记语义记录来源，实际执行者用 publisher 或 staff。关联已存在返回已有结果；新建后关联失败整笔回滚，不留孤立事项。
2. me-too 达阈值自动桥接：使用 `help_escalation` 与 system 执行者。先预读是否可能跨阈值；需桥接时从 resource 开始，取得／创建并锁定 case，再锁 help、插关系、关联。锁内发现预读漏了跨阈值则回滚短事务，按正确锁序有界重试；未达阈值不留新事项。复用同资源同类型未结事项，每帖只关联一次，不冒用提问者手工提交额度。
3. 事项转求助：候选只接受 `resource_runtime`、`resource_request`、`resource_other`（含 `resource_request × patch`），须在 03 登记并经用户审阅；`resource_mismatch`、违规类及其它 kind 默认不提供此入口，不能一概以“不在受理范围”转换。由当前有结案权限的处理方执行，原开启者继续是提问者。预览确认可公开初始描述与对象；资源运行问题锚定资源，求资源意图锚定所属游戏，禁止把求物挂资源。转换不收任一方发布费，不消耗原开启者发帖额，也不检查其是否还有发布费余额；来源事项标记永久禁止求助系统奖。初始不带悬赏，之后仅原提问者可主动设置。原事项结案与新帖创建同事务；按 D39 发布者附指南、管理员写理由。已有转换重放返回同帖；无原开启者、目标失效、无法形成安全公开文本或事项已发生不兼容变化时拒绝并保留原事项。不得复制私有举报、后续对话、附件、私人联系方式或站方备注；公开内容不能由客户端任意冒名改写，处理方负责预览脱敏。

**桥接读取身份候选（待用户审阅并登记 03）。** 前两条求助→事项路径创建新事项时，均建议 `reporter_id = null`：自动来源为 `help_escalation`、操作者分类 system，手动来源为 `publisher_convert`、操作者分类 publisher／staff。关联已有事项时保留它的原 reporter，不改写、不自动订阅提问者或处理方，也不占提问者手工提交额度。原提问者／操作者／锚定的来源事实按第 4 节保留，null 不表示丢弃身份。提问者与 me-too 用户默认只在求助侧看许可公开的回贴；若其本来是事项参与者或管理员，仍按 03 独立权限读取。公开求助链接、通知或来源身份不能赋予全部私有对话访问权，候选未定前该桥接读取合同不开放。无 reporter 的新事项不能等待不存在的开启者，也不走 03 的无回应自动结案，处理方与站方沿现有内部事项规则收尾。

关闭帖的首次 me-too 仍可登记、订阅及在达阈值时桥接，社区验证也仍可在尚未采纳且条件满足时标记／发唯一系统奖；两者都不自动重开求助、不结算已释放悬赏。

事项每次有效终结取 03 的结案消息 ID（含解决、隐藏、移动），给每条关联求助一条系统回贴；重开再结案用新 ID，重复事件跳过。只写许可公开的结果摘要，不带私有载荷；事项深链仍执行 03 权限。通知集合由提问者、me-too 用户、同问作者以及适用的资源发布者派生，按用户去重并排除操作者／注销账号；关闭帖新回答只通知提问者。通知正文和链接标题同样过滤隐藏与分级，私有摘要不可抄进公开通知。

**资源回答与共享发布守卫。** 当前门槛在 [旧 route](../../app/api/patch/resource/route.ts)，不能只抽 [create.ts](../../app/api/patch/resource/create.ts) 的事务体。拟把存储类型／角色、普通用户可用点至少 20、至多一条待审及同一 `lock:patch:resource:create:{uid}` 短锁抽成一个共享守卫，旧资源路由、help 资源回答和文字转资源都调用；不复制第二套规则，也不通过调用旧 HTTP 路由伪造跨业务原子性。

守卫分事务前准备与事务内权威复核：先按现有短锁行为去重／限并发，快速校验后进行上传准备；随后在调用方事务按上方锁序取得所需资源／父帖与用户行锁，**在创建奖励入账前**重验当前账号角色、可用点、已有待审和首条资源判定。旧 route 也取得相同用户行锁再查待审与创建，因此即使短锁到期或两个入口交错，也最多生成一条需审核的资源；并发消费余额与发布按同一账户锁串行判断。不得在锁账户后反向请求既有资源／父帖。资源创建数据库原语接受调用方事务，旧 route 自己提供事务，help 在同一事务内创建回答、资源、关联和贡献奖；任一门槛失败整笔回滚。

共享守卫统一持有与按 token 释放短锁；上传准备保留现有消费锁、补偿及 finalize。事务失败补偿已上传对象并释放消费锁；提交成功后 finalize／清理按现有流程，通知或缓存失败不能被报成“未创建”并再次发奖。重放应在上传准备前读已有结果，事务内仍靠唯一键兜底。未来 E07-04 必须同时从旧 route 和 help API 验证门槛及互相并发，不能只测共用函数的 mock。

文字转资源还须锁原回答，从 `resource_state=none` 条件认领，不只看 `resource_id IS NULL`；不同请求并发也只创建一份。被采纳／获奖／验证的回答可以补资源关联，但不得重写已锁定正文。审核拒绝拟增加兼容的 `outcome: not_listed/violation`（旧调用默认 not_listed），通过写 listed，不收录保留回答，违规同事务隐藏回答；删除资源前写好最后结论，外键置空不丢回答。管理员拒绝表单与 01 接线由同批整合，不改现行奖励。06 实际合并若已交付，07 将自己的引用接入受支持迁移；尚未交付就按现有资源查询，不能假定卡片所有权细节。

**悬赏状态矩阵（候选包语义）。** 所有采纳先检查资格与用户本次确认结果，表中“系统奖”均指来源允许、尚有名额且双方资格／回答者日额满足时才可能发。

| 当前状态            | 初设／追加          | 撤回                         | 采纳                                                                                 | 自动关闭／整帖隐藏  |
| ------------------- | ------------------- | ---------------------------- | ------------------------------------------------------------------------------------ | ------------------- |
| `none`              | 允许时建预留 → held | 无                           | 可发系统奖，无悬赏                                                                   | 不变                |
| `held`              | 满足帖状态时追加    | 无他人回答时释放 → withdrawn | 合格则扣所有预留、支付 → settled；资格不足释放 → unsettled                           | 释放全部 → released |
| `released`          | 不开放              | 无                           | 合格且可用余额足，经确认直付 → settled；不足或资格不足，经明确只采纳确认 → unsettled | 不变                |
| `withdrawn`         | 不开放              | 无                           | 永不扣悬赏，可发系统奖                                                               | 不变                |
| `settled/unsettled` | 不开放              | 无                           | 已采纳，不再支付或补发                                                               | 不变                |

父帖隐藏与回答隐藏不同：整帖隐藏释放 held，回答隐藏不单独释放整帖悬赏，但阻止该回答被采纳。已完成结算后再隐藏不撤销历史；恢复不重新预留。关闭、隐藏、采纳及验证争用同一父帖锁：先结算则后续不释放，先释放则采纳只能走已释放分支，不得同时“确认扣除预留＋迟到直扣”。不合格采纳也必须释放 held，禁止 solved 帖遗留 pending。

采纳确认携带所见悬赏状态、金额与付款／只采纳结果，服务端锁内重验。若关闭、隐藏、可用余额或收款账号状态变化改变该结果，返回状态已变化并保留输入，刷新说明后重新确认；不静默改变付款条件。单次采纳已完成后的网络重放返回既有事实。

**回答者注销。** 作者关系已为空，或事务取得账户锁后确认收款账号不存在时，该用户回答仍可被采纳：按无点数资格显示并确认“只采纳”，写 solved／采纳标记；若 held 则同事务释放全部并转 unsettled，已 released 则转 unsettled，none／withdrawn 保持原悬赏状态；不调用该账号的 earn，不占系统奖日额或唯一名额，不给其他账号代收。若用户刚确认付款后回答者才注销，先返回条件变化，再按“只采纳”确认，不静默改结果。

并发注销需分别验证：注销先提交→重读后走无账号分支；采纳先取得存活账户锁并提交→只结算一次，后续注销按现有账户规则处理，不倒改采纳；撞外键／死锁／序列化失败→整笔回滚，按确定可重试错误有界重试并重读账号与回答。不能在已失败事务内吞 `MoemoepointUserNotFoundError` 后继续写采纳或释放，也不能把任意账务错误视为“账号不存在”。提问者注销仍按现有级联，实测不留无主 pending。

系统奖先检查回答者为存在的非提问者账号、来源（`from_case_id` 非空永不发）、资格和日额，再争夺空的 `awarded_answer_id`，成功者与奖励明细同事务写入。不合格事件只留标记、不消耗名额、不为该事件日后补发；后来另一合格社区事件仍可获空名额，但采纳后不新增社区验证，故不合格采纳会让空名额永久不用。

**提交 03 的求助举报处置合同（候选阈值未批准，组合未开放）。** 使用 `content_violation × help`，归 staff，权限 `role >= 3`；帖子／回答的子目标、ID 解析、去重键与处置轮先登记 03，不能只加类型而不接动作。目标身份与正文读取按 03 的私有举报矩阵登记：举报者只见本人的说明、站方回复及允许的系统事件，不见其他举报人；被举报作者仅有求助侧自己的受控视图，不因被举报而获事项对话权限。

| 动作                       | 前置与原子结果                                                                                                                              | 事项结论／后续                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 阈值暂时隐藏               | 当前目标轮内 3 名满 7 天的合格他人举报（候选），服务器去重；隐藏帖同时释放 held，隐藏回答不释放全帖悬赏；记录目标、轮次及造成隐藏的事项绑定 | **不结案**，留站方队列，不把达到阈值等同违规成立                               |
| 站方确认违规隐藏           | 确认目标与轮次、处置理由及操作确认；已由本轮暂藏则确认其事实，否则同事务隐藏并按帖／回答规则处理预留                                        | 经 `closeCaseInternal` 记 `violation_hidden`；不能只写结论不执行／确认真实处置 |
| 误判／不成立               | 若本轮事项造成隐藏，恢复同一目标，记录恢复并推进该目标新轮；若未隐藏，仅写不成立理由；不能恢复别的事项或新轮造成的隐藏                      | 经统一出口记 `not_established`；恢复不重新预留，旧举报不能再触发新轮           |
| 已完成其它处置／目标已删除 | 先核实实际处理结果；目标已删除则保留缺失事实与理由，不伪造隐藏或恢复                                                                        | 用 `handled` 结案，无新增通用处理动作或求助物理删除能力                        |
| 已结案后的纠错恢复         | 只允许本事项造成、当前仍属于同一轮且尚未恢复的隐藏；确认后恢复目标、推进新轮；旧请求重放无效                                                | 沿 03 恢复补充动作记录，不重开／重复结案，不重新预留                           |

恢复新轮仅影响该帖或该回答，不清除旧举报审计事实；“推进举报轮”不等于重开事项。`timeout=module-07` 表示由 07 声明治理时限，本候选不设举报自动结案，也不走 03 的七天／十四天扫描或求助无活动关闭任务。涉及举报的锁序仍为 case→help→账户，有资源动作才先 resource；直接治理动作先解析本次事项，不持 help 再反向拿 case。合同与真实动作接入前禁止开放该组合，E07-03 记未具备条件，不以伪造接口充数。

## 7. 定时任务

拟新增 `server/tasks/helpZoneTask.ts` 并注册现有 cron，每 15 分钟按上海时区运行，复用 withTaskLock；技术锁 TTL 初拟 1800 秒，正确性由条件更新及事务保证，不依赖锁一直有效。每批最多 200，按到期事实分页处理至无候选；执行耗时超出锁时并发实例仍不得重复结算。测试注入 now，不修改机器时钟。

| 步骤     | 条件                                                      | 同事务动作                                                                          |
| -------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 自动关闭 | open、未隐藏、当前 `last_activity_at + 14 天 <= now`      | 条件更新 closed／closed_at；仅 held 释放并转 released，其余悬赏状态不变；通知提问者 |
| 社区验证 | 用户回答未隐藏、未标记且满票；父帖可公开、未采纳、满 7 天 | 锁父帖后重验、标记；仅合格且有名额时发奖；只由成功写入方发通知                      |

关闭的时间条件放在数据库条件更新中，新他人回答／首次 me-too 与其串行化，自答不续期。社区验证遍历同帖多回答时采用稳定顺序，奖只给第一条满足资格的事件；被标记但不合格的不在次日补奖。两步执行顺序不得改变单次奖励和预留终态。

只有这两类新任务。正常关闭／隐藏与释放同事务，不设置用来掩盖半提交的补偿任务；停机后按 `<= now` 补跑积压。隔离验收除可控时钟外须观察一次自然调度、多实例竞争与恢复补跑；任务不得代扫 03／04／06 类型。

## 1. 目标与基线

把「官方镜像」从全量政策改成选择性备份：备份是原用户卡片下的一条资源盘链接，存储类型 `touchgal`，由站方维护；用户选择「交由站方维护」时卡片与备份留下，交站方维护；历史上站方另建且经管理员核实确为同一份内容的重复卡片，与用户卡片逐对合并。官方与社区继续独立分组，不假定两组资源一一对应。分组沿用发布者身份：合并保留用户卡片和原发布者，因此带站方镜像的合并卡片仍归社区；添加备份、交由站方维护均不改变分组。基线是[运营层设计](../7.operations-layer-redesign.md)第 5 节，该基线 2026-09-05 冻结，其正文不再修改，偏离在下一节逐项记录。

实施前基线（实施前核对过当时源码和当时的备份资料。下列条目是实施前事实，不是实施后的现行源码；历史数量保留原资料来源，本文不重算，也不再读取私有数据）：

- 站方备份已经以 `storage = 'touchgal'` 区分：[链接健康策略](../../constants/linkHealth.ts)把它定为站方存储，[添加入口](../../app/api/patch/resource/route.ts)只允许管理员，[更新权限](../../app/api/patch/resource/update.ts)对非管理员锁定其内容，[事项归属](../../app/api/case/service.ts)在链接类事项上按它归站方。
- 资源类事项的归属按资源作者的角色推导：作者角色不高于 2 归发布者，否则归站方。
- 普通用户不能删除含 `touchgal` 链接的卡片，[删除服务](../../app/api/patch/resource/delete.ts)直接返回无权限；可以删除时，同一事务回收 3 点发布奖励。
- 链接的创建时间不能表示「何时加入卡片」：[链接拆分迁移](../../migration/migratePatchResourceLinks.ts)用 `CURRENT_TIMESTAMP` 写入创建时间，2026-05-07 的一次迁移给 1159 条链接写下了同一个时刻（备份库里 918 条 `touchgal`、85 条 `user`、156 条 `s3`）。备份库共有 `touchgal` 1323 条、`user` 390 条、`s3` 294 条，其余约 848 条（含 305 条 `user`）的创建时间是真实的。
- 点赞按唯一键 `[user_id, resource_id]` 去重，奖励与通知发给 `resource.user_id`（[点赞服务](../../app/api/patch/resource/like/service.ts)），自己不能给自己点赞。
- 公开的「下载次数」由[点击上报](../../app/api/patch/resource/download/service.ts)累加：卡片按钮按下时前端发 `PUT /patch/resource/download`，与是否真的取得链接无关。
- 控制台已有「下载资源」页，通过旧后台资源接口读取。其「到游戏页编辑」按钮跳到游戏页，由那里的保存走普通更新接口，不写管理日志，也不通知发布者；后台资源更新接口（`PUT /admin/resource`）则写管理日志并通知发布者。

## 2. 偏离与理由

下表记录与基线第 5 节的偏离。写法沿用 [04 第 2 节](./04-link-health.md#2-偏离与理由)。

| 偏离 | 基线 | 本文做法与理由 |
| --- | --- | --- |
| 不建 `official` 列，用 `storage = 'touchgal'` 判定站方备份 | 5.1、5.9 | 代码已把该存储类型当作站方存储，事项归属、权限、删除保护都按它判断；再加一列会产生两份事实，需要持续对账。「站方已备份」仍是由是否存在这类链接推导，与基线 5.1 的原意一致 |
| 不建 `official_verified_at`、`mirror_check`、`origin_user_id`、`credit_visible`、`takedown_requested_at`，也不建 `mirror_queue_entered_at` | 5.1、5.4、5.6、5.9 | 备份旁显示备份日期，不设版本确认状态；不允许匿名，原发布者始终是卡片的 `user_id`，不需要另存来源；队列由事实推导，不另存进入时间；申请下架另见下一行 |
| 发布者退出含备份卡片的维护：明确选择「交由站方维护」 | 5.4 | 保留原发布者信息、不允许匿名，也不改 `user_id`；交接只转移维护责任，入口明确命名「交由站方维护」；「删除我的链接」是普通编辑，已有；「申请下架」要建新状态和新事项类型，而文件有害这类情形本来就走现有事项与管理员处理，不为它单设流程。因此 03 预留的 `takedown_request`、`mirror_version_check` 类型本模块不使用，第 9 节安排清理 |
| 交接后点赞奖励、个人主页列表和创作者申请计数保持不变 | 5.4 | 基线的「移交给站方账号」会让这三项随卡片离开原发布者。站长确认原发布者保留署名，交接前后他的奖励、主页和创作者资格不变：点赞仍给 `resource.user_id`，已发的发布奖励不收回 |
| 全量镜像改为选择性备份，三层优先级改为一个可筛选的列表，默认按获取次数降序 | 5.5 | 站长决定只备份值得备份的资源，由管理员挑选；分层排序依赖的网盘存活率、体积等信号不再作为入队条件 |
| 不做镜像版本确认：不问发布者，不设 7 天超时 | 5.6 | 版本信号改为「备份日期」加「备份之后外部链接被改或新增」，由管理员判断是否重新备份。「待重新备份」只提示变动，不断言内容不同 |
| 存量合并中，高置信对批量合并，不询问发布者 | 5.7 | 不逐个询问发布者，但管理员须核实两张卡片确为同一内容。属性匹配和互为唯一只用于筛选核对顺序；官方与社区可能发布不同资源，不能因此推定重复。历史 207 对仅是候选样本，按最终条件重新盘点 |
| 合并时不迁移站方卡片上的点赞 | 5.7（合并获取次数与点赞） | 站长决定。备份库中高置信对的站方卡片共 53 个点赞：其中 6 个是发布者自己点的（用户卡片上不允许自赞）、23 个与用户卡片重复，约 24 个会因此舍弃。这也取消了旧 06 的「点赞奖励接收者可追溯」不变量 |
| 合并只限用户卡片与站方卡片 | 5.7 | 站长确认，不做用户与用户的合并 |
| 候选实时计算，不存待处理候选，没有检测任务，没有手动配对 | 5.7 | 候选完全由卡片现状决定，存下来就要持续对账。需要记住的只有「已驳回」和「已合并」两种结果，合并进同一张记录表，它同时兼作旧链接的重定向依据。一张用户卡片有多个站方候选时，由管理员在详情里选定一张 |
| 自动或半自动搬运不做 | 5.5「省时间的三个杠杆」 | 站长确认，之后可能作为独立工具出现，搬运机器也不一定是同一台 |
| 获取计数切换、资源管理迁入新控制台仍在 06 | 5.8 | 沿用基线，与 06 其余项一起排期；资源管理页已迁入控制台，本模块只补接线 |

## 3. 术语

| 术语 | 定义 |
| --- | --- |
| 站方备份 | 卡片下一条 `storage = 'touchgal'` 的链接。由站方维护，用户不可改、不可删 |
| 外部链接 | 卡片下 `storage = 'user'` 的链接，即用户自填的网盘链接 |
| 站方卡片 | 作者角色不低于 3 的账号发布的卡片。当前只有一个这样的账号 |
| 用户卡片 | 作者角色不高于 2 的账号发布的卡片 |
| 链接变动时间 | 一条链接的 `GREATEST(attached_at, content_changed_at)`，即加入卡片的时间与最近一次改地址的时间中较晚的一个（`GREATEST` 忽略空值） |
| 备份时间 | 卡片所有站方备份链接的链接变动时间的最大值。站方把备份换成新地址，也会推进它 |
| 交接 | 交由站方维护的简称。卡片保留原发布者作为 `user_id`，同时记录 `publisher_left_at`；此后站方负责维护，原发布者失去管理权。数据模型见第 4 节 |
| 候选 | 同一游戏、同一分区下，一张用户卡片与一张站方卡片的配对。用户卡片需 `status = 0`、至少有一条外部链接、未交接；站方卡片状态不限。候选实时计算、不存储，一张用户卡片可以有多个候选 |
| 高置信对 | 候选中同时满足：站方卡片 `status = 0` 且创建晚于用户卡片；类型、语言、平台两两相同（不计顺序）；用户卡片与站方卡片互为唯一候选，判断时不计已驳回的对。仅表示可以进入批量核对，不证明版本、文件内容或用途相同，也不保证没有其它阻塞原因；批量合并仍须管理员逐对确认同一份内容 |
| 需人工核对 | 其余候选：属性不一致、一侧有多个实时候选、站方卡片比用户卡片早、站方卡片状态不是正常。一个用户卡片行只有在唯一的实时候选为高置信时，整行才按高置信筛选 |
| 推荐 | 对同一张用户卡片同分区、当前无阻塞且未留下记录的站方配对进行排序。最高项至少在类型、语言、平台中匹配两项；只有一个可合并项时可以推荐，有多个时须比次高项多至少两个匹配信号。信号包括属性、近似大小、规范化名称、站方发布较晚和互为唯一。推荐只是核对顺序，不是内容相同证明、高置信的必要条件或自动合并许可 |
| 幸存卡片、被并卡片 | 合并后留下的用户卡片，与被删的站方卡片 |
| 合并记录 | `patch_resource_merge_record` 中的一行，记录一对候选已被驳回或已合并 |

## 4. 数据模型与迁移合同（M06-1）

核心原则：不加 `official`、`mirror_check` 之类的状态列；只加事实，让每个队列和显示都能由事实推导。

### 4.1 既有表新增

1. `patch_resource.publisher_left_at`：可空时间，空表示仍由发布者维护。不改 `user_id`。
2. `patch_resource_link.attached_at`：非空时间，默认写入时刻，表示链接加入所在卡片的时间。存量回填见 4.4。
3. `patch_resource_link.click`：整数，默认 0，按第 5.4 节保留后台辅助点击统计。

链接改地址（补链）沿用 04 的 `content_changed_at`，`attached_at` 保持不变；两者的较晚者就是链接变动时间。合并后链接 ID 不变，`attached_at`、`content_changed_at` 跟随链接，不需要重算；此时 `attached_at` 保留来源卡片的加入时间，不表示合并发生时间。

### 4.2 新表

**资源文件清理记录**：交接事务登记待清理对象、来源资源标量编号、创建时间、执行状态及不含秘密的失败类别；对象定位唯一，资源删除不级联删除待办。写入和重放合同见第 7 节。

**备份队列记录**（表 `patch_resource_backup_state`，一张卡片至多一行，主键为 `resource_id`，外键级联删除）：

| 字段 | 含义 |
| --- | --- |
| `ignored_at`、`ignored_by_user_id`（标量，不建关系）、`ignore_reason` | 站方忽略这张卡片的时间、操作人和可选理由（最多 500 字）；撤销忽略清空三项 |
| `rebackup_dismissed_at` | 站方最近一次确认无需备份的外部链接变动时间（已检查水位） |

没有这一行等于未忽略、未表态。撤销忽略后若两个时间都为空，行可以保留空值，也可以删除，实现自选，查询必须同时覆盖两种情况。

**合并记录**（表 `patch_resource_merge_record`）：

| 字段 | 含义 |
| --- | --- |
| `id` | 自增主键 |
| `user_resource_id`、`staff_resource_id` | 用户卡片与站方卡片的 ID。均为标量，不建外键：被并卡片删除后记录仍在 |
| `patch_id`、`section` | 所在游戏与分区（`galgame` 或 `patch`），用于列表筛选 |
| `status` | `dismissed`（已驳回）或 `merged`（已合并） |
| `handled_at`、`handled_by_user_id` | 处理时间与处理人（标量） |
| `detail` | 小型 JSON：`merged` 时记录移动的链接 ID、备注是否追加了「站方备份说明」、管理员确认同一内容的事实与预览摘要，不存下载凭据 |

约束与用法：

- 唯一键 `(user_resource_id, staff_resource_id)`；索引 `(staff_resource_id, status)`，供旧链接重定向按被并卡片 ID 反查幸存卡片。
- 没有记录且满足候选条件的对就是待处理。驳回写 `dismissed`；在「已驳回」里重开，只删除 `dismissed` 行。合并写 `merged`，之后不可被驳回或重开。
- 卡片一旦作为幸存卡片有 `merged` 记录，不再参与任何一侧的合并候选；即使作者后来变为管理员也不能再次作为被并卡片，避免产生映射链。同一用户卡片的其余站方候选退出此用户的配对列表，但站方卡片本身和其他用户的有效配对不受影响；不自动删除卡片，不伪造驳回记录。预览须列明这些退出配对，合并确认一并说明。
- 不使用部分唯一索引（生产结构检查不允许），不建候选占位表，不建检测任务。

### 4.3 不新增

不新增 `official`、`mirror_check`、`origin_user_id`、`credit_visible`、`takedown_requested_at`、`official_verified_at`、`mirror_queue_entered_at`；不新增站方接管账号（卡片保留原 `user_id`）；不新增候选表和重定向表；不新增事项类型和事项状态（`merged` 状态已存在，本模块不写入）。第 5.1 节新增的 `publisher_left` 是已有「转交触发器」枚举的一个取值，不是新的事项类型。

### 4.4 迁移与回填

按仓库既有流程：结构变更走审定的 preflight、sync、postflight，先在隔离库演练，生产由站长在服务器执行。文件入口、判定参数与回填清单见[运维指南的站方备份与资源合并结构](../../docs/guides/operations.md#站方备份与资源合并结构)，不把参数省略成无参数命令。

`attached_at` 的 sync 分三步，每步可重复执行：先 `ADD COLUMN IF NOT EXISTS`（可空），再只对 `attached_at IS NULL` 的行回填，最后设默认值 `CURRENT_TIMESTAMP` 并改为非空。postflight 断言没有空值，并打印实际按确认分组回填的链接数。

回填口径：

- 统一盖章的链接取所在卡片的 `created`。识别方式是按链接 `created` 分组，同一时刻被大量链接共用（筛选阈值：组内超过 50 条），经迁移来源核对后视为统一盖章，不写死 2026-05-07 那一刻。备份库上预期识别出约 1159 条。
- 其余链接取 `GREATEST(链接 created, 卡片 created)`。
- 估算的限制：统一盖章的链接比真实加入时间更早或更晚都有可能，仅凭估算时间无法还原迁移前更新的先后，可能漏报或误报「待重新备份」；已有 `content_changed_at` 仍参与比较。PM 版 2.2 同步说明。存量备份链接旁显示的备份日期同样是估算值。

上线窗口按[迁移与停写要求](../../docs/guides/operations.md#停写备份与执行文件)执行：停止旧应用和相关写入进程，取得并验证备份后再回填。预检列出时间分组、数量与判定依据，超过 50 条仅用于找出待核对的组，须确认来自链接拆分迁移才按卡片创建时间回填；不能把真实批量上传误判为迁移。复检同时核对新表、默认值、非空与唯一约束、记录数量，并验证重复执行和中断恢复。历史样本的 1159 条不是生产验收常数。sync 在同一事务内完成回填与设为非空之前的校验，按预检确认清单核对结果，失败整笔回滚。若提交后复检发现判定错误，保持停写，仅按本次回填清单校正本次原为空的行，再复检；禁止清空全部非空值或覆盖上线后新增事实。小于阈值的时间组也须对照迁移来源核对，阈值不是完整性依据。

恢复边界：尚未发生交接或合并时，可保留新增结构并回退兼容旧应用；首次交接或合并之后，旧应用不识别已移交权限和旧 ID 映射，禁止直接回退。此时保持停写，优先前向修复；确需恢复数据库时由站长选择备份与恢复窗口，核对窗口内新增写入和对象存储，不能靠删除新字段或合并记录撤销操作。已清理对象不由数据库备份恢复；没有独立对象备份时不能承诺完整回退。

除时间回填外，其余新字段按默认值初始化、新表从空开始。不回填「站方备份日期」：它由 `touchgal` 链接的变动时间推导。

## 5. 接口、权限、事务与幂等

### 5.1 交由站方维护（M06-2）

**入口**：卡片作者、角色低于 3 且卡片含 `touchgal` 链接时，操作菜单与确认按钮均显示「交由站方维护」；不含站方备份时才显示「删除资源」，沿用整张删除与回收 3 点的规则。管理员的真正删除仍保留。实现可复用[删除服务](../../app/api/patch/resource/delete.ts)及其[条目页接口](../../app/api/patch/resource/route.ts)、[工作台调用](../../app/api/workspace/resources/service.ts)，但交接与删除是两个明确的业务动作，请求携带用户确认的动作，服务端在资源锁内复核；备份状态变化导致动作不适用时要求重新确认，不能把一次交接请求执行成整张删除。旧客户端未明确确认交接时，不得静默转成交接。

响应区分两种结果：条目页接口返回 `action`（`handed_over` 或 `deleted`）和余额，工作台响应增加 `handedOver`。作者重复提交同一次交接请求，返回同样的交接结果，不产生任何副作用；编辑与链接管理则拒绝。

**确认框与提示**：条目页的[资源操作对话框](../../components/patch/resource/Resource.tsx)和工作台的[编辑器](../../components/dashboard/workspace/WorkspaceResourceEditor.tsx)按卡片是否含 `touchgal` 链接选择文案。交接用：

> 交由站方维护后，你添加的链接会被移除，卡片和站方备份保留，仍署你的名字。你将不能再编辑这份资源，仍可在个人主页查看发布记录。已获得的萌萌点不收回，交接后暂不支持重新认领。

整张删除沿用现有文案。交接成功后条目页不把卡片从列表移除，而是刷新它，卡片显示「站方维护」，提示「已交由站方维护，你仍可在个人主页查看发布记录」，提供个人主页资源列表入口。工作台标题、导航和返回链接统一改为「我维护的资源」，列表按维护责任筛选；个人主页「发布资源」按原发布贡献展示。

**事务**（经 `runResourceMutation` 执行，沿用 04 的锁序：资源行 → 链接行（按 ID 升序）→ `lockLinkMaintenance` → 事项行；事务内不做网络与缓存操作）：

1. 锁资源行与全部链接，复核调用者是 `user_id`、卡片含 `touchgal` 链接、`publisher_left_at` 为空。已交接的重复请求在此返回，不继续。
2. 发布者自己的链接（`storage` 不是 `touchgal`，含 `s3`）：复用[更新服务](../../app/api/patch/resource/update.ts)的移除逻辑，先取 `lockLinkMaintenance`，每条写一条链接历史（原因 `remove`），以「链接已移除」结案其链接类事项（`closeLinkCases`），再删除链接行；获取记录的 `link_id` 置空保留；`s3` 对象在同一事务登记清理待办，在提交后清理。
3. 写入 `publisher_left_at`。卡片状态与其他字段不变。
4. 未结事项转交站方，见下一段。
5. 正常交接不回收 3 点发布奖励，不重新发奖，不写零金额或补偿流水；保留原卡片 ID、作者及已有账务引用。
6. 写管理日志：新增类型 `resource_handover`，在[管理日志类型表](../../constants/admin.ts)登记；操作人是发布者本人；内容含卡片 ID、被移除的链接数、删除前晚于备份时间的外部链接数及比较时间，不保存地址或下载凭据；这些链接被删后仍能追溯站方保留的副本是否可能较旧。
7. 提交后失效条目内容、资源列表和作者页缓存，再执行已持久登记的 `s3` 清理；失败不改报交接失败，也不重新执行交接事务。恢复要求见第 7 节。

**未结事项的交接**：

当前先归站方，长期责任分工和站方新增工作量作为 [PM 版的后续问题](./06-official-mirror-pm.md#7-定稿决定与上线前核对)记录。`publisher_left` 仅说明主动交接，不表示发布者超时，也不证明站方已处理完毕。

- 03 的转交触发器（`CASE_ESCALATION_TRIGGERS`，现有 `timeout`、`review_request`）新增第三个取值 `publisher_left`。[事项服务](../../app/api/case/service.ts)里写死的 SQL 列表（第 3518 至 3520 行）同步加入，类型随常量变化；03 文档与测试同步。09 把它归为「站方接手」，不计发布者超时。
- 本卡片上归属为发布者的未结事项只剩资源类（发布者自己的链接类事项已在事务第 2 步结案）：
  - `open`、`waiting_owner`：变为 `open`，归属站方（`owner_type = staff`、`owner_id` 为空），`status_changed_at`、`queue_entered_at`、`escalated_at` 取当前时间，`revision` 加一。
  - `waiting_reporter`：状态与 `status_changed_at` 不变，`owner_type = staff`、`owner_id` 为空，`queue_entered_at`、`escalated_at`、`updated` 取当前时间，`revision` 加一；切换到站方的等待规则，不重启开启者等待时间，不再运行发布者事项的自动提醒与自动结案。上述两类转交都更新 `updated`，保留已发生的首次回应事实。
  - 所有事项写入先按 ID 升序锁定并复核状态；每个被转交的事项追加一条 `escalated` 事件，`escalation_trigger` 为 `publisher_left`，带 `from_status`、`to_status`、`from_state_entered_at`、`queue_entered_at`，不带 `from_owner_type`、`from_owner_id`。对话与关注者保留。
- 原发布者不再拥有「原发布者」权限。转交事实的三处读取（`loadLatestHandoffFacts`、`loadOwnedCaseWindow`、`representedPublisherLinkCaseIds`）统一排除所属资源 `publisher_left_at` 非空的事项。这一排除也覆盖交接前已经因超时或复核请求转给站方的事项：原发布者基于发布者身份的结案权（要求触发器为 `timeout` 且重开次数为零，D36）和通知一并终止。若该用户另有开启者、关注者或管理员身份，仍按相应身份参与和接收通知，不能整人屏蔽。
- 已结案的事项保持原样。重开（`reopenCase`）时若所属资源已交接，归属推导为站方。
- 事项创建不需要新增锁。`openCaseInternal`（[事项服务](../../app/api/case/service.ts)第 2669 行）对资源类目标先调用 `lockResource`（`SELECT … FOR UPDATE`，第 2682 至 2688 行），再推导目标，顺序已经是「资源行 → 事项行」，与 06 的锁序一致。因此创建与交接、合并天然互斥：创建先提交，则交接转交这条新事项、合并因未结事项被阻塞；交接或合并先提交，则创建看到最新的 `publisher_left_at`，或在资源已被并入时返回「资源不存在」。事项事务（`runCaseTransaction`，第 259 行）使用默认的 READ COMMITTED，取锁之后的读取能看到最新提交的数据，所以归属推导只需让 `deriveTarget` 的资源查询多选出 `publisher_left_at`，`lockResource` 本身不用改。事项服务里的移动资源路径（第 4763 行）同样先锁资源，不与上述顺序冲突。链接类事项由链接健康服务创建，只锁链接行（`lockLinkCaseTarget`，[链接事项](../../app/api/case/linkHealth.ts)第 56 行起，不取资源行锁）。交接和合并都在锁定资源行之后再锁同一条链接行，创建与它们因此互斥：创建先提交，则合并被这条未结事项阻塞，交接把它随链接一起结案；交接先提交，则链接已删除，创建返回「链接上下文已变化」。合并先提交时，链接已改挂到用户卡片：创建要么读到新的所属卡片，按幸存卡片创建，要么因等锁期间的条件复核返回「链接上下文已变化」，两种结果都不会留下挂在已删除卡片上的事项，实际是哪一种由 E06-03 的「合并与事项创建并发」测试确认。这条路径同样不需要新增锁。

| 位置 | 行为 |
| --- | --- |

**账务与历史记录**：

交接保留原作者，因此[点赞服务](../../app/api/patch/resource/like/service.ts)在交接前后向同一个人发奖或回收；点赞关系的唯一约束与事务内实际增删行数仍是计费依据，不能因为维护人变化再结算一次。发布奖励记录使用原卡片编号，交接也不产生新的创建奖励。

[萌萌点流水](../../prisma/schema/moemoepoint.prisma)保存发生时的收款人、余额变动、原因和标量资源编号；资源删除不会通过该编号级联删除流水。已有流水不改写、不迁给站方，不用当前资源数量或点赞关系倒推历史余额，不伪造早期不存在的流水。交接日志负责解释维护责任变化，普通清理日志记录「已交接，保留原发布奖励」的依据；没有金额变化时不新造账务记录。

合并同样不改写任何一侧的旧流水。被并卡片的点赞关系虽删除，已发给站方作者的奖励保留；合并审计保留来源作者编号、删除前点赞数与两张卡片编号，以便解释计数与历史奖励的差异。取消幸存卡片上的点赞仍只回收该次点赞给原作者的一点，不追溯扣除被并卡片的旧奖励。

正常退出维护保留发布贡献奖励，是本方案的产品规则；现有提前发奖、驳回及后台删除未统一追回的[账务问题](../../docs/reference/known-issues.md#资源奖励在审核前发放且不总是收回)仍独立存在。`publisher_left_at` 只表示维护交接，不表示奖励已经审核、违规已经豁免或历史账务已结清。

**对外数据**：公开资源卡片下发 `publisherLeftAt`，对应列 `publisher_left_at`，界面用该值是否非空判断「站方维护」；公开资源类型不另写 `staffMaintained`。个人主页的 `UserResource.staffMaintained` 由同一列 `publisher_left_at` 是否非空构造，不从公开字段反推。`PatchResourceLink` 增加 `backedUpAt`（仅 `touchgal` 链接，取链接变动时间）。工作台摘要与详情增加 `hasStaffBackup`，因为 `linkDiskKinds` 按网址主机判断，不能代替存储类型。[链接健康投影](../../app/api/patch/resource/linkHealthProjection.ts)补选所需的列。[下载卡片](../../components/patch/resource/DownloadCard.tsx)在站方备份链接旁显示「站方备份」徽标和日期。

**首版没有重新认领**。账号删除仍会级联删除名下卡片及其站方链接，这是[已知问题](../../docs/reference/known-issues.md)，不在本模块处理。

### 5.2 站方备份队列与忽略（M06-3）

**范围**：卡片 `status = 0`，作者角色不高于 2，`publisher_left_at` 为空，至少有一条 `storage = 'user'` 的链接。只有 `s3` 链接的卡片不入队，站方卡片不入队；已交接的卡片明确排除，站方后来添加外部链接也不回到发布者备份队列。

**三个标签的谓词**（均不建状态列，由事实推导；一张卡片至多出现在一个标签里）：

| 标签 | 谓词 |
| --- | --- |
| 已忽略 | 有忽略记录（`ignored_at` 非空）。忽略优先于另外两个标签 |
| 未备份 | 无 `touchgal` 链接；无忽略记录。存在合并候选不代表已有备份，不排除入队；详情提供核对候选入口 |
| 待重新备份 | 有 `touchgal` 链接；无忽略记录；存在外部链接，其链接变动时间大于备份时间，也大于 `rebackup_dismissed_at`（若有） |

备份时间取该卡片所有 `touchgal` 链接的链接变动时间的最大值（第 3 节）。站方为重新备份把站方链接换成新地址会推进备份时间，待重新备份随之清除；新增站方链接同理。

这些是管理队列条件，不能用来计算全部备份覆盖率：09 按已公开用户卡片中「含外部链接或含站方备份」的去重集合为分母，其中实际含站方备份的卡片为分子；交接或忽略不抹去既有备份事实。

忽略只在「未备份」里提供。被忽略的卡片之后即使加了站方备份或换了外部链接，也只出现在「已忽略」，不会自己回到「未备份」；撤销忽略后再按谓词归位。默认排序为获取次数（`patch_resource.download`）降序。

**接口**（`app/api/admin/backup/`，对外路径带 `/api`，写法同[会社合并](../../app/api/admin/company-merges/route.ts)，`role < 3` 拒绝）：

| 接口 | 作用 |
| --- | --- |
| 读取队列 | GET。参数：标签、分区、搜索、分页、排序（默认获取次数降序）。返回行内字段（卡片、游戏、发布者、获取次数、外部链接数、最近一次链接变动时间）和三个标签各自的数量 |
| 忽略、撤销忽略 | POST。忽略写 `ignored_at`、操作人和可选理由；撤销清空三项。重复请求幂等，不重复写日志 |
| 无需重新备份 | POST。携带详情返回的链接事实基点；锁内复核后写入本次已检查的最新外部链接变动时间。相同基点的重复请求不推进水位，不重复写日志 |

三个写操作都先锁资源及链接、重读队列条件：忽略仅对当前未备份项生效，撤销仅对已忽略项生效；「无需重新备份」基点包含链接 ID、版本、存储类型与变动时间，基点变化则要求重新核对，不能用请求到达时间忽略未查看的新变动。三个写操作仅在事实改变时各写一条管理日志，类型 `backup_ignore`、`backup_unignore`、`backup_dismiss`，在[管理日志类型表](../../constants/admin.ts)登记。

**添加备份**不新增写接口：详情里的入口打开[收件箱的资源编辑表单](../../components/dashboard/inbox/ResourceEditForm.tsx)，提交到[后台资源更新](../../app/api/admin/resource/update.ts)，它写管理日志并通知发布者。表单成功提示由调用方传入，不写死「资源仍待审核」；它需要的 `baseLinks` 由 `GET /admin/resource?resourceId=` 提供。控制台「下载资源」页的「到游戏页编辑」走普通更新接口，不写管理日志，备份页不复用它。

### 5.3 存量合并（M06-4）

**候选**：实时计算，不存待处理项。同一游戏、同一分区下，一张用户卡片（`status = 0`、作者角色不高于 2、至少一条外部链接、`publisher_left_at` 为空）与一张站方卡片（作者角色不低于 3，状态不限）构成候选。以下两类不再是候选：合并记录里已有记录的对（已驳回、已合并），以及任一侧卡片已作为幸存卡片有 `merged` 记录的配对。高置信与需人工的分类见第 3 节。历史样本只有数百对，服务端计算后分页，不需要缓存。候选是核对入口，不能作为内容相同的证据；同一游戏的不同版本或附加内容即使属性相同也应独立保留。

工作台读取同一游戏的全部站方卡片，不限于实时候选，用于人工排除相似但不同内容、不同分区或曾经驳回的卡片。列表中的「官方」数量也包含两个分区的站方卡片；选中其他分区的卡片只供查看，服务端返回分区不符且不提供合并预览，不允许借此建立跨游戏或跨分区配对。已驳回的配对仍在工作台显示并可重开，不再计入「互为唯一」的实时候选数；已合并的站方卡片以处理记录中的名称和编号留痕。

2026-11-03 文档所记历史备份资料聚合如下，仅用于方案背景，不是当前数据或 2026-11-05 的 dump 核查结论：

- 有站方卡片的游戏里，296 张用户卡片能配出候选，其中 207 对满足当时未按站方卡片状态过滤的高置信条件。
- 其余 89 张需要人工：62 张属性对不上，21 张有多个候选，6 张站方卡片比用户卡片还早。
- 另有 77 张有外部链接的用户卡片没有站方卡片，属于第 5.2 节的备份队列。
- 历史高置信对里的站方卡片各只有一条链接；当时尚未核对这些资料的完整链接构成。按当前算法重算的候选与链接阻塞见第 11 节；非 `touchgal` 链接按下文规则阻塞。

**阻塞原因**（任一项成立则不能合并，界面显示原因，批量时记为跳过）：

- 站方卡片或所属游戏未公开（`status != 0`）：须先走既有审核或恢复流程，不能借合并公开受限内容。
- 管理员未确认两张卡片确为同一份内容；只有属性相似或互为唯一不够。
- 站方卡片含非 `touchgal` 链接：首版阻塞，避免移到用户卡片后将原站方链接的修改权和维护责任转给用户；管理员先独立整理，不能直接伪改存储类型。
- 站方卡片上有未结事项，含目标是它的链接的事项。
- 合并后的备注超过 10007 字。
- 任一卡片已不存在，或用户卡片已有 `merged` 记录。
- 用户卡片已交接，或不是 `status = 0`。
- 这一对已被驳回：需先重开。
- 两张卡片不同分区，或任一侧已作为幸存卡片留下过合并记录。
- 预览之后卡片、链接或站方卡片未结事项集合发生变化，核对基点失效；单对和批量均须重新核对。

**推荐信号与限制**（[推荐判定](../../lib/officialMirror/decide.ts)）：

类型、语言、平台各自比较是否同集合，不计顺序与重复值。大小只比较用户外部链接和站方链接中的可解析大小，支持 KB、MB、GB、TB 的十进制数值，以 MB 换算，较大值为基准允许 3% 的相对差；空白、零和其它写法不命中，也不会推断真实文件内容。名称经过 NFKC 规范化、转小写并去除空白与标点，一方非空且包含另一方时命中；它不识别版本或用途。另两个信号是站方创建较晚、双方在实时候选中互为唯一。

推荐只从同分区、无阻塞、没有合并或驳回记录的配对中产生。只有一个此类配对时，类型、语言、平台至少命中两项即可推荐；有多个时还要求最高项比次高项多至少两个信号。信号相同时以属性命中数、站方编号确定显示先后，但不会把并列最高项标成推荐。阻塞项不参与推荐竞争，也不靠「没有推荐」判断内容不同。无论是否推荐，管理员都须打开实际卡片核对；当前可合并的高置信对会成为推荐，推荐却不能替代任何合并检查。

**备注合并**：用户备注为正文。站方备注非空，且去除首尾空白后不是正文的子串时，在正文后加一个空行和「站方备份说明：」，再接站方备注；其余情况正文保持原样。名称、类型、语言、平台保持用户卡片的值。高置信对已保证类型、语言、平台一致，需人工对由管理员在预览中核对。

**预览**：返回幸存卡片合并后的字段和链接列表（原有链接在前，移入的链接在后）、被并卡片的信息、合并后将退出且不记为驳回的其他配对、阻塞原因和一个基点。基点覆盖两张卡片的 `updated`、身份与发布状态、链接完整内容与排序及其版本、站方卡片上未结事项的集合。服务端把这些事实收成字段 `basis`，即 64 位小写十六进制字符串，再交给管理端；它不是摘要正文，也不是数组。这些事实不向公开接口暴露地址或内部事项。管理员在预览中核实内容相同，并对这一对提交 `contentConfirmed: true`。确认只对本次 `basis` 有效。单次合并和批量里的每一对都各自携带 `contentConfirmed: true` 与 `basis`，不能共用一次确认。执行时在事务内重算 `basis`，不一致即拒绝，提示重新预览。

**接口**（`app/api/admin/resource-merges/`，对外路径带 `/api`，写法同[会社合并](../../app/api/admin/company-merges/route.ts)，`role < 3` 拒绝。字段以[官方镜像类型](../../types/api/officialMirror.ts)为准）：

| 接口 | 作用 |
| --- | --- |
| 读取列表 | GET。标签「待处理」实时计算候选，每行是一张用户卡片，附候选数量、配对分类、阻塞原因和推荐；「已驳回」「已合并」读合并记录。参数：标签、配对分类、分区、搜索、排序、分页 |
| 读取同游戏站方卡片 | `options` GET。入参用户卡片 ID，返回同游戏两个分区的全部站方卡片、推荐与阻塞原因，以及该用户卡片的合并和驳回记录。只读，不是合并授权 |
| 预览 | `preview` GET。入参用户卡片 ID 与站方卡片 ID，返回上文预览内容和 `basis`。`basis` 是 64 位小写十六进制字符串 |
| 合并 | `merge` POST。入参两个 ID、`basis` 与 `contentConfirmed: true`。成功返回合并结果；仅这一对已有 `merged` 记录时返回同一结果，驳回、删除或已与其他卡片合并均返回具体冲突 |
| 批量合并 | `batch` POST。入参一组已逐对核对内容的 ID 对，每对携带自己的 `basis` 与 `contentConfirmed: true`。只接受高置信对，每批最多 50 对。每对在自己的事务里重算高置信条件、基点与阻塞原因。返回 `{ outcomes, remaining }`。`outcomes` 包含已经开始事务的每一对：`merged` 并附结果、`skipped` 并附原因，或 `failed` 并附原因。`remaining` 只列出基础设施中断后尚未开始的对。业务上的跳过或失败不停止后面的对，也不写入 `remaining` |
| 单对驳回、重开 | `dismiss`、`reopen` POST。驳回写 `dismissed` 记录，重复提交幂等；重开仅删除 `dismissed` 行。两者沿用资源锁与锁内复核，不能覆盖或删除 `merged` 记录 |
| 整卡驳回 | `dismiss-card` POST。一次提交当前用户卡片下同分区、可驳回的全部配对，最多 50 对。用户卡片本身不合格时整个请求拒绝；其它站方卡片消失、跨分区、已合并或已成为幸存卡片等原因逐项跳过。结果分别列出本次写入、原本已驳回和未驳回的项，不删除任何卡片 |

合并、驳回、重开各写一条管理日志，类型 `resource_merge`、`resource_merge_dismiss`、`resource_merge_reopen`，在[管理日志类型表](../../constants/admin.ts)登记。合并的日志内容含两张卡片 ID、移动的链接 ID、备注是否追加、来源作者与舍弃的点赞数。合并记录的 `detail` 另保存本次核对基点及是否属于当时推荐，后者只用于统计，旧记录没有该值；它不参与后续推荐、权限或内容相同判断。

**合并事务**（`mergeStaffIntoUser`，重试与退避参照[资源变更](../../app/api/patch/resource/mutation.ts)的写法，但要锁两张卡片）：

1. 锁：按资源 ID 升序锁两张卡片，再按链接 ID 升序锁两边全部链接，再取链接维护锁，最后锁相关事项。锁序与 04、第 5.1 节一致。锁内重读状态，核对这一对仍是候选、没有阻塞原因、基点一致；精确这一对已有 `merged` 记录时返回已保存结果；被并卡片缺失但无该记录时返回不存在，幸存卡片已与其他卡片合并时返回冲突。
2. 移动链接：被并卡片的链接改 `resource_id` 到幸存卡片，不改 ID、版本、健康状态、`attached_at` 与 `content_changed_at`；每条写一条链接历史，原因 `merge`；排序值接在幸存卡片现有链接之后。
3. 移动获取记录：被并卡片的获取事件全部改指幸存卡片，包括 `link_id` 为空的配额事实。访客配额按访问者和时间窗口统计 `resource_grant` 记录，不看资源 ID（`checkVisitorResourceQuota`，[授权服务](../../app/api/patch/resource/download/access/grant.ts)第 58 行起），但这些记录对资源外键是级联删除，必须在删除被并卡片之前改指，否则配额事实会随卡片丢失。授权的主键是「访问者＋资源」，按访问者稳定顺序锁授权，两边都有授权时保留到期较晚的一份，不重新计算 24 小时。事件的创建时间、类型和到期时间原样保留，不合并或删除原有配额事件。只把资源级的 `download` 加到幸存卡片；链接级计数随链接移动，条目级计数不变（两张卡片同属一个条目）。
4. 重新指向：链接检测快照与链接维护记录里的标量资源 ID 改指幸存卡片。失效报告只关联稳定的链接 ID，不存在资源 ID 列，随链接保留，无需改写。链接历史对资源有级联删除的外键，必须在删除被并卡片之前改指；求助帖的资源外键是置空，也先改指，否则合并后会丢失关联。
5. 事项：仅把 `target_type = resource` 且 `target_id` 为被并卡片的已结案事项改指幸存卡片，不能误改编号相同的链接或其他目标事项。结案时去重键已置空（[事项服务](../../app/api/case/service.ts)第 3122 行），所以改指不会撞唯一键；以后重开时按新的目标重新计算去重键。已结案的链接类事项消息里记着旧资源 ID，不改写，界面按该 ID 定位时由本节「旧链接的定位」换算。
6. 点赞：被并卡片上的点赞随卡片级联删除，不迁移，不回收已发奖励，不发通知；删除前把来源作者编号、点赞数和原卡片编号写入本次合并审计，已有萌萌点流水保持原样。
7. 把合并后的备注写入幸存卡片，同时更新幸存卡片的 `updated`。
8. 删除被并卡片，不调用普通删除服务：不回收萌萌点，不清理对象存储（该事务不删除链接或文件）。`patch.resource_count` 由数据库触发器维护，不手工增减；删除后调用 `updatePatchAttributes` 刷新条目的类型、语言、平台聚合。
9. 写合并记录（`merged`，`detail` 含移动的链接 ID 和备注是否追加）和管理日志。

整对失败整体回滚。提交后失效缓存：两张卡片所在条目的内容与列表缓存、作者页、后台队列。失效失败只重试失效，不重新合并。

**合并后的授权与恢复**：

获取与恢复服务仍先校验有效资源授权和可见范围，再同步改成按「该访问者、当前链接版本、事件尚未到期」认定已揭示，不能继续要求事件到期时间大于等于合并后的授权到期时间；否则较早一侧仍有效的链接会丢失恢复资格并被重复计数。

[获取响应类型](../../types/api/patch.ts)、[恢复服务](../../app/api/patch/resource/download/access/restore/service.ts)、[资源恢复状态](../../components/patch/resource/ResourceDownload.tsx)和[链接卡片](../../components/patch/resource/DownloadCard.tsx)须一并接线：保留资源授权的 `obtainedExpiresAt`，另给每个已揭示链接返回 `revealedExpiresAt`；[资源列表投影](../../app/api/patch/resource/get.ts)、首次获取、`reused` 和恢复都从命中当前版本的有效事件取得该期限，多条有效事件取最晚期限。前端凭据按 `revealedExpiresAt` 逐链接保存和失效，资源授权标签仍按 `obtainedExpiresAt` 显示；资源级较晚期限不延长较早链接的揭示期限，已过期事件不复活。较早链接到期后用户主动再次获取可使用仍有效的资源授权，新增链接揭示，不再扣资源额度。

**并发**：

- 同一对重复提交，或同一张用户卡片被两个管理员合并到不同的站方卡片：同一对后到者按精确合并记录返回同一结果；同一用户卡片的另一配对返回已与其他卡片合并的冲突。
- 获取事件与求助帖的写入引用资源外键，会取该行的键共享锁，与合并持有的行锁冲突，因此在合并提交前后串行化：先提交的获取或求助写入随合并迁移；等待合并后才写入旧资源的请求返回已合并或不存在，访问者定位到幸存卡片后重试。不得对已成功提交的获取重复扣额度或计数，也不承诺请求耗时只等于一个事务。
- 新建事项与合并的互斥靠事项创建已有的资源行锁（第 5.1 节）：创建先提交，则合并因未结事项被阻塞；合并先提交，则创建发现资源已不存在而失败。
- 陈旧预览按基点拒绝。

**驳回与重开**：驳回把这一对写成 `dismissed`，之后它不再是候选，也不再计入「互为唯一」的判断，所以另一张候选可能因此升为高置信对。驳回、重开与合并并发时在同一资源锁下复核记录状态；重开只删除 `dismissed` 行，这一对回到待处理。成功合并的映射不能重开、覆盖或删除。

**旧链接的定位**：条目页是定时再生成的静态页面，不读取查询参数，无法在服务端换 ID，因此在浏览器端换。

1. 公开查找是 `GET /api/patch/resource/resolve`，查询参数为资源编号。它读取合并记录中被并卡片等于该编号且状态为已合并的一行，再核对幸存卡片：须为已公开的游戏资源或补丁，所属游戏已公开，并符合当前访问者的内容可见范围。命中时返回幸存卡片的当前资源编号、当前游戏编号、当前游戏唯一标识 `patchUniqueId` 和分区。不存在、未公开或当前访问者不可见时，正文为 JSON null，状态为成功，不区分原因。不返回原始链接、发布者私有资料或合并审计。响应为私人且禁止存储，不能进入共享缓存，避免混用成人内容和屏蔽偏好。
2. [条目页的资源定位](../../components/patch/resource/Tabs.tsx)读取 `resourceId` 与 `resourceSection`，在已加载的资源里找不到该 ID 时调用查找接口，命中则用 `router.replace` 换成幸存卡片的当前游戏、分区与 ID，再走原有的滚动与高亮。查询不命中停止处理，不循环重试；旧 ID 尚在缓存列表中但操作返回不存在时也允许重新定位一次，迟到响应不得覆盖用户的新导航。
3. 求助创建页（`app/(site)/help/create/page.tsx`，服务端组件）的查询参数是资源编号。所查卡片仍在、已公开且属于当前可见的查询游戏时，预填该编号，不查合并。所查卡片已不存在时，用上述公开查找做一次映射：仍在同一游戏则预填幸存卡片；幸存卡片当前位于另一公开且该访问者可见的游戏时，预填换成该游戏。没有映射或不可见时，保留仍可见的查询游戏，不填资源编号，不暴露隐藏卡片。卡片仍在但未公开，或不属于查询游戏时，不跟随合并。
4. 其他生成 `resourceId` 链接的入口（[事项展示](../../components/case/caseDisplay.ts)第 92 行、[分享按钮](../../components/patch/resource/ResourceShareButton.tsx)第 14 行）不改，它们读到旧 ID 时由第 2 点换算。历史通知正文里的链接不批量改写。
5. 后台收件箱对待审核资源申请的预览页 `/preview/resource/[id]` 不涉及已公开的卡片，不处理。

### 5.4 获取计数切换（M06-5）

实施前公开计数由点击上报累加，与是否取得链接无关，见第 1 节基线。要求改为按「获取」计数。计数点放在[获取授权链路](../../app/api/patch/resource/download/access/grant.ts)的 `resolveResourceAccessGrant`，它在可串行化事务里运行并自带重试，按结果分支计数：

| 分支 | 含义 | 链接 | 资源 | 条目 |
| --- | --- | --- | --- | --- |
| `resource_granted` | 24 小时内第一次获取这张卡片，新建授权并揭示链接 | +1 | +1 | +1 |
| `link_revealed` | 已有授权，第一次揭示另一条链接 | +1 | 0 | 0 |
| `reused` | 已有授权，重复获取已揭示的链接 | 0 | 0 | 0 |
| `limited` | 配额拒绝 | 0 | 0 | 0 |

恢复访问（[恢复服务](../../app/api/patch/resource/download/access/restore/service.ts)不经过该函数）与后台读取不计数。未登录的访问者同样计数。旧数值保留，切换之后只按新规则累加。授权到期后再次获取会再计一次；补链会产生新的链接版本，同一访问者可以对它再计一次，这是预期行为。

实现要点：

- 三处计数用原生 SQL 在同一个事务里递增，不经 Prisma 更新，避免推进 `updated`（合并基点依赖它），写法同[点击上报](../../app/api/patch/resource/download/service.ts)。事务重试时计数随事务回滚，不会重复。
- 提交后失效缓存，沿用点击上报的三个调用：`setRealtimePatchDownloadStats`、`invalidatePatchContentCache`、`invalidatePatchListCaches`。
- `PUT /patch/resource/download`（调用方 `DownloadCard.tsx` 第 254 至 261 行）不再累加公开计数。

**辅助点击统计**（本版采用既有默认方案）：点击上报改为只累加新增的链接级 `click` 列，保留基线 5.8 的辅助统计。首版只在控制台「下载资源」页的链接详情显示，工作台暂不显示。点击接口仍校验资源和链接归属及公开可见范围，沿用现有防滥用限制；部署切换时旧客户端的点击请求也只能写辅助列，不能继续累加公开计数。

**文案**：公开计数的名称统一为「获取次数」。涉及位置：`components/dashboard/resource/DashboardResources.tsx` 第 304 行（「下载次数」）、`components/dashboard/resource/resourceFilters.tsx` 第 65 至 66 行（「下载次数（多到少／少到多）」）、`components/resource/FilterBar.tsx` 第 23、57 行（「下载数」）、`components/ranking/RankingContainer.tsx` 第 29 行（「下载数」）、`components/kun/CardStats.tsx` 第 32 行（提示「下载数」）、`components/galgame/FilterBar.tsx` 第 59、167 行（「下载量」）；`components/resource/ResourceCard.tsx` 第 57 至 64 行显示的是 `resource.download`，核对其提示文字。数据库字段名 `download` 不改。条目级与资源级的 `download` 都是累计值，切换后新增量按新口径，排行榜按它排序，口径变化写进更新日志。

## 6. 控制台界面（M06-3、M06-4）

沿用控制台搜索列表与详情的交互。在[导航常量](../../constants/dashboard.ts)「内容」分组里、「会社合并」之后提供两项，`minRole` 为 3：`站方备份`（`/dashboard/backup`）、`资源合并`（`/dashboard/resource-merges`）。

**站方备份页**：顶部三个标签，各带数量；左栏筛选分区；列表行显示游戏名、卡片名、发布者、获取次数、外部链接数。详情显示外部链接（地址、存储类型、变动时间）、备注、站方备份及日期。操作按标签分开：「未备份」里是「忽略」（可填理由）和「去添加备份」；「待重新备份」里是「去添加备份」和「无需重新备份」；「已忽略」里是「撤销忽略」。「去添加备份」打开收件箱的资源编辑表单。

**资源合并工作台**（[页面布局](../../components/dashboard/official-mirror/merge/MergeWorkbenchPage.tsx)与[配对工作台](../../components/dashboard/official-mirror/merge/MergeWorkbench.tsx)）：标签是「待处理／已驳回／已合并」，按用户卡片一行；可以搜索游戏、资源或发布者，筛选分区，待处理另筛高置信与需人工核对。待处理默认按获取次数从高到低，也可按等待最久、游戏名称排序；历史标签默认最近处理，可改为最早处理、游戏名称或获取次数。相同排序条件以用户卡片编号决定稳定顺序。每行只显示一个主要徽标：当前没有任何可合并配对时显示「无可合并项」，唯一实时候选为高置信时显示「高置信」，有推荐时显示「推荐 #编号」，其余显示「需人工核对」。「官方」数量是同游戏两个分区的站方卡片总数，不等于实时候选数。

桌面为可调整宽度的用户列表和工作台，窄屏在列表与详情之间切换；选中编号保留在网址，直接打开不在当前分页中的编号也可读取。待处理工作台默认选择推荐项，没有推荐则选择首个可合并项，再退回首项；已驳回标签优先选已驳回配对。站方卡片按「推荐」「其他可合并」「不可合并」分组显示；不可合并项可以展开，查看跨分区、已驳回及其它阻塞原因。选中配对不会构成内容确认。

左侧通过同源嵌入页对照用户卡片与合并后外观，右侧列出各站方卡片和逐项匹配信号；结果区按当前预览说明站方卡片删除、用户卡片保留的名称与属性、链接顺序与站方备份数、备注、获取次数、舍弃点赞以及其它退出的配对。确认合并或加入清单时必须逐对勾选「已核实两张卡片为同一份内容」。单对合并、单对驳回、重开分别确认；「驳回全部配对」处理当前卡片下所有可驳回的同分区配对，返回部分跳过时留在当前卡片展示原因。「已合并」只显示处理记录和当前卡片，不能重开、驳回或再次合并，也不请求新的合并预览。

**批量清单**（[清单状态](../../components/dashboard/official-mirror/merge/useMergeBatchList.ts)）：高置信且当前可合并的配对，在预览中逐对确认后才能加入；一张用户卡片最多保留一项，整批最多 50 对。加入清单不发送合并写请求，执行前还有整批后果确认。结果逐对区分合并、跳过、失败和基础设施中断后的未开始；已开始的配对从清单移除，未开始或未返回结果的保留，以便重新核对后重试。跳过和失败不因为名称被省略而消失，结果使用加入时的卡片名称。

清单只存于当前浏览器标签页的 `sessionStorage`，不含下载地址或提取、解压凭据，但保存了配对编号、名称与核对基点。页面重新载入或同一标签页的导航可以恢复，关闭标签页或清除站点数据后消失，不是服务端队列，也不承诺跨标签页、跨设备同步。存储不可用或内容损坏时退回当前页面的内存清单；只恢复结构合法、带确认的高置信项。单对合并成功或整卡驳回会清掉该用户卡片对应的清单项；会话历史或凭据切换不属于这份本地清单的隔离机制。

**管理员受限只读预览**（[单卡预览](../../app/(site)/preview/resource-card/[id]/page.tsx)、[合并后预览](../../app/(site)/preview/resource-merge/page.tsx)与[预览投影](../../lib/officialMirror/previewCard.ts)）：两类页面都先要求管理员身份，再读取资源，不限制卡片或游戏必须公开；动态生成并声明不索引。它们用于核对任意状态的单卡和指定配对的合并后外观，仍没有编辑、事项处理、下载获取或恢复、点赞写操作。合并后预览保留用户卡片的发布者、点赞、创建时间与事项徽标，按预览合成名称、属性、备注、链接顺序和合计获取次数；链接沿用各自来源的健康与备份信息。管理员能看到链接地址，但投影不提供提取码或解压码，也不附带管理员的获取授权、已揭示状态或点赞状态。它不是公开资源页，不能用管理员预览绕过普通读者的可见性或取得下载凭据。

**迟到响应**：工作台以选中用户卡片、配对和请求序号筛选候选与预览响应；组件卸载或目标改变后，旧响应不覆盖当前配对。合并确认保存打开对话框时的预览，若同一配对的新预览基点已经变化，则要求重新核对。写入结果必须匹配原请求的两张卡片及幸存卡片，异常响应只提示结果未知，不冒充成功。单对合并的迟到成功结果不会把管理员已选中的另一张卡片跳走；旧目标完成后的列表推进也须先核对当前选中项。缓存重试分别绑定原合并对或批量结果行，迟到的刷新结果不能改写另一对的状态。批量结果只认本次运行，关闭上次结果后其迟到的缓存响应不再恢复旧面板。

确认框只写后果，不加复述标签或开发者视角的小字。

## 7. 任务与缓存

不新增常驻定时任务，也没有候选检测任务：候选实时计算。交接、合并、添加备份、忽略和获取计数后的缓存失效按第 5 节逐项列出。提交后刷新失败只记录可定位的失败，不重做已经提交的业务变更，也不是自动重试。单对合并保留结果条，批量保留每一对的结果，管理员可点「仅刷新缓存」，通过 `POST /api/admin/backup/refresh-cache` 重放这次刷新；它携带对应游戏标识与相关作者，不再调用合并或批量接口。浏览器关闭结果条或整批结果面板后，不再保留相应的点击重试入口；生产缓存是否实际失效仍须按目标环境证据判断。

交接的文件清理须有持久待办：在删除 `s3` 链接的同一事务中写入资源文件清理记录，保存受限的对象定位、来源资源标量编号和执行状态，不随资源级联删除，不保存下载密码或令牌，不向公开接口和普通管理日志暴露对象定位。提交后尝试清理；执行前复用现存文件引用复查，有活动引用则取消删除；对象确认已删或已不存在才完成待办，失败保留。由受控维护命令重放，进程退出后仍可续作；不能把日志中的一句失败当作清理凭据。清理表与命令属于 M06-1/2，按现有存储规则实现，不扩展为通用任务平台。

管理日志类型登记（[管理日志类型表](../../constants/admin.ts)）：`resource_handover`、`resource_merge`、`resource_merge_dismiss`、`resource_merge_reopen`、`backup_ignore`、`backup_unignore`、`backup_dismiss`。

下列实验仍定义完整验收标准。上述结论限于实际运行的样本和并发时序，不证明绝对无死锁。对象存储、链接检测与邮件使用本机受控服务，未验证真实提供方、Safari、Firefox 或真实手机软键盘；高度收缩只模拟软键盘占用视口。删除期间新增对象引用的已知风险仍在。第 11 节的 dump 核查与隔离运行验收相互独立，均不证明生产已经迁移或部署。

- **E06-01 交接**：
  - 普通用户明确选择交由站方维护：自己的链接移除，卡片与备份保留，`publisher_left_at` 写入；重复请求幂等；之后该用户无法编辑、删除、管理链接。
  - 事项：新事项归站方；原发布者的未结事项转站方，对话与关注者保留，转交事件的触发器是 `publisher_left` 且不带原归属；`waiting_reporter` 保持状态；交接前已因超时转给站方的事项，原发布者基于发布者身份的结案权与通知一并终止，其他参与身份保留；重开已结案事项时归属站方。
  - 竞态：确认交接后备份被移除，不得转成整张删除；确认删除后站方新增备份，不得静默转成交接；事项创建与交接并发时，不会留下归属原发布者的新事项（创建路径已有的资源行锁，此条用并发测试证明）。
  - 通知：求助帖、后台修改、失效反馈都不再发给原发布者。
  - 展示：工作台维护列表不列出；个人主页发布列表仍列出且带标识，成功提示可直达发布记录；创作者申请计数不变；菜单与确认按钮区分「交由站方维护」和「删除资源」，工作台显示「我维护的资源」，交接后条目页刷新卡片而不是移除。
  - 奖励：交接前点赞、交接后取消，仍向同一原作者回收一点；交接后新增点赞奖励同一原作者；重复交接不改余额、不新增流水，既有流水字段保持不变；管理员普通清理已交接卡片不回收 3 点，并保留审计依据。
  - 失败恢复：交接事务回滚不留下清理待办；提交后进程退出仍能找到并重放待办；共享文件引用保护；外部链接新于备份时交接日志保留比较结果；缓存与清理失败不重复交接或写奖励；`waiting_reporter` 的陈旧 revision 被拒，开启者或关注者的独立参与身份保留。
  - 分组：原用户卡片在添加备份、交接和合并后始终位于社区组，独立站方资源仍位于官方组。
- **E06-02 备份队列**：
  - 三个标签的进入与退出各自覆盖：未备份；未忽略且已备份无变动不出现；备份后外部链接新增或改地址出现在待重新备份；站方把备份换成新地址后消失；点「无需重新备份」后消失，更晚的变动再次出现。
  - 忽略优先于其他标签，忽略后换链接不回流，撤销忽略按当前事实归位，已有备份且无新变动时退出队列；有待处理合并候选但无备份的用户卡片仍在「未备份」；只有 `s3` 链接的卡片、站方卡片不出现。
  - 迁移：`attached_at` 回填分别覆盖统一盖章与其余链接两类；sync 重复执行结果不变；postflight 断言无空值并打印实际核实的统一盖章链接数；覆盖误判候选、存量非空、中断后续跑和回退兼容边界，不把历史 1159 条写成生产断言。
  - 竞态：详情打开后外部链接新增、换地址或存储类型变化，「无需重新备份」拒绝旧基点；重复提交不推进水位、不吞掉之后的更新；已交接卡片后来添加外部链接仍不入队。
- **E06-03 合并**：
  - 真实 PostgreSQL 上的并发合并：同一对重复提交、同一用户卡片合并到不同站方卡片、合并与事项创建并发、合并与获取并发、合并与求助帖写入并发；陈旧预览被拒；失败整体回滚。
  - 数据完整：链接 ID、版本、健康状态与两个时间保持；获取事件含 `link_id` 为空的配额事实，授权按访问者合并取较晚到期；资源级 `download` 相加、条目级不变；链接历史、求助帖、已结案事项改指幸存卡片，重开后去重键按新目标计算；点赞不迁移且不回收奖励；站方卡片有未结事项、备注超长、用户卡片已交接时被阻塞；被并卡片删除后不回收萌萌点、不触碰对象存储；条目资源计数由触发器正确维护。
  - 候选：一张用户卡片多个候选时只能人工；驳回后另一张候选升为高置信；重开恢复；批量合并只处理经管理员确认同一内容且基点有效的高置信对并报告跳过项；相同属性但版本或用途不同的卡片不得合并；非公开站方卡片、含非 `touchgal` 链接的站方卡片被阻塞。
  - 旧链接：条目页带旧 `resourceId` 时被换成幸存卡片，求助创建页同理。
  - 授权与恢复：同一访问者两份授权到期不同，较早一侧仍有效链接可恢复且不重复计数；逐链接到期后退出已揭示状态，过期与旧版本不复活；原有游客日／周配额事件不减少。
  - 冲突与隐私：驳回、重开与合并并发不能删除成功映射；无成功记录的删除不冒充已合并；旧 ID 查找遵守游戏与资源可见范围，跨游戏移动后定位当前路径，不发生重定向循环。
- **E06-04 获取计数**：四个分支的计数符合第 5.4 节的表；同一访问者在同一轮固定 24 小时资源授权内只计一次，不按任意滚动 24 小时去重；恢复访问与后台读取不计数；补链后可再计一次；事务重试不重复计数；旧数值保留；点击上报不再累加公开计数；缓存失效被调用；文案已改。



## 9. 实施顺序与任务

M06-1（数据与权限合同）→ M06-2（交接）→ M06-3（备份队列）→ M06-4（合并）→ M06-5（计数）→ M06-6（接线、说明与清理）。

- M06-2 必须先于或同时与 M06-3、M06-4 上线：生产环境在交接可用之前，普通用户没有退出含 `touchgal` 链接卡片维护的入口。站方一旦开始把备份放进用户卡片，这个拒绝就会变成用户能看到的问题。
- M06-5 独立，可与其他项并行。
- 后端按交接、备份队列与忽略、合并的顺序实现，每项在真实 PostgreSQL 上通过事务测试后再接页面。
- M06-6 包含：第 5.5 节的接线；向 09 提供备份队列口径（三个标签的数量、最老条目的年龄、忽略数量；未备份取外部链接最早加入时间，待重新备份取同时越过备份时间与已检查水位的外部链接最早变动时间，待合并取两张卡片创建时间的较晚者，再对队列取最老值；忽略时间只用于审计，不冒充等待起点，各项公式与 [09 队列口径](./09-metrics-and-retirement.md#41-现状与处理完成时间来源只读核实)保持一致，不提供等待时长中位数，因为队列进入时间不另存）；公告的本地待发布文案；清理 03 预留的 `takedown_request`、`mirror_version_check`。公告尚未对外发布，这两类事项类型仍等生产记录确认。

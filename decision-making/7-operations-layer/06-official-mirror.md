# 模块 06：官方备份、资源接管与合并（实施计划）

状态：2026-10-08 已确认管理员后台合并推荐与人工合并、有官方备份时站方接管原卡片；关键资源说明默认保留，用户不能一键清空整段备注。混合个人内容的管理员整理、匿名生效和多贡献者资料维护仍需落实施工细节；本轮仅改计划。配对 [PM 版](./06-official-mirror-pm.md)，任务编号 M06-1～6、实验 E06-01～04 保持不变。

## 1. 目标与基线

资源卡片是内容／版本资料的载体，官方镜像是站方维护的链接副本。用户退出维护不删除仍可用的官方副本或使其失去必要说明。候选从同游戏的不同资源中产生，按标题、类型、语言等事实给推荐，由管理员决定合并，不能仅支持旧的“官方卡片并入用户卡片”组合。

## 2. 已定规则与设计边界

- 同游戏后台候选与人工合并、站方接管原卡片已获确认；首版以逐对合并形成可审阅事务，候选界面可按游戏分组。
- 退出维护时保留官方链接、原卡片 ID 和必要标题／版本／属性资料；重要安装、依赖、适用版本、已知问题等备注默认保留。
- 署名保留或匿名与资料维护归属分别判断；关键资源说明默认保留。涉及混合个人内容的管理员整理和匿名完成时点仍待定，不能只隐藏昵称却公开其它身份内容，也不能让用户一键清空整段备注。
- 多用户合并必须保留各自链接权限和贡献事实。单个幸存卡片的 user_id 不能代表所有被搬入链接的所有者。
- 06 是未来实现，不改当前 03/D37 历史参与规则，不改变首批 04／05／10 的七天、机器判定和冲突复核。

## 3. 术语

| 概念       | 含义                                                             |
| ---------- | ---------------------------------------------------------------- |
| 卡片维护方 | 负责标题、分类及整理后的资源说明；接管卡片由站方负责             |
| 链接归属方 | 该条链接的管理者；官方链接归站方，用户贡献链接保留原归属         |
| 贡献署名   | 对来源贡献的公开展示，不能被当作当前维护义务或全部链接权限       |
| 合并候选对 | 同游戏两条资源的证据、冲突、基点和处置记录，组合不限于用户＋官方 |
| 接管       | 保留资源 ID，明确把维护责任交站方；不是调用旧资源删除接口        |

## 4. 数据模型与迁移合同（M06-1）

当前 [资源 schema](../../prisma/schema/patch-resource.prisma) 没有 official 与多贡献者关系，真实删除会级联影响 access/grant。新数据在实施前由一个后端作者冻结并交付 SQL，不能先上合并界面再补权限。

建议最小数据合同：

1. 官方链接标记、测试时间、镜像版本确认与进度、暂停发放状态，沿既有模块范围落实。
2. 每条普通链接的贡献者／管理者归属，回填依据原资源作者；合并搬迁后不随卡片 owner 改写。退出只删除本人有权管理的链接，整表单更新自动保留他人及官方链接。
3. 卡片维护方与来源贡献记录。单用户移交可使用原始作者快照；多用户合并必须保留每个来源贡献、署名可见性和必要来源说明，不能用一个 origin_user_id 覆盖其它贡献者。具体关系表由 M06-1 按定稿的资料管理规则确定。
4. 候选用排序后的 resource_a_id/resource_b_id 等价唯一键，记录游戏、双方基点、证据与冲突、人工决定、幸存 ID、创建／解决时间。资源 ID 与必要名称快照不能因源卡片删除而级联丢失。终态候选不被重复扫描自动重开。
5. 点赞的 reward_user_id、各来源发布奖励实际接收者，必须在合并／移交后保持可追溯；接收账号已注销时按既有账务规则处理，不能把回退扣到站方或幸存卡片作者。
6. 模块 10 的最新检测快照跟随稳定 link_id，版本不变时不重造结果；机器／用户冲突来源、反馈和事项引用一并核对。

供 09 读取的队列时间合同继续保留：首次镜像使用 `mirror_queue_entered_at`，重新镜像使用 `mirror_basis.capturedAt`，合并候选使用 `created/resolved_at`，成功处理审计带 `admin_log.queue_entered_at`。持续在队不重置起点，离队后再入队开始新一轮；不从 `updated` 或资源创建时间猜历史等待。

关键备注的源文和整理稿需要在管理预览里可对照；只保留执行当前需求所需的来源记录，不新建通用编辑历史平台。公开 DTO 不暴露匿名贡献者、联系方式、真实下载凭据或管理员审计内容。

## 5. 接口、权限、事务与幂等

### 5.1 退出维护与接管

含可用官方备份时，用户删除／退出入口显示接管结果并二次确认。事务内锁资源与链接，复核官方备份仍存在、资源未被并发删除／暂停；移除本人普通链接走 04 的历史、链接事项收尾和 access.link_id SetNull 逻辑；保留官方及其它贡献者链接，资源 ID 不变；更新站方维护方和署名选择，保留关键标题、属性和说明。

已有官方副本登记但其分享链接暂时失效时，不得按“无官方备份”回落到用户物理删除路径。保留卡片、必要说明和站方文件引用，交站方核查或补链；退出界面如实说明待修复，不宣称官方链接仍可用。

重复退出不再次删链、发消息或回退奖励。只移交维护不回退发布奖励，不把原奖励转记到站方；真正删除时再按实际奖励接收者处理。移交后新反馈进入当前负责方队列，旧事项参与关系和既有对话权限按 03/D37 保留；不通过改当前 user_id 重写旧身份。

接管事务还须把原归发布者、针对该资源的未结维护事项交给站方，保留对话、订阅与既有权限并记录真实交接原因；否则新反馈按去重规则并入旧事项时，仍会落回原发布者。只迁处理责任，不自动结案，不改已有私有举报的读取范围；交接原因不能伪装成七天超时，不自动赋予 D36 的超时结案特例。由 M06-1 在 03 登记相应事件载荷并纳入 E06-01。

匿名若涉及备注中的个人信息，必须按已定整理流程处理后才报告完成；该细则未定前不实现整段自动删除，也不假报匿名成功。无官方备份且仅有本人链接的普通资源沿既有删除规则；多贡献卡片不能由一人清空其它人的链接。

### 5.2 编辑与管理读取

复用 04 的 baseLinks 基点和稳定 ID 更新。非管理员可变载荷只能修改本人链接，官方行和他人行只读保留，不能利用遗漏字段达到删除效果。卡片元数据维护权由 06 的定稿规则检查，不能把链接编辑权扩大成公共说明清空权。

管理读取独立鉴权，返回必要私有字段而不制造 access/grant、获取计数或报告资格。写入口保留 CSRF 与对象归属校验；新后台仍按既有管理员／超级管理员边界，不因按钮确认而放宽权限。

### 5.3 候选生成与合并预览

范围固定同 patch_id；分区、类型、语言、平台和版本说明共同提供证据。名称规范化／相似匹配用于推荐，明显冲突不作为高置信候选；更新时间和大小不证明内容相同。允许管理员手工配对并查看冲突，但合并前仍须明确核实内容兼容。

界面按游戏分组，给出推荐原因、双方字段与关键备注差异、链接归属和官方标记、版本／健康／机器快照、幸存卡片与合并后的资料预览。管理员明确确认保留目标与整理内容，取消确认零写入。重复扫描幂等，误配可以排除；源数据变化后旧预览失效并要求刷新。

执行规则是：证据充分时管理员说明依据后合并；内容或版本不明时询问、补资料或排除。等待七天或无人回复本身不是内容相同的证明，不触发自动合并。候选不得无限阻挡资源维护：终态／失效／排除的候选从占用中释放，仍有真实待核候选的情况要明确展示。

### 5.4 合并事务（M06-4）

固定两资源 ID 升序→候选→链接 ID 升序→事项 ID 升序取锁；锁内重读双方状态、游戏／分区、内容基点和确认结果。两对共享资源的并发只允许合法顺序，败方返回冲突／按既有有界事务重试，网络与缓存不放入重试事务。被删侧不再要求必须是管理员作者，但所有贡献者权限保护必须先交付。

| 对象             | 合并不变量                                                                                                                                              |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 链接             | 搬 resource_id，保持 link_id、地址版本和原链接归属；官方标记只按可信站方事实，不因源作者是管理员就把全部链接变官方                                      |
| 获取事件         | 源 access 全部搬迁，含 link_id 为空的配额事实；不删除、不去重历史事件                                                                                   |
| 授权             | 同 actor/resource 冲突保留较晚的原 expires，不从当前时间重新算 24 小时                                                                                  |
| 报告、检测与历史 | 稳定 link_id 的报告和检测快照原样保留；链接历史 resource_id 改指幸存卡片，保留来源 ID／合并记录                                                         |
| 贡献与说明       | 保留所有来源、真实奖励接收者和必要使用说明；合并稿由管理员核对，不能只留幸存卡片那一份备注                                                              |
| 点赞             | 按关系去重，保留真实 reward_user_id；重合点赞的既有奖励是否追溯调整仍是 D7 取舍，默认候选不追溯                                                         |
| 事项             | 使用 03 open/append/close 与目标迁移合同；未结唯一冲突按合并／订阅规则处理，私有正文不向新参与者广播；保留历史与 merged_to，不裸改 target_id 撞唯一约束 |
| 计数             | 资源历史计数按已定口径合并，条目计数不再加一遍；resource_count 交既有触发器，不能手工再减                                                               |
| 源卡片           | 事务内完成引用搬迁后处理源行，不调用会清 S3／回退奖励的普通删除服务；不得删除仍被引用的文件                                                             |
| 幂等             | 候选只成功一次，其它受影响候选失效并留原因；失败整体回滚，提交后缓存失败只重试失效，不重新合并                                                          |

旧 resourceId 深链用合并映射有界跟随并防环，定位到幸存卡片并说明已合并；历史通知正文不批量重写。合并成功审计包含基点、管理员选择、来源和目标，原记录不能随源资源删除消失。

### 5.5 官方文件下架

退出维护不等于文件有问题。真正暂停／下架走明确理由和管理员处理：暂停后新的 access/restore 按规则拒绝，管理读取独立授权；盘侧文件处理与本站删除分清失败边界，不能声称已收回用户此前复制的地址。恢复或删除必须有明确状态条件、一次通知和对应审计。S3 清理仍按现有引用核查与补偿规则，不用合并调用链顺带删文件。

## 6. 前后台界面与文件

前台 HeroUI：官方标记、来源署名、当前维护方、退出／接管说明、关键备注及多链接只读权限。dashboard shadcn：按游戏的合并候选列表、两侧对照、整理后的标题／说明预览、确认／排除、镜像与重新镜像队列、资源管理迁移。

API 继续在 app/api/admin/mirror 与资源服务边界，DTO／schema／校验由后端冻结，前端不自行改变资料或链接权限。每个修改点列入文件归属；共用 update、access、case 和缓存入口单写整合。

## 7. 任务与缓存

镜像队列沿首次／重新镜像区分，审核与镜像解耦；只含站内对象存储的资源不重复进入外链搬运队列。记录真实入队与完成时间供 09 使用，历史缺口不推算。具体镜像确认等待参数在本模块定稿，不复用 04 已确定的疑似七天规则。

合并候选只推荐不自动合并。退出、接管、署名与备注整理、合并、官方链接变动提交后，失效条目内容／资源列表、作者页、后台队列和深链相关缓存。按事件实际需要通知，不因重试重复发送。

## 8. 迁移与回填

先盘点现有官方存储、作者、链接与授权，再按可信数据回填；不能仅凭名称猜官方身份或文件版本。新增链接归属和来源贡献字段必须在允许多用户合并前就绪。站方接管账号、匿名资料整理策略和真正删除奖励落点在 SQL 前明确。

使用审定的 preflight/sync/postflight，固定切换基点并验证重跑，不覆盖切换后的真实归属／计数／署名数据。schema guard 不能放宽。应用回退不等于拆回已合并数据；暂停新增合并、保留映射与来源记录，按具体补偿方案处理，不能盲目恢复旧卡片。

## 10. 实施任务与验收

M06-1 先冻结数据／链接权限／贡献与维护边界；M06-2 接管与退出；M06-3 两类镜像队列；M06-4 候选、对照和管理员合并；M06-5 计数与账务接收者；M06-6 新后台资源管理和运营说明。后端与前端按共享合同并行，但合并、删除、授权和奖励的最终事务由单一后端作者整合。

所有 E06 与 E2E 通过、必要细则确认后才成为发布候选；生产按具体授权执行，未完成的存量合并可以长期运营，不阻塞后续模块开发。

## 11. 非目标

不做自动合并、定时全站链接扫描、自动判断文件内容相同或通用版本平台；不通过匿名选择清空重要使用说明；不让一个贡献者取得他人链接权限；不重新计算全部历史下载或重做全站账务。07 将来新增引用需按自己的上线合同接入，不预查询不存在的求助表。

## 12. 已定与待定

已定：同游戏后台合并推荐与管理员最终合并；有可用官方备份时站方接管原卡片；必要标题／版本资料保留，署名可保留或匿名；关键备注不能因退出自动丢失。

施工细节：混合备注的整理和匿名生效流程；多用户合并后的公共资料维护方与贡献署名表现；官方字段回填依据、接管账号及原有重复点赞奖励处理。证据充分时说明依据、证据不足时询问或排除已是执行规则。上述细节只阻塞对应06工作包，不回头阻塞04／05／10。

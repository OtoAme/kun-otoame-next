## 3. 术语

| 术语         | 本文定义                                                                                 |
| ------------ | ---------------------------------------------------------------------------------------- |
| 官方链接     | 同一资源下 `official = true` 的链接，存储类型 `touchgal`，归属方站方                     |
| 镜像进度     | 站方手工搬运的四个阶段：待下载、已下载待上传、已上传待建链接、完成（完成即存在官方链接） |
| 镜像版本确认 | 向发布者提出的二选一：当前链接与官方备份是否同一内容，结果写 `mirror_check`              |
| 候选对       | 同条目下一条用户资源与一条站方资源组成的待合并记录，含状态与询问时间                     |
| 获取次数     | 按揭示累加的计数，沿用 `download` 列，旧点击数值作为起点                                 |
| 点击辅助计数 | 跳转点击写入链接级 `click_count`，只给发布者与管理员看                                   |
| 移交         | 资源 `user_id` 改为站方账号、原发布者记入 `origin_user_id`、署名由 `credit_visible` 控制 |
| 申请下架     | 发布者写入 `takedown_requested_at` 并开工单，期间该资源所有链接停止发放                  |

## 4. 数据模型

### 4.1 现状事实（只读核查）

- [patch-resource.prisma](../../prisma/schema/patch-resource.prisma)：`patch_resource` 没有官方、测试、镜像、下架、原署名字段，`status` 只有 0/1/2；`patch_resource_link` 没有 `official`；`patch_resource_access` 与 `patch_resource_access_grant` 对资源、链接都是级联删除，删资源即删揭示与授权。
- 授权语义：grant 主键 `(actor_key, resource_id)`、24 小时；access 用 `access_kind` 区分 `resource_grant` 与 `link_reveal`（[grant.ts](../../app/api/patch/resource/download/access/grant.ts)）。恢复接口只读（[restore/service.ts](../../app/api/patch/resource/download/access/restore/service.ts)）。
- 计数现状：[download/service.ts](../../app/api/patch/resource/download/service.ts) 用原生 SQL 累加链接、资源、条目三张表的 `download` 并保持 `updated` 不变，因此 `updated` 既不刷新也不能证明文件版本；基线 5.7 关于「点击刷新 updated」的描述已经过时，但存量仍必须逐对询问。
- 链接持久化：[update.ts](../../app/api/patch/resource/update.ts) 读取输入 ID 后仍在事务内 `links.deleteMany({})` 再 `create`，链接 ID 不稳定。模块 04 的 M04-1 是本模块的硬前置。
- 权限现状：[resourcePermissions.ts](../../components/patch/resource/resourcePermissions.ts) 只有资源级判断；[app/(site)/admin/resource/actions.ts](../../app/(site)/admin/resource/actions.ts) 用 `role < 4`，而 [app/api/admin/resource/route.ts](../../app/api/admin/resource/route.ts) 用 `role < 3`。
- 奖励现状：[create.ts](../../app/api/patch/resource/create.ts) 在创建事务内无条件发 3 点（含 `status = 2` 的待审），[resource-apply/service.ts](../../app/api/admin/resource-apply/service.ts) 通过时不再发奖励、拒绝时直接删除且不回退；普通删除路径回退 3 点。本模块不改这些规则。
- 点赞唯一约束 `(user_id, resource_id)`，点赞附带既有点数变动（[like/service.ts](../../app/api/patch/resource/like/service.ts)）。
- 资源盘：已有 [app/api/cloudreve/share-size/route.ts](../../app/api/cloudreve/share-size/route.ts) 与 [fetchAlistSize.ts](../../components/patch/resource/publish/fetchAlistSize.ts) 调用 Cloudreve 的公开分享接口（`/api/v3/share/info`、`/api/v3/share/list`，域名常量 `pan.otoame.top`）读取分享大小与文件列表，这是只读且不带凭据的；没有任何管理客户端，未接入文件删除、离线下载或存储级别操作。`touchgal` 链接的 `content` 是人工填写的分享地址。站内没接入不等于资源盘没有这些能力，核对方式与结论见第 11、12 节。

### 4.3 拟新增表

拟新增 `prisma/schema/mirror.prisma`，一张 `patch_resource_mirror_candidate`：`id`、`patch_id`、`user_resource_id`、`official_resource_id`、`user_resource_name`、`official_resource_name`、`status` varchar(20)（`unasked`/`awaiting_publisher`/`same`/`changed`/`no_response`/`merged`/`excluded`/`stale`）、`asked_case_id?`、`asked_revision?`、`asked_snapshot?`（问句里双方被问链接的 `[{linkId, version}]`）、`asked_at?`、`answered_at?`、`merged_into_resource_id?`、`resolved_at?`（`merged`、`excluded`、`stale` 三种终止状态都写，`created` 到它就是一对候选的完整生命周期）、`decided_by?`、`note`、`created`、`updated`。同一条用户资源可能同时落在多个候选对里，问句因此按候选行而不是按资源去重，每条候选各自记自己的工单、修订号、快照与计时。两个资源 ID 与名称是普通整数与字符串快照，不建外键：合并要删除源资源行，级联外键会把处置记录一起删掉，留痕就没了。`@@unique([user_resource_id, official_resource_id])` 防重复配对；`@@index([status, created])` 供队列分页；读取与合并时校验两侧资源仍存在，缺失的候选按 `stale` 显示而不是静默消失。重复扫描命中已经是 `merged`、`excluded`、`stale` 的候选时按唯一约束原样跳过，不重开、不刷新 `created` 与 `resolved_at`、不写第二条审计；人工要重新配对同一对时沿用现有候选规则，由管理员显式把该行改回 `unasked` 并清空 `resolved_at`，`created` 保持原值（等待时长因此偏保守，宁可显得更久也不隐藏积压），已经写出的那条终止审计保留不删，不另开工作流。

### 4.4 约束与索引

- 不限制一条资源的官方链接条数：基线没有这个要求，决策六明确允许一条资源下有多个镜像，队列口径只问「是否存在官方链接」，与条数无关。「添加官方链接」的幂等靠事务内对目标地址的重复检查：同资源下已存在相同 `content` 的官方链接即拒绝并写 `admin_log`，不用禁止多镜像来换幂等。
- 状态列用字符串加服务端枚举校验，不建数据库枚举，沿用仓库现状。
- 队列查询与计数判定先复用现有索引（access 侧的 `[link_id, created desc]`、`[resource_id, created desc]` 与两个 actor 索引）；是否补 `patch_resource_link(storage)` 索引按上线后实测决定，不预先添加。

## 5. 接口、校验、权限、幂等

所有写接口沿用中间件的 CSRF 与 origin 校验；管理响应与揭示响应保持 `private, no-store`；地址、提取码、解压码只出现在获准的揭示结果或管理视图。

### 5.3 队列口径

- 公共可处理条件（两个集合都要满足）：`patch_resource.status = 0` 且 `takedown_requested_at IS NULL`。
- 首次镜像集合：存在 `storage = 'user'` 的链接、不存在官方链接、且没有被候选对暂缓。暂缓只算 `unasked`、`awaiting_publisher`、`same`、`changed`、`no_response` 五种状态，`merged`、`excluded`、`stale` 的候选不再阻挡资源进队。`storage = 's3'` 不构成入队理由，但混合了 user 与 s3 链接的资源照常入队，只有「只含 s3 链接」的资源被排除。
- 重新镜像集合：存在官方链接且 `mirror_check` 为 `stale` 或 `unconfirmed`，这一集合不套「不存在官方链接」的条件；`unconfirmed` 标「发布者未确认」并排在所属层末尾。
- 分层用互斥判断，避免同一条资源落进两层：一为 `section = 'galgame'` 且 `type` 不含 `material`；二为 `type` 含 `material`（基线的资料集第二层保留）；三为 `section = 'patch'`。
- 层内排序是一个最小稳定全序，两个集合共用：获取次数降序 → 是该条目唯一可用资源的在前 → 模块 04 提供的「该网盘主机当前 `broken` 比例」降序（更可能失效的先做，没有样本的按 0 计排在最后）→ 体积小的在前（`size` 是手填字符串，解析失败视为最大）→ 资源 ID 升序兜底。
- 计数口径（模块 09 复用同一套谓词）：分母是满足公共可处理条件且存在 user 链接的资源数，分子是其中没有官方链接者；被候选对暂缓的资源单列一个数，且这些资源在待合并队列里始终是可处理项（`no_response` 显示为「待人工决定」），不会因为长期未回应从所有视图消失。
- 进度字段口径一致：首次添加官方链接与重新镜像完成都清空 `mirror_stage`，重做与首次镜像复用同一字段。
- 指标事实（本模块冻结，模块 09 直接引用，不另建事件表、任务表或统计平台）：

| 队列     | 在队与最老等待                                                                             | 完成时长                                                                                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 首次镜像 | 按首次镜像业务谓词取在队集合，最老等待 = `now` 减集合内 `mirror_queue_entered_at` 的最小值 | `admin_log` 中 `type = 'mirror_official_added'` 的行，时长 = 审计行创建时间减该行 `queue_entered_at`；`queue_entered_at` 为空的行（给本来不在队的资源额外加一条镜像）不计入中位数 |
| 重新镜像 | 在重新镜像集合内的资源，起算时间取 `mirror_basis.capturedAt`                               | `type = 'mirror_redone'`，时长同上                                                                                                                                                |
| 待合并   | 候选 `resolved_at` 为空即在队，起算时间取候选 `created`                                    | `type = 'mirror_candidate_merged'` 或 `mirror_candidate_excluded`，时长 = `resolved_at` 减 `created`，审计行同样带 `queue_entered_at`                                             |

`mirror_queue_entered_at` 由一个本模块私有的资格同步 helper 收口，不建队列平台。helper 只做一件事：按上面的业务谓词算出「此刻是否在首次镜像队列」，然后不在队→在队时（当前值为 NULL）写 `now`，在队→仍在队时原值一律不动，→不在队时置空。因此再加一条普通链接、或多个候选里只解除其中一个，都不会把最老等待重置。调用点全是既有写入处，由本模块实施时逐处接线，模块 03、04 的阶段不预查这个字段：首次公开与[审核通过](../../app/api/admin/resource-apply/service.ts)、资源编辑增删普通链接、隐藏与恢复（`status` 变化）、写入或清空 `takedown_requested_at`、候选扫描加入暂缓与候选解除暂缓、官方链接的新增与移除。队列查询始终以业务谓词为准，这个时间列只用于测量，实验要断言两者一致，不能靠冗余时间戳悄悄漏项。完成时先把旧入队时间带进审计的 `queue_entered_at` 再清空该列；完成时长只从审计行读取，不用当前值反推历史。

### 5.4 计数切换（M06-5）

- 两个计数资格各自独立判定，都在 [grant.ts](../../app/api/patch/resource/download/access/grant.ts) 的同一个事务内完成：
  - 链接级：插入本次 access 行之前，查同访问者、同 `link_id`、`counted = true` 且 `created > now - 24h` 的行；没有才累加链接 `download`，并把本次 access 行的 `counted` 写为 `true`。这条规则同时覆盖模块 04 的同 ID 新版本再揭示，以及第二条链接在授权中途首次揭示后跨授权边界再揭示两种情形。
  - 资源与条目级：只有新建授权（现有 `resource_granted`）时累加资源与条目 `download`。现有授权只在不存在或已到期时才重建，因此它本身就是「同访问者同资源 24 小时一次」，不需要另加状态。
- 累加用原生 SQL（`SET download = download + 1`）以保持 `updated` 不变；判定与累加同事务，重复请求由既有的 Serializable 加有限重试保证只有一次胜出，`reused`、`limited` 与恢复接口既不插行也不计数。累加失败时整个揭示事务回滚，客户端重试后恰好计一次。
- 合并只搬移 access 行而不重建，`counted` 标记随行迁移，因此合并后重放同一链接不会重复计数。
- 点击端点改为只累加 `patch_resource_link.click_count`，不再触碰三张表的 `download`，也不再推条目实时统计。
- 旧 `download` 数值原样保留为起点，不重算。

### 5.5 合并事务（M06-4）

合并在一个事务内完成，加锁次序在本模块内统一：先按资源 ID 升序锁涉及的两条资源，再锁候选行，随后按链接 ID、工单 ID 升序锁其余对象；锁到候选行之后重新读一遍并复核状态。两对候选共享同一条资源时只承诺其中一方按合法串行顺序完成、另一方明确失败后可重试，不声称全站无死锁。模块 03、04 的动作在已持有工单锁时不得反向去锁资源。复核清单：候选状态必须是 `same`、`changed`、`no_response` 三者之一，`no_response` 还要求 `asked_at` 确实已满 7 天，`unasked` 与 `awaiting_publisher` 一律拒绝——这是 M06-4「每对先询问」的硬门槛，不是只在已有答复时才校验；两条资源都存在、都是 `status = 0`、同 `patch_id`、同 `section`、两侧都没有 `takedown_requested_at`；被删侧由 `role >= 3` 发布（防止误删用户卡片）且确实含至少一条 `storage = 'touchgal'` 的镜像链接，避免把一条只有普通链接的管理员资源当成镜像删掉，其余链接类型不限；保留侧不存在与待搬入官方链接 `content` 相同的官方链接；候选对已有答复时，双方当前的 `[{linkId, version}]` 与 `asked_snapshot` 一致，不一致即拒绝合并并要求重新询问。

## 9. 测试与实验方案

通用前提：全部实验在隔离数据库与隔离 Redis 上进行，模块 04 的稳定链接 ID 与链接历史已落地；日期边界注入 `now` 或假时钟，不改机器时间；并发用测试层屏障或受控事务交错，不加生产延迟开关；不新增通用测试平台。四个实验状态均为未执行。

**E06-01 官方链接权限与发布者三种动作。** 目的：证明链接级权限与三动作的即时效果。样本：一条含 1 条用户链接与 1 条官方链接的资源、一条无官方链接的资源、发布者与管理员两个账号。步骤：发布者带完整 `baseLinks` 快照（含官方行的只读 ID 与版本）但可变 `links` 不含官方行，只改名称与普通链接地址；发布者分别在可变 `links` 里提交官方行 ID、把某行 `storage` 改成 `touchgal`、要求删除官方行；管理员用自己的编辑正常提交官方行；发布者删除自己的唯一链接后再编辑名称与备注（普通链接为 0 条），同一载荷也走一次创建接口；执行移交并分别选择保留署名与匿名，移交后原发布者再调用管理读取端点与编辑接口，随后由管理员删除该资源；申请下架的同时并发发起一次揭示；管理员在下架期间调用管理读取；管理员拒绝下架后发布者重新添加链接；管理员同意下架，并单独构造一次盘侧处理失败。判据：带只读快照的正常编辑成功且官方行的 ID、版本、地址、大小不变；三类在可变载荷里碰官方行的提交被拒，而管理员提交官方行成功；普通链接为 0 条时更新通过、创建仍要求至少一条链接；三个动作删除普通链接都走 04 的删除路径，写了链接历史、关掉该链接的未结工单与报告、`access.link_id` 置空且配额事件仍在，没有裸删除；删除自己的链接后资源与署名保留、点数未回退；移交后 `user_id` 为站方账号、`origin_user_id` 记录原发布者、匿名时响应不含原发布者身份、发布奖励未回退、原发布者的管理读取与编辑都被拒，移交后再删除资源时 3 点回退落在原发布者而不是站方账号；下架与揭示的并发有合法线性顺序（揭示先提交则该次揭示成立且不被追溯撤销，下架先落库则该次揭示被拒），下架落库后新的揭示与恢复对所有访问者关闭、已复制的站外地址不声称收回，管理读取按权限照常返回且不写揭示记录、不计数；拒绝下架后恢复发放；同意下架在盘侧处理失败时停在暂停状态不删数据，确认后在一个事务内完成删除、奖励回退、全部未结工单结案与通知；任一项不成立即失败。执行时间点：M06-1 与 M06-2 完成后、上线前。证据：请求与响应记录、动作前后的资源与链接行快照、点数流水查询结果、通知与工单记录。清理：回滚隔离库快照。相关单测扩展 [tests/unit/api/patch-resource-update.test.ts](../../tests/unit/api/patch-resource-update.test.ts) 与新增的三动作 service 测试。

**E06-02 镜像队列、重新镜像与分层排序。** 目的：证明队列口径与顺序。样本：只含 s3 链接的资源、只含 user 链接的资源、同时含 user 与 s3 链接的资源、分别有一条与两条官方链接的资源、`mirror_check` 为 `stale` 与 `unconfirmed` 的资源、处在各种候选状态里的用户资源、待审（`status = 2`）资源，覆盖三个层级与不同获取次数、主机、体积。步骤：分别用与实现同一套谓词手写 SQL 取首次镜像与重新镜像两个集合，再与两个队列接口比对；构造候选状态分别为 `awaiting_publisher`、`no_response`、`stale`、`excluded`、`merged` 的同一批用户资源；构造 `section = 'galgame'` 且 `type` 含 `material` 的资源；构造申请下架中的资源；推进一条资源的四个进度阶段并中途重复提交；一键添加官方链接后再读队列；对 `stale` 资源执行「重新镜像完成」，并另做「重做期间发布者又补链」「重做期间新增一条普通链接」「资源上有两条官方链接且只勾选一条处置」三个用例；审核通过一条待审资源后再读队列。判据：只含 s3 的资源不入队，混合 user 与 s3 的资源入队，有官方链接（含两条）的资源不进首次镜像集合但按 `mirror_check` 进重新镜像集合，重新镜像集合不套「无官方链接」条件；两个集合都排除 `status != 0` 与申请下架中的资源；被 `unasked`/`awaiting_publisher`/`same`/`changed`/`no_response` 暂缓的资源不在首次镜像队列但在待合并队列可处理并单列计数，`stale`/`excluded`/`merged` 的候选不再阻挡该资源进队；galgame 的资料集只出现在第二层且第一层不含它；待审资源既不公开也不入队，审核通过后立即公开并入队；「未镜像 / 总数」与手写谓词一致；层内排序按获取次数、唯一可用、主机当前 `broken` 比例降序（无样本按 0 排最后）、体积小者优先、ID 兜底逐键可复现，`unconfirmed` 排各自层末尾；重复提交进度不产生第二条记录；添加官方链接不改 `mirror_check` 且不写第二条成功审计，只有「重新镜像完成」在当前普通链接与 `mirror_basis.links` 完整集合相等、且 `mirror_basis.officials` 里仍存在的旧备份逐条都有已替换/已移除/人工确认三种处置之一时才回到 `fresh` 并清空 `mirror_stage` 与 `mirror_basis`；两条官方链接只勾选一条被拒，重做期间又补链或新增一条普通链接都要求重新询问，重复点完成不写第二条审计；首次镜像的一次完整生命周期可复算：资源公开时写入 `mirror_queue_entered_at`，此后再加一条普通链接、或对始终在队的资源重复执行资格同步时该值保持不变，被候选暂缓或申请下架时置空、解除后重新写入新时刻，添加官方链接时先把旧值带进审计再置空且能算出等待时长；给本来不在队的资源额外加一条官方链接时审计的 `queue_entered_at` 为空、不计时长；任意时刻该列非空的集合与业务谓词算出的集合完全一致；重新镜像的起算时间取 `mirror_basis.capturedAt`；前台文案在添加官方链接后从「站方备份排队中」变为「站方已备份」；出现漏项、重复项、错误的公开时机或顺序不符即失败。执行时间点：M06-3 完成后。证据：队列查询结果与手工核对清单、`admin_log` 记录、前台文案截图。清理：回滚快照。

**E06-03 版本确认、存量合并与引用迁移回退。** 目的：证明先问后合与引用迁移完整。样本：三对候选（未询问、已询问未回应、已回答内容有变化）、一对误配、一对人工配对；保留侧带有效授权、揭示记录、点赞（含双方都点赞的用户）与未结工单。步骤：构造一条用户资源同时落在两个候选对里，对两对分别单条与批量询问并各自重复点击，再对其中一对做「版本变化后重问」；发布者分别回答两个选项，并对已结案的确认、以及带错误修订号的答复各再试一次；对同一资源做一次资源级手动询问并用补链回答，检查候选问句是否被误结；对未回应的候选把时钟推过 7 天后运行定时任务两次；构造「答复后发布者又补链」再尝试合并；对共享同一条资源的两个候选并发发起合并；执行合并（两侧都带未结与已结工单，并包含一对同目标同类型会撞未结唯一键的工单，保留侧与源侧各有一位相同用户的点赞，源侧还有一条保留侧发布者本人给站方卡片点过的赞——合并后它变成对自己资源的点赞，这条路径当前就可达，不构造现在不允许的新自赞）；合并后由这两位点赞者分别取消点赞；对误配标记不是同一资源，随后对全部已终态的候选再跑一次扫描；用旧 `resourceId` 访问条目页，并构造连续两次合并的链式跳转与一条人为成环的数据；构造合并中途失败（在删除源资源行前抛错）；构造提交后缓存失败。判据：两个候选各有自己的工单、修订号与快照，不被合并成一条问句；重复询问返回既有问句且不刷新 `asked_at`，显式重问才关旧开新并重新计时；已结案的确认与修订号不符的答复都按陈旧拒绝且不写状态；补链只结掉资源级问句，候选问句保持未结；超时任务重复运行只把状态改一次、用候选自己的工单按未回应结案且不自动合并；答复后源版本再变化时合并被拒；`unasked` 与 `awaiting_publisher` 的候选一律不能合并，`no_response` 只有在 `asked_at` 满 7 天后才可合并；合并按答复写保留侧标记（`same` 且官方覆盖成立时 `fresh`，`changed` 为 `stale`，`no_response` 为 `unconfirmed`，后两者都带完整 `mirror_basis` 与 `capturedAt`）；共享同一条资源的两个候选并发合并时，一方按串行顺序完成、另一方明确失败后可重试；合并后链接 ID 与版本不变且只有资源盘行标官方，源资源的全部揭示记录（含 `link_id` 为空的配额事件）都改指保留侧、一行未删且 `counted` 标记保留，授权按两者较晚的原 `expires` 合并且没有被延长，点赞按去重后的关系计数而不是两边相加，重合的点赞保留保留侧那条，迁移后取消点赞回退给 `reward_user_id` 记录的原接收者而不是新归属者，本人在移交前点的赞可以正常取消；资源级获取次数合到保留侧而 `click_count` 留在各自链接行、条目 `download` 未被二次累加、条目 `resource_count` 只由触发器减一；未结工单按 03 的 `open`/`append`/`close` 合同合并为订阅或按「已合并」结案而不是直接撞唯一键，被合并的工单保留原历史并记 `merged_to`、私有正文没有广播给新订阅者，已结工单与链接历史改指保留侧并新增一条原因「合并」的记录；候选行在源资源删除后仍可查询且带 `merged_into_resource_id` 与 `resolved_at`，源资源参与的其他候选被置为失效并同样写 `resolved_at` 与一条 `mirror_candidate_excluded` 审计；对已是 `merged`/`excluded`/`stale` 的候选重复扫描不重开、不刷新 `created` 与 `resolved_at`、不写第二条审计；旧 `resourceId` 深链能解析到保留卡片并给出「已并入」提示，链式合并在 5 跳内解析、成环数据不死循环；合并事务内没有文件删除调用，也没有任何点数回退或重复发放；合并之后由点赞者取消点赞时才有回退，且落在 `reward_user_id` 记录的接收者，接收者账号已删除时按已删除账号处理而不是改扣当前归属者；失败用例整对回滚且候选状态复原，缓存失败只重试缓存不重复搬数据；任一项不成立即失败。执行时间点：M06-4 完成后、上线前。证据：合并前后的双方行快照与外键计数、任务日志、失败用例的事务日志、文件删除调用的断言记录。清理：回滚快照；不在生产执行演练合并。

**E06-04 揭示获取计数、并发去重与点击口径切换。** 目的：证明计数口径切换正确且不重复。样本：登录用户与访客各一，一条含官方链接与两条用户链接的资源，同条目下另一条资源，含历史 `download` 数值的旧资源。步骤：同一访问者揭示第一条链接，在第 23 小时首次揭示第二条链接，在第 25 小时再揭示第二条；对同一链接在距上次计数恰好 24 小时时再揭示一次；24 小时内重复揭示同一条；跨授权边界再揭示第一条；对某条链接执行模块 04 的补链使版本加一后再揭示；调用恢复接口；同一访问者并发发起两次首次揭示（测试屏障对齐）；触发配额受限的揭示；发布者与管理员打开编辑表单；点击跳转端点若干次；构造计数 SQL 失败一次；把回填脚本按固定 `cutoverAt` 重跑两次（同一次重跑覆盖 `reward_user_id` 与 `mirror_queue_entered_at` 的补 NULL 逻辑，样本里含一条移交后已保存原接收者的点赞，以及一条切换之后才入队、入队时刻非空的资源）；在 E06-03 的合并样本上重放同一链接的揭示。判据：首次揭示使链接、资源、条目各加一；同一授权内第二条链接只加链接计数；第 25 小时再揭示第二条时链接不再计数（距其上次计数不足 24 小时）而资源按新授权计一次；恰好满 24 小时的那次可以重新计链接；同 ID 新版本在 24 小时内再揭示不重复计链接；重复揭示走 `reused` 时既不插入事件也不计数；恢复不增量；并发用例在受控可恢复冲突下两个请求最终都成功且只产生一次计数（不承诺任意数据库故障都不出 503）；受限揭示不计数；编辑表单不产生任何揭示记录与计数；点击只增加 `click_count` 且三张表的 `download` 与 `updated` 不变；旧数值保留为起点；计数 SQL 失败时整个揭示事务回滚、客户端按既有重试后恰好计一次；回填重跑只影响 `[cutoverAt - 24h, cutoverAt)` 区间、不改切换后新增的 `counted = false` 行、不重算旧 `download`，`reward_user_id` 只补 `IS NULL` 的行且移交后已保存的原接收者不被改写，`mirror_queue_entered_at` 同样只补 NULL、切换之后由业务写入的真实入队时刻不被覆盖；合并后重放不重复计数，并按 E06-03 的判据核对取消点赞与删除回退的接收者；任一项不成立即失败。执行时间点：M06-5 完成后、上线前，且必须与 E06-01 的下架用例一起复跑一次。证据：计数前后的行快照、access 与 grant 行、并发时序日志、缓存失效调用记录。清理：回滚快照。相关单测扩展现有 `tests/unit/api/resource-access*.test.ts` 与计数 service 测试。

本模块另按仓库约定运行受影响的单测、类型检查，并在涉及 schema、CSS 或 SQL 资产时运行全量测试与生产构建。

## 11. 非目标

不给创作者镜像权限；不实现自动搬运、离线下载、哈希去重或低频存储切换；本模块只核对资源盘当前版本的官方文档与接口能力（离线下载、哈希去重、低频存储读取兼容）并留一段结论，仓库内没有资源盘 API 客户端是既有事实，但不等于资源盘没有这些能力；不新增消息总线、队列框架或规则后台；不改萌萌点既有规则与角色层级；不做资源级担保等级枚举；不给链接加生命周期状态；不在前台重复实现合并；不重算历史计数；不做定时链接扫描（属模块 10）；不重构前台资源分组与 UI 框架；不预先实现或查询模块 07 的表，`help_answer.resource_id` 与本模块合并引用的接线由 07 上线时自己接入，本文只记录这条责任。

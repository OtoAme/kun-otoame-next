# 模块 06：站方备份、资源接管与存量合并（实施计划）

状态：2026-11-03 按站长确认的业务规则修订；尚未实现、迁移或部署。配对 [PM 版](./06-official-mirror-pm.md)，任务编号 M06-1～6、实验 E06-01～04 保持不变。

## 1. 目标与基线

把「官方镜像」从全量政策改成选择性备份：备份是原用户卡片下的一条资源盘链接，存储类型 `touchgal`，由站方维护；用户退出时卡片与备份留下，交站方维护；历史上站方另建的重复卡片，与用户卡片一对一合并。基线是[运营层设计](../7.operations-layer-redesign.md)第 5 节，该基线 2026-09-05 冻结，其正文不再修改，偏离在下一节逐项记录。

现状事实（均核对过当前源码）：

- 站方备份已经以 `storage = 'touchgal'` 区分：[链接健康策略](../../constants/linkHealth.ts)把它定为站方存储，[添加入口](../../app/api/patch/resource/route.ts)只允许管理员，[更新权限](../../app/api/patch/resource/update.ts)对非管理员锁定其内容，[事项归属](../../app/api/case/service.ts)在链接类事项上按它归站方。
- 资源类事项的归属按资源作者的角色推导：作者角色不高于 2 归发布者，否则归站方。
- 普通用户不能删除含 `touchgal` 链接的卡片，[删除服务](../../app/api/patch/resource/delete.ts)直接返回无权限；可以删除时，同一事务回收 3 点发布奖励。
- 链接的创建时间不能表示「何时加入卡片」：[链接拆分迁移](../../migration/migratePatchResourceLinks.ts)用 `CURRENT_TIMESTAMP` 写入创建时间，2026-05-07 的一次迁移给 1159 条链接写下了同一个时刻（备份库里 918 条 `touchgal`、85 条 `user`、156 条 `s3`）。备份库共有 `touchgal` 1323 条、`user` 390 条、`s3` 294 条，其余约 848 条（含 305 条 `user`）的创建时间是真实的。
- 点赞按唯一键 `[user_id, resource_id]` 去重，奖励与通知发给 `resource.user_id`（[点赞服务](../../app/api/patch/resource/like/service.ts)），自己不能给自己点赞。
- 公开的「下载次数」由[点击上报](../../app/api/patch/resource/download/service.ts)累加：卡片按钮按下时前端发 `PUT /patch/resource/download`，与是否真的取得链接无关。
- 控制台已有「下载资源」页，通过旧后台资源接口读取。其「到游戏页编辑」按钮跳到游戏页，由那里的保存走普通更新接口，不写管理日志，也不通知发布者；后台资源更新接口（`PUT /admin/resource`）则写管理日志并通知发布者。

## 2. 偏离与理由

下表记录与基线第 5 节的偏离。写法沿用 [04 第 2 节](./04-link-health.md#2-偏离与理由)。

| 偏离 | 基线 | 本文做法与理由 |
| --- | --- | --- |
| 不建 `official` 列，用 `storage = 'touchgal'` 判定站方备份 | 5.1、5.9 | 代码已把该存储类型当作站方存储，事项归属、权限、删除保护都按它判断；再加一列会产生两份事实，需要持续对账。「站方已备份」仍是由是否存在这类链接推导，与基线 5.1 的原意一致 |
| 不建 `official_verified_at`、`mirror_check`、`origin_user_id`、`credit_visible`、`takedown_requested_at`，也不建 `mirror_queue_entered_at` | 5.1、5.4、5.6、5.9 | 备份旁显示备份日期，不设版本确认状态；不允许匿名，原发布者始终是卡片的 `user_id`，不需要另存来源；队列由事实推导，不另存进入时间；申请下架另见下一行 |
| 发布者的三种动作合成一种：删除含备份的卡片即交由站方维护 | 5.4 | 站长要求保留原发布者信息、不允许匿名，也不改 `user_id`，「移交给站方」和「匿名」两种动作都不成立；「删除我的链接」是普通编辑，已有；「申请下架」要建新状态和新事项类型，而文件有害这类情形本来就走现有事项与管理员处理，不为它单设流程。因此 03 预留的 `takedown_request`、`mirror_version_check` 类型本模块不使用，第 9 节安排清理 |
| 交接后点赞奖励、个人主页列表和创作者申请计数保持不变 | 5.4 | 基线的「移交给站方账号」会让这三项随卡片离开原发布者。站长确认原发布者保留署名，交接前后他的奖励、主页和创作者资格不变：点赞仍给 `resource.user_id`，已发的发布奖励不收回 |
| 全量镜像改为选择性备份，三层优先级改为一个可筛选的列表，默认按获取次数降序 | 5.5 | 站长决定只备份值得备份的资源，由管理员挑选；分层排序依赖的网盘存活率、体积等信号不再作为入队条件 |
| 不做镜像版本确认：不问发布者，不设 7 天超时 | 5.6 | 版本信号改为「备份日期」加「备份之后外部链接被改或新增」，由管理员判断是否重新备份。「待重新备份」只提示变动，不断言内容不同 |
| 存量合并中，高置信对批量合并，不询问发布者 | 5.7 | 基线要求每对都先问发布者，原因是存量里没有版本信号。本次在备份库核对得到 207 对（同游戏同分区、站方卡片晚于用户卡片、类型语言平台一致、互为唯一；该统计没有按站方卡片状态过滤，见第 11 节核对项），站长决定对这批直接合并，其余人工处理。代价是少数对的内容可能并不相同：卡片上的备份日期让玩家自行判断，管理日志记下移动的链接 ID，其余候选逐对人工核对 |
| 合并时不迁移站方卡片上的点赞 | 5.7（合并获取次数与点赞） | 站长决定。备份库中高置信对的站方卡片共 53 个点赞：其中 6 个是发布者自己点的（用户卡片上不允许自赞）、23 个与用户卡片重复，约 24 个会因此舍弃。这也取消了旧 06 的「点赞奖励接收者可追溯」不变量 |
| 合并只限用户卡片与站方卡片 | 5.7 | 站长确认，不做用户与用户的合并 |
| 候选实时计算，不存待处理候选，没有检测任务，没有手动配对 | 5.7 | 候选完全由卡片现状决定，存下来就要持续对账。需要记住的只有「已驳回」和「已合并」两种结果，合并进同一张记录表，它同时兼作旧链接的重定向依据。一张用户卡片有多个站方候选时，由管理员在详情里选定一张 |
| 自动或半自动搬运不做 | 5.5「省时间的三个杠杆」 | 站长确认，之后可能作为独立工具出现，搬运机器也不一定是同一台 |
| 获取计数切换、资源管理迁入新控制台仍在 06 | 5.8 | 沿用基线，与 06 其余项一起排期；资源管理页已迁入控制台，本模块只补接线 |

## 3. 术语

| 术语 | 定义 |
| --- | --- |
| 站方备份 | 卡片下一条 `storage = 'touchgal'` 的链接。由站方维护，用户不可改、不可删 |
| 外部链接 | 卡片下 `storage = 'user'` 的链接，即用户自填的网盘链接 |
| 站方卡片 | 作者角色不低于 3 的账号发布的卡片。当前只有一个这样的账号 |
| 用户卡片 | 作者角色不高于 2 的账号发布的卡片 |
| 链接变动时间 | 一条链接的 `GREATEST(attached_at, content_changed_at)`，即加入卡片的时间与最近一次改地址的时间中较晚的一个（`GREATEST` 忽略空值） |
| 备份时间 | 卡片所有站方备份链接的链接变动时间的最大值。站方把备份换成新地址，也会推进它 |
| 交接 | 交由站方维护的简称。卡片保留原发布者作为 `user_id`，同时记录 `publisher_left_at`；此后站方负责维护，原发布者失去管理权。数据模型见第 4 节 |
| 候选 | 同一游戏、同一分区下，一张用户卡片与一张站方卡片的配对。用户卡片需 `status = 0`、至少有一条外部链接、未交接；站方卡片状态不限。候选实时计算、不存储，一张用户卡片可以有多个候选 |
| 高置信对 | 候选中同时满足：站方卡片 `status = 0` 且创建晚于用户卡片；类型、语言、平台两两相同（不计顺序）；用户卡片与站方卡片互为唯一候选，判断时不计已驳回的对 |
| 需人工对 | 其余候选：属性不一致、一张用户卡片有多个站方候选、站方卡片比用户卡片早、站方卡片状态不是正常 |
| 幸存卡片、被并卡片 | 合并后留下的用户卡片，与被删的站方卡片 |
| 合并记录 | `patch_resource_merge_record` 中的一行，记录一对候选已被驳回或已合并 |

## 4. 数据模型与迁移合同（M06-1）

核心原则：不加 `official`、`mirror_check` 之类的状态列；只加事实，让每个队列和显示都能由事实推导。

### 4.1 既有表新增

1. `patch_resource.publisher_left_at`：可空时间，空表示仍由发布者维护。不改 `user_id`。
2. `patch_resource_link.attached_at`：非空时间，默认写入时刻，表示链接加入所在卡片的时间。存量回填见 4.4。
3. `patch_resource_link.click`：整数，默认 0，只在第 5.4 节的辅助点击统计保留时才加（待站长确认，见第 11 节）。

链接改地址（补链）沿用 04 的 `content_changed_at`，`attached_at` 保持不变；两者的较晚者就是链接变动时间。合并后链接 ID 不变，`attached_at`、`content_changed_at` 跟随链接，不需要重算。

### 4.2 新表

**备份队列记录**（拟名 `patch_resource_backup_state`，一张卡片至多一行，主键为 `resource_id`，外键级联删除）：

| 字段 | 含义 |
| --- | --- |
| `ignored_at`、`ignored_by_user_id`（标量，不建关系）、`ignore_reason` | 站方忽略这张卡片的时间、操作人和可选理由（拟限 500 字）；撤销忽略清空三项 |
| `rebackup_dismissed_at` | 站方最近一次点「无需重新备份」的时间 |

没有这一行等于未忽略、未表态。撤销忽略后若两个时间都为空，行可以保留空值，也可以删除，实现自选，查询必须同时覆盖两种情况。

**合并记录**（拟名 `patch_resource_merge_record`）：

| 字段 | 含义 |
| --- | --- |
| `id` | 自增主键 |
| `user_resource_id`、`staff_resource_id` | 用户卡片与站方卡片的 ID。均为标量，不建外键：被并卡片删除后记录仍在 |
| `patch_id`、`section` | 所在游戏与分区（`galgame` 或 `patch`），用于列表筛选 |
| `status` | `dismissed`（已驳回）或 `merged`（已合并） |
| `handled_at`、`handled_by_user_id` | 处理时间与处理人（标量） |
| `detail` | 小型 JSON：`merged` 时记录移动的链接 ID，以及备注是否追加了「站方备份说明」 |

约束与用法：

- 唯一键 `(user_resource_id, staff_resource_id)`；索引 `(staff_resource_id, status)`，供旧链接重定向按被并卡片 ID 反查幸存卡片。
- 没有记录且满足候选条件的对就是待处理。驳回写 `dismissed`；在「已驳回」里重开，删除该行。合并写 `merged`。
- 用户卡片一旦有 `merged` 记录，它的其他候选不再出现。
- 不使用部分唯一索引（生产结构检查不允许），不建占位表，不建检测任务。

### 4.3 不新增

不新增 `official`、`mirror_check`、`origin_user_id`、`credit_visible`、`takedown_requested_at`、`official_verified_at`、`mirror_queue_entered_at`；不新增站方接管账号（卡片保留原 `user_id`）；不新增候选表和重定向表；不新增事项类型和事项状态（`merged` 状态已存在，本模块不写入）。第 5.1 节新增的 `publisher_left` 是已有「转交触发器」枚举的一个取值，不是新的事项类型。

### 4.4 迁移与回填

按仓库既有流程：结构变更走审定的 preflight、sync、postflight，先在隔离库演练，生产由站长在服务器执行。

`attached_at` 的 sync 分三步，每步可重复执行：先 `ADD COLUMN IF NOT EXISTS`（可空），再只对 `attached_at IS NULL` 的行回填，最后设默认值 `CURRENT_TIMESTAMP` 并改为非空。postflight 断言没有空值，并打印被识别为统一盖章的链接数。

回填口径：

- 统一盖章的链接取所在卡片的 `created`。识别方式是按链接 `created` 分组，同一时刻被大量链接共用（拟阈值：组内超过 50 条）即视为统一盖章，不写死 2026-05-07 那一刻。备份库上预期识别出约 1159 条。
- 其余链接取 `GREATEST(链接 created, 卡片 created)`。
- 估算的限制：统一盖章的链接比真实加入时间更早或更晚都有可能，迁移前就已经比站方备份新的外部链接因此不会进入「待重新备份」；阈值识别的误判只会让个别链接的时间偏早，PM 版 2.2 已如实说明。存量备份链接旁显示的备份日期同样是估算值。

其余字段与表全部从空开始。不回填「站方备份日期」：它由 `touchgal` 链接的变动时间推导。

## 5. 接口、权限、事务与幂等

### 5.1 交由站方维护（M06-2）

**入口**：沿用用户删除卡片的现有入口（[删除服务](../../app/api/patch/resource/delete.ts)，被[条目页接口](../../app/api/patch/resource/route.ts)与[工作台](../../app/api/workspace/resources/service.ts)调用）。调用者是卡片作者、角色低于 3，且卡片含 `touchgal` 链接时，不返回无权限，执行交接；卡片不含 `touchgal` 链接时沿用现有删除（整张删除并回收 3 点）；管理员调用保持现有删除。

响应区分两种结果：条目页接口返回 `action`（`handed_over` 或 `deleted`）和余额，工作台响应增加 `handedOver`。作者对已交接的卡片再次提交删除，返回同样的交接结果，不产生任何副作用；编辑与链接管理则拒绝。

**确认框与提示**：条目页的[删除对话框](../../components/patch/resource/Resource.tsx)和工作台的[编辑器](../../components/dashboard/workspace/WorkspaceResourceEditor.tsx)按卡片是否含 `touchgal` 链接选择文案。交接用：

> 这份资源有站方备份。删除后会移除你添加的链接，卡片和站方备份保留，仍署你的名字，之后由站方维护。已获得的萌萌点不收回。

整张删除沿用现有文案。交接成功后条目页不把卡片从列表移除，而是刷新它，卡片显示「站方维护」，提示「已交由站方维护」。

**事务**（经 `runResourceMutation` 执行，沿用 04 的锁序：资源行 → 链接行（按 ID 升序）→ `lockLinkMaintenance` → 事项行；事务内不做网络与缓存操作）：

1. 锁资源行与全部链接，复核调用者是 `user_id`、卡片含 `touchgal` 链接、`publisher_left_at` 为空。已交接的重复请求在此返回，不继续。
2. 发布者自己的链接（`storage` 不是 `touchgal`，含 `s3`）：复用[更新服务](../../app/api/patch/resource/update.ts)的移除逻辑，先取 `lockLinkMaintenance`，每条写一条链接历史（原因 `remove`），以「链接已移除」结案其链接类事项（`closeLinkCases`），再删除链接行；获取记录的 `link_id` 置空保留；`s3` 对象在提交后清理。
3. 写入 `publisher_left_at`。卡片状态与其他字段不变。
4. 未结事项转交站方，见下一段。
5. 不回收 3 点发布奖励，不写萌萌点流水。
6. 写管理日志：新增类型 `resource_handover`，在[管理日志类型表](../../constants/admin.ts)登记；操作人是发布者本人；内容含卡片 ID 和被移除的链接数。
7. 提交后失效条目内容、资源列表和作者页缓存，清理 `s3` 对象，失败只重试这一步。

**未结事项的交接**：

- 03 的转交触发器（`CASE_ESCALATION_TRIGGERS`，现有 `timeout`、`review_request`）新增第三个取值 `publisher_left`。[事项服务](../../app/api/case/service.ts)里写死的 SQL 列表（第 3518 至 3520 行）同步加入，类型随常量变化；03 文档与测试同步。09 把它归为「站方接手」，不计发布者超时。
- 本卡片上归属为发布者的未结事项只剩资源类（发布者自己的链接类事项已在事务第 2 步结案）：
  - `open`、`waiting_owner`：变为 `open`，归属站方（`owner_id` 为空），`status_changed_at`、`queue_entered_at`、`escalated_at` 取当前时间，`revision` 加一。
  - `waiting_reporter`：状态与 `status_changed_at` 不变，只把归属改给站方，`queue_entered_at` 取当前时间；实现时对照 03 的计时语义确认。
  - 每个被转交的事项追加一条 `escalated` 事件，`escalation_trigger` 为 `publisher_left`，带 `from_status`、`to_status`、`from_state_entered_at`、`queue_entered_at`，不带 `from_owner_type`、`from_owner_id`。对话与关注者保留。
- 原发布者不再拥有「原发布者」权限。转交事实的三处读取（`loadLatestHandoffFacts`、`loadOwnedCaseWindow`、`representedPublisherLinkCaseIds`）统一排除所属资源 `publisher_left_at` 非空的事项。这一排除也覆盖交接前已经因超时或复核请求转给站方的事项：原发布者对它们的结案权（要求触发器为 `timeout` 且重开次数为零，D36）和通知一并终止。
- 已结案的事项保持原样。重开（`reopenCase`）时若所属资源已交接，归属推导为站方。
- 事项创建时，`deriveTarget`（[事项服务](../../app/api/case/service.ts)第 584 行起）对所属资源行取 `FOR SHARE`（原生 SQL），取锁后重读目标并核对它仍属于该资源。这使创建与交接、合并互斥：创建先提交，则交接转交这条新事项、合并因未结事项被阻塞；交接或合并先提交，则创建看到最新的归属，或发现卡片已被并入而失败。当前这里是不加锁的普通读取，会留下「交接后仍产生发布者归属事项」和「事项挂在已被并入的卡片上」两个窗口。实现时核对 `runCaseTransaction` 的隔离级别，以及事项服务里是否有先锁事项再锁资源的路径，后者会与上述锁序冲突。

### 5.2 站方备份队列与忽略（M06-3）

**范围**：卡片 `status = 0`，作者角色不高于 2，至少有一条 `storage = 'user'` 的链接。只有 `s3` 链接的卡片不入队，站方卡片不入队；已交接的卡片没有外部链接，自然不入队。

**三个标签的谓词**（均不建状态列，由事实推导；一张卡片至多出现在一个标签里）：

| 标签 | 谓词 |
| --- | --- |
| 已忽略 | 有忽略记录（`ignored_at` 非空）。忽略优先于另外两个标签 |
| 未备份 | 无 `touchgal` 链接；无忽略记录；没有待处理的合并候选（第 5.3 节的候选里，还没被驳回的对，用户卡片一侧） |
| 待重新备份 | 有 `touchgal` 链接；无忽略记录；存在外部链接，其链接变动时间大于备份时间，也大于 `rebackup_dismissed_at`（若有） |

备份时间取该卡片所有 `touchgal` 链接的链接变动时间的最大值（第 3 节）。站方为重新备份把站方链接换成新地址会推进备份时间，待重新备份随之清除；新增站方链接同理。

忽略只在「未备份」里提供。被忽略的卡片之后即使加了站方备份或换了外部链接，也只出现在「已忽略」，不会自己回到「未备份」；撤销忽略后再按谓词归位。默认排序为获取次数（`patch_resource.download`）降序。

**接口**（拟放在 `app/api/admin/backup/`，仿[会社合并](../../app/api/admin/company-merges/route.ts)的路由写法，`role < 3` 拒绝）：

| 接口 | 作用 |
| --- | --- |
| 读取队列 | GET。参数：标签、分区、搜索、分页、排序（默认获取次数降序）。返回行内字段（卡片、游戏、发布者、获取次数、外部链接数、最近一次链接变动时间）和三个标签各自的数量 |
| 忽略、撤销忽略 | POST。忽略写 `ignored_at`、操作人和可选理由；撤销清空三项。重复请求幂等，不重复写日志 |
| 无需重新备份 | POST。写 `rebackup_dismissed_at` 为当前时间。重复请求幂等 |

三个写操作各写一条管理日志，类型 `backup_ignore`、`backup_unignore`、`backup_dismiss`，在[管理日志类型表](../../constants/admin.ts)登记。

**添加备份**不新增写接口：详情里的入口打开[收件箱的资源编辑表单](../../components/dashboard/inbox/ResourceEditForm.tsx)，提交到[后台资源更新](../../app/api/admin/resource/update.ts)，它写管理日志并通知发布者。表单需要两处调整：成功提示不再写死「资源仍待审核」，由调用方传入；它需要的 `baseLinks` 由 `GET /admin/resource?resourceId=` 提供（该筛选已存在）。控制台「下载资源」页的「到游戏页编辑」走普通更新接口，不写管理日志，备份页不复用它。

### 5.3 存量合并（M06-4）

**候选**：实时计算，不存待处理项。同一游戏、同一分区下，一张用户卡片（`status = 0`、作者角色不高于 2、至少一条外部链接、`publisher_left_at` 为空）与一张站方卡片（作者角色不低于 3，状态不限）构成候选。以下两类不再是候选：合并记录里已有记录的对（已驳回、已合并），以及已有 `merged` 记录的用户卡片的其他配对。高置信与需人工的分类见第 3 节。存量只有数百对，服务端一次算出后分页，不需要缓存。

备份库实测（2026-11-03，只读聚合，比线上约旧六周）：

- 有站方卡片的游戏里，296 张用户卡片能配出候选，其中 207 对满足高置信条件。这个数没有按站方卡片状态过滤，见第 11 节核对项。
- 其余 89 张需要人工：62 张属性对不上，21 张有多个候选，6 张站方卡片比用户卡片还早。
- 另有 77 张有外部链接的用户卡片没有站方卡片，属于第 5.2 节的备份队列。
- 高置信对里的站方卡片各只有一条链接。需人工的 89 张站方卡片的链接构成尚未核对，合并事务不依赖它，一律整体移动。

**阻塞原因**（任一项成立则不能合并，界面显示原因，批量时记为跳过）：

- 站方卡片上有未结事项，含目标是它的链接的事项。
- 合并后的备注超过 10007 字。
- 任一卡片已不存在，或用户卡片已有 `merged` 记录。
- 用户卡片已交接，或不是 `status = 0`。
- 这一对已被驳回：需先在「已驳回」里重开。

**备注合并**：用户备注为正文。站方备注非空，且去除首尾空白后不是正文的子串时，在正文后加一个空行和「站方备份说明：」，再接站方备注；其余情况正文保持原样。名称、类型、语言、平台保持用户卡片的值。高置信对已保证类型、语言、平台一致，需人工对由管理员在预览中核对。

**预览**：返回幸存卡片合并后的字段和链接列表（原有链接在前，移入的链接在后）、被并卡片的信息、阻塞原因和一个基点。基点是下列内容的摘要：两张卡片的 `updated`、两张卡片的链接 ID 与版本集合、站方卡片上未结事项的数量。执行合并必须携带基点，事务内重算后不一致即拒绝，提示重新预览。

**接口**（拟放在 `app/api/admin/resource-merges/`，写法同[会社合并](../../app/api/admin/company-merges/route.ts)，`role < 3` 拒绝）：

| 接口 | 作用 |
| --- | --- |
| 读取列表 | GET。标签「待处理」实时计算候选，每行是一张用户卡片，附候选数量、配对分类、阻塞原因；「已驳回」「已合并」读合并记录。参数：标签、配对分类、分区、搜索、分页 |
| 预览 | 入参用户卡片 ID 与站方卡片 ID，返回上文预览内容和基点 |
| 合并 | 入参两个 ID 与基点。成功返回合并结果；这一对已经处理过则返回「已处理」，不报错 |
| 批量合并 | 入参一组 ID 对，只接受高置信对。不带基点，每对在自己的事务里重算高置信条件与阻塞原因，条件不再成立则跳过。返回成功数和每个被跳过的对及原因 |
| 驳回、重开 | 驳回写 `dismissed` 记录，重复提交幂等；重开删除该行 |

合并、驳回、重开各写一条管理日志，类型 `resource_merge`、`resource_merge_dismiss`、`resource_merge_reopen`，在[管理日志类型表](../../constants/admin.ts)登记。合并的日志内容含两张卡片 ID、移动的链接 ID、备注是否追加。

**合并事务**（拟名 `mergeStaffCardIntoUserCard`，重试与退避参照[资源变更](../../app/api/patch/resource/mutation.ts)的写法，但要锁两张卡片）：

1. 锁：按资源 ID 升序锁两张卡片，再按链接 ID 升序锁两边全部链接，再取链接维护锁，最后锁相关事项。锁序与 04、第 5.1 节一致。锁内重读状态，核对这一对仍是候选、没有阻塞原因、基点一致；被并卡片已不存在或已有 `merged` 记录时返回「已处理」。
2. 移动链接：被并卡片的链接改 `resource_id` 到幸存卡片，不改 ID、版本、健康状态、`attached_at` 与 `content_changed_at`；每条写一条链接历史，原因 `merge`；排序值接在幸存卡片现有链接之后。
3. 移动获取记录：被并卡片的获取事件全部改指幸存卡片，包括 `link_id` 为空的配额事实。授权的主键是「访问者＋资源」，两边都有授权的访问者保留到期较晚的一份，不重新计算 24 小时。只把资源级的 `download` 加到幸存卡片；链接级计数随链接移动，条目级计数不变（两张卡片同属一个条目）。
4. 重新指向：链接检测快照、失效报告与链接维护记录里的标量资源 ID 改指幸存卡片。链接历史对资源有级联删除的外键，必须在删除被并卡片之前改指；求助帖的资源外键是置空，也先改指，否则合并后会丢失关联。
5. 事项：目标是被并卡片的已结案事项改指幸存卡片。结案时去重键已置空（[事项服务](../../app/api/case/service.ts)第 3122 行），所以改指不会撞唯一键；以后重开时按新的目标重新计算去重键。已结案的链接类事项消息里记着旧资源 ID，不改写，界面按该 ID 定位时由本节「旧链接的定位」换算。
6. 点赞：被并卡片上的点赞随卡片级联删除，不迁移，不回收已发奖励，不发通知。
7. 把合并后的备注写入幸存卡片，同时更新幸存卡片的 `updated`。
8. 删除被并卡片，不调用普通删除服务：不回收萌萌点，不清理对象存储（`s3` 链接已随链接移到幸存卡片）。`patch.resource_count` 由数据库触发器维护，不手工增减；删除后调用 `updatePatchAttributes` 刷新条目的类型、语言、平台聚合。
9. 写合并记录（`merged`，`detail` 含移动的链接 ID 和备注是否追加）和管理日志。

整对失败整体回滚。提交后失效缓存：两张卡片所在条目的内容与列表缓存、作者页、后台队列。失效失败只重试失效，不重新合并。

**并发**：

- 同一对重复提交，或同一张用户卡片被两个管理员合并到不同的站方卡片：后到者在第 1 步看到被并卡片已不存在，或用户卡片已有 `merged` 记录，返回「已处理」。
- 获取事件与求助帖的写入引用资源外键，会取该行的键共享锁，与合并持有的行锁冲突，因此在合并提交前后串行化：合并提交前发起的获取请求会因资源已被并入而失败，访问者刷新后在幸存卡片上重新获取，窗口只有一个合并事务的时长。
- 新建事项与合并的互斥靠第 5.1 节的 `FOR SHARE`：创建先提交，则合并因未结事项被阻塞；合并先提交，则创建发现资源已不存在而失败。
- 陈旧预览按基点拒绝。

**驳回与重开**：驳回把这一对写成 `dismissed`，之后它不再是候选，也不再计入「互为唯一」的判断，所以另一张候选可能因此升为高置信对。重开删除该行，这一对回到待处理。

**旧链接的定位**：条目页是定时再生成的静态页面，不读取查询参数，无法在服务端换 ID，因此在浏览器端换。

1. 查找接口（拟 `GET /patch/resource/merged?resourceId=`）：读合并记录中 `staff_resource_id` 等于入参且 `status = 'merged'` 的行，返回幸存卡片 ID；幸存卡片已不存在则返回空。
2. [条目页的资源定位](../../components/patch/resource/Tabs.tsx)读取 `resourceId` 与 `resourceSection`，在已加载的资源里找不到该 ID 时调用查找接口，命中则用 `router.replace` 换成幸存卡片 ID，再走原有的滚动与高亮。
3. 求助创建页（`app/(site)/help/create/page.tsx`，服务端组件）的查询参数是 `resource`，找不到资源时在服务端查合并记录换成幸存卡片。
4. 其他生成 `resourceId` 链接的入口（[事项展示](../../components/case/caseDisplay.ts)第 92 行、[分享按钮](../../components/patch/resource/ResourceShareButton.tsx)第 14 行）不改，它们读到旧 ID 时由第 2 点换算。历史通知正文里的链接不批量改写。
5. 后台收件箱对待审核资源申请的预览页 `/preview/resource/[id]` 不涉及已公开的卡片，不处理。

### 5.4 获取计数切换（M06-5）

现状见第 1 节：公开计数由点击上报累加，与是否取得链接无关。目标：改按「获取」计数。计数点放在[获取授权链路](../../app/api/patch/resource/download/access/grant.ts)的 `resolveResourceAccessGrant`，它在可串行化事务里运行并自带重试，按结果分支计数：

| 分支 | 含义 | 链接 | 资源 | 条目 |
| --- | --- | --- | --- | --- |
| `resource_granted` | 24 小时内第一次获取这张卡片，新建授权并揭示链接 | +1 | +1 | +1 |
| `link_revealed` | 已有授权，第一次揭示另一条链接 | +1 | 0 | 0 |
| `reused` | 已有授权，重复获取已揭示的链接 | 0 | 0 | 0 |
| `limited` | 配额拒绝 | 0 | 0 | 0 |

恢复访问（[恢复服务](../../app/api/patch/resource/download/access/restore/service.ts)不经过该函数）与后台读取不计数。未登录的访问者同样计数。旧数值保留，切换之后只按新规则累加。授权到期后再次获取会再计一次；补链会产生新的链接版本，同一访问者可以对它再计一次，这是预期行为。

实现要点：

- 三处计数用原生 SQL 在同一个事务里递增，不经 Prisma 更新，避免推进 `updated`（合并基点依赖它），写法同[点击上报](../../app/api/patch/resource/download/service.ts)。事务重试时计数随事务回滚，不会重复。
- 提交后失效缓存，沿用点击上报的三个调用：`setRealtimePatchDownloadStats`、`invalidatePatchContentCache`、`invalidatePatchListCaches`。

## 8. 测试与验收（均未执行）

- **E06-01 交接**：
  - 普通用户删除含备份的卡片：自己的链接移除，卡片与备份保留，`publisher_left_at` 写入；重复请求幂等；之后该用户无法编辑、删除、管理链接。
  - 事项：新事项归站方；原发布者的未结事项转站方，对话与关注者保留，转交事件的触发器是 `publisher_left` 且不带原归属；`waiting_reporter` 保持状态；交接前已因超时转给站方的事项，原发布者的结案权与通知一并终止；重开已结案事项时归属站方。
  - 竞态：事项创建与交接并发时，不会留下归属原发布者的新事项（`FOR SHARE`）。
  - 通知：求助帖、后台修改、失效反馈都不再发给原发布者。
  - 展示：工作台不列出；个人主页仍列出且带标识；创作者申请计数不变；确认框文案按是否含 `touchgal` 链接切换，交接后条目页刷新卡片而不是移除。
  - 奖励：点赞仍给原发布者加点并通知，取消点赞回收；管理员后来删除该卡片不回收 3 点。
- **E06-02 备份队列**：
  - 三个标签的进入与退出各自覆盖：未备份；已备份无变动不出现；备份后外部链接新增或改地址出现在待重新备份；站方把备份换成新地址后消失；点「无需重新备份」后消失，更晚的变动再次出现。
  - 忽略优先于其他标签，忽略后换链接不回流，撤销忽略回到原标签；有待处理合并候选的用户卡片不在「未备份」；只有 `s3` 链接的卡片、站方卡片不出现。
  - 迁移：`attached_at` 回填分别覆盖统一盖章与其余链接两类；sync 重复执行结果不变；postflight 断言无空值并打印统一盖章链接数（备份库上预期约 1159）。
- **E06-03 合并**：
  - 真实 PostgreSQL 上的并发合并：同一对重复提交、同一用户卡片合并到不同站方卡片、合并与事项创建并发、合并与获取并发、合并与求助帖写入并发；陈旧预览被拒；失败整体回滚。
  - 数据完整：链接 ID、版本、健康状态与两个时间保持；获取事件含 `link_id` 为空的配额事实，授权按访问者合并取较晚到期；资源级 `download` 相加、条目级不变；链接历史、求助帖、已结案事项改指幸存卡片，重开后去重键按新目标计算；点赞不迁移且不回收奖励；站方卡片有未结事项、备注超长、用户卡片已交接时被阻塞；被并卡片删除后不回收萌萌点、不触碰对象存储；条目资源计数由触发器正确维护。
  - 候选：一张用户卡片多个候选时只能人工；驳回后另一张候选升为高置信；重开恢复；批量合并只处理高置信并报告跳过项。
  - 旧链接：条目页带旧 `resourceId` 时被换成幸存卡片，求助创建页同理。
- **E06-04 获取计数**：四个分支的计数符合第 5.4 节的表；同一访问者对同一资源 24 小时内只计一次；恢复访问与后台读取不计数；补链后可再计一次；事务重试不重复计数；旧数值保留；点击上报不再累加公开计数；缓存失效被调用；文案已改。

## 9. 实施顺序与任务

M06-1（数据与权限合同）→ M06-2（交接）→ M06-3（备份队列）→ M06-4（合并）→ M06-5（计数）→ M06-6（接线、说明与清理）。

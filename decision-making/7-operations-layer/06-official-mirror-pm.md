# 模块 06：官方镜像作为链接（项目管理版）

状态：设计草稿，待站长审阅。技术细节见[实施计划](./06-official-mirror.md)；编排与任务编号见[总计划](./00-master-plan.md)；产品依据见[运营层设计基线](../7.operations-layer-redesign.md)第 5 节。

## 1. 目标与责任人

目标是取消「站长搬运后另建一条资源」这个做法：镜像变成原资源下的一条官方链接，一个资源只有一张卡片，署名留给原发布者，官方链接的可用性归站方、文件内容问题归发布者。同时把前台的「下载次数」改成以揭示为准的「获取次数」，并把历史上已经分裂成两张卡片的存量逐条合并回去。

责任人：站长做设计审定与上线验收；实现由单人开发完成；上线后镜像队列、重新镜像与存量合并由持有资源盘账号的管理员逐条消化（目前只有站长持有）。

## 2. 功能介绍与使用流程

本模块改变的是「同一份资源在站内呈现成几张卡片、谁对它的哪一部分负责」。现状是站方把用户资源搬进资源盘后另建一条资源：同一份内容出现两张互不关联的卡片，镜像那张署名站方，而两张卡片上的问题最后都落到站长。改完之后，资源盘上的那份备份变成原资源下的一条官方链接：卡片仍然是发布者的，署名留给原发布者，站方只对自己那条链接负责。

### 2.1 一张卡片上的两种链接

条目页的资源卡片保持一张：标题与类型 / 语言 / 平台、发布者头像与名字、备注，下面是这条资源的全部链接，底部是点赞、获取次数与「遇到问题」入口（分流入口由模块 05 提供）。链接列表里官方链接排在最前并标「站方镜像」，其余按发布者自己的排序显示并标明由发布者提供；已失效的链接折叠在末尾（失效判定与「报告失效」按钮由模块 04 提供）。

卡片上会出现这几种状态说明：

| 卡片上的说明                   | 什么时候出现                             | 含义                                                                                     |
| ------------------------------ | ---------------------------------------- | ---------------------------------------------------------------------------------------- |
| 站方已备份                     | 这条资源下存在官方链接                   | 除了发布者的链接，还能选站方保存的那一份；这条官方链接自己能不能用，仍按它的链接状态显示 |
| 站方已测试                     | 站方确实运行过这份文件并在后台标记       | 只有站方亲自验过才显示，发布者自称测试过不算                                             |
| 站方备份排队中                 | 还没有官方链接的社区资源                 | 站方在排队搬运，不是「没有保存副本」                                                     |
| 官方备份为旧版本               | 发布者已回答「内容有变化」、站方还没重做 | 提醒用户官方那份不是最新内容                                                             |
| 发布者已申请下架，等待站方处理 | 发布者提交了下架申请                     | 期间这条资源的所有链接都拿不到                                                           |

责任也随之分开：官方链接坏了是站方的事，不会转给发布者；文件内容本身的问题仍归发布者。「站方已备份」由有没有官方链接自动推导，不需要谁手动打标；上线时哪些历史的资源盘链接直接算作官方链接，还要站长划定边界（见第 7 节）。

### 2.2 发布者能改什么、不能改什么

发布者照常编辑资源的名称、备注、类型、语言、平台，也照常增删和更换自己的链接（换地址即补链，由模块 04 处理）。官方链接在编辑界面里是只读的一行：看得到它在资源盘上、多大、是第几个版本，但改不动、删不掉，也不能被自己的链接顶替；提交整条资源的编辑同样不会把它带走。

自己的链接全部删完之后，只要这条资源还有官方链接，发布者仍然可以继续编辑资源信息，也可以随时再添加新的链接。添加官方链接是管理员动作，且实际能不能执行取决于是否持有资源盘账号，目前只有站长持有。发布者或管理员打开编辑界面查看自己有权管理的链接，不算一次「获取」，不会让获取次数虚增。

### 2.3 发布者的三种退出方式

原则是：发布者随时可以让自己的贡献从公开视图消失或与自己的名字脱钩，只有物理删除站方文件需要站方出手。

| 动作         | 立即发生什么                                                                                                         | 需要站方吗 | 适合什么情况                                   |
| ------------ | -------------------------------------------------------------------------------------------------------------------- | ---------- | ---------------------------------------------- |
| 删除我的链接 | 自己那条链接立刻从卡片上消失，资源、署名、点赞与官方链接都保留；发布奖励不收回                                       | 否         | 不想再维护网盘                                 |
| 移交给站方   | 资源归属转给站方账号，自己的链接删除；署名二选一：继续显示原发布者名字，或显示「用户投稿」；已经发放的发布奖励不收回 | 否         | 离站、隐私、不想再与这条资源关联               |
| 申请下架     | 必须填写理由；自己的链接立刻删除，整条资源暂停发放，卡片显示等待站方处理，同时生成一条给站方的处理事项               | 是         | 文件本身有问题：版本错误、含有害内容、发错游戏 |

几条配套规则：移交之后这条资源由站方管理，原发布者不再能编辑它，也不再有管理视角下查看链接内容的权限；作为普通用户，他和其他访客一样可以正常获取公开的链接。将来这条资源若被删除，当初的发布奖励按真正拿到过的人处理，不会记到站方账号头上（移交具体用哪个站方账号仍待定，见第 7 节）。申请下架期间，正常的「获取下载链接」与「恢复已获取链接」对所有访问者关闭，包括此前已经获取过的人，站方仍可按权限查看和处理；已经复制到本地的地址站方收不回来。站方的两种处理是同意下架（确认资源盘上的文件已按约定处理后，删除这条资源、结案并通知）或拒绝下架（附理由，恢复发放，发布者可以重新添加自己的链接）；站方没处理之前暂停一直有效，系统不会自动删除资源。资源盘文件具体由谁删、怎么在处理事项里留痕，仍是待定项（见第 7 节）。「移交给站方」与「申请下架」只在资源已经有官方链接时出现；没有官方链接的资源，删掉自己的某一条链接和平常编辑一样，要整条撤下仍按现状删除资源，包含发布奖励的收回。

### 2.4 站方搬运：镜像队列与处理顺序

全量镜像是既定政策，队列的作用是不遗漏、按顺序、每条省时间。进队列要同时满足几条：资源已经公开、没有在申请下架、带外部网盘链接、还没有官方链接、也没有被待合并候选暂缓。只放在站方对象存储上的资源本来就在站方手里，不需要镜像；混着外部网盘和对象存储的资源，只要还有一条外部网盘链接没备份、并且同样满足上面这几条，就照常进队列。

顺序分三层：一是游戏资源（不含资料集），二是资料集，三是补丁区。层内优先处理获取次数多的、该条目唯一还能用的、所在网盘当前失效比例高的、体积小的。

一条资源的处理是四个状态：待下载 → 已下载待上传 → 已上传待建链接 → 完成。最后一步「添加官方链接」填入资源盘的分享地址，大小自动带出，卡片上的「站方备份排队中」随即变成「站方已备份」。审核和镜像是两件事：资源审核通过就公开，镜像按优先级慢慢补，不会因为还没镜像而压着不发。后台首页能看到「未镜像 / 总数」：未镜像数按统一口径把所有还没有官方链接的资源都算进去，其中因为存量候选而暂缓的另外单列一个数——待备份的总量和当前能动手处理的队列是两个数字，分开看。

### 2.5 官方备份还是不是最新：版本确认与重新镜像

官方备份保存的是搬运当时那份文件。发布者之后换网盘或重新打包，站方无法从地址和大小推断内容有没有变，所以这件事只问发布者，不猜。

问法有三种：发布者补链时在表单里当场问一次（资源没有官方链接时不出现这个问题）；存量合并的每一对候选都要问一次；管理员也可以随时手动问一次，例如有人反馈官方那份是旧版本。同一个问题问的对象不同，后果也不同：

| 发布者的回答 | 已经有官方链接的资源                                                     | 待合并的候选对                                                                             |
| ------------ | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| 内容相同     | 官方备份视为当前版本，不进重新镜像队列                                   | 这一对恢复为可合并，管理员一键合并                                                         |
| 内容有变化   | 进重新镜像队列，官方链接旁显示「官方备份为旧版本」，直到站方重做完成     | 这一对恢复为可合并；合并之后，保留下来的那张卡片才带上「官方备份为旧版本」并进重新镜像队列 |
| 7 天没有回应 | 记为「发布者未确认」，排在重新镜像队列所在层的末尾，由管理员决定是否重做 | 这一对保持暂停并标「发布者未确认」，由管理员决定是按未确认合并还是继续等                   |

重做完成需要站方明确点一次「完成」，并核对期间发布者没有再改动链接；一条资源上如果有不止一份官方备份，要把仍然在用的旧备份都处理完，才算恢复到「官方备份是最新的」，提示随之消失。重做期间发布者又换了链接，就要重新问一次。对同一个问题重复点「询问」不会新开第二条，也不会把 7 天的期限往后推。

### 2.6 历史遗留的重复卡片：存量合并

存量指历史上站方搬运后另建的重复资源：同一条目下一条用户资源、一条站方资源，内容相同却互不关联。不处理的话，镜像队列会把用户那条当成没备份而重复搬一次，点赞和获取次数被两张卡片摊薄，用户网盘失效时两张卡片也各管各的。

待合并队列只做在后台：系统按同条目、同分区、名称相似给出候选对，列出两条资源的名称、发布者、创建时间与链接；管理员可以把系统没配上的两条手工配成一对，也可以把配错的一对标成「不是同一资源」。每一对都必须先问发布者，队列上提供「询问发布者」与「批量询问本页」两个按钮；拿到回答、或满 7 天由管理员按未确认处理之后，才能合并。

合并把站方那条上的资源盘链接移进用户资源并标为官方链接（站方那条上的其他链接也一并搬过去，只是不算官方），把获取次数与点赞并到保留的卡片上（同一个人在两张卡片上的点赞只算一次），删掉站方那张卡片，并留下处置记录。合并不会因为删掉那张卡片而收回任何人的发布奖励。合并之后署名是原发布者，失效报告、未结的处理事项、仍在有效期内的「已获取」都跟着落到保留的卡片；用旧地址访问被合并掉的那条资源时，会落到保留的卡片并提示「该资源已并入」。

节奏是队列驱动、逐条手动、不设截止日期；有候选对的资源在合并前不会重复进镜像队列，长期没回应的会一直显示为「待人工决定」而不是从视图里消失。被标成「不是同一资源」的那一对不再暂缓这条资源；只要它没有被别的候选对暂缓，并且满足 2.4 的入队条件，就回到镜像队列正常排队。前台条目页只放一个「去后台合并」的跳转，不在前台重复做一套。

### 2.7 从「下载次数」到「获取次数」

公开数字从「下载次数」改成「获取次数」，口径也跟着变：点了「获取下载链接」才计数，不再按跳转点击计；同一个人对同一条链接 24 小时内只算一次；同一个人拿了同一资源的多条链接（例如官方镜像和发布者网盘），在资源层面 24 小时内也只算一次。链接与资源是两级分别判断，各有各的 24 小时窗口，不是同一个窗口一起开始、一起结束。访客的获取也计入，按访客身份去重，这与「报告失效必须登录」是两件事，计数是统计、报告是证据；窗口还没过时重复点开、刷新页面恢复已经获取过的链接，都不会再加一次，窗口过去之后再来获取才重新计一次。

官方链接的获取算在这条资源上，署名仍归发布者，每条链接下面还能看到各自的份额。跳转点击仍然记录，但只作为发布者与管理员可见的辅助数字，不再是公开计数。历史数值原样保留作为起点，不重算、不清零。

### 2.8 站方的操作入口与记录

站方的日常操作集中在后台：镜像队列、重新镜像队列、待合并队列，以及从旧后台迁过来的资源管理页（原来只有超级管理员能进，迁移后与其他后台队列一样按管理员权限）。添加官方链接、重做完成、合并或排除候选都会留下处理记录，站方据此看得到各队列的积压与等待情况，后续的运营指标也从这里取数。

## 3. 范围

做：官方链接与链接级权限、卡片结构、发布者三动作、镜像队列与进度流、重新镜像、镜像版本确认、存量合并工具、获取计数切换、现有资源管理页迁入新后台。

不做：不给创作者镜像权限；不建自动搬运、离线下载或新的云存储控制台；不改萌萌点既有规则；不做资源级担保等级枚举；不在前台重复实现合并；不要求上线前清空存量队列。

## 4. 依赖与上线批次

依赖模块 01 的后台、模块 03 的工单、模块 04 的稳定链接 ID 与链接历史。模块 04 若没有先把「删除后重建全部链接」改成按 ID 更新，官方链接就无法被保护，本模块不能开工。本模块是独立的一批上线：新镜像流程、链接权限、下架、版本确认、计数切换与合并工具一起发布；存量合并允许上线后长期消化，不阻塞模块 07。

## 6. 验收

一，发布者编辑整条资源既不能覆盖也不能删除官方链接，添加官方链接仍需管理员门槛。二，三个动作的即时效果、署名选择与奖励处理与基线一致；申请下架后正常获取与恢复对所有访问者关闭、已获取的也不恢复，站方仍能按权限查看与处理，但已经复制到本地的站外地址无法收回。三，首次镜像队列不包含只有对象存储链接的资源，也不包含仍被存量候选暂缓的资源；未镜像总数按统一口径保留暂缓项，并单列其数量。四，每一对候选都先询问发布者；合并后点赞、获取次数、仍在有效期的授权与工单指向都落在保留的那张卡片上，且不误删资源盘文件。五，同一个人拿到同一资源的多个镜像只计一次获取，重复请求与恢复不增量，旧点击不再累加同一个展示数字，旧数值原样保留。六，上线后由站长实际处理若干条队列项与至少一对存量合并，并记录处理结果。

## 7. 风险与未决事项

- 站内目前只有对资源盘公开分享的只读调用（用来算文件大小），没有接入删除或离线下载，「同意下架」和合并都不会自动删文件；流程改为「确认文件已处理 → 在一个事务内删除资源、回退奖励、结案与通知」，本模块只保证站内数据正确。人工删文件的做法属 D7 候选，未定前不当成已批准；资源盘自身是否具备离线下载、哈希去重与低频存储能力，仍要按其官方文档核对后留一段结论。
- 官方字段回填边界、移交时使用的站方账号、合并后的引用与统计口径（含合并去重掉的重复点赞不追溯结算）、资源盘研究项范围仍是 D7。未定前不写死回填 SQL，也不把合并按钮的默认行为定为已批准。
- 合并与资源删除一旦提交，应用回退不能把卡片拆回两张；回退顺序必须先关闭合并与下架入口，再处理代码。
- 计数口径切换后增长会看起来变快（揭示通常多于点击），这是基线已接受的结果，不重算历史。

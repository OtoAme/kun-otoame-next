# 模块 10：链接检测与公开结果（PM 视角）

首批 04／05／10 的本地实现与技术验收状态见[首批验收记录](./12-first-batch-acceptance.md)；当前尚未提交、推送或生产部署。 固定服务、网站接线和双重事实展示已完成，首批仅夸克准入；生产主机及独立出口仍待确认。技术细节见[实施计划](./10-link-check.md)。

## 1. 目标

让用户同时知道检测服务器看到的结果、其他用户实际遇到的问题和本站当前的处理状态。机器能够确定分享失效时及时折叠；结果冲突时保留反馈与获取入口，避免把任一方的观察直接抹掉。七天仅用于仍处于疑似失效且无人处理的情况，不能把机器冲突的争议项按七天直接判坏。

## 2. 责任人

站长决定支持范围和实际生产部署目标。后端作者负责服务适配、状态流转、结果记录和运行验证；前端作者负责每条链接的双重信息展示、操作提示与浏览器 E2E。模型分工、auto 权限和回退沿 worker 计划。

## 3. 功能介绍与使用流程

### 3.1 一条链接显示两类事实

展示粒度为资源卡片里的每一条镜像链接，不能用一条镜像的结果概括整张卡片。

| 展示项   | 示例                     | 表达什么                                                                 |
| -------- | ------------------------ | ------------------------------------------------------------------------ |
| 机器检测 | 检测端可访问 · 10 分钟前 | 最近一次对当前地址版本的程序观察                                         |
| 用户反馈 | 近期 3 人报告问题        | 当前地址版本最近 72 小时去重后的用户反馈（跨轮次保留）；不展示身份和正文 |
| 处理状态 | 有争议 · 等待复核        | 本站依据事实决定的处理状态，不合并成一个含糊的红绿标签                   |

未检测显示“未检测”；过期结果显示时间与“结果已过期”，不宣称当前仍有效；检测失败显示“无法判断／检测失败”。新地址不继承旧地址的检测标签。页面读取这些记录，不因每次打开资源卡片就发起网盘检测。

### 3.2 检测怎样触发

| 触发                 | 条件                                                                 | 结果用途                                                           |
| -------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 用户报告失效         | 已登录、目标可见、获取记录与当前版本匹配等 04 资格成立               | 保存用户报告和检测事实；按 3.3 处理                                |
| 发布者／站方主动检测 | 服务端校验链接管理权限；按钮说明可能更新链接状态，按既有确认规则操作 | 更新公开检测事实；可靠失效结果可以折叠链接                         |
| 补链保存后检测       | 先成功保存新版本，再检测该版本                                       | 更新新地址事实；若可靠确认新地址失效则折叠，但不回滚已经成功的补链 |

只有以上三种触发，不新增普通下载者独立检测按钮，不做定时全站扫描。七天任务本身不发网盘请求。检测不产生下载授权或获取次数。

### 3.3 三态与处理结果

| 检测事实                       | 用户反馈／既有状态                               | 本站处理                                                                   |
| ------------------------------ | ------------------------------------------------ | -------------------------------------------------------------------------- |
| 可靠确认已删除、已取消或已过期 | 任一已授权触发，结果仍对应当前版本和处理轮次     | 直接标记失效并折叠，归属方收到一次必要通知；已有对应链接事项按检测结论收尾 |
| 检测端可访问                   | 报告尚未累计到阈值                               | 保留报告、原权重和双重展示；不驳回报告，也不因单条反馈折叠                 |
| 检测端可访问                   | 有效报告累计达到阈值，或原已疑似且本轮证据仍成立 | 进入现有“有争议”，保留获取入口，交人工复核，不走七天自动折叠               |
| 无法判断／检测故障             | 仍未达到报告阈值                                 | 保留反馈，按 04 继续积累证据                                               |
| 无法判断／检测故障             | 达到报告阈值                                     | 进入疑似失效；未处理时由七天规则兜底                                       |

“可靠”需要已审 provider 样本、明确原因、新鲜检测结果，以及服务端版本和轮次校验。缺提取码、需要登录、验证码、限流、超时、未知码和无法区分部分／全部失效的结果都不能直接判坏。上游原始 `dead` 不是无条件折叠指令。

### 3.4 冲突如何收尾

机器可用与用户失效反馈可以同时成立：检测服务器和用户的网络、地区、账号条件不同，分享存在也不等于用户能成功取得全部文件。界面应显示“检测端可访问，但有用户反馈异常”，并保留各自时间与事实。

达到阈值的机器冲突使用已有“有争议”状态并记录冲突来源。管理员核实可用后恢复正常，核实失效后折叠；新鲜可靠的机器失效结果也可结束争议，换地址则重新开始。此类争议不能被七天任务折叠，也不沿用旧争议的强证据自动判坏或三十天自动恢复来绕过复核；其它归属方核实引起的争议规则仍由 04 定稿。

已被标记失效的链接后来检测为可用，只更新机器事实并提示复核，不自动推翻既有结论或恢复入口。恢复由归属方／管理员明确执行。已经进入冲突复核的链接，后续一次检测失败也不会把它退回普通七天路径。

### 3.5 时效与隐私

公开结果只含状态、简短原因、检测时间和必要的处理提示，不含下载地址、提取码、解压码、原始响应、用户身份或服务密钥。用户人数与机器结果分别读取，不把机器算作一个报告者。公开人数跨证据轮次保留当前地址的近期反馈；后台判定仍只计算当前轮次的有效权重，二者不混用。

用于直接判坏或触发冲突的结果须为本次新鲜检测；上游默认七天失效缓存不能直接用作这次判定。历史结果可带时间展示，但不能冒充本次检测。结果迟到时若链接已换版本，丢弃；处理轮次变化后不能越过新裁决继续写旧结论。

## 4. 范围

交付三类触发、机器结果最新快照、每链接双重展示、可靠失效直接折叠、机器可用与用户反馈冲突复核、自部署服务接入与 E2E。保留报告资格、对象权限、下载授权及资源公开状态语义；不会因为检测改变资源本身的封禁或审核状态。

## 5. 依赖与上线批次

建议把 10 前移到 04／05 同批交付：服务评估和隔离部署与 04 开发并行；本站接入等稳定链接 ID、版本、健康流转和共享 DTO 就绪后完成；04／05／10 合在同一轮 E2E 验收。它不依赖 06～09。

生产顺序为：先部署并验证受控 checker 服务 → 应用所需迁移与检查 → 发布已验收的 04／05／10 网站版本 → 冒烟与上线观察。单独启动 checker 不会改变任何本站数据。服务地址、出口与生产操作窗口仍需在具体部署方案中确认，本轮不执行部署。

运行中 checker 不可用时明确降级为 unknown，报告与补链继续；已有争议和已失效状态保留。若上线前 checker 或支持清单未验收，不能把只交付 04／05 冒充完整批次，需显式调整发布范围。

## 7. 验收

1. 可靠机器失效不等待多人投票或七天，链接直接折叠且通知不重复。
2. 单条用户反馈与机器可用同时可见；达到阈值后进入争议，七天及三十天任务不能越过此类复核。
3. 页面刷新、切换端和多个镜像展示仍有对应结果；没有检测／过期／失败明确可辨，不触发逐页网盘探测。
4. 新旧版本和并发返回不会覆盖错地址；手动检测的可用结果不会自行恢复已折叠链接。
5. checker 故障不丢报告或回滚补链，不制造获取记录、不泄露凭据。
6. 真实浏览器 → 网站/API → 实际 checker HTTP 服务 → 隔离数据库完成 E2E；provider 受控样本与故障注入边界明示。未执行的项目不得标通过。

## 10. M10-1 服务评估结果（2026-10-09）

固定上游提交在隔离目录原样构建成功，75 个上游测试／子测试通过；实际 localhost checker HTTP 加合成 UC 网盘替身有 30 项通过，另有 24 个 provider 合成测试／子测试通过。服务鉴权、实际三态返回、零缓存与时间已验证，没有检测真实分享或读取用户／环境数据，全部临时进程已停止。详细记录与精确样本在 `/private/tmp/otoame-ops-20261009/checker-report.md`，[实施计划第 13 节](./10-link-check.md#13-m10-1-固定版本评估记录2026-10-09) 保留仓库内结论。

**当前没有网盘完成生产资格验收。** 合成测试确认上游能运行，也复现了接入前必须修复的问题：不同提取码串用旧缓存；缺响应字段仍称可用；服务故障响应带失效码仍称失效；跟随内网跳转；原始错误文本写日志。这些问题要在 checker 服务侧修复，网站只看现有返回无法全部辨别。

首批五家仍是候选。明确删除／取消／过期的原因码须通过修复后的服务分支回归和映射审阅；用户最新确认真实验收只要求正常／异常，不要求逐类失效真样本。百度的提取码页面、和彩云的码非法、123 盘的提取码错误，都不足以支持“当前可访问”，本站按无法判断处理；部分屏蔽、验证码、登录、限流与故障同样不能判坏。服务三个缓存寿命均为零，避免把旧结论当本次检测；上游尝试完成时间不等于成功检测时间。
